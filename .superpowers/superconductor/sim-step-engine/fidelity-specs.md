**L1-1 (should-fix). Built-in switches are not policies of the same shape.** D 3.4 line 105 and R3 (D line 165): built-in switches (rent-control protection, SB 423, today's City funding) "are policies of the same shape with their settings filled in ... so a later editor can open them". policy-timeline rule 7 (line 55) does the opposite: the three defaults "are not in the document"; timeline-ui rule 7 (line 43) draws them as fixed rows outside the document. **L1-2 (should-fix). OD-3's 48 worlds and the 480-month window have no owner.** S14 `openTimeline` takes `worlds` and `months`, but `TimelineClient.open(manifest, policy, lots)` (ensemble-runner rule 18, line 80) has no such arguments, and timeline-ui never states 48 or 480. ensemble-runner states 48 only in its Purpose (line 7) and tests with 96. *Fix:* ensemble-runner rule 18: `open` sends `worlds: 48, months: 480` (constants exported from the client); timeline-ui references them.

**L1-3 (should-fix). **L1-4 (note). **L1-5 (note).** D section 9 "`exp` and `log` only from `src/lib/timelapse/math.ts`" is repeated in every spec but tested by none. *Fix:* a lint or grep test in world-core.

**L1-6 (note). ## Leg 2: Contradictions

**L2-1 (blocker). `comparisonOf` cannot return the default document's twin.** S13 (D line 252): `comparisonOf(doc: SimPolicy4): SimPolicy4`; "the default document's twin is the zoning before the plan". The schema 4 document cannot express "zoning before the plan": the Selector/Effect table (policy-timeline line 37-45) has no such tag, and the default document (empty lists) *means* "the plan as adopted" (policy-timeline rule 7). policy-timeline rule 19 (line 77) says the twin is "a document compiled against the zoning before the plan (`baseZoning`, as `twinInput(…, 'preFzp')`)", that is, a different compile base, not a different document. ensemble-runner rule 3 (line 49) compiles `comparisonOf(policy)` with the same ctx. Built as written, the default document's twin is the default document: the plan effect is zero on the page's landing state. Today's code: `twinInput` (`src/lib/sim/levers/apply.ts:91-110`) applies `baseZoning` (`src/lib/sim/scenario/policy.ts:23`) to the base input. *Fix:* change S13 to `comparisonOf(doc): { doc: SimPolicy4; base: 'preFzp' | 'plan' }` (or add a `base` field to `CompileCtx`), and have ensemble-runner rule 3 compile with that base.

**L2-2 (blocker). Pool indices are not stable across an edit, but kept worlds are resumed under the new timeline.** S5 (D line 244) fixes the order of `pools`/`programmes` only "in every frame of one timeline". policy-timeline rule 14 (line 69) orders them "baseline first, then added, in document order", so adding, removing or reordering a money policy changes indices. world-funding defines `World.pools` per pool (world-funding line 33; D 3.1 line 54). ensemble-runner rules 13-14 (lines 65-66) resume worlds (and kept copies made under the old timeline) under the new timeline. No spec remaps pool rows. Related: since every frame's `pools` is the whole-document union, `firstDifference` (S6) compared by object identity reports month 1 for any money edit, so every money edit refills from 2026, contradicting D 3.7 and world-funding's own test "An inflow raised from month m: every event before month m is identical" (line 84). *Fix:* world-funding keys pool rows by pool id (and programme rows by programme id) and maps them through the frame's arrays each step; policy-timeline rule 17-style text defines `firstDifference` for money as the first month in which any pool's inflow arrivals, `offered`, terms or slope differ.

**L2-3 (blocker). Streamed demolitions cannot reach the map.** map-stream rule 7 (line 36): "`demolish` lists, in revision 0, every demolition known so far, and in later revisions is empty, with demolitions carried by the cells as today". Today the cells carry no demolitions: `TimedPackedCell` (`src/lib/map/types.ts:50-57`) has no demolish field; the existing building is hidden only by the demolish pump fed from `TimelineUpdate.demolish`, "complete list in revision 0; empty afterwards" (`types.ts:64`), and the controller ignores a non-empty list after revision 0 with a console error (`src/lib/map/timeline-controller.ts:191-194`). In the stream, almost every demolition becomes known after revision 0 (a project entering construction in a later month), so existing buildings would never be hidden, and a rewind could never un-hide one. map-stream line 9 says "The map itself does not change". *Fix:* map-stream sends a `swap: true` revision 0 carrying the complete demolish list whenever it grows or a rewind changes it (the controller already diffs the list on swap, `timeline-controller.ts:336-346`), or the package allows a controller change to accept appended demolitions; state which.

**L2-4 (blocker). A free lot's built-up start total has nowhere to live after a frame change.** world-core rule 7 (line 66): when the frame changes in month m, "the total a free lot has built up before m is kept". world-core rule 4 (line 60) and S1 give a lot a row only when a project starts on it, a pipeline project holds it, or it is freed; a lot that has only lived through a rate change stays row-less, and its draws alone no longer determine its total, because `step` and `planDue` (S2, S11) receive only the current frame, never the earlier ones. So `planDue` "from scratch" cannot reproduce the carried list after a zoning or market change, and world-core's own rule 19 test (rebuild every 12 months, line 87) and ensemble-runner's restore-and-rebuild (S16) will diverge. The same holds for world-funding's market and affordable totals (world-funding rule 4, line 47). The spike handled this with a dense per-lot `clock` array (`spike/world.ts.txt:329`, inferred from a grep, not read in full), which world-core line 50 forbids copying. A market change (`touched` null) touches every lot, so storing rows naively costs about 10 MiB a world (D line 41). *Fix:* decide in world-core either (a) a free lot touched by a frame change gets a row holding its ordinary (and, via the hook, funded) totals as of the change, plus a ruling on the market-change case; or (b) `planDue` takes the `PolicyTimeline` and recomputes totals over the frame history (changes S11 and the copy rule).

**L2-5 (blocker). The route rule for funded starts is carried by no spec.** Today, on an award (`src/lib/sim/scenario/funded.ts:1738-1748`): a Local Program lot takes `streamlined`; a *certain* affordable award takes `pathwayFrom(run.newCal.affordableRoutes!, stream)`; otherwise the route is drawn normally. world-core rule 8 (line 67) draws every start's route on `frame.newCalibration`; `FundedStart` (S12) has no route; world-funding rule 10 (line 56) does not mention the route. The funded referee is statistical (OD-2), so the miss may not be caught. *Fix:* world-core rule 17 states the route rule for `startProject` with `funded` non-null (Local Program, then certain affordable via `affordableRoutes`, else normal), citing `funded.ts:1743-1748`.

**L2-6 (blocker). Baseline-scale dates cannot be span dates.** policy-timeline rule 2 (line 50): baseline-scale policies take spans at "their own dates"; the table (line 43): "its spans are the stretches between scale dates". policy-timeline rule 4 (line 52): the parser rejects any span `from` that is not the first day of a model month. Schema 3 scale dates are arbitrary days (`parseScale`, `src/lib/sim/levers/finance.ts:88-96`), and model months (30.436875 days from `asOf`) essentially never start on a calendar date the funding UI would pick. Every upgraded document with scales is then rejected by its own parser, or the dates must be snapped, which breaks the round-trip test (line 89, "equals what `applyLevers(compileLevers(p))` gives today"). *Fix:* keep the scale entries (`{pool, from, scale}[]`) inside `what` with one span from the dataset date, as is done for a programme's own `from`/`to` (rule 6), or rule a snapping rule and exempt it from the round-trip test.

**L2-7 (blocker). The page has no source for `ScoreStatics`.** S15: the page builds `viewOf(chunks, statics: ScoreStatics)`; world-score line 30 defines `ScoreStatics { asOf; months; baseline; tierBaseline; phasing; references }`. `phasing` and `baseline` come from the dataset's projects file (worker side); `references` depend on the comparison (`apply.ts:155-160`). No S14 message carries any of them (`compiled` has only `capacity` and `unknownLots`), and today they arrived inside `TimelineScore` on the retired `timeline` message. timeline-ui cannot build the results face. *Fix:* add `statics: ScoreStatics` to the `compiled` message (S14), filled by the runner via a world-score function.

**L2-8 (should-fix). Certain projects use `sampleAdvance`, not the transition draws.** Today a certain (fully funded) job's stage time is `sampleAdvance(t, STAGE_TIME draw)` and `P.STAGE` is not read (`src/lib/sim/scenario/engine.ts:509-523`; `sampleAdvance` at `src/lib/timelapse/model.ts:350`). world-core rule 10 (line 72) names only `sampleTransition`, `sampleKind`, `sampleTime`; rule 15 (line 77) says only "never drops out". *Fix:* rule 15 adds "its length is `sampleAdvance` on the `STAGE_TIME` draw; `STAGE` is not read".

**L2-9 (should-fix). Timer combination: floor, clamp and the speed/speedNew split disagree.** policy-timeline rule 12 (line 66): timers multiply across policies "and the product is then raised to the stage's floor". Rule 13 (line 67) then splits the factors into `speed` (reach `all`) and `speedNew` (reach `new`), so the product a project sees (S4: `speed` × every applicable `speedNew`) is known only at step time, where no floor is applied (world-core rule 11, line 73). Today the floor is applied once, to a preset's own scale (`withFloor`, `src/lib/sim-page/timing.ts:284-290`), and the cohort product is clamped to `[MIN_SCALE, MAX_SCALE]` (`scaleTable`, `src/lib/sim/levers/timers.ts:37-50`), which no spec mentions. The round-trip test's "the same scales" (policy-timeline line 89) is ill-defined: today's frame has `inFlightScale` and `newProjects.scale`, the new one `speed` and `speedNew`. *Fix:* S4 and world-core rule 11 state that the step clamps the project's product to `[MIN_SCALE, MAX_SCALE]`; policy-timeline drops "raised to the floor" for products (floors stay inside each preset); the round-trip test compares `speed` with `inFlightScale` and `clamp(speed × speedNew[0].scale)` with `newProjects.scale`.

**L2-10 (should-fix). Partial compile results are needed but not offered.** policy-timeline rule 16 (line 74): "the runner can begin before later frames are ready; `result()` may be called once every frame is done". S13: `step` "returns true when `result()` may be called". ensemble-runner rule 3 (create worlds "when the first frame of each is ready"), rule 11 (compile "until the frame for the next month exists"), and rule 12 ("frames up to the fill point") all need a partial `PolicyTimeline`. *Fix:* add `readyThrough(): number` and allow `result()` once the first frame is ready, with `frameAt(m)` valid for `m <= readyThrough()`.

**L2-11 (should-fix). `compileTimeline` cannot see the brush lots or report what S14 posts.** S14 `setPolicy` carries `lots: Record<string, ParcelId[]>`, and today's `compileLevers(p, lots)` needs them (`src/lib/sim-page/policy.ts:561`), but S13's `compileTimeline(doc, ctx)` takes no `lots`, and `CompileCtx` is defined as the loaded dataset. The `compiling` message (`done`, `total`, `failedCells`) and `compiled` (`capacity: LeverCapacity`, `unknownLots`) have no source in `TimelineCompile` or `PolicyTimeline`; under dated zoning, `capacity` also needs a ruling (capacity of which month?). *Fix:* S13 `compileTimeline(doc, lots, ctx)`; `TimelineCompile` gains `progress(): { done; total; failedCells }`; `PolicyTimeline` gains `capacity(): LeverCapacity` with its month stated.

**L2-12 (should-fix). "Is this the default" by canonical identity breaks "an off policy changes nothing".** policy-timeline rule 8 (line 56) makes `canonicalJson` the identity for "is this the default", and `comparisonOf` switches on default-ness (S13; today `isDefaultPolicy`, `policy.ts:128`). Adding a policy that is off makes the document non-default, so the comparison flips from pre-plan zoning to the plan; the comparison timeline differs from month 1 and refills, and the page relabels the comparison. ensemble-runner's test (line 91) requires "a policy that is off: no `refill`, no change". *Fix:* for the comparison, a document is "default" when no policy is in force in any month.

**L2-13 (should-fix). Card funding fields have no single owner or storage.** world-funding rule 10 (line 56): `funded` is "built as `fundingOf` builds today's funding fields", which include `granted`, `lent`, `guaranteed` (`funded.ts:1657-1675`); but `FundedStart` (S12) carries no dollar fields. world-funding line 33 keeps dollars only for an awarded project "that still has money events to come", so after completion they are gone; `scheduleAt` (world-core rule 21, line 92) must still produce `Schedule.funding`, including `displaced` from the shadow, whose storage world-funding leaves to the builder (line 93). world-core is built first (Release A order) and cannot read a column world-funding has not defined. *Fix:* extend `FundedStart` with `granted`, `lent`, `guaranteed`; world-core stores the funding fields on the project row; world-core defines a per-row `displaced` column that the funding hook writes when the shadow passes.

**L2-14 (should-fix). world-score's money series cannot use "today's functions" as stated.** world-score rule 10 (line 49) builds money "with today's functions (`finance-score.ts`)". `moneyOf` counts `displacedHomes` at the funded project's *completion* month (`src/lib/sim/scenario/finance-score.ts:490-520`), whereas D 3.5 (line 114) and world-funding rule 17 count them when the shadow passes. `moneyOf`, `poolSeries` and `addedBorrowing` also need one undated `SimInput['finance']`, a `baseline` pool list and a horizon (`finance-score.ts:382-386, 468-473, 496-504`); no S row hands world-score the whole-document finance. *Fix:* world-score counts `displacedHomes` from `'displaced'` events, and the chunk builder receives the compiled document's finance and baseline pools (via `ScoreStatics` or a named argument).

**L2-15 (should-fix). The new error code would change a hashed file.** ensemble-runner rule 17 (line 76) adds error code `'timeline'`. The error codes of the scenario protocol are `ScenarioErrorCode` in `src/lib/sim/scenario/types.ts:229-230`, a hashed file outside the one permitted exception. ensemble-runner line 18 permits `router.ts`, `protocol.ts`, `worker.ts` only. *Fix:* the runner defines its own request/response unions (with their own error-code union) in `protocol.ts` or a new file, and says so.

**L2-16 (should-fix). The end of the window, as a calendar month, is undefined.** The window is 480 model months (ensemble-runner rule 10) ending about 2066-10 (14,609.7 days after `asOf`), mid-calendar-month. A calendar month is final only when the model month holding its last day has been stepped (world-score rule 2), so the month holding the window's last day never becomes final. Still, timeline-ui rule 18 (line 60) unlocks Play when `filledThrough` "reaches the end of the window", rule 21 (line 66) prints "by 2066", ensemble-runner's test (line 86) expects `filled` to end "at the last calendar month of the window", and `ScoreStatics.months` is "as `monthsOf` gives" (which needs a horizon, `score.ts:24`). *Fix:* world-score defines `lastIndex` = the last calendar month whose last day is at or before the last day of model month 480, puts it in `ScoreStatics`, and timeline-ui and the runner use it.

**L2-17 (should-fix). Frame ids and the month-0 frame.** `frameAt` is "total for month >= 1" (S6), but `createWorld` (S2) needs a frame at month 0; nothing says which frame to pass. ensemble-runner rule 13 (line 65) carries worlds whose `world.frame` holds an id from the *old* timeline into the new one; if ids are per-compile counters, a new frame can reuse an old id and the step's policy system (world-core rule 16, `frame.id !== world.frame`) is skipped. *Fix:* S2 says `createWorld` takes `frameAt(1)`; S4 says ids are unique across all compiles in a worker (a global counter, with shared frames keeping their id).

**L2-18 (note).** D 3.3 system 5 (line 82) says the line is served "in key order"; world-funding rule 8 (line 54) orders by (month applied, key), which matches today's `(applied, key)` line (`src/lib/sim/scenario/line.ts:48, 96-101`). Update D's wording.

**L2-19 (note).** D 3.6 (line 125) and OD-3 say 1.28 standard deviations; world-score rule 6 says 1.2816. world-score's figure is the right one; align D.

**L2-20 (note).** ensemble-runner numbers "17a" before "17" (lines 72, 76); map-stream rule 1 (line 30) refers to "rule 6's batching" but rule 6 is about chunks (batching is rule 4).

**L2-21 (note).** timeline-ui rule 13's inventory (line 52) of lock and run-phase sites misses `SimPage.svelte:108` (import), `:485` (`new RunPhase()`), `:511` (`store.locked = false`) and `policy-store.svelte.ts:27` (the field).

**L2-22 (note).** policy-timeline rule 9 (line 64) says rules combine "in list order" and "each lot takes the highest rule that names it". These conflict in wording only: the maximum does not depend on order (`SimLevers` comment, `src/lib/sim/levers/types.ts:64-66`). Drop "in list order".

## Leg 5: Delegation check

For each spec, I checked the "Left to the builder" list and the body for decisions that leak outside the module.

- **world-core.** Its "Left" list (columns, `Due`'s structure, file split, `skipAbove` constrained to change no event) is internal. The leaking undecided items are L2-4 (where totals live), L2-5 (funded route) and L2-17 (the month-0 frame); they are reported in leg 2.
- **world-funding.** See L5-2, L5-3 and L2-13.
- **policy-timeline.** Its "Left" list is internal, apart from frame-id uniqueness (L2-17).
- **ensemble-runner.** See L5-1, L5-5 and L5-6.
- **world-score.** See L5-4.
- **map-stream.** Its "Left" list is internal, provided the first test holds; the demolition gap is L2-3.
- **timeline-ui.** Its "Left" list (component boundaries, colours, short-label wording within rule 24) is acceptable. See L5-7.

**L5-1 (should-fix). ensemble-runner leaves copy thinning to the builder, but also says it decided it.** "Left to the builder: ... whether copies of worlds past month 240 are thinned" (line 100) against "Decided here, not left: ... where copies are taken (rule 15)" (line 103) and S16's "every 12 model months". Thinning changes where a restore starts and therefore which calendar months a `refill` withdraws. The user sees this as how much of the chart re-hatches after an edit. *Fix:* delete the thinning item, or rule it and amend S16.

**L5-2 (should-fix). world-funding's "month" is ambiguous where it orders the line.** Rule 4 (line 47): `planLot` returns "the first month in which either total passes"; rule 6 (line 49): `keyDay` is "the first day of the month in which the lot's ordinary total ... would pass". Lot-months (counted from the day the lot became free; world-core rule 5) do not line up with model months, and both readings are plausible. `keyDay` orders the line, so the choice changes who is awarded. *Fix:* say "model month" and define it as the model month containing the day the clock passes (the lot-month's start day, or the drawn day).

**L5-3 (should-fix). The day of a `'displaced'` event is unspecified.** world-funding rule 17 (line 72): "In the month it passes, `shadow` sends `{ kind: 'displaced', lot, day, units }`", with no rule for `day`. The day decides which calendar month the displaced homes count in (money series, card). *Fix:* `day` is the ordinary start day the shadow would have had (`INIT_DAY` draw, as world-core rule 5).

**L5-4 (should-fix). world-score leaves money and limit fields to the builder.** "Left to the builder: `MoneyRow` and `MoneyView`'s fields, within rule 10" (line 75); line 31: "this spec's builder fixes their fields from `finance-score.ts`". These are the money panel, "per added home", and the limit statements the user reads, and timeline-ui consumes them without a contract. *Fix:* define `MoneyRow` as one month's entries of `TimelineScore['money']` (`pools[].received … lostCredit`, `fundedHomes`, `displacedHomes`, `publicSpent`), and `MoneyView` as `TimelineScore['money']` cut at `filledThrough`, with `owed` and `limits` computed as of `filledThrough`.

**L5-5 (should-fix). No spec decides which month's zoning the lever overlays use.** S14 keeps `heights`, `heightLids`, `lotAt`, `previewBuildings` and `resolveBrush` "with their type and meaning", answered by the old host's shared handlers (ensemble-runner rule 1). Their meaning today is "the latest complete city of a session initialised with levers" (`scenario/types.ts:166-177`). Under dated zoning there is no single city of the levers, and no spec decides which month's zoning the height overlay, lids and "who sets this lot's limit" show. The user sees these on the map. *Fix:* ensemble-runner rules that they answer for the zoning in force at a month the page sends (the playhead's), and adds that month to the requests (or to `setPolicy`).

**L5-6 (should-fix). Filling while a new document compiles is undecided.** ensemble-runner rule 12 (line 64) compiles the new document and acts "when its frames up to the fill point are ready", but does not say whether filling continues under the old timeline meanwhile. The client drops old-`rev` messages (rule 18), so the user would see the fill mark freeze or advance depending on the choice, and the 50 ms slice budget is shared. *Fix:* rule that filling stops on `setPolicy` and resumes after `firstDifference`, or that it continues, and that old-`rev` posts are suppressed.

**L5-7 (note). The brush queries a schema 4 document needs have no named owner.** timeline-ui rule 14 (line 54) resolves "brush queries ... through `resolveBrush`" and passes `lots` by query key, which the compiler must read under the same keys. No spec names the function that lists a schema 4 document's queries (today `queryKey`/`customQuery` over schema 3, `sim-page/policy.ts:457, 473`). *Fix:* policy-timeline exports `queriesOf(doc: SimPolicy4): BrushQuery[]`, keyed by `queryKey`.
