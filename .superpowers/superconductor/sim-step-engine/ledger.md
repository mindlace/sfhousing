- **Findings at primary source:**
  - F1. The model's own grain is the month. A `Transition` is a table of cumulative incidence per kind for months 1..K (K <= 240) plus a geometric tail of monthly rate `rho`; days come from linear interpolation inside a month (`model.ts:58-63, 150-157, 230-233, 294-342, 369-390`). Initiation is a monthly Bernoulli per lot, `hazard = logistic(z)`, drawn as a geometric month by inverse CDF (`engine.ts:947-955`, `model.ts:465-469`). So "state at month t to state at month t+1" is the model's native form; the engine's whole-life sampling is a speed choice, not a modelling one.
  - F2. A piecewise hazard is already evaluated as an accumulated log-survival against one latent: `piecewiseMonth(L, bounds, rates)` walks segments adding `months x rate` until it passes `L = log(1 - u)` (`input.ts:243-263`). A step engine that keeps that accumulated sum as a per-lot value and adds the current month's rate gives the same month for the same draw, with no need to know later segments.
  - F3. Draws are stateless and keyed `(seed, entity, attempt k, purpose, stage index)` (`rng.ts:50-72`); a stage takes two uniforms, kind on `P.STAGE` and time on `P.STAGE_TIME`, and a timer multiplies only the time in days, `survived + floor(s x (days - survived))` (`engine.ts:490-534`). So a stage's outcome and its length at unscaled speed are fixed at stage entry, and the calendar day follows from the timer in force. A per-project stage clock that advances by `1/s` unscaled days per day reproduces this and extends it to a timer that changes mid-stage; the kind cannot flip (pairing kept).
  - F4. Without finance a lot's outcome depends only on its own stream and on `Holds` from pipeline rows on that lot (`engine.ts:1094-1148`); pipeline rows each run on their own stream (`:661-704`); a phase depends on its master (`:814-898`). Nothing else couples entities. The initiation rate of a lot depends on the lot and the policy, never on the seed: every world accumulates the same log-survival for a lot that has been at risk since `asOf`; worlds differ only in the latent.
  - F5. With finance, `Treasury.award` schedules every later money event of a project from its finished `Schedule` on the award day (`money.ts:97-163`); pool arrivals for the whole horizon are built in the constructor (`:60-74`). The funded pass is a day-ordered loop over a calendar (`funded.ts:1423-1450`; order of work within a day per `finance-engine.md:45-48`, not yet verified in code).
  - F6. A lever change discards the band and the shown run and starts both again from `asOf` (`scenario-host.ts:994-1003`); a null seed makes every FZP band run finish before the shown run starts (`:876-882`).
  - F7. Lever families reach the engine as: zoning (rules, paint, protections) into one `ScenarioParcels` view (`apply.ts:71`), timers into two undated `StageScale`s (`:79, 68`), route shares into `newProjects.calibration` (`:72`), finance into `SimInput.finance` (`:74`). Dated zoning already exists as `SimInput.regimes` (one full parcels view and one precompute per date; `types.ts:110-117`, `input.ts:163-172`), used only by `/lesscars`.
  - F8. Verified: `pipeline/lib/version.ts:42-53` hashes `pipeline`, `src/lib/data`, `src/lib/generator`, `src/lib/timelapse`, `src/lib/plan/{geometry,types}.ts`, `src/lib/sim/{scenario,levers,finance}` and `src/lib/scoreboard` into the dataset version. A new engine in a new folder is outside the hash until `/lesscars` runs on it.
  - Correction owed to the partner: the first message said results must change and bit-exact goldens die. F1-F3 mean a step engine can be built to give the same schedules as today for the same draws while the policy never changes (certainly without finance); whether to require that is a design decision, not a given.
