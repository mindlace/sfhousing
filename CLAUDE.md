# CLAUDE.md

This file provides guidance to Claude Code when working with this repository.

## What This Is

SF Housing: a free, open-source educational game on a map of San Francisco. A new game opens with the brush: paint zoning until there is room for the homes goal, then press Start. From then on the page is the simulation tool for the whole game: the map in 3D, the timeline, Play and Pause, limited to the policies offered so far. Seeing current law's goal month is the first win. Each win is taken by opening the gift, which offers three of twelve real policies (three a round over four rounds), fixed until you have won with them and editable after. The target is your own best month: each win sets an earlier one to beat. After the last round every lever is open. Plans (`/p`) and policies (`/s`) are published as before. SvelteKit 2 + Svelte 5 (runes) + Tailwind 4 on a single Cloudflare Worker. Code is MIT; the data is open (ODbL / PDDL).

## Setup

```bash
nvm use                 # Node 24 (.nvmrc); engines require node >=22 <26, npm >=11.3.0
npm install             # also runs `wrangler types --strict-vars=false` and `svelte-kit sync` via prepare
npx playwright install chromium   # browser for client tests and e2e (the one download beyond npm)
echo 'PUBLIC_DATASET_VERSION=fixture-0' > .dev.vars   # dev override; the build computes the real dataset version
npm run data:fixture    # load the fixture dataset (fixture-0) into local R2
# npm run data:transit  # optional: live transit (Muni/BART/Caltrain GTFS) into the local dataset; fixture-0 already has a mini network
npm run db:migrate      # apply D1 migrations to the local database
npm run dev
```

If you see type errors about `worker-configuration`, run `npm run types`.

`.npmrc` sets `legacy-peer-deps=true` (the drizzle release candidates declare an optional `effect` peer). The lockfile pins `drizzle-orm` 1.0.0-rc.4-5d5b77c and `drizzle-kit` 1.0.0-rc.4-ca0f029 while `package.json` keeps caret ranges: do not run a blind `npm update` on drizzle.

## Architecture

One Cloudflare Worker (SvelteKit via `@sveltejs/adapter-cloudflare`) with bindings `DB` (D1), `BUCKET` (R2, bucket `sfhousing`, shared by both environments), `ASSETS` and six rate limits (`PUBLISH_RL`, `AUTH_LINK_RL`, `AUTH_PASSWORD_RL`, `PSEUDO_MINT_RL`, `ACCOUNT_EDIT_RL`, and `MUTATION_REGISTERED_RL`, which guards saved-game writes; see [docs/dev/auth.md](docs/dev/auth.md)). The vars are `ENVIRONMENT`, `AUTH_METHODS` (`magic-link,password,google,passkey`), `SES_FROM` and `PUBLIC_APP_RELEASE` (`wrangler.jsonc`); the secrets are `BETTER_AUTH_SECRET`, `SES_ACCESS_KEY_ID` and `SES_SECRET_ACCESS_KEY`, with `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` switching Google on once set (see [docs/dev/deploy.md](docs/dev/deploy.md)). Accounts own saved games (`game_save`, `/api/game`, see [docs/dev/game-save.md](docs/dev/game-save.md)); the game's rules are in `src/lib/game/` (see [docs/dev/game.md](docs/dev/game.md)). All geographic data is static and versioned on R2 at key `data/<datasetVersion>/<path>`, served at `/data/<datasetVersion>/<path>` by `src/routes/data/[version]/[...path]/+server.ts`. The build computes the dataset version from the source tree (`treeDatasetVersion`, injected as `__SFH_DATASET_VERSION__`); `PUBLIC_DATASET_VERSION` is a development-only override. The version reaches the client as data from the root layout load, never as a global. Published versions are immutable.

Shell: the root layout renders the skip link, header and `<main>`, and the footer on document routes only (`isFullHeightRoute` routes, `/`, `/p/<id>` and `/s/<id>`, have none). The game is one page at one address: `/` holds the brush editor while the current game is in its opening and the simulation after it, and `/sim` is a 308 to `/`. The header has no steps. From lg it reads: the site name "SF Housing" (`SITE_NAME`, `src/lib/shell/name.ts`), in a game's runs on `/` the round as plain text ("Round 2", never a control; below sm in the Menu beside the name; never on `/p/<id>`, `/s/<id>` or another page), the page's status cell, the pinned item, the page's actions and the Menu button; below lg the actions sit in the Menu too. The Menu button shows at every width; its panel (a pop-over under the header from lg, full width below; never taller than the room down to the viewport's bottom, it scrolls in itself when its entries need more, as on a landscape phone) holds the saved games (`GamePanel`: saved games, New game and the sync line), the account entry and About. The game's screens and header parts are in `src/lib/game/ui/` ([docs/dev/game.md](docs/dev/game.md)). Pages put actions in the header with `useHeaderActions(snippet, { pinned?, status? })` from `src/lib/shell/header-actions.svelte.ts` (`null` for none); only the root layout calls `provideHeaderActions()`. The map's layer switches are not header actions: they sit in the map toolbar's Layers panel beside Key (`MapKeyControl`, [docs/dev/map-interfaces.md](docs/dev/map-interfaces.md)). `status` is the page's one status cell, never in the Menu: the save state, with nothing visible when saved; on the simulation "Updating" covers it while the numbers are stale or Play waits, and sits beside "Autosave off" instead while autosave is off; below sm in a game both are icons (a spinner in a box always reserved, an icon-only "Autosave off"), each named by its word. On the simulation the actions hold Undo and Redo only while some pointer is coarse (a phone, a tablet, a touch laptop), then Publish; keyboard shortcuts are in About this model, not the header. Publish sends what is true: the plan during the opening, the policy the forecast runs after it. `pinned` is one item always in the bar: in the opening and on `/p/<id>` the room box (line 1 "Room for 47,335 homes", line 2 "57% of the goal", undated); after the opening the goal (`GoalHeadline`: pending, win or late; line 1 the homes of the goal and the month to beat, a bar, line 2 what beating it brings, or by how much it was early or late; a win carries the gift, which takes the win and opens one explainer per new policy; pressing the goal opens the information-only round panel); in the open game, which `/s/<id>` and every e2e page with no seeded game show, the simulation headline (line 1 the homes from today to the playhead's month, line 2 the effect and the goal) and no game panel. Below sm, on a page that pins an item, the site name moves into the Menu and the pinned item leads the bar, the status between it and the Menu. The Menu also carries an account entry (`@handle` linking `/account`, fed by the root layout's `user`; or `Sign in` while a sign-in method is in effect, `signInAvailable`) and an About entry after it.

## Conventions

- All work happens in git worktrees under `.claude/worktrees/`.
- Conventional Commits.
- PRs merge only with the `chreode/signoff` commit status. Run `npm run signoff` ([chreode](https://github.com/mindlace/chreode); config in `chreode.config.ts`): it merges `origin/main`, runs only the steps the changes since the last signoff need (a path no rule matches runs everything), pushes, and posts the status; do not `git push` first. `npm run signoff -- --dry-run` prints the plan; `-- --full` runs every step. Signoff is the only required check; no workflow runs on pull requests.
- A branch that changes the dataset version uploads its dataset before signoff: see [docs/dev/pipeline.md](docs/dev/pipeline.md) (Finishing a branch that changes the dataset).
- A dataset is uploaded only after `npx tsx scripts/reach-check.ts pipeline/out/<v>` exits 0 (D1: every policy at its fixed values reaches the goal inside the window).
- Schema change: edit `src/lib/server/db/schema/` → `npm run db:generate` → `npm run db:migrate`. Never hand-edit migrations.
- Code style: 2-space indent, single quotes, no trailing commas, 100 columns (Prettier + ESLint).
- CSP (`kit.csp` in `svelte.config.js`) changes are interface changes: raise them with the owning subsystem rather than widening ad hoc. Map glyphs and sprites are self-hosted under `/data/<version>/`.
- Runtime dependencies that ship in the bundle get a credit in the `SOFTWARE` list in `src/lib/attribution.ts` (rendered at `/about#about-data`).
- Route tests that need R2 use `FakeR2Bucket` (`src/lib/server/test/fake-r2.ts`); Playwright against workerd is the source of truth for real R2 behaviour.
- Vitest runs with `expect.requireAssertions`: every test must call `expect`.
