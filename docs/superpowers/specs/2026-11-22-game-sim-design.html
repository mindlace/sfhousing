Game sim design

The /sim page under the game: locks by level, the playable document, given measures, the seen result, the win card, the bar, levelling up, the locked page, and the published view outside the game.

Goal

This unit puts /sim inside the game of the incremental game design. A saved game runs and edits only what its level allows, sees its result, wins against its bar and levels up on the page. The published view at /s/<id> and the open game stay outside the game.

  • The page reads the current game from the store: what is allowed, the level and the bar.
  • Locked kinds and locked policies stay on the timeline, cannot be selected, and have no "+".
  • The worker and Publish get the playable document. The stored document and autosave keep every policy.
  • Money policies made from a funding preset carry the preset's id and label, and are dated from their start (M1).
  • The page knows when a result is seen, and the player's standing against the bar. It sets the store's offer while the result wins.
  • A win shows the win card. A seen result short of the bar shows the outcome message naming the bar.
  • The ruler has a "To beat" flag and Details a "To beat" line.
  • When the level rises, the clock returns to today and the new kind's row opens, with the policies kept.
  • At level 1 /sim is a locked page that links to Paint.
  • At level 5 a given measure's dates, switch, order and Remove work, and what it pays is read-only text. "+" on Public money lists the given measures only.
  • The page reads the e2e goal seam (X1), and tells the store when autosave writes.

G1 Levels and results

// src/lib/game/levels.ts
import type { Day } from '$lib/timelapse/time';

import type { GoalOutcome } from '$lib/timeline/outcome';

export type Level = 1 | 2 | 3 | 4 | 5;
export const LAST_LEVEL: Level = 5;

/** What the months reached so far show: `{ kind: 'reached'; on }` or `{ kind: 'missed'; short }`. */
export type Result = GoalOutcome;

/** The result to beat: the day a banked result reached the goal. */
export interface Bar {
  on: Day;
}

export function beats(seen: Result, bar: Bar): boolean;

/** Paint is won: capacity is at least the goal's amount. */
export function paintWon(net: number, amount: number): boolean;
reached.on
The first day of the calendar month in which the goal's amount is first met, as readGoal gives it.
  • beats(seen, bar) is true when seen reached the goal and seen.on is in an earlier calendar month than bar.on.
  • It is false in every other case: a tie never beats, and a missed result never beats.
  • paintWon(net, amount) is net >= amount.
  • Only a reached result is ever banked, so a bar is always a date.

SAVES_KEY
Holds { v: 1, current: string, saves: SaveEntry[] }.
saveKey(id)
Holds one GameSave. For the current game its plan and policy are stale: the records under sfhousing:plan:v1 and sfhousing:sim:v2 are the truth.
  • barOf is { on: banked[level - 1].on } at levels 3 to 5.
  • levelUp from level 1 takes null and banks nothing.
  • levelUp from levels 2 to 4 stores the day under the level being left and adds one to the level.
  • levelUp at level 5 stores banked[5] and keeps the level at 5.
  • The page calls won() when a win card first shows.
  • allowed is allowedAt(progress.level).
  • While open is true no page shows a game part: no level cell, no win card, no bar or "To beat" flag, no locked lane, no reworded outcome message, no Remix button, and no offer is set. The pages read open; they never compare allowed with ALL_ALLOWED.
  • The page calls setOffer with the win while its seen result wins the level, and with null as soon as its seen result stops winning and when it unmounts. On /sim every edit clears the seen result, so an edit clears the offer. On Paint the result is the latest complete score, so a stroke leaves the offer as it is and a complete score below the goal clears it. The offer is kept in memory only.
  • The store's levelUp() banks the offer with the pure levelUp, clears the offer, and stores the game. The win card and the level panel both call it.
  • The page that set the offer reacts to the level changing: /sim returns the clock to today, and Paint opens /sim.
  • The page calls touched() each time its autosave's status goes from saving to saved: after the autosave writes a record key, and when an edit inside the debounce returns the document to the text already written. The store sets the current game's savedAt and calls sync.changed(currentId).
  • A page that autosaves a record key registers its autosave's flush with beforeLeave when it mounts and removes it when it unmounts. newGame, switchTo of another game, remix, remove of the current game and adopt of saves that hold the current game's id call every registered function, in registration order, once they will go ahead and before they read or write a record key. So an edit still waiting in the page's autosave is in the record keys when the old game is copied out, and nothing is left waiting to be written over the new game's records when the page unloads.
  • When a function that adopt called writes a record key, the current game had an edit that was still waiting: adopt then changes nothing and answers { ok: false, reason: 'changed' }. The save sync sends that game instead, and a 409 keeps both versions (S2, D8). No other change answers changed.
  • After newGame, switchTo of another game, remix, remove of the current game, or adopt of the current game's id answers ok, the store ignores touched() for the rest of the document's life: the page is about to unload, and nothing it still writes belongs to the game now in the record keys.
  • On first construction with no SAVES_KEY, the store makes one saved game at level 1 whose plan and policy are whatever the two record keys hold.
  • newGame, switchTo and remix first copy the two record keys into the current game's stored save, then write the new current game's plan and policy into the two record keys. remove of the current game removes its save without copying it out, then writes the new current game's plan and policy into the two record keys.
  • After newGame, switchTo or remove answers ok, the caller loads the new current game's page with a full page load: / at level 1, /sim above it.
  • After remix answers ok, the caller loads / for a plan and /sim for a policy, with a full page load.
  • remix's record is the text the page's autosave holds under the record key for the published document. The caller builds it with the codec the page already uses, so the store never reads inside a plan or a policy.
  • remix of a policy copies the current game's progress and plan; remix of a plan copies the current game's progress and policy. The new game's name is defaultSaveName({ kind: 'remix', title }).
  • newGame, remix and adopt answer full and change nothing when they would pass MAX_SAVES.
  • rekey of the current game leaves it current, keeps the offer and needs no page load: the records and the progress are untouched. The save sync uses it when it keeps both sides of a conflict (S2).
  • A write that the browser refuses answers storage and leaves the stored games as they were.
  • remove of the current game makes the most recently changed other game current; with none left it makes a new game.
  • rename trims the name, cuts it at SAVE_NAME_MAX, ignores an empty one, and sets nameIsDefault false.
  • defaultSaveName gives "Game, 22 Nov", "Remix of {title}" or "{name} (this device)", and adds " (2)", " (3)" while the name is in taken.
  • The store calls sync.changed(id) after every change to a saved game and sync.removed(id) after a remove.
  • A stored value that will not parse is copied to sfhousing:save:corrupt:<ISO time> and left out of the list.
  • With storage: null the store keeps one game in memory.
  • useGame() outside a provider returns openGame(), so a component test that provides no game sees every control.
  • Only the root layout calls provideGame. It makes the save sync with createSaveSync (S2), constructs the store with it, calls sync.attach(store) and provides the store.
  • When e2eOpen (X1) is true, the root layout provides openGame() instead and makes no sync.
  • The root layout's script that makes and provides the store belongs to game-core.

G3 What a level allows

// src/lib/game/allowed.ts
import type { Policy, PolicyKind, SimPolicy4 } from '$lib/timeline/policy4';

export interface Allowed {
  /** Kinds whose policies run and can be edited. */
  kinds: ReadonlySet<PolicyKind>;
  /** 'given': only given measures run, and what they pay is read-only. */
  money: 'given' | 'all';
}

export const ALL_ALLOWED: Allowed;
export function allowedAt(level: Level): Allowed;
/** permitting 3, zoning 4, money 5. */
export function unlocksAt(kind: PolicyKind): Level;
/** A money policy made from a funding preset: its `preset` is the preset's id. */
export function isGiven(p: Policy): boolean;
export function runs(kind: PolicyKind, p: Policy, a: Allowed): boolean;
export function playable(doc: SimPolicy4, a: Allowed): SimPolicy4;
/** The lowest level whose `allowedAt` runs every policy of `doc`; 6 when none does. */
export function levelNeeded(doc: SimPolicy4): Level | 6;
/** True while the game's level is below the one that opens the simulation. */
export function simLocked(p: Progress): boolean;
/** The level that runs all of `doc`, when it is above the game's level; null otherwise. */
export function needsHigher(doc: SimPolicy4, p: Progress): Level | 6 | null;
  • allowedAt(1) and allowedAt(2) have no kinds.
  • allowedAt(3) has permitting; allowedAt(4) adds zoning; allowedAt(5) adds money with money: 'given'.
  • ALL_ALLOWED has all three kinds and money: 'all'. No level in this round returns it.
  • The published view at /s/<id> runs under ALL_ALLOWED, so playable returns its document unchanged (D5).
  • runs is false for a kind not in a.kinds.
  • runs is false for a money policy that is not given while a.money is 'given'.
  • playable returns the document with only the policies that run, in their order, and returns the same object when nothing is removed.
  • Every money policy that addPolicy makes from a funding preset carries the preset's id in preset and the preset's label as its label.
  • The schema 4 parser accepts null or a preset id of 1 to 60 characters in a money policy's preset. Zoning and permitting are unchanged.
  • A money policy stored or published before this build has preset null, so it is not a given measure. It runs in the published view and is locked in a game.
  • An edit that changes what a given measure pays sets its preset to null.
  • isGiven is false for every zoning and permitting policy.
  • isGiven does not check the id against the presets on offer. A hand-made document can carry any id on any pool; nothing ranks one player against another, so that is accepted.
  • simLocked is true exactly at level 1. Pages call it and needsHigher; no page compares a level itself.
  • levelNeeded of a document with no policies is 2.

What is there today

Every claim here was read on commit 8125e557. This unit starts after finite-funding and game-core; the uncapped reads in TimelineMode.svelte and SimDetails.svelte are gone by then.

The mount chain and the edit path

  • /sim renders SimRoute mode="edit" persist="restore" with the Remix hand-off from history state (src/routes/sim/+page.svelte:14).
  • /s/<id> renders SimRoute mode="view" persist="off" with the opened document (src/routes/s/[id]/+page.svelte:78-85).
  • SimRoute renders SimPage inside #map-region, remounted on a new load result (src/lib/sim-page/SimRoute.svelte:54-72).
  • Read-only is one boolean fixed at mount, mode === 'view' (src/lib/sim-page/SimPage.svelte:155).
  • The document lives in PolicyStore, whose normalize runs on every applied change with the new and the previous document (SimPage.svelte:182-194; src/lib/sim-page/policy-store.svelte.ts:59-63). Undo, redo and a load do not run it.
  • Every change goes to PolicySync.update (SimPage.svelte:294-301), and TimelineMode gets policy={store.policy} and lots={sync.lots} (SimPage.svelte:1173-1174).
  • TimelineMode opens the session on policy (src/lib/timeline/TimelineMode.svelte:1171-1174), treats a new policy object as an edit (:1189-1201) and sends it with its lots (:1249). The same policy draws the rows (:1765-1787).
  • Autosave writes the policy record after a debounce and reports it through its status, which goes from saving to saved (src/lib/sharing/autosave.svelte.ts:175, :241-244). SimPage schedules each change (SimPage.svelte:305-312).
  • Publish gets the whole document (SimPage.svelte:1083-1091). After publishing, onPublished records lastPublished against the current document (:316-321).
  • On the map a stroke with no painted policy selected adds a painted policy (SimPage.svelte:513-542). The brush controller attaches unless read-only (:587), and the palette strip shows below md while a stroke tool is chosen (:1209-1218).

The goal, the outcome and the ruler

  • The goal is the goal test seam or defaultGoal(asOf) (TimelineMode.svelte:383). SimPage passes no goal.
  • The outcome is computed only while the numbers are current and no search for an edit's first changed month is under way. A view that does not yet cover the months read keeps the last outcome (TimelineMode.svelte:592-622).
  • outcomeText says "Goal reached in Mar 2049, by the Sep 2066 deadline." or "Goal missed by 3,313 homes. Change the policy and play again." (src/lib/timeline/outcome.ts:67-73).
  • The goal notice is a dismissible Message in a polite region in the notice stack, once per distinct outcome per visit (TimelineMode.svelte:625-645, :1606-1612).
  • The ruler's "Goal" flag sits at the goal's deadline while the chart draws the goal's step (TimelineMode.svelte:577; src/lib/timeline/Playhead.svelte:294-300). The ruler's description is rulerDescription(seenTo, deadline) (Playhead.svelte:103; src/lib/timeline/copy.ts:69-74).
  • Details renders the goal rows from goalRows (src/lib/timeline/SimDetails.svelte:130).
  • The playhead's moves go through handleDay (TimelineMode.svelte:1082-1088). Nothing returns the clock to today but a Retry with a new calibration.

Rows, "+" and the editor

  • The kinds shown are zoning, permitting, and money when the data can run money (src/lib/timeline/Timeline.svelte:102-104).
  • A kind's "+" shows unless read-only, and a closed empty kind says in its lane what "+" adds (src/lib/timeline/KindRow.svelte:74, :97-126).
  • A span bar is a button with aria-pressed. Keys and edge handles are off when read-only (src/lib/timeline/SpanBar.svelte:103, :151-182). Its keys and drag edit through moveEdge, moveSpan, setFrom and setTo (SpanBar.svelte:107-108, :142-143).
  • WhenEditor edits through setFrom, setTo, addSpan, splitSpan and removeSpan (src/lib/timeline/WhenEditor.svelte:121-144), handed to the Inspector's whenEdit, which applies them to the store (src/lib/timeline/Inspector.svelte:259-266).
  • addChoices offers on Public money every available preset, then "Your own pool", "City funding scale" and "Market terms" (src/lib/timeline/add.ts:96-109). addPolicy dates the new policies' spans and appends them (add.ts:237-246).
  • Activity's starters come from startersFor(calibration, policy) while nothing is in force (TimelineMode.svelte:565-567).
  • The Inspector shows the switch, Move up, Move down, Remove and the policy part only when not read-only, then When and What (Inspector.svelte:415-483). WhatEditor shows PolicySummary for the span part when read-only (src/lib/timeline/WhatEditor.svelte:122-125).
  • The funding editors in What write through the span lens: tryWriteBack reads the edited projection back into the policy (src/lib/timeline/lens.ts:261-290).

Money policies carry no preset

  • A money policy made from a funding preset is built by upgradePolicy, whose make defaults preset to null, under labels such as the pool's (src/lib/timeline/upgrade.ts:21-35, :95-133).
  • The schema 4 parser refuses a non-null preset on any zoning or money policy (src/lib/timeline/parse4.ts:266-274).
  • The server's publish route parses with the same parser: SIM_SERVER_CODEC4.parse calls parseSimDoc4(text, null) (src/lib/timeline/server-codec.ts:101-104).

Design

Where the game is read

  • SimRoute reads the store with useGame() in edit mode, and passes it to SimPage as a new prop, game.
  • SimRoute takes an optional storage prop, () => Storage | null, default getStorage, and passes it to SimPage's existing storage prop. It is a test seam: a component test gives the page's autosave and the GameStore one memory storage.

run
The playable document. TimelineMode opens the session on it, sends it, treats a new run object as an edit, and falls back to it for the numbers' document. policy draws the rows and the Inspector.

The playable document

  • SimPage derives allowed as game?.allowed ?? ALL_ALLOWED, and run = playable(store.policy, allowed) once per change of either.
  • PolicySync takes run, not store.policy, so it resolves the brush queries of the policies that run and no others. Its first open takes the playable document of the opened one.
  • TimelineMode gets policy={store.policy} and run={run}. playable returns the same object when it removes nothing, so a level up that unlocks a kind with no policies is no edit.
  • Starters, the key's mark row and the "From your policy" wording read run, so a locked policy never counts as in force.
  • Publish gets { ...doc, policy: run }, and the published policy plays for everyone as it played for its author (D5).
  • onPublished keeps the title and records lastPublished against the whole document, as today. The button reads "Share link" while the playable document is unchanged.
  • Autosave, undo and redo keep working on store.policy, the whole document. A locked policy is never dropped from storage.
  • Each time the autosave's status goes from saving to saved, SimPage calls game.touched(). Without a game it calls nothing.
  • With a game, SimPage registers its autosave's flush with game.beforeLeave when it mounts and removes it when it unmounts. The registered function hands the autosave the current document (schedule) and then calls flush, so an edit is in the policy record before the level panel's New game, switch or Delete changes the current game (G2), whether it is still in the autosave's debounce or not yet handed to the autosave by the page's effect.
  • At level 2 the playable document is empty, so Publish is disabled with its hint, "Change the policy first."

Locked kinds and locked policies

A kind is locked when it is not in allowed.kinds. A policy is locked when runs(kind, policy, allowed) is false. Fixed rows are never locked.

  • A locked kind's row stays in the timeline in its usual place. Its toggle opens and closes it as today; below md a tap opens its sheet as today.
  • A locked kind has no "+" and no "+" in words. Its label row's lane shows lockedLane(kind, level) whether the kind is open or closed. Its words are lockedLane's (G5).
  • The toggle's aria-describedby names the count and the lane's text, so a screen reader hears the kind, its count, then the lane's text.
  • A locked kind that holds policies shows its count. Closed, its lane shows the lock text and no miniature. Open, it shows the fixed row and a row per policy.
  • A locked policy's row draws its bars dimmed. A locked bar is no button: it is not focusable, takes no press, no keys and no drag, and has no edge handles.
  • In a kind that is not locked, a locked policy's label has a second, muted line, "Unlocks in a later round". At level 5 this marks a money policy that is not a given measure (isGiven false): one whose preset is null, including every money policy stored or published before this build, or one whose selector is not a money selector (G3).
  • The Inspector never shows a locked policy. select(ref) ignores a ref to a locked policy, and startAdd(kind) ignores a locked kind.
  • If the selection names a policy that stops running, the selection clears and focus goes where Close sends it. The same holds for an open "+" menu of a locked kind. The level only rises on this page, so this is a guard, not a flow.
  • A tap on the map selects only what the worker reports, which only knows policies that run.
  • While zoning is locked, the brush controller does not attach, the palette strip does not show, the tool stays Move, and Space plays as in read-only mode. When zoning becomes allowed, the controller attaches as it does on load.
  • The fixed rows ("Current law", "Current timelines", "Current funding", "Market conditions") are unchanged and stay selectable.

Given measures

G3 defines a given measure as a money policy whose preset is a funding preset's id. This unit makes the code carry that id.

  • addPolicy of a money preset sets, on every policy the preset makes, preset to the preset's id and label to the preset's label (FundingPreset.label).
  • After it dates the new policies' spans (add.ts:237-241), addPolicy calls dateMeasure(policy, cal) (M1) on each policy it made from a funding preset.
  • parsePolicy4 accepts on a money policy a preset that is null or a string of 1 to 60 characters. Zoning keeps requiring null. Permitting keeps requiring a timing preset id. The 60 is a named constant, MONEY_PRESET_MAX.
  • Nothing fills preset on load: upgradePolicy, reconcilePolicy4 and the loaders leave a stored null as null.
  • The server's publish route uses the same parser, so a published policy may hold a given measure. In its body a given measure is a money policy such as { "id": "fund-u-housing-bond-1", "label": "A housing bond", "preset": "housing-bond", "on": true, "where": { "tag": "fund", "pool": "u-housing-bond-1" }, "spans": [ … ] }.
  • A "City funding scale", "Market terms" or own pool policy has preset null.

An edit to what a given measure pays sets its preset to null (G3):

  • Every such edit goes through the span lens. tryWriteBack sets preset to null on a money policy whose spans' what it changes. Its label stays.
  • The editors that reach it are the funding editors in What (FundingTab and what it mounts: the pool row, the programme list and editor, the scale lines, the market terms), through the Inspector's edit store.
  • In a game at level 5 they are never shown for a given measure (What is read-only). Without a game, in the open game, every editor is reachable, and an edit there makes the measure an own measure.
  • The switch, Move up, Move down, Remove and every When edit keep preset.

A given measure's money follows its start (M1):

  • SimPage's normalize compares, for each given measure in the new document, its first span's from with the same policy's in the previous document. Each one that moved is replaced by dateMeasure(policy, cal).
  • This covers every edit that moves a first start: setFrom, moveEdge on the start, moveSpan, addSpan and removeSpan from spans.ts, whether they come from SpanBar's keys and drag (through Timeline's onedit) or from WhenEditor (through the Inspector's whenEdit).
  • A policy that is new in the document was dated by addPolicy and is left alone.
  • Undo, redo and a load never re-date, because normalize runs only on applied changes.
  • The comparison is a pure function in src/lib/timeline/add.ts, redateMoved(before, after, cal), returning after itself when nothing moved.

At level 5, where allowed.money is 'given':

  • "+" on Public money lists only the available funding presets, in today's order and labels. "Your own pool", "City funding scale" and "Market terms" are not listed.
  • addChoices(kind, cal, doc, allowed) takes allowed as a fourth argument, default ALL_ALLOWED. It returns no entries for a locked kind. The AddMenu and startersFor pass the page's allowed.
  • Selecting a given measure shows its switch, Move up, Move down, Remove and its When editor, all working as today. Its bars' keys and drag work.
  • Its What section renders WhatEditor with readonly for the span part, so PolicySummary shows what it pays as text through its existing props. The Inspector does this when allowed.money is 'given' and isGiven(policy).
  • Move up and Move down move the measure past its neighbour in the list, whether or not the neighbour runs.

The seen result and the offer

  • TimelineMode keeps a seen: GoalOutcome | null beside today's outcome.
  • Every edit (a new run) sets seen to null at once.
  • seen is set only when the outcome effect computes a fresh outcome with the numbers current, no search under way, the open not provisional, and the view covering the months read. It is then that outcome, which may be null.
  • A view that does not yet cover the months read leaves seen as it is. After an edit that is null, so a held outcome from an older document is never seen.
  • So a result is seen when the playhead has reached the month the goal is met, or the window's end, under the current playable document.
  • After an edit whose first changed month is later than the month the goal is met, the result is seen as soon as the scan ends, because the months the player saw are unchanged.
  • The standing is standing(level, barOf(progress), seen).
  • While the standing is won, TimelineMode calls game.setOffer({ on: standing.on, datasetVersion }) with the dataset the page runs on.
  • It calls game.setOffer(null) as soon as the standing stops being won (any edit does this), and when it unmounts.

The outcome message in a game

With a game, the goal notice reads the standing, not outcomeText. It shows only for a short standing. Its region, dismissal and testid are today's, keyed by outcomeKey(seen).

  • Reached, short of the bar: "Goal reached in Mar 2058. Beat Jun 2057 to level up."
  • Missed, with a bar: "Goal missed by 3,313 homes. Reach it before Jun 2057 to level up."
  • Missed, with no bar (level 2): "Goal missed by 3,313 homes."
  • Won: no notice. The win card is the message.
  • Playing (nothing seen): no notice.

The win card

  • TimelineMode renders G5's WinCard in the notice stack, right after the goal notice's region, in a wrapper with data-testid="tl-win". From md the stack lies over the top of the map; below md it is in flow above the map.

When the level rises on /sim

The card's "Level up" and the level panel's both call game.levelUp(), which banks the offer and raises the level (G2). The page reacts to game.progress.level rising, and at level 5 to roundComplete(game.progress) turning true, whoever pressed. Nothing reacts to the offer going to null. In order:

  1. TimelineMode stops playback and returns the clock to today: the day becomes asOf through handleDay, so the session, the map and the card follow.
  2. The reveal returns to revealOpen(asOf). seen, outcome, the dismissed outcomes and the kept month are cleared, and the card closes. Focus that was in the card moves to the ruler (tl-ruler).
  3. SimPage works out the kinds the new game.allowed has that the old one did not. From md, after the next tick, it opens each one's row if closed (openKind). Below md nothing opens.
  4. SimPage announces levelledUp(level, unlocked) in its polite status region, for example "Level 3. Permitting unlocked.", or "Round complete." once the round is complete.
  5. The policies stay. If the new level runs policies the old one did not, run changes and the page refills as for any edit.
  • A level up is not a document change: undo and redo do not see it, and the undo history is kept. Every entry in it touches only kinds the old level allowed, which every later level allows too.
  • At level 5 the level stays 5 when the store banks banked[5] (G2). There the trigger is roundComplete(game.progress) turning true: steps 1, 2 and 4 run, with no kind to open. Once the round is complete no control offers "Level up" (the card has none and the panel and the level cell hide it), and a game.levelUp() call changes no progress and banks nothing (G2): it only clears the offer, so the page does nothing and the clock stays where it is.

Global constraints

  • Work happens in git worktrees under .claude/worktrees/. Commits follow Conventional Commits. No attribution to an AI anywhere.
  • Code style: 2-space indent, single quotes, no trailing commas, 100 columns.
  • Every Vitest test calls expect.
  • Signoff fails on server stderr, on timing crutches and on a retried flake. Each unit runs npm run lint, npm run check and the Vitest projects its files belong to before it hands back.
  • Port 4173 is shared by every session on this machine. A unit never kills a server it did not start; it waits.
  • Every agent runs every command in the foreground and never ends a turn while something it started is running.
  • Schema changes go through npm run db:generate. Nobody edits a migration.
  • No unit runs npm run signoff: its dataset step fails until the dataset is uploaded. closing runs it once, after the upload.
  • The dataset version changes in this build. The dataset is uploaded once, by closing, from the integration branch, after every unit has merged; no other unit uploads a dataset. reach-check builds one earlier to run the check and uploads nothing.
  • A unit that writes a hashed path regenerates the fixture dataset with npm run pipeline -- fixture and commits it.
  • WCAG 2.2 AA: every new control is at least 24 px and passes expectNoA11yViolations in light and dark.
  • Page text is short. No sentence says what something is not.
  • Nothing on the main screen says "RHNA". The goal is read from the Goal value, never from a constant.
  • The game's rules are read from src/lib/game/. No component compares a level to a number.
  • One future: no seed control, no band, no average over runs.
  • Published plans and policies, their ids and their pages keep working, including every policy published before this build.
  • A number that is a claim about the world carries its source and tier, in the existing Sourced, Unsourced and Evidence shapes.
  • A runtime dependency that ships in the bundle gets a credit in SOFTWARE. This build adds none.
  • CSP changes are interface changes. This build makes none.
  • Timing is measured only on a quiet machine. A unit that cannot get one defers the measurement and says so.
