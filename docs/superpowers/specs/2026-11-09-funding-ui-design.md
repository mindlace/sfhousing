# `funding-ui`: the money on the page

Part of the `sim-financing` package. Design: [2026-11-09-1911-sim-financing.md](../design/2026-11-09-1911-sim-financing.md) (approved). Evidence: [the financing evidence digest](../research/2026-11-09-financing-evidence.md). This spec is built last (dependency step 5) and ships in Release 2.

Terms used throughout:

- **Baseline funding**: today's public money for affordable homes, as the dataset gives it (`calibration.baselineFunding`, row F12): City pools, one state pool, one federal tax-credit pool, and one grant programme per pool.
- **Added money**: the pools and programmes the user adds (`FinanceLevers.pools`, `.programmes`, row F7).
- **Dated change**: one `baselineScale` entry (row F7): from a date, a baseline pool's money is multiplied by a scale.
- **Uncovered cost**: what a home costs to build plus land, less what its own income supports (design, "The model", section 2).
- **Coverage**: the share of the uncovered cost that a project's public money pays (row F8).
- **Evidence field** and **choice field**: an evidence field holds a claim about the world (what a bond costs to repay, how much a bank lends per dollar, what an enacted measure pays); a choice field holds what the user proposes (how much money, from when, for which homes). Only evidence fields carry a source or the label "custom, not sourced".

## 1. Scope

From the design's Subsystems table:

| Slug | Scope |
| --- | --- |
| `funding-ui` | The dock's Funding tab (the baseline and its dated scales, added pools, added programmes, presets), the read-only summary on `/s/<id>`, the Results rows, the project card line, sources and tiers in the interface, accessibility, e2e. |

**In:**

1. The Funding tab on `/sim`: its place, icon, layout on the 320 px panel and the phone sheet, the baseline view, dated changes (scaling a source and switching it off), presets, building a pool and a programme (on an added pool or on a baseline pool), the one field for a market term the user types, the pre-run previews, validation, undo labels, announcements and focus.
2. The tab's fallback when the dataset cannot run money, and the funding notices on load, built from `finance-levers`' `FundingLoadReport` (F15).
3. The read-only "Public money" rows in `PolicySummary` on `/s/<id>`.
4. The new Results rows (money, income tiers, displacement, repayment, legal limits) and their sources in `SimResults` and the sources dialog, extending, for Release 2, the `fzp-market` paragraph and the `src-market` dialog section that `market-baseline` ships in Release 1 (4.12).
5. The project card's "Funded by" line (OD-F5).
6. The copy, number formats, component and e2e tests, and the developer doc.

**Out:** the policy schema, parser, loader, its report and the presets (`finance-levers`); every number the model runs on and the one pricing rule, `fundBundle` (`finance-model`, `finance-data`, `market-baseline`); what the engine does (`finance-engine`); the score series and their helpers, `perAddedHome` among them (`finance-score`); the first statement of today's market in the sources and `marketLevel`, the one rule for which market level runs (`market-baseline`, Release 1); the header score (unchanged: its one number stays "homes added"); a market control (R7); any change to a path hashed into the dataset version.

**Hands to others:** nothing that other subsystems build on. It builds on: `ProjectCard.kind` and `ProjectCard.funding` and `PIPELINE_FUNDED` (`finance-engine`, F10 and F9 (l)); preset ids `u-<presetId>-<n>`, `valueSource`, `pastItems`, `nextAddedId`, the limits and the loader's report (`finance-levers`, F7, F15, F16); `fundBundle`, `isCertain`, `resolveTerms` and `MARKET_TERMS` (`finance-model`, F8); `perAddedHome` and the money helpers (`finance-score`, F14).

**No hashed path is edited.** `pipeline/lib/version.ts:40-50` hashes `src/lib/sim/scenario`, `src/lib/sim/levers`, `src/lib/scoreboard`, `src/lib/timelapse` (and the design adds `src/lib/sim/finance/`). All code here lives in `src/lib/sim-page/`, `src/lib/fzp/` and `src/lib/dock/`, so this subsystem never forces a dataset build. It imports from hashed paths freely.

## 3. Global constraints

Copied verbatim from the design.

- **Evidence hierarchy.** Every number the simulation uses carries a `Provenance` with its tier and source, and the interface can show both. A value that cannot be sourced is `Unsourced` with a reason; what depends on it is unavailable, or runs on a value labelled "custom, not sourced" that the user typed. No tier 3 or 4 number is presented as data.
- **Money never decides alone.** A funded project needs a lot the user's zoning makes hostable and free, takes its size from the same draw, and passes through the same stage tables as every other project. Only a fully funded project is exempt from drop-out (R6).
- **Deterministic and paired.** A run is a pure function of (dataset, levers, seed). The plan and the twin share draws: no existing draw purpose changes, and a lot's draws do not depend on the order lots are processed in.
- **No public money means no change.** With `finance` absent, the engine's output is identical, schedule for schedule, to its output before `finance-engine` under the same `market`. A test asserts it. The site's default is not that case: it runs the baseline funding.
- **The engine is in the dataset version.** `src/lib/sim/scenario`, `src/lib/sim/levers`, `src/lib/scoreboard`, `src/lib/timelapse` and `pipeline/` are hashed into the dataset version. The finance model shapes published data too, because the `/lesscars` build step runs the baseline funding: `src/lib/sim/finance/` (the functions and constants of F4 and F8) is added to the hashed paths in `pipeline/lib/version.ts` by `market-baseline`, the first subsystem whose pipeline code imports it. Any change in a hashed path needs a dataset build and upload before signoff ([pipeline.md](../../dev/pipeline.md), "Finishing a branch that changes the dataset"). The page's code stays outside them, in `src/lib/sim-page/`.
- **Goldens change only at the two releases.** The pipeline fixture goldens, the lesscars fixture goldens and `fixture-0` are regenerated by their documented commands for Release 1 (`market-baseline` with `finance-data`) and for Release 2 (`finance-engine`, when the default starts running the baseline funding), each reviewed as an engine or data change. The fixture build emits a fixture market model and fixture baseline funding, labelled tier 4, so the page and its e2e tests have both. `golden-seed1.json` and `model-golden.json` (the mini city and the small calibration, which have no market model and no funding) never change: they are the lock on "no public money means no change".
- **Open data only.** The dataset stays ODbL and PDDL. New sources go in the lock and the attribution list.
- **Worker-safe and client-side.** The simulation stays in the worker; nothing here adds a server computation or a binding. Shared policies stay in the `plan` table's `body`: no migration.
- **Stored documents keep loading.** A schema-2 policy, saved locally or published, opens with default funding. It is never treated as corrupt.
- **Constant dollars.** Every dollar figure is in the dataset year's dollars except bond repayment, which is nominal and labelled.
- **House rules.** Svelte 5 runes, Tailwind 4, colocated Vitest with `expect.requireAssertions`, Playwright e2e, WCAG 2.2 AA, compact results with detail on demand, status apart from controls, Conventional Commits, work in worktrees, signoff as the only merge gate.

### 4.2 Number formats

- **Dollars** (`formatDollars(n)`, `src/lib/fzp/format.ts`): below $1 million, rounded to the nearest $1,000 with grouping ("$412,000", "$300,000"); from $1 million to below $1 billion, three significant figures and the word "million" ("$234 million", "$26.2 million", "$1.53 million"); from $1 billion, three significant figures and "billion" ("$1.25 billion"). Trailing zeros after the point are dropped. Negatives use U+2212, as `formatCount` does (`src/lib/scoreboard/format.ts:12-15`). Zero is "$0". Words, not "M" or "B", because a screen reader reads "$26.2M" as "twenty-six point two M" and the audience reads plain English. The value is rounded first and the unit chosen on the rounded value, so a value that rounds up to the next unit takes that unit. Expected strings: 0 → "$0"; 999 → "$1,000"; 412,499 → "$412,000"; 999,500 → "$1 million"; 1,000,000 → "$1 million"; 26,155,367 → "$26.2 million"; 999,999,999 → "$1 billion"; 1,250,000,000 → "$1.25 billion"; −412,499 → "−$412,000".
- **Dollars a home** (`formatDollarsExact(n)`, `src/lib/fzp/format.ts`): whole dollars with grouping ("$300,027", "$181,637"), U+2212 for negatives. Every amount stated per home uses it, and nothing else does: the group rows' "pays … of each home" and "lends … a home" (4.5), the coverage steps' City part and lending (4.5), the programme preview's per-home figures, alone, in the bundle and lent (4.8), and the Results' per-added-home figures (4.11). Reason: per-home figures are compared with the Budget Analyst's published per-home amounts (Exhibit F), which are whole dollars; totals are not, and read better rounded.
- **Shares and coverage**: `formatPercent` (`src/lib/scoreboard/format.ts:27-36`), which floors (snapping within 10⁻⁹ of a whole number, `format.ts:18-21`), so coverage of 99.6% never reads "100%". Whether a bundle is fully funded is decided only by `isCertain(coverage)` (F8: at least 1 − 10⁻⁹, a floating-point tolerance), never by the formatted percent: a certain bundle reads "fully funded" and its percent is not shown; an uncertain one reads its floored percent, which is then at most "99%".
- **Odds change**: `exp(shift) − 1` as a whole percent with a sign, truncated toward zero so it never overstates ("+12%" for the design's $50,000 grant on prototype B: 1.75 × 50,000 ÷ 736,700 = 0.119, exp − 1 = 12.6%; tier 2 slope from OD-F9a, tier 1 cost); from +1,000% it reads "more than 10 times as likely".
- **Dates**: a month and year ("July 2028", `formatMonthYear`, `src/lib/fzp/format.ts:30`). Every date the user enters is the first of a month.
- **Homes**: `formatCount`.

### 4.5 The coverage line and what the page computes before a run

The page computes, without the worker, everything that follows from the policy and the sourced constants alone. It never shows a homes count, a pool running dry, a date money runs out, displacement or limits before a run: those need the queue, which only the engine runs. The tab says so once, in the coverage disclosure: "Whether the money lasts, and how many homes it pays for, is what a run shows."

| Preview | Computed from | On the page |
| --- | --- | --- |
| Coverage of an affordable home's uncovered cost by the bundle active on a date, and what the City pays of it | the programmes' instruments, pool kinds and dates, the off spans of `baselineScale` (F7), `resolveTerms(MARKET_TERMS, funding.terms)`, `fundBundle` and `isCertain` (F8) | yes |
| Dollars per home a programme pays, alone and in today's bundle | `grantEquivalentPerHome` and `fundBundle` (F8), `uncoveredPerHome`, the prototypes (F4) | yes |
| A private project's change in odds of starting | `oddsShift` (F8) with `calibration.market.slope.perCostShare` (F2) | yes |
| Bond repayment | `debt.rate`, `debt.termYears`, amounts; the finance-model debt-service function | yes |
| A bank's lending capacity | `leverage` × money received | yes |
| Homes funded, money left, displacement, legal limits | the engine and score | no: Results only |

**One pricing rule.** The page never adds shares itself. Every coverage and every per-home split it shows is `fundBundle` (F8, OD-F10), the function the engine prices bundles with, so the tab cannot disagree with a run about what a bundle is worth. Its rule (F8): the bundle is priced in three tiers, federal pools, then state pools, then the City's (the bank, City taxes, City general fund, City bonds, City lease financing). Within each tier, its loans and guarantees count first, at their full grant-equivalent; then the tier's grants each pay their share when they fit in what is left of the uncovered cost, and otherwise the same fraction of their share, so grants never pay more than the whole uncovered cost and the City's sources share what is left in proportion. The coverage disclosure says it in the page's words: "Federal and state money count first. The City's sources share what is left."

**The bundle on a day** (`bundleOn(day)`, in `funding-view.ts`): the programmes with `reach: 'affordable'`, baseline first in dataset order and then the added ones in policy order (the order of `finance.programmes`, F9 (b)), that are active on that day (`from ≤ day`, and `to` null or `≥ day`), and whose pool is not switched off that day. A pool is switched off on a day when the latest `baselineScale` entry for it at or before that day has scale 0 (F7), for any baseline pool, capped or uncapped. Each item is `{ instrument, poolKind }` with the kind of the programme's pool (baseline or added), priced by `fundBundle(items, 'affordable', PROTOTYPES[0], terms)` with `terms = resolveTerms(MARKET_TERMS, policy.funding.terms)`; the prototype is ignored for an affordable home (F4). A programme whose instrument needs a term that resolves to null (`missingTerms`, 4.8a) is left out of the bundle and its row shows the error of 4.8a, because pricing it would throw.

**What the line ignores, and says it ignores.** Pool balances. A scale above 0 does not change what a programme pays per home, only how much money its pool receives, so it never changes the coverage line: a pool that is on but runs short keeps projects waiting in a run (F9 (c)), and only a run shows that. A pool switched off is different: its programmes leave the bundle, so the coverage falls and projects go ahead on the rest, at lower odds (F7, F9 (b)). The disclosure says both in one sentence: "Switching a source off takes it out of every offer, so projects go ahead on the rest, at lower odds. A source that is on but has run short makes projects wait for it; how long is what a run shows."

**Project size.** The line describes a project large enough for every programme in the bundle (its `minHomes`, F6). When the bundle's programmes have different `minHomes`, the step's line adds "for projects of {minHomes} homes or more" with the largest of them, and the disclosure ends with "Smaller projects get only the programmes that reach their size." Reason: every baseline programme has the same `minHomes` (F12), so the default shows no clause; an added programme with a higher threshold is the case that needs it.

**The coverage line** (top of the tab). It states the bundle at the present (`calibration.asOf`): "Affordable homes: fully funded today" when `isCertain(coverage)`, otherwise "Affordable homes: {p} of the cost is covered today; they start only by chance" with `p` from `formatPercent`. Beneath it a disclosure button "Coverage over time" (`aria-expanded`) lists one line per date on which the bundle changes, up to the horizon, in date order. The dates are every `from` of a programme, every day after a programme's `to`, and every `baselineScale` date on which a pool goes off or comes back on (scale 0 after a scale above 0, or the reverse). A line is written only when the coverage or the City's part changes: "From July 2027: 86%, not fully funded; the City pays $300,027 of each home" or "From July 2029: fully funded; the City pays $181,637 of each home". The City's part is the sum of `grantEquivalent` (whole dollars) over the bundle's items whose pool kind is `goBond`, `cop`, `generalRevenue`, `dedicatedTax` or `bank`: a grant's `granted`, and a loan's or guarantee's worth to the project, never the principal lent, which comes back. When those items lend, the line adds "; it also lends ${cityLentPerHome} a home, repaid at completion". (86% is (861,525 − 118,390) ÷ 861,525 = 86.3%, floored: the state's $118,390 taken out of the $861,525 uncovered cost; tier 1 inputs, Budget Analyst Exhibit F, through F12; tier 2 arithmetic. The $181,637 is an illustration: a federal grant of $118,390 added to the federal tier leaves $861,525 − $443,108 − $118,390 − $118,390 = $181,637 for the City's tier; tier 2 arithmetic.) The disclosure ends with the sentences quoted above and "Private projects are not covered by today's funding; programmes you add for them show their own effect." Computed by `coverageSteps(policy.funding, calibration.baselineFunding, asOf, horizon): CoverageStep[]`.

**Today's funding rows** (three groups, from `calibration.baselineFunding`): City (every baseline pool of kind `goBond`, `cop`, `generalRevenue`, `dedicatedTax` or `bank`), State (kind `state`), Federal tax credits (kind `federal`). A group's amount is the sum of its pools' yearly inflows at the present ("$234 million a year"), "no limit" for the uncapped pool, or "switched off" when every pool of the group is off at the present. Its second line is "pays ${perHome} of each home", where `perHome` is the sum of `grantEquivalent` over the group's items in `bundleOn(asOf)`, in whole dollars, and, when the group's items lend, "; lends ${lent} a home, repaid at completion" with the sum of their `lent`. On the default policy this equals each source's published share ($300,027, $118,390, $443,108, F12), because the three shares sum to the whole uncovered cost; once the user adds federal or state money, the City's figure falls; once the user adds City money while the City's tier is already full, the City's sources share what is left and each existing City source's figure falls in proportion; that is the point of adding money (design, "The model", section 3). When a dated change touches the group, a third line reads "Changes from July 2027" (the earliest). Groups with no pool in the dataset are not shown.

**A group's editor** holds, in order:

1. "Sources" (City only): one line per City pool, "{label}: $80.5 million a year", then its own dated changes if any.
2. "Dated changes": one line per change. A City-group change (entries with the same `from` and `scale` on every City pool) is one line, "City money", removed as one store change; an entry on a single City pool that is not part of such a set is its own line, named by the pool. Lines are in date order. An entry with scale 0 reads "From {Month Year}: switched off" for every pool, capped or uncapped (F7: a scale of 0 switches any baseline pool off). An entry above 0 reads "From {Month Year}: {pct}% of today's amount" on a capped pool, with "switched back on, " before the percent when the pool's previous entry was 0; on the uncapped pool it reads "From {Month Year}: switched back on" (F7: for an uncapped pool any scale above 0 leaves it on). Each line has a "Remove" button named "Remove change from {Month Year}".
3. "+ Change from a date", which reveals the inline entry: a month select and a year input ("From", 4.7), and for a capped group a number input "Amount, % of today's" (default 0, min 0, max 1000, step 5; F7's 0 to 10 as a percentage) whose description reads "0% switches the source off: its programmes leave every offer.", or for the federal group a two-option radio group "Switched off" / "Switched back on", writing scale 0 or 1 (an uncapped pool is on or off, not scaled: F7 and the design's "Out of scope"). Then "Apply change" and "Cancel". A change on the City group writes one entry per City pool with the same date and scale, as one store change; a change inside "Sources" on a single City pool writes one entry. An entry on a pool and day that already has one replaces it (as `addPreset` does, `finance-levers` section 4.7), and `baselineScale` is kept sorted on every insert in the order the parser requires (by pool, then by `from`; `finance-levers` section 4.1). "+ Change from a date" is `aria-disabled` when the entries the change would add (one for a source; one per City pool for the City group; less those it replaces) would take `baselineScale` past 24 (F7), with the description "A policy can hold 24 dated changes; this one needs {n}. Remove one first."; the check is made again on "Apply change", and nothing over the limit reaches the store.
4. "What it pays for": the group's baseline programmes, read-only, one line each: "Grants to affordable homes of {minHomes} or more: {pct} of the uncovered cost ({tiers})", where `tiers` is the income mix as "52% very low, 31% low, 17% moderate": whole percents rounded by largest remainder so they sum to 100 (ties to the earlier tier, the timers' rule), zero tiers left out; `{pct}` is the share through `formatPercent` (0.072329 reads "7.2%", 0.348251 reads "34%"). Then the user's programmes on the group's pools, each a nested row with the editor of 4.8 and the word "Added" before its sentence. Then "+ What it pays for" (named "Add a programme to {group name}"): added programmes on baseline pools are allowed (F7: `programme.pool` names an added or a baseline pool). On the City group the new programme's editor starts with a select "Pays from" listing the City pools by label (default the first City pool in dataset order); on the state and federal groups the pool is the group's one pool and no select is shown. A new programme on a baseline pool takes the starting values of 4.8; its preview says what it pays alone and in the bundle, so a City programme that shares the City's part with today's City sources says how much of it it pays.
5. Sources: `SourceList` (`src/lib/sim-page/SourceList.svelte:15-24`) over the group's pools' and programmes' provenance as given in `baselineFunding.provenance`.

Default scale 0% for a new dated change: an entry at 100% changes nothing, and switching a source off is the case the design names first ("no state money from 2027", "federal tax credits withdrawn"). Tier 4 UI default; it is a choice field, not evidence.

### 4.6 Adding money: presets and your own pool

**"+ Add money"** (`data-funding-add`, named "Add money") follows the added rows. It is a disclosure button (`aria-expanded`, `aria-controls` the chooser) that reveals a list, in four groups with `h4` headings ("City money", "The public bank", "State money", "Federal money"): one button per available preset of `fundingPresets(calibration)` (F16), grouped by the preset's `group` (`city` under "City money", `bank` under "The public bank", `state` under "State money", `federal` under "Federal money"; a group with no available preset is not shown), in the list's order within a group, showing `label` with the preset's `description` (F16, written by `finance-levers`) as visible muted text and as its accessible description (`aria-describedby`), then, last in the list, "Your own pool". Presets with `available: false` are not offered (F16); they are listed in "Sources and tiers" as "Not offered yet: {label}: {reason}", so the hard choice stays visible. While the policy holds 12 added pools, "+ Add money" is `aria-disabled` with the description "A policy can hold 12 added sources of money. Remove one to add another." (F7), and a press does nothing.

**Choosing a preset** adds its `baselineScale`, `pools` and `programmes` in one store change labelled "Added: {preset label}". If the result would exceed a limit of F7 (12 pools, 24 programmes, 24 scale entries), nothing is added and the chooser shows, in its always-present `role="alert"` line, "This would pass the limit of {12 added sources of money | 24 programmes | 24 dated changes}. Remove one first." After adding, the chooser closes, the preset's first pool row is selected and expanded, and focus moves to its first field after one `tick()`. A preset that adds only dated changes (for example "No state money from a date") selects and expands the affected baseline group and focuses its new change's "From" month.

**"Your own pool"** opens a draft pool (below) with: kind "City general fund" (`generalRevenue`), label generated (4.9), one yearly inflow from July of the year after `asOf` with an empty amount, no programme. Focus moves to the draft's "Kind of money" select. The empty amount shows its error at once ("Enter an amount above $0 and at most $100,000 million.").

**Drafts.** A policy can only hold complete pools and programmes: `parseFinanceLevers` requires 1 to 12 inflows of whole dollars on an added pool, and `validateInstrument` a finite loan rate (`finance-levers` section 4.1, F5, F6). So an unfinished pool or programme is a **draft**: page state in `FundingTab` (`$state`), outside the policy store. Autosave, undo and redo, publish and the worker never see a draft (`policy-store.svelte.ts:61-74` is not called for it).

- **What opens one.** "Your own pool" (its amount is empty); "+ What it pays for" when the new programme needs a value with no source (a loan on a pool whose `POOL_KIND_DEFAULTS[kind].loanRate` is `Unsourced` starts with an empty rate); and changing a stored programme's instrument to a loan whose rate has no source (the stored programme stays as it was, and the editor shows the loan as a draft of that programme). A new programme whose every field has a value (a grant, or a loan on a bank) is not a draft: it is added at once, as before.
- **How it is shown.** In the place the item will take, with the muted line "Not added yet: fill in every field to add it. It is lost if you reload or leave the page." and a "Discard" button (named "Discard {name}"). Its fields are the item's fields, with the same validation (4.7, 4.8).
- **How it becomes part of the policy.** When the last required field gets a valid value, the draft is added in one store change with the item's "Added: …" label ("Added: your own pool", "Added: {programme sentence}", or for an instrument change "Changed: {new sentence}"), takes its id from `nextAddedId` at that moment, and from then on is an ordinary row; focus stays in the field the user just committed.
- **One at a time.** While a draft is open, "+ Add money", every "+ What it pays for" and the preset buttons are `aria-disabled` with the description "Finish or discard the item you are adding first.", and the draft counts toward the limits of F7. Undo and redo do not touch it. Starting a run with a draft open discards it, and the run's announcement adds "An unfinished item was discarded."
- **Reload.** A draft is not saved; after a reload it is gone, which its line says while it is open.

**Ids.** The page never makes an id itself: a hand-made pool or programme takes `nextAddedId(f, 'pool')` or `nextAddedId(f, 'prog')` (`u-pool-<n>`, `u-prog-<n>`), and a preset's items take the ids `addPreset` gives them (`u-<presetId>-<n>`, F16). Programme ids are never split or suffixed by the page or anywhere it reads them: the card and the sources look a programme up by the exact id the run reports (F9 `off`, F10).

**Dates before the simulation.** An added pool, inflow or programme that `pastItems(f, asOf)` reports shows a muted line under its row, "Before the simulation starts: not counted." It is kept, not removed, because the document did not change (`finance-levers`, section 4.6 at drafting).

### 4.8a Market terms you set

`FinanceLevers.terms` (F7) holds market terms the user typed; a typed term replaces the sourced or unsourced one, and everything that reads it is labelled "custom, not sourced" (F7, F8). Today that is one term, the guarantee's rate cut (`guaranteeRateCut`, `Unsourced` in `finance-model` 4.3 at drafting), so one field. A term the policy already holds is also shown, whether or not it has a source (a loaded document may carry one), so nothing typed is hidden. With nothing to show, the section is not rendered.

- **Focus.** While the "Loan guarantee" option is disabled, a button "Go to Market terms you set" follows the radio group (outside the option's description, so the description stays plain text); it moves focus to the rate-cut input.

## 5. Seams

- **Market scenarios and a market control (R7).** The tab and the sources read the market only through `calibration.market` and `market-baseline`'s `marketLevel(cal)` (`src/lib/sim/scenario/market.ts`), the one rule the engine also uses; this spec adds no rule of its own (4.12). The statement of today's market is `market-baseline`'s `fzp-market` paragraph and `src-market` section, which this spec extends for the private level and the slope and nothing more; a later scenario package replaces the level lines and adds its control in a new tab section above "Today's funding". Nothing else here names the market.
- **The pipeline and drop-out (R1, R8).** The card shows no line on pipeline projects and the sources state the assumption once, through the engine's own `PIPELINE_FUNDED` (4.12); a later package that reaches the pipeline adds the line by giving pipeline schedules `funding`, and the card reads it with no change here. The results never imply that partial money changes drop-out.
- **A rent model (R4).** The tiers block reports homes by income level only; the table's columns are fixed and a later "rent" column would be added there. No rent, price or affordability goal is shown or implied.
- **Retiring a spent programme** (design, "Out of scope"). An application waits for a pool that is on but short, even when no more money is due to it. The page keeps this visible without modelling it: the "By source" table shows each pool's balance, the coverage disclosure says a short source makes projects wait, and the user ends a programme with its "Until" field. A later package that retires spent programmes changes none of these controls.
- **Scaling the federal pool** (design, "Out of scope"). The federal group's dated change is an on/off radio (4.5). A later per-home scale on a programme would add a field to that programme's editor, not to the group.

## 9. Open questions

1. **The fixed starting values of a new programme (35% grant; 60% loan; 10% reserve; 5.25% return).** Recommended as written: they are the design's examples and published figures, shown as the user's choices.
2. **The tier table without meters.** Recommended: no meters (compact). If the owner wants meters, `TargetRow` takes a tier target unchanged.
3. **Typed values for terms that have a source.** F7 lets a typed term replace a sourced one; this page offers a field only where a term has no source (4.8a), and shows a typed sourced term only when a loaded document carries one. Recommended: keep it so; a field over every market term would invite custom values where sourced ones exist, against the evidence hierarchy.
