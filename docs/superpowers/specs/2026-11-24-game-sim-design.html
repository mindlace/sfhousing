Game sim: the simulation page under the incremental loop

The page after the opening becomes run, tally, tree and workshop over today's map and timeline; the five-level parts go.

Purpose

This unit owns the simulation page under the game. After the opening the game's page is a loop of four states over one map: a run, the tally, the tree and the workshop. The workshop is today's forecasting tool, with its editors held to what is bought.

  • It adds the run seam: a run plays the forecast from today to the rung's deadline in 20 seconds of wall time, feeds the drops layer and settles at the deadline.
  • It wires buying to the policy document: a purchase writes the game, then applies the grant to the document, and the forecast starts while the player is in the tree.
  • It replaces every five-level lock (allowed, runs, playable, lockedLane, the level) with Limits, within and runnable.
  • It removes the bar, the standing, the win card, the offer, the level-up reaction, the locked page and Remix on /s/<id>.

Rulings it carries: P1 (the workshop keeps the tool), P4 and P7 (the loop and the tree between runs), P9 (nothing collected reaches the worker), P11 (no painted area in a game), P12 (a bought lever can be switched off), P13 (no Remix), P14 (Publish sends the runnable document), and composer calls 1, 5, 9, 13 and 14.

Interfaces

This unit produces no row. It needs G1 to G7, E1, M1, R1 and U1, and reads E2 when present. The rows are copied from the design with no change.

Decisions

  • Five phases, with starting. A separate starting state gives "waits and says so" one place, for the first run from the opening and for Run pressed while busy.
  • Landing by runs. A mount with no run settled starts the first run, so / needs no prop to say "start now", and a reload in a later run returns to the tree with nothing paid.
  • The run has its own clock. RunClock drives the run and Playhead is not mounted in it, so the ruler is off by construction and Playhead changes only by losing the bar.
  • advance takes a rate. One stepping function serves the two speeds and the run.
  • Ready is the first fill. The run starts at the first month filled with the numbers current; the clock waits at the computed edge after that, so a run never shows numbers ahead of the forecast.
  • Drops are planned again on each feed update in a run. City deltas arrive at most every 250 ms and may lag the series; re-planning on cityVersion keeps every completion.
  • The map stays mounted under the tree. A second mount would cost the map's load; inert under an opaque pane it keeps its instance and camera.
  • No prefetch and no view following in a run. The lock's moveend reports the whole city, whose chunks and lids the run does not draw (call 19).
  • The tree's Publish clicks the header's. PublishButton is game-shell's and exposes no open method; its button is the one dialog on publishDoc.
  • Tally keeps the run view. The map holds at the deadline until Continue, as the source model's "the map holds".
  • No pause in a run. Space is swallowed; "Collect for me" is the accommodation the design gives.
  • Edit re-adds only a missing policy. Re-applying every grant on each Edit would overwrite the player's own values.
  • "+" Transit rule fits the limits. Today's default rule (two stop types, two bands at 6 stories) would fall outside early limits and not run.
  • A given measure stays read-only in a game. An edit to what it pays sets its preset to null (src/lib/timeline/lens.ts:280-286), which takes it outside the limits.
  • No starters in a game. The tree is how a lever is added.
