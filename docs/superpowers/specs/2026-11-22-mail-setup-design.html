Mail setup design

Sign-in mail from sfhousing.mindlace.net through Amazon SES, on staging and production, proved by a real mail.

Goal

This unit makes sign-in mail deliverable in both environments, as ruling D12 and Sign-in mail in the design doc require. It writes no application code. Its operator performs outward-facing setup the owner authorised in D12 ("We'll need to set up email sending as well, against the aws account that planafoot uses. `aws` is authenticated.").

  • An SES domain identity for sfhousing.mindlace.net in us-west-1, with Easy DKIM and the MAIL FROM domain mail.sfhousing.mindlace.net.
  • Six DNS records in the mindlace.net zone on Cloudflare, added by the owner from the exact list this runbook produces.
  • One IAM user per environment, sfhousing-mail-staging and sfhousing-mail-production, each allowed to send from that identity and nothing else, each with one access key.
  • SES_ACCESS_KEY_ID and SES_SECRET_ACCESS_KEY set on the staging and production Workers by the operator.
  • One real sign-in mail on staging, then one on production, accepted by SES; the owner confirms DKIM, SPF and DMARC pass in the received headers.
  • The Google sign-in client as the one owner step, written down exactly.
  • The mail section and the bootstrap checklist of docs/dev/deploy.md.

The code that sends mail

  • mailProvider picks SES when EMAIL_PROVIDER is unset or not resend and both SES_ACCESS_KEY_ID and SES_SECRET_ACCESS_KEY are set; with neither provider it returns null (src/lib/server/email/provider.ts:19-24).
  • mailCanBeDelivered is true exactly when mailProvider is not null (provider.ts:27-29).
  • sendEmail takes its From from SES_FROM and throws when it is unset (src/lib/server/email/send.ts:38-43).
  • With no provider, sendEmail runs in mail log mode: it logs [email:log-mode] with from, recipients and subject, and returns { sent: false, logged: true } (send.ts:50-53).
  • SES is called through the SESv2 outbound-emails endpoint, signed with aws4fetch, in SES_REGION or us-west-1 when it is unset (send.ts:61-84).
  • An SES error makes sendEmail throw SES SendEmail failed: {code}: {message} (send.ts:86-96).
  • parseAuthMethods always puts magic-link in the set, whatever AUTH_METHODS says (src/lib/server/auth/methods.ts:17-24).
  • enabledAuthMethods drops magic-link when mail cannot be delivered, except in an e2e build (methods.ts:47-57).
  • Google is dropped unless both GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET are set (methods.ts:36-40, src/lib/server/auth/google-provider.ts:9-14).
  • The /signin action sendLink answers 404 while magic link is off (requireMethod, src/routes/signin/+page.server.ts:57), limits by IP and by address on AUTH_LINK_RL (:65-71, :84-90), and calls auth.api.signInMagicLink (:105-113). Its answer is { sent: true } whether or not the address has an account (:122-123).
  • The magic-link plugin's sendMagicLink sends the sign-in template through sendEmail (src/lib/server/auth/better-auth.ts:312-318). Its subject is Your SF Housing Simulator sign in link (src/lib/server/email-templates/copy.ts:9-10, PRODUCT_NAME in src/lib/server/auth/brand.ts:2).
  • Better-Auth's base URL is BETTER_AUTH_URL, else the request origin (better-auth.ts:115); its routes are served by src/routes/api/auth/[...all]/, and Google's callback is /api/auth/callback/google (methods.ts:84, :93).

Configuration

  • AUTH_METHODS is magic-link in both (wrangler.jsonc:41, :95). SES_REGION is not set.

The cloud accounts

  • wrangler secret list shows only BETTER_AUTH_SECRET on production and on staging. Mail runs in log mode in both, so magic link is off in both.
  • The aws CLI is authenticated to the account ending 1215, default region us-west-1, with the account's root credentials.
  • aws sesv2 get-account in us-west-1: production access, sending enabled, status HEALTHY, 50,000 a day, 14 a second.
  • SES identities in us-west-1: the domains planafoot.com and traceclue.com, and one single-address identity. None for mindlace.net or sfhousing.mindlace.net.
  • IAM has one user, planafoot, with the attached policy send-email. Its keys belong to planafoot.
  • Route 53 has no hosted zones.
  • dig NS mindlace.net answers two ns.cloudflare.com servers: the zone is on Cloudflare.
  • mindlace.net has its own mail: an MX at Google, SPF v=spf1 include:_spf.google.com ~all, and DMARC with p=none and no sp.
  • Nothing exists yet under _dmarc.sfhousing.mindlace.net or mail.sfhousing.mindlace.net.
  • wrangler whoami: the OAuth token's zone scope is zone (read), with no DNS write scope. The operator's tools cannot write DNS records.

Design

The runbook runs in the order of the numbered subsections. A step whose check fails stops the runbook at that step; the operator reports the step and the output, with every secret and the account id beyond its last four digits left out.

Rules for the operator

  • Every command runs from the unit's worktree, in the foreground.
  • No secret value is ever printed, logged, written to a file, put in a commit or put in the handback. The access key is passed from aws to wrangler inside one shell command.
  • The AWS account id is never printed whole. Commands that need it read it into a shell variable in the same command.
  • The test address is never written to a file, a commit, a doc or the handback. The handback says "an address the owner named".
  • No SES identity, IAM user, key or DNS record other than those named here is created, changed or deleted. The planafoot user, its policy and its keys are never touched.
  • Secrets go on an environment only after the identity reads verified (Waiting for the owner's records), because SES refuses mail from an identity that is not verified.
  • Setting the two SES secrets on an environment switches magic-link sign-in on at once in the deployed Worker, before this build ships, because parseAuthMethods always lists it.
  • The owner was told on 2026-11-22 that setting the secrets switches magic-link sign-in on at once in the deployed Worker, and that the existing invitation pages can then send real mail until this build ships. The operator sets the secrets on staging and then on production without asking and without waiting.
  • The DNS step is the one wait (Hand-backs).

1. The SES identity

Create the domain identity with Easy DKIM at 2048 bits:

aws sesv2 create-email-identity \
  --region us-west-1 \
  --email-identity sfhousing.mindlace.net \
  --dkim-signing-attributes NextSigningKeyLength=RSA_2048_BIT \
  --tags Key=project,Value=sfhousing \
  --query 'DkimAttributes.Tokens' --output text

The output is the three DKIM tokens. They are not secret; the operator keeps them for the records.

Set the MAIL FROM domain:

aws sesv2 put-email-identity-mail-from-attributes \
  --region us-west-1 \
  --email-identity sfhousing.mindlace.net \
  --mail-from-domain mail.sfhousing.mindlace.net \
  --behavior-on-mx-failure USE_DEFAULT_VALUE
  • USE_DEFAULT_VALUE: if the MX record ever fails, SES sends with its own MAIL FROM. DKIM still aligns, so DMARC still passes.
  • No configuration set and no event destination is attached.

2. The DNS records

The mindlace.net zone is on Cloudflare and the operator cannot write it. The operator stops here and hands back partial (Hand-backs) with this list, the three tokens filled in:

Records to add in the Cloudflare zone mindlace.net
NameTypeContentProxy
<token1>._domainkey.sfhousingCNAME<token1>.dkim.amazonses.comDNS only
<token2>._domainkey.sfhousingCNAME<token2>.dkim.amazonses.comDNS only
<token3>._domainkey.sfhousingCNAME<token3>.dkim.amazonses.comDNS only
mail.sfhousingMXfeedback-smtp.us-west-1.amazonses.com, priority 10Not proxiable
mail.sfhousingTXTv=spf1 include:amazonses.com ~allNot proxiable
_dmarc.sfhousingTXTv=DMARC1; p=quarantine; adkim=r; aspf=rNot proxiable
  • Names are relative to mindlace.net, as Cloudflare's dashboard takes them.
  • The CNAMEs must be "DNS only" (grey cloud). Cloudflare proxies a new CNAME by default, and a proxied DKIM record never verifies.
  • TTL is Auto.
  • No record is added at sfhousing.mindlace.net itself. Its address records belong to the Worker custom domain and are not touched.
  • The From domain needs no SPF record of its own: SPF is checked on the MAIL FROM domain, which aligns with the From domain under relaxed alignment.
  • DMARC is p=quarantine from the start: the subdomain sends only through SES, so every real mail aligns on DKIM and on SPF.
  • mindlace.net's own SPF, MX and DMARC records are not changed.
Decision The owner adds the records. The operator's Cloudflare token has no DNS write scope, and the owner's own mail runs in this zone, so no new token is minted for this.

3. Waiting for the owner's records

When the conductor resumes the operator with the owner's answer, the operator checks each record resolves:

for t in <token1> <token2> <token3>; do dig +short CNAME "$t._domainkey.sfhousing.mindlace.net"; done
dig +short MX mail.sfhousing.mindlace.net
dig +short TXT mail.sfhousing.mindlace.net
dig +short TXT _dmarc.sfhousing.mindlace.net

Each answer must equal the table's content (a CNAME answer carries a trailing dot). A missing or different answer goes back to the owner with the one record that is wrong.

Then the operator reads the identity's state:

aws sesv2 get-email-identity --region us-west-1 --email-identity sfhousing.mindlace.net \
  --query '{sending:VerifiedForSendingStatus,identity:VerificationStatus,dkim:DkimAttributes.Status,mailFrom:MailFromAttributes.MailFromDomainStatus}'
  • The operator goes on only when sending is true and identity, dkim and mailFrom are all SUCCESS.
  • While the records resolve but a status reads PENDING, the operator hands back partial again with "waiting on SES verification". SES checks again by itself; the conductor resumes the operator later and it reads the state again.
  • A status of FAILED while the records resolve as listed stops the runbook and is reported.

The environment parameter

Every command from here on concerns one environment, staging or production, and touches only that environment's user, key and secrets. Each block starts with this prelude, in the same shell command:

E=staging   # the one parameter: staging or production
U="sfhousing-mail-$E"
ENVF=(); [ "$E" = staging ] && ENVF=(--env staging)
HOST=$([ "$E" = staging ] && echo sfhousing-staging.mindlace.net || echo sfhousing.mindlace.net)
  • ENVF is an array, so "${ENVF[@]}" expands to nothing for production and to --env staging for staging, in bash and in zsh.
  • The operator never runs a block with an E other than staging or production.

4. The sending users

Each environment has its own user. Both carry the same inline policy, send-from-sfhousing: ses:SendEmail on this identity and nothing else. The policy, with the account id shown as <account>:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "SendFromSfhousing",
      "Effect": "Allow",
      "Action": "ses:SendEmail",
      "Resource": "arn:aws:ses:us-west-1:<account>:identity/sfhousing.mindlace.net"
    }
  ]
}

Create one environment's user, attach the policy, and check it allows this identity and refuses another, printing only the decisions (prelude first):

ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text) && \
aws iam create-user --user-name "$U" --tags Key=project,Value=sfhousing "Key=environment,Value=$E" \
  --query 'User.UserName' --output text && \
aws iam put-user-policy --user-name "$U" --policy-name send-from-sfhousing \
  --policy-document "$(jq -nc --arg r "arn:aws:ses:us-west-1:$ACCOUNT_ID:identity/sfhousing.mindlace.net" \
    '{Version:"2012-10-17",Statement:[{Sid:"SendFromSfhousing",Effect:"Allow",Action:"ses:SendEmail",Resource:$r}]}')" && \
aws iam simulate-principal-policy \
  --policy-source-arn "arn:aws:iam::$ACCOUNT_ID:user/$U" \
  --action-names ses:SendEmail \
  --resource-arns "arn:aws:ses:us-west-1:$ACCOUNT_ID:identity/sfhousing.mindlace.net" \
                  "arn:aws:ses:us-west-1:$ACCOUNT_ID:identity/planafoot.com" \
  --query 'EvaluationResults[].EvalDecision' --output text
  • The last line printed must be allowed then implicitDeny.
  • The operator runs it for staging, then for production.

5. The key and the secrets

One command per environment creates the user's one access key and hands both halves to wrangler on stdin (prelude first):

[ "$(aws iam list-access-keys --user-name "$U" --query 'length(AccessKeyMetadata)' --output text)" = 0 ] && \
read -r KEY_ID KEY_SECRET <<<"$(aws iam create-access-key --user-name "$U" \
  --query 'AccessKey.[AccessKeyId,SecretAccessKey]' --output text)" && \
printf '%s' "$KEY_ID" | npx wrangler secret put SES_ACCESS_KEY_ID "${ENVF[@]}" && \
printf '%s' "$KEY_SECRET" | npx wrangler secret put SES_SECRET_ACCESS_KEY "${ENVF[@]}"
  • The first line refuses to run when the user already has a key: a second key is made only by a rotation.
  • If any part fails after the key was made, the operator runs Rollback for that environment, then steps 4 and 5 again for it.
  • The check is the secret names: npx wrangler secret list "${ENVF[@]}" lists BETTER_AUTH_SECRET, SES_ACCESS_KEY_ID and SES_SECRET_ACCESS_KEY.
  • wrangler secret put deploys the secret to the running Worker. Later deploys keep it.
  • Order: steps 5 and 6 for staging, then steps 5 and 6 for production.

6. The proof mail

The test address is the one the owner gave with the DNS answer. It is typed in place of ADDRESS and used nowhere else.

First the page must offer the link form. This prints a count of at least 1 (prelude first):

curl -fsS "https://$HOST/signin" | grep -c 'sendLink'

Then the operator submits the form's action as the page does:

curl -sS -X POST "https://$HOST/signin?/sendLink" \
  -H "Origin: https://$HOST" \
  -H 'Accept: application/json' \
  -H 'x-sveltekit-action: true' \
  --data-urlencode 'identifier=ADDRESS'
  • The answer must be JSON with "type":"success": SES accepted the mail.
  • An answer with "type":"error" and status 404 means magic link is still off: the two secrets are not both set.
  • Status 500 means SES refused the mail. The Worker logs SES SendEmail failed: {code}: {message}.
  • The rate limit allows 5 sends a minute per IP and per address. The operator sends once per environment, and again only after a fix.
  • Production's step 5 runs only after staging's POST answered success.

To read the log of a 500, the operator sends once more under a bounded tail, in one foreground command (the tail ends by itself after 45 seconds):

timeout 45 npx wrangler tail "${ENVF[@]}" --format pretty & sleep 10; \
curl -sS -X POST "https://$HOST/signin?/sendLink" \
  -H "Origin: https://$HOST" \
  -H 'Accept: application/json' -H 'x-sveltekit-action: true' \
  --data-urlencode 'identifier=ADDRESS'; wait

A 500 whose cause the operator cannot fix within this runbook ends the runbook for that environment: the operator runs Rollback for it, which returns it to log mode, and reports the logged error.

What the owner confirms after the final hand-back, for each of the two mails:

  • The mail arrived in the inbox, not in spam.
  • Its subject is Your SF Housing Simulator sign in link and its From is SF Housing Simulator <noreply@sfhousing.mindlace.net>.
  • Authentication-Results (in Gmail: "Show original") has dkim=pass with header.i=@sfhousing.mindlace.net (or header.d=sfhousing.mindlace.net).
  • It has spf=pass with smtp.mailfrom at mail.sfhousing.mindlace.net.
  • It has dmarc=pass with header.from=sfhousing.mindlace.net.
  • On staging, the link opens on https://sfhousing-staging.mindlace.net and signs the owner in. The production link is not followed; it expires unused.

A line that fails is a DNS or identity fault. The conductor resumes the operator with it; the operator checks step 3 again and hands the corrected record to the owner as in step 2.

Hand-backs

The operator runs as a conducted session. The owner's inputs reach it through the conductor.

  • Partial, "waiting on owner: DNS records and a test address". After step 1: the six records of the DNS table, and the request for one address the owner reads. The conductor resumes the operator with the owner's answer; the address is passed in the session only.
  • Partial, "waiting on SES verification". Only when step 3 reads PENDING with every record resolving. The conductor resumes the operator later, with no owner input.
  • Final. After steps 4 to 6 for both environments, the checks of step 7, and the commit of docs/dev/deploy.md. It asks the owner to confirm the proof lines of step 6 for both mails, and names the Google step as the owner's.

No other point waits on the owner.

7. What is checked afterwards

  • For each environment, aws iam list-access-keys --user-name "$U" --query 'AccessKeyMetadata[].Status' --output text prints exactly one Active.
  • On both hosts a signed-out /signin contains the sendLink form.
  • Magic link is in effect on both environments from this unit on. AUTH_METHODS itself becomes magic-link,password,google,passkey in game-save; that change needs nothing from this unit, and magic link stays tied to the two secrets through mailCanBeDelivered.
  • SES_FROM in wrangler.jsonc is unchanged and its domain is the verified identity.
  • No secret, key or account id appears in the unit's diff.

Rotating one environment's key

The user has one key. A rotation makes a second, swaps the secrets, proves a mail, and deletes the first (prelude first):

OLD=$(aws iam list-access-keys --user-name "$U" --query 'AccessKeyMetadata[0].AccessKeyId' --output text) && \
[ "$(aws iam list-access-keys --user-name "$U" --query 'length(AccessKeyMetadata)' --output text)" = 1 ] && \
read -r KEY_ID KEY_SECRET <<<"$(aws iam create-access-key --user-name "$U" \
  --query 'AccessKey.[AccessKeyId,SecretAccessKey]' --output text)" && \
printf '%s' "$KEY_ID" | npx wrangler secret put SES_ACCESS_KEY_ID "${ENVF[@]}" && \
printf '%s' "$KEY_SECRET" | npx wrangler secret put SES_SECRET_ACCESS_KEY "${ENVF[@]}" && \
echo "old key ends ${OLD: -4}"
  1. Run the block above. It refuses unless the user has exactly one key.
  2. Send a proof mail with step 6 for the same environment; it must answer success.
  3. Delete the old key, the one of the user's two keys with the older CreateDate in aws iam list-access-keys --user-name "$U", whose last four characters the block printed: aws iam delete-access-key --user-name "$U" --access-key-id <old key id>.

Mail keeps flowing throughout: the old key works until it is deleted.

Rollback

One environment, which turns magic link off there at once (prelude first):

npx wrangler secret delete SES_ACCESS_KEY_ID "${ENVF[@]}"
npx wrangler secret delete SES_SECRET_ACCESS_KEY "${ENVF[@]}"
for k in $(aws iam list-access-keys --user-name "$U" --query 'AccessKeyMetadata[].AccessKeyId' --output text); do
  aws iam delete-access-key --user-name "$U" --access-key-id "$k"
done
aws iam delete-user-policy --user-name "$U" --policy-name send-from-sfhousing
aws iam delete-user --user-name "$U"
  • It touches only that environment's user, keys and secrets; the other environment keeps sending.
  • The identity goes only after both environments are rolled back: aws sesv2 delete-email-identity --region us-west-1 --email-identity sfhousing.mindlace.net, then the owner removes the six records of the DNS table.
  • The operator rolls back only an environment whose step 5 or 6 failed. Any other rollback happens only on the owner's word.

Global constraints

  • Work happens in git worktrees under .claude/worktrees/. Commits follow Conventional Commits. No attribution to an AI anywhere.
  • Code style: 2-space indent, single quotes, no trailing commas, 100 columns.
  • Every Vitest test calls expect.
  • Signoff fails on server stderr, on timing crutches and on a retried flake. Each unit runs npm run lint, npm run check and the Vitest projects its files belong to before it hands back.
  • Port 4173 is shared by every session on this machine. A unit never kills a server it did not start; it waits.
  • Every agent runs every command in the foreground and never ends a turn while something it started is running.
