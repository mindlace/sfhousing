Game save: the store, the sync and the table for the incremental loop

The browser's game store, its sync, the server store, the game_save table and /api/game carry the v2 game state; Remix and the five-level rule files go.

Purpose

This unit keeps a player's game between visits and between devices. It holds the GameState of G1 in the browser (G7) and on the account (G8), and nothing else about the game's rules: buying, limits, the ladder and settling are the pure functions of game-core and tree-catalogue, which the store calls and then writes.

  • P13: the store's remix and its "Remix of" default name go.
  • P15: a save, an index entry and a table row are v2 only. Five-level saves in a browser are removed unread; five-level rows on the server are dropped with the table.
  • D7: the account is made at the first win. won() sets state.firstWinAt; PUT answers no_win without it.
  • D8, D14: saved games stay separate, up to 12, with switch, rename, delete and new unchanged.
  • Call 9: the open game is built here from the catalogue: the last rung met, every node bought, no units.

This unit is the first part of one lane: one unit, merged once. Its parts, in dependency order, are game-save, part B of tally-tree, game-sim and game-shell; the unit's plan orders its tasks across the parts as its tests need, inside the lane's write set, and each file ends as the spec that owns it says (design, sec-write-sets). It deletes levels.ts, progress.ts, standing.ts, allowed.ts, copy.ts and navigate.ts, and removes store members that pages read. The application does not build or type-check after this unit alone. The lane names every importer left broken and the unit that mends it.

  • parseGameSave returns null unless v is 2 at both levels (P15).

  • parseGameSave checks the shape only. It keeps a node, a level, a side goal or a rung the catalogue does not have; fitGame (G6) drops those in the browser.
  • The server stores what parseGameSave returns.
  • Unit amounts and runs are whole numbers of 0 or more.
  • plan and policy stay opaque text, as they are today.

The node is shown once GameState.rung is at least this.

The words for the level, such as "8 stories".

One line saying what the node does.

// src/lib/game/limits.ts

  presets: ReadonlySet<string>;

  stops: ReadonlySet<StopType>;

  stories: number;
  reachM: number;
  custom: boolean;
  hands: Hands;
}

export const OPEN_LIMITS: Limits;
export const BASE_HANDS: Hands;
export const START_BANDS = 1;
export const START_STORIES = 4;
export const START_REACH_M = 402;
export const FREE_MEASURES: readonly string[];

export function limitsOf(s: GameState, nodes?: readonly TreeNode[]): Limits;
export function within(kind: PolicyKind, p: Policy, l: Limits): boolean;
export function runnable(doc: SimPolicy4, l: Limits): SimPolicy4;
export function isGiven(p: Policy): boolean;
open
The open game: every control, no limit (call 9).
presets, measures
The permitting preset ids and funding preset ids that run.
bands, stories, reachM
The most bands a transit rule may have, its tallest band and its furthest band. All 0 before the first stop type is bought.
custom
Custom timing and custom route shares may be set.
FREE_MEASURES
state-off and federal-credits-off.
  • limitsOf folds the grants of every level bought. The largest stories, reach, bands, radius and linger win.
  • Once a stop type is bought, bands, stories and reachM are at least START_BANDS, START_STORIES and START_REACH_M.
  • BASE_HANDS is a radius of 48 px, a linger of 4,000 ms and no auto. Every Hands step in the catalogue is above it.
  • Once the last rung is met, stories is 80, bands 3, reachM 3219, every stop type is in, custom is true, and presets also holds observed, the preset a custom timing policy carries.
  • within does not read a policy's on.
  • A permitting policy is within the limits when its preset is in presets, and, unless custom, it has no custom edit and no custom route shares.
  • A transit rule is within the limits when its stop types are in stops, it has at most bands bands, no band is taller than stories and none is further than reachM.
  • A protection is within the limits once stops is not empty.
  • A painted area is within the limits only when open (P11).
  • A money policy is within the limits when it is given and its preset is in measures, or its preset is in FREE_MEASURES and measures is not empty. Any other money policy only when open (D4).
  • runnable keeps the policies within the limits and returns the same document when it drops none.
  • With OPEN_LIMITS, within is always true.

Unchanged: isGiven. Removed: Allowed, ALL_ALLOWED, allowedAt, unlocksAt, runs, playable, levelNeeded, simLocked, needsHigher.

LADDER_YEARS
The deadline years after the window's end, latest first, at most four. The measurement in tree-catalogue sets them.
RUNG_LUMP, SIDE_TUNING
The numbers the balance script tunes: the lump for a rung first met, and each side goal's target and reward by its id.
RUNGS
LADDER_YEARS.length + 1.
homes
The goal's measure at the deadline's month.
reachedOn
The day the amount was first met at or before the deadline, or null.
stages
Homes in each stage short of complete at the deadline's month.
waitingMoney
Homes waiting for money at the deadline's month; null when the view has no such series.
lump
RUNG_LUMP when this run is the first to meet its rung, else null.
index
The deadline's month in the view.
  • Rung 0's deadline is defaultGoal(asOf).deadline. Rung k is the last day of December of LADDER_YEARS[k - 1].
  • A rung's deadline is never after the rung before it and never before the dataset date's month.
  • The first ladder year is the largest multiple of five that is at least five years before the window's end year. The last is the first multiple of five at or after the measured year. When more than four five-year steps fit, the first and last are kept with two evenly between.
  • The cheapest node shown at rung 0 costs no more than RUNG_LUMP.
  • A side goal's reward and target are read from SIDE_TUNING by its id.
  • goalAt is defaultGoal(asOf) with the rung's deadline, and with amount when given.
  • readRun returns null while the view does not cover the deadline's month.
  • resultOf lists a side goal when it is shown, not yet met, and its value is at least its target.
  • settle credits collected, lump and each side reward; records the rung in met when reachedOn is set and the rung is not there; records each side goal; adds 1 to runs; sets last.
  • settle never removes a met rung (call 8).
  • settle pays a lump or a side reward only when it also records it, so a result settled twice pays its lump and its side rewards once. The store refuses a second settle of one result (G7).
  • takeNext moves to the next rung when the rung in play is met and a next one exists. Otherwise it returns the same state.
  • finished is true once the last rung is in met.
  • fitGame drops a bought entry for a node the catalogue does not have and lowers a level above the node's last to it.
  • fitGame drops a side entry for an id SIDE_GOALS does not have.
  • fitGame lowers a rung at RUNGS or above to RUNGS - 1 and drops met rungs at RUNGS or above.
  • fitGame returns the same object when nothing is dropped or lowered.
  • sideShown returns the first SIDE_SHOWN goals whose ring is open and which are not met.
  • A side goal's read returns null when the view lacks what it reads.

  • state and limits are reactive. limits is OPEN_LIMITS for the open game, else limitsOf(state).
  • Every save the store reads, from storage or from the server, passes through parseGameSave and then its state through fitGame (G6).
  • won sets firstWinAt once and writes.
  • startRuns sets phase to 'runs'. It does nothing while firstWinAt is null.
  • buy writes the new state when the purchase is good and returns what buy of G3 returns. A refused write returns { ok: false, reason: 'short' } and changes nothing.
  • The store does not hold the policy document. The page applies the grant (G5).
  • Each write calls sync.changed(id), as today.
  • The open game is in phase 'runs' with the last rung met, every node bought and no units; its methods that write do nothing.
  • settle does nothing for a result already settled.

Unchanged: the saved-games methods, touched, beforeLeave, the storage keys, SaveSync. Removed: progress, allowed, offer, setOffer, levelUp, remix, Offer.

Global constraints

  • One future: the same policy document always gives the same forecast. No game state reaches the worker except through the policy document.
  • No file the dataset version hashes is changed: pipeline, src/lib/config.ts, src/lib/{data,generator,timelapse}, src/lib/plan/{geometry,types}.ts, src/lib/sim/finance (pipeline/lib/version.ts:41). The dataset version stays as it is.
  • A policy node acts on a lever the code already has, at a value the code already sources. No node invents a value.
  • The painted area, own pools, the City funding scale and market terms are never offered in a game.
  • Published plans and policies open and play in full, as today.
  • WCAG 2.2 AA: everything works from the keyboard; targets are at least 24 px; motion follows the reduced-motion setting; nothing flashes more than three times a second.
  • Page text is short. A node is a name, a line and a price.
  • The CSP is not widened. Sound is made in the browser; no audio file, font or script is added.
  • A runtime dependency is not added without a credit in src/lib/attribution.ts. None is expected.
  • Code style: 2-space indent, single quotes, no trailing commas, 100 columns.
  • Vitest runs with expect.requireAssertions. Tests are colocated.
  • A schema change goes through npm run db:generate. Migrations are never edited by hand.
  • Signoff fails on server stderr, on timing crutches and on retried flakes. Timing is measured only on a quiet machine.
  • Port 4173 belongs to whichever session started the preview. Never kill it; wait.
  • Commits use Conventional Commits and carry no Claude attribution.
  • Work happens in git worktrees under .claude/worktrees/.

// src/lib/game/store.svelte.ts (module private)
/** A JSON object whose `v` is 1: a save or an index of the five-level game (P15). */
function isV1(text: string): boolean {
  try {
    const json: unknown = JSON.parse(text);
    return isPlain(json) && json.v === 1;
  } catch {
    return false;
  }
}
  • An index text for which isV1 holds is treated as an invalid index (construction step 4), except that it is not copied to a corrupt key. The rebuilt index overwrites it.
  • In that rebuild, and in a valid index's entries (step 5), a save text for which isV1 holds is removed ([key, null] in the same write sequence) instead of being copied to a corrupt key.
  • Every other text that does not parse goes to a corrupt key, as today.
  • So a browser that held only five-level games ends with one new game made from the two record keys (step 6), the five-level save keys removed, and no corrupt key added.
  • The plan and policy records are not saved games and are kept. The first game made from them starts in the opening with nothing bought; what of its policy runs is runnable's rule (G4), applied by game-sim.
  • The sync's record keeps its key and its v: 1 shape. Entries it holds for removed five-level ids are never consulted again, because new ids are fresh. An id left in its deleting list is sent as a DELETE, which answers 204 for an unknown id, and is then dropped.
  • An existing sfhousing:save:corrupt: key is left as it is.

won()

  • When state.firstWinAt is set, it does nothing.
  • Otherwise it calls #write with state.firstWinAt and savedAt both the current time.
  • A refused write leaves memory as it was: firstWinAt stays null, no sync call is made, and the next won() tries again.
  • In memory mode it changes memory and calls sync.changed, as today.

startRuns()

  • While state.firstWinAt is null it writes nothing and answers { ok: false, reason: 'storage' }. The only way to get there after won() is a refused write, so the page shows the storage words.
  • When state.phase is already 'runs' it writes nothing and answers { ok: true }.
  • Otherwise it calls #write with state.phase set to 'runs' and savedAt now, and answers { ok: true }.
  • A refused write answers { ok: false, reason: 'storage' } and changes nothing.

buy(id)

  • It calls buy(state, id) of G3 with the default catalogue.
  • A refusal (unknown, hidden, done, short) is returned as it is, with nothing written.
  • An accepted purchase calls #write with the returned state and savedAt now, and returns G3's answer.
  • A refused write returns { ok: false, reason: 'short' } and changes nothing (G7).
  • The store never reads or writes the policy record. The page applies the returned grant (G5).

settle(r)

  • When state.last is not null and its at and rung equal r.at and r.rung, the run is already settled: it writes nothing and answers { ok: true }.
  • Otherwise it calls #write with settle(state, r) of G6 and savedAt now, and answers { ok: true }.
  • It does not check phase, the rung or the dataset version: the page builds r with resultOf.
  • A refused write answers { ok: false, reason: 'storage' } and changes nothing; the page may call it again with the same r.

takeNext()

  • It calls takeNext(state) of G6.
  • When that returns the same state, it writes nothing and answers { ok: true }; the page reads state.rung to see that nothing moved.
  • Otherwise it calls #write with the new state and savedAt now, and answers { ok: true }.
  • A refused write answers { ok: false, reason: 'storage' } and changes nothing.

Fitting a save to the catalogue

// src/lib/game/store.svelte.ts (module private)
/** A save as the store holds it: parsed, then its state fitted to the catalogue (G6). */
function fitted(json: unknown): GameSave | null {
  const save = parseGameSave(json);
  if (save === null) return null;
  const state = fitGame(save.state);
  return state === save.state ? save : { ...save, state };
}
  • The store takes a save in at two places, and both call fitted: parseSaveText, which construction uses for every save key it reads (steps 4 and 5), and adopt, for every save from the account.
  • Every other read (read, switchTo, remove, rekey, #makeCurrent, state, saves) reads the games in memory, which are fitted already.
  • A fitted state that differs from the stored one is held in memory and is not written at once. The save's key is rewritten with the fitted state at the next ordinary write of that save (#write, a copy out, rekey, adopt).
  • Fitting does not change savedAt. So the sync does not see a fitted save as changed here, and no PUT goes until the player changes the game. The account's copy is fitted when it is next sent.
  • The index entry carries the fitted rung. When it differs from the stored entry, construction rewrites the index (step 7), as for any entry that differs from its save.
  • The sync parses the account's answers with parseGameSave and passes them to adopt, which fits them. The sync itself never calls fitGame.

Decisions

  • A v1 record is removed in the write sequence and never copied to a corrupt key. Call 24 deletes it at load; copying it aside would keep the five-level data P15 drops.
  • The index becomes v: 2. Its entries carry phase and rung, so the version says which shape it holds.
  • The two migrations come from removing the table, then adding it back. Each step is a schema change npm run db:generate turns into one statement with no rename question, and SQLite takes a NOT NULL column with no default only in a CREATE TABLE.
  • startRuns answers storage while firstWinAt is null. The only path there after won() is a refused write, and an ok would let the page start a run the store never recorded.
  • A fitted state is written at the next ordinary write, not at once. Writing at load would change every stored save after a catalogue update with no act of the player's.
  • A result is already settled when its at and rung equal those of last. Every result carries its own at, so the pair names one run.
  • takeNext with nothing to take answers ok and writes nothing. It matches levelUp today, which wrote nothing when progress did not change.
  • The open game's met rungs carry reachedOn: 0, datasetVersion: 'open' and the epoch as at. They are never saved or shown; only their rung numbers matter (finished).
  • The open game's answering methods return { ok: true }, and buy returns done. They do nothing (G7), and no page shows a game part for the open game.
  • save-api.ts's types are corrected to the 500 and the error bodies the routes already send, since the file is rewritten anyway.
  • seedGame takes a partial state and sets firstWinAt for a game past the opening. It keeps today's rule that a seeded game past the first win is a won game the sync sends.
  • No ladder seam. Seeding rung and met reaches any rung in one load, and seedRunMs makes the run short.
  • seedRunMs refuses a value outside 100 to 20,000. e2eRunMs would ignore it silently, and a spec would then wait for a 20-second run.
  • The sync record is left as it is. Its stale entries are harmless and its shape did not change.
