Game save design

Saved games reach the account: the table, the API, the anonymous account made at the first win, the browser's sync with its keep-both rule, and the account offer on the win card.

Goal

This unit puts a player's saved games on their account, as the incremental-game design rules (R1, D7, D8, D12, D14). It builds on the identity code left by remove-multiuser (I1).

  • The game_save table and /api/game (S1).
  • The first PUT after a first win, with no session, makes the anonymous account and the first save (D7).
  • The browser's save sync in place of the stub (S2): debounced sends, pulls, offline retry, and the keep-both rule (D8).
  • The account offer the win card renders (S3).
  • A join of two accounts moves the absorbed identity's saved games to the survivor; deleting an account deletes its saved games.
  • AUTH_METHODS is magic-link,password,google,passkey in both environments (D12).

SAVES_KEY
Holds { v: 1, current: string, saves: SaveEntry[] }.
saveKey(id)
Holds one GameSave. For the current game its plan and policy are stale: the records under sfhousing:plan:v1 and sfhousing:sim:v2 are the truth.
  • barOf is { on: banked[level - 1].on } at levels 3 to 5.
  • levelUp from level 1 takes null and banks nothing.
  • levelUp from levels 2 to 4 stores the day under the level being left and adds one to the level.
  • levelUp at level 5 stores banked[5] and keeps the level at 5.
  • The page calls won() when a win card first shows.
  • allowed is allowedAt(progress.level).
  • While open is true no page shows a game part: no level cell, no win card, no bar or "To beat" flag, no locked lane, no reworded outcome message, no Remix button, and no offer is set. The pages read open; they never compare allowed with ALL_ALLOWED.
  • The page calls setOffer with the win while its seen result wins the level, and with null on any edit and when it unmounts. The offer is kept in memory only.
  • The store's levelUp() banks the offer with the pure levelUp, clears the offer, and stores the game. The win card and the level panel both call it.
  • The page that set the offer reacts to the level changing: /sim returns the clock to today, and Paint opens /sim.
  • The page calls touched() after its autosave writes a record key. The store sets the current game's savedAt and calls sync.changed(currentId).
  • A page that autosaves a record key registers its autosave's flush with beforeLeave when it mounts and removes it when it unmounts. newGame, switchTo of another game, remix and remove of the current game call every registered function, in registration order, once they will go ahead and before they read or write a record key. So an edit still waiting in the page's autosave is in the record keys when the old game is copied out, and nothing is left waiting to be written over the new game's records when the page unloads.
  • After newGame, switchTo of another game, remix or remove of the current game answers ok, the store ignores touched() for the rest of the document's life: the page is about to unload, and its last write was copied out with the old game.
  • On first construction with no SAVES_KEY, the store makes one saved game at level 1 whose plan and policy are whatever the two record keys hold.
  • newGame, switchTo and remix first copy the two record keys into the current game's stored save, then write the new current game's plan and policy into the two record keys. remove of the current game removes its save without copying it out, then writes the new current game's plan and policy into the two record keys.
  • After newGame, switchTo or remove answers ok, the caller loads the new current game's page with a full page load: / at level 1, /sim above it.
  • After remix answers ok, the caller loads / for a plan and /sim for a policy, with a full page load.
  • remix's record is the text the page's autosave holds under the record key for the published document. The caller builds it with the codec the page already uses, so the store never reads inside a plan or a policy.
  • remix of a policy copies the current game's progress and plan; remix of a plan copies the current game's progress and policy. The new game's name is defaultSaveName({ kind: 'remix', title }).
  • newGame, remix and adopt answer full and change nothing when they would pass MAX_SAVES.
  • rekey of the current game leaves it current, keeps the offer and needs no page load: the records and the progress are untouched. The save sync uses it when it keeps both sides of a conflict (S2).
  • A write that the browser refuses answers storage and leaves the stored games as they were.
  • remove of the current game makes the most recently changed other game current; with none left it makes a new game.
  • rename trims the name, cuts it at SAVE_NAME_MAX, ignores an empty one, and sets nameIsDefault false.
  • defaultSaveName gives "Game, 22 Nov", "Remix of {title}" or "{name} (this device)", and adds " (2)", " (3)" while the name is in taken.
  • The store calls sync.changed(id) after every change to a saved game and sync.removed(id) after a remove.
  • A stored value that will not parse is copied to sfhousing:save:corrupt:<ISO time> and left out of the list.
  • With storage: null the store keeps one game in memory.
  • useGame() outside a provider returns openGame(), so a component test that provides no game sees every control.
  • Only the root layout calls provideGame. It makes the save sync with createSaveSync (S2), constructs the store with it, calls sync.attach(store) and provides the store.
  • When e2eOpen (X1) is true, the root layout provides openGame() instead and makes no sync.
  • The root layout's script that makes and provides the store belongs to game-core.

export const gameSave = sqliteTable(
  'game_save',
  {
    identityId: text('identity_id').notNull().references(() => userIdentity.id),
    id: text('id').notNull(),
    rev: integer('rev').notNull(),
    name: text('name').notNull(),
    level: integer('level').notNull(),
    /** The GameSave as JSON; empty once removed. */
    body: text('body').notNull(),
    savedAt: integer('saved_at', { mode: 'timestamp_ms' }).notNull(),
    removedAt: integer('removed_at', { mode: 'timestamp_ms' })
  },
  (t) => [primaryKey({ columns: [t.identityId, t.id] })]
);
  • PUT with no session makes an anonymous account, behind PSEUDO_MINT_RL, and stores the saved game at rev 1.
  • PUT with no session on a device that has signed in before (the sfh_known cookie) answers 401 sign_in and makes nothing.
  • PUT with no session and a save whose progress.firstWinAt is null answers 422 no_win and makes nothing: an account is made at the first win, never before.
  • PUT stores the save and adds one to its rev when baseRev equals the stored rev, or when the account has no saved game with that id and baseRev is null.
  • PUT of an id the account has never held stores it at rev 1 whatever baseRev says.
  • PUT of an id the account holds with any other baseRev answers 409 with the stored save and changes nothing.
  • PUT to a removed id answers 410.
  • PUT of a new id when the account has 12 saved games answers 422 too_many.
  • The id in the path must equal save.id, else 422 invalid. A body parseGameSave refuses is 422 invalid. A body over MAX_SAVE_BYTES is 413.
  • DELETE clears the body and sets removedAt; the row stays so other devices learn of it. Deleting an unknown or removed id is 204.
  • GET /api/game lists the saved games that are not removed, and under removed the ids removed in the last 90 days.
  • Every write requires a same-origin JSON request, as the account routes do; a write from another origin is 403. /api/game is a session route prefix.
  • When two identities are joined, the absorbed identity's rows move to the survivor. Nothing is merged.
  • When both identities hold a saved game under one id, the absorbed one moves under a new id; an absorbed row that is removed is dropped. The cap of 12 is not applied to a join.
  • Deleting an account deletes its game_save rows.
  • The server never reads inside plan or policy.

S2 The browser's save sync

// src/lib/game/save-sync.svelte.ts
export type SyncState = 'local' | 'saving' | 'saved' | 'offline' | 'sign-in' | 'full';

export interface SaveSync {
  /** Reactive. */
  readonly state: SyncState;
  /** Reactive: the account as the server last answered (S1's `AccountLine`); null until it has. */
  readonly account: AccountLine | null;
  /** The saved game `id` changed. */
  changed(id: string): void;
  /** The saved game `id` was deleted in this browser. */
  removed(id: string): void;
  /** Bring the account's saved games here and send this browser's there. */
  pull(): Promise<void>;
  /** The store saved games are read from and adopted into. Called once by the root layout. */
  attach(store: GameStore): void;
}

export function createSaveSync(opts: {
  storage: Storage | null;
  fetchFn: typeof fetch;
  /** Whether the root layout's `user` is set now. */
  signedIn: () => boolean;
}): SaveSync;
  • state is local until this browser has a session.
  • changed(id) sends nothing while this browser has no session and the game's firstWinAt is null.
  • When the sync attaches with no session, every saved game that has firstWinAt set and has not been sent since it last changed is queued to send, so a first win whose send never went still makes the account.
  • changed(id) debounces to one PUT per saved game per 2 seconds, with the save read from the store at send time.
  • The browser keeps each saved game's last seen rev under sfhousing:saves:revs.
  • A 409 keeps both: the browser's version is stored as a new saved game with a new id and the name defaultSaveName({ kind: 'conflict', name }), the account's version is adopted under the old id, and the new saved game is sent.
  • When the old id was the current game, the browser's version stays current under its new id, so nothing changes under the player's hands.
  • A 410 keeps the saved game in this browser under a new id and sends it again: a change made here is never lost to a delete made on another device (D8).
  • pull() lists the account's saved games. It fetches and adopts those this browser lacks, and those it holds unchanged at an older rev. It removes those listed under removed that are unchanged here. It sends those the account lacks.
  • pull() runs once on load when signedIn(), and again when signedIn() turns true.
  • account is set from every answer that carries an AccountLine. After the PUT that made the account, the header shows the handle from it. The sync never invalidates page data: a page keeps its playhead, its card and its undo history.
  • Once a PUT has answered 200 the sync treats this browser as having a session, whatever signedIn() says.
  • The root layout calls createSaveSync once and gives the result to the store (G2). Components reach it as useGame().sync.
  • A network failure sets offline and the next changed tries again.
  • A 401 sign_in sets sign-in and stops sending until the page loads signed in.
  • A 422 too_many, or the store answering full, sets full.
  • The stub shipped by contracts has state local, a null account, and does nothing. game-save replaces the body of createSaveSync; no caller changes.

Design

The table

  • src/lib/server/db/schema/gameSave.ts holds the table exactly as S1 gives it, importing sqliteTable, text, integer and primaryKey from ../columns and userIdentity from ./users.
  • src/lib/server/db/schema/index.ts adds export * from './gameSave';.
  • The migration is generated with npm run db:generate and committed as generated. It creates game_save and touches no other table.
  • identity_id is always a survivor identity id: the id of locals.user, or of the user the mint returns.
  • rev starts at 1 and goes up by one on every stored change. A removal keeps the rev.
  • saved_at is the save's own savedAt. name and level are copies of save.name and save.progress.level.
  • A removed row has body '' and removed_at set. Removed rows are never deleted, except with their account.

The server module

src/lib/server/game/ holds every query on game_save. The routes and the two hooks call it; nothing else touches the table.

accountLine
handle is the user's handle. handleClaimed is true when a handle_tombstone row has released_by equal to the identity id: the handle has been changed at least once.
listGames
The rows with no removed_at, most recent saved_at first, as { id, name, nameIsDefault, savedAt, level, rev }; savedAt as an ISO string and nameIsDefault read with json_extract(body, '$.nameIsDefault'). removed is the ids whose removed_at is within REMOVED_LIST_DAYS of now.
putGame
Applies the store rules below in one transaction (a D1 batch with the read guarded in the write's WHERE).
  • putGame answers as the rules of S1 say: removed for a removed row, stored for a matching baseRev or an id the account never held, conflict for any other baseRev, too_many for a 13th new id.
  • A store sets the body, name, level and saved time; a new id starts at rev 1, an existing one goes up by one.
  • A write that would set a row's rev when another request changed it first answers conflict with the row as it now is.
  • removeGame of a live row sets body to '' and removed_at to now. A removed or unknown id is left as it is.
  • The module parses a stored body only to answer it back (readGame, the conflict) and rewrites only the top-level id (moveGames). It never reads plan or policy.

The routes

Two route files: src/routes/api/game/+server.ts (GET) and src/routes/api/game/[id]/+server.ts (GET, PUT, DELETE). /api/game joins SESSION_ROUTE_PREFIXES in src/lib/server/auth/session-gate.ts.

GET /api/game

  1. No locals.user: 401, empty body.
  2. 200 { handle, handleClaimed, saves, removed } from accountLine and listGames.

GET /api/game/[id]

  1. No locals.user: 401, empty body.
  2. No row: 404. A removed row: 410. Both with an empty body.
  3. 200 { rev, save }.

PUT /api/game/[id]

  1. refuseUnlessSameOriginJson: 415 { error: AUTH_COPY.jsonRequired }, or 403 { error: AUTH_COPY.crossOrigin } (S1).
  2. A content-length over MAX_SAVE_BYTES: 413, empty body, before reading.
  3. The body is read as text. Over MAX_SAVE_BYTES bytes in UTF-8: 413, empty body.
  4. Text that is not JSON, a value that is not an object, a baseRev that is neither null nor a positive integer, a save that parseGameSave refuses, or a save.id that differs from the path's id: 422 { error: 'invalid' }.
  5. With no locals.user and the sfh_known cookie: 401 { error: 'sign_in' }. Nothing is made.
  6. With no locals.user and save.progress.firstWinAt null: 422 { error: 'no_win' }. Nothing is made.
  7. With no locals.user: mintPseudonymousSession(event). A 429 refusal answers 429 with an empty body. A 500 refusal answers 500 { error: message }. On success the user it returns is the account for the rest of the request, and the session cookie goes out on this response.
  8. enforceRate(MUTATION_REGISTERED_RL, 'game_write:' + identityId, env), not critical. Refused: 429, empty body.
  9. putGame. stored: 200 { handle, handleClaimed, rev }. conflict: 409 { rev, save }. removed: 410, empty body. too_many: 422 { error: 'too_many' }.
  • A refusal at steps 1 to 6 makes no account and sets no cookie.
  • A mint followed by a refusal at step 8 or 9 keeps the account and its cookie; the browser's next send uses the session.

DELETE /api/game/[id]

  1. refuseUnlessSameOriginJson: 415 or 403 as above. The browser sends content-type: application/json and the body {}.
  2. No locals.user: 401, empty body.
  3. enforceRate(MUTATION_REGISTERED_RL, 'game_write:' + identityId, env). Refused: 429, empty body.
  4. removeGame, then 204.

A join of two accounts

  • better-auth.ts passes onFuse: (survivorId, absorbedId) => moveGames(drizzleDb, survivorId, absorbedId) to handleAccountLink.
  • An upgrade moves nothing: the pseudonymous identity survives and keeps its rows.
  • moveGames applies the join rules of S1 in one batch: every row of the absorbed identity, live and removed, moves to the survivor.
  • The new id of a clashing live row is a fresh newId(), and the top-level id in its body is set to it. Its name, rev and the rest of the body are kept.
  • After a join above 12 live saves, the account's existing ids still save, and a PUT of a new id answers too_many until it is below 12.

Account deletion

  • closeAccountRows calls deleteGamesOf(db, idUnion) after hashing earlier versions and before purging credentials. It deletes every game_save row, live and removed, of the survivor and of every identity fused into it.
  • Published plans and policies stay: the plan table has no owner.

The browser's sync

The root layout's script (game-core) calls createSaveSync once, gives the result to new GameStore, and calls sync.attach(store). This unit replaces the body of createSaveSync in src/lib/game/save-sync.svelte.ts; no caller changes. Components reach the sync as useGame().sync, and its account as useGame().sync.account. The file also exports the record.

// src/lib/game/save-sync.svelte.ts (in addition to S2)
export const SAVE_REVS_KEY = 'sfhousing:saves:revs';

/** What this browser last agreed with the account. */
export interface SyncRecord {
  v: 1;
  /** Per saved game: the rev and the savedAt of the version last sent or adopted. */
  seen: Record<string, { rev: number; savedAt: string }>;
  /** Saved games deleted here whose DELETE has not yet been answered. */
  deleting: string[];
}

Set-up

  • createSaveSync puts nothing in context. On the server (!browser) the sync it returns does nothing: state local, no listeners, no requests.
  • Calls of changed and removed made before attach are kept and acted on at attach.
  • The browser has a session while signedIn() is true, and from the moment a PUT answers 200 until signedIn() next turns from true to false (S2).
  • At attach with signedIn() true, it runs pull().
  • At attach with no session, it queues the won saved games that were never sent, as S2 rules: a save is queued when its progress.firstWinAt is set and its savedAt differs from seen, or it has no seen entry.
  • It reads signedIn() inside an $effect under $effect.root. When it turns true (a sign-in, which is a page load or a form action's navigation), the sync clears sign-in and runs pull(). When it turns from true to false (a sign-out), the browser has no session.
  • It runs pull() when document.visibilityState becomes visible while it has a session, and on the window's online event it sends every waiting save.
  • It reads and writes SAVE_REVS_KEY through the storage it was given; a value that does not parse is replaced by an empty record. With storage: null the record lives in memory.
  • It never invalidates or reloads page data, except the one reload after a pull that replaced the current game (Pull).

Sending one saved game

  • changed(id) marks the save waiting and starts a 2-second timer for it, replacing any running timer for that id. The store calls it after every change, and after each autosave write through touched() (G2), so edits on an open page reach the sync.
  • With no session, changed(id) of a save whose progress.firstWinAt is null marks nothing.
  • When the timer fires, the save is read with store.read(id) and sent: PUT /api/game/<id> with { baseRev: seen[id]?.rev ?? null, save }. A save the store no longer has is dropped.
  • One request per saved game is in flight at a time. A changed(id) during it marks the save waiting again, and its timer starts when the request ends.
  • No send starts while a pull runs. Saves that became due wait and go when it ends.
  • 200: seen[id] becomes the answered rev and the sent savedAt; account takes the answer's line.
  • A 200 to a send made with no session means the PUT made the account and set its cookie. From then on the browser has a session; the header and the account offer show the handle from account. The new account holds nothing else, so nothing is pulled: every other saved game here is marked waiting and sent, the cookie going with each.
  • 409: keep both (below).
  • 410: the save was removed on another device (below).
  • 401 sign_in, or 401 to any request while the browser has a session: state sign-in, and the browser has no session. Nothing is sent until signedIn() turns true.
  • 422 too_many: state full. The save stays waiting.
  • 422 no_win: the save stays unsent until its next changed.
  • 413 and 422 invalid: the save is dropped from the waiting set and console.error names the id and the status. These answers mean a defect, never a player's act.
  • A fetch that throws, a 5xx or a 429: state offline; the save stays waiting. The next changed of any save, the online event or the page becoming visible sends every waiting save.

Keep both

A 409 to the send of save A carries the account's version, theirs. In order:

  1. B = newId() and name = defaultSaveName({ kind: 'conflict', name: store.read(A).name }, names), where names are the names in store.saves.
  2. store.rekey(A, B): the browser's version keeps everything under B. When A was the current game, B is current, the offer is kept and no page loads (G2). A storage answer sets offline and stops, with A waiting.
  3. store.rename(B, name).
  4. store.adopt([theirs]) under A; seen[A] becomes the answered rev and theirs.savedAt. A full answer sets full, and seen[A] is dropped so a later pull adopts it.
  5. B is sent with baseRev: null.

The player sees two saved games: "{name} (this device)" holds what they had, and the old name holds the other device's version.

A saved game removed elsewhere

  • A 410 to the send of a save keeps it, current or not: the sync only sends a save that changed here, so the account removed a game this browser still changed (D8). store.rekey(oldId, newId()) keeps it under the new id with its name and, for the current game, its offer and no page load; seen[oldId] is dropped, and the game is sent under the new id with baseRev: null.
  • removed(id) of a save in seen adds the id to deleting and, while the browser has a session, sends DELETE /api/game/<id>. A 204 drops the id from deleting and seen. A failure leaves it in deleting, sent again with the waiting saves.
  • removed(id) of a save not in seen sends nothing: the account never had it.
  • A removed call clears state full and sends every waiting save.
  • The sync ignores the changed and removed calls the store makes while the sync itself is calling the store, so its own adopts, rekeys, renames and removes are never echoed back as sends.

Pull

  1. Wait for in-flight sends to end. Then GET /api/game. A 401 sets sign-in and stops. A network failure or 5xx sets offline and stops. account takes the answer's line.
  2. Send DELETE for every id in deleting.
  3. For each listed save, most recent first. "Unchanged here" means store.read(id).savedAt equals seen[id].savedAt.
    • Absent here and not in deleting: GET /api/game/<id> and adopt it; seen[id] becomes its rev and savedAt. A 404 or 410 skips it.
    • Present, unchanged here, listed rev above seen[id].rev: fetch and adopt it the same way.
    • Present and changed here: send it now with baseRev: seen[id]?.rev ?? null.
    • Present, unchanged, same rev: nothing.
  4. For each id under removed that is present here: unchanged here and not current, remove it here; unchanged and current, keep it under a new id as for a 410; changed here, send it, which answers 410 and follows the 410 rule, so it is kept under a new id.
  5. Every save present here that is neither listed nor under removed is sent with baseRev: null, and its seen entry is dropped first.
  6. Adopts go one save at a time. The first that answers full stops further adopts and sets full; sends go on.
  7. When an adopt replaced the current game's content, the page reloads once (location.reload()) after the pull, so the page shows the account's version. The next pull finds the same rev and does not reload.

State

The first rule that holds gives the state:

  1. sign-in: a 401 stopped sending and the browser has not signed in since.
  2. full: a too_many answer or a full store answer, with no removed call since.
  3. offline: the last request failed by network, 5xx or 429, and something is waiting.
  4. saving: a timer runs, a request is in flight or a pull runs.
  5. saved: the browser has a session.
  6. local: otherwise.
  • Retry is driven by events (changed, removed, online, visibility), never by a timer of its own. The only timer is the 2-second debounce.
  • The player's games are in localStorage first in every state; no state blocks play or levelling up.

The account offer

AccountOffer.svelte reads page.data.user ($app/state) through currentUser.overlay, and useGame().sync with its account. The account it shows is the user when there is one, else sync.account (S3). It shows one of four states. The two texts it shares with the level panel's sync line come from syncText in src/lib/game/copy.ts (game-core), so each condition has one string.

Sign in
While the sync's state is sign-in: a link with the text syncText('sign-in') ("Sign in to save") to /signin?returnTo= and the current path.
No account
No user and a null sync.account: the text syncText('local') ("On this device only").
Handle never chosen
sync.account.handleClaimed is false: a form with the label "Save as", a "@" before the input (hidden from assistive technology), an input whose placeholder is the current handle, and a "Save" button.
Handle chosen
sync.account.handleClaimed is true, or a user is present while sync.account is null: a link "@handle" to /account. Under it, while the account has no email, a link "Add an email to play on another device" to /account.
  • The handle shown is the overlaid user's, else sync.account.handle.
  • The account has an email when a user is present and is not pseudonymous. Pseudonymity ends only when an email or Google is added; a password or a passkey keeps it, and the address of a pseudonymous account is the undeliverable PSEUDONYMOUS_EMAIL_DOMAIN one. With no user (the account the first save just made), the account has no email.
  • Under the open game (openGame(), X1) no win card shows, so the offer does not render.
  • Save is disabled while the trimmed input is empty or a request is in flight; in flight it has aria-busy="true".
  • Save sends PATCH /api/account/profile with content-type: application/json and the body { handle } only, so the display name is left as it is.
  • A 200 calls currentUser.apply(user.id, { handle: body.handle }) when a user is present, and sync.pull(), whose list answer sets account to the new, claimed handle. Until that answer the offer holds the saved handle itself and shows the chosen-handle state; a live region says "Saved."
  • A 400 or 429 shows the body's error under the input, associated with it and focused, exactly as the server wrote it: the reasons of updateProfile (src/lib/server/user-store/profile.ts:9-16,60-94), and "Too many changes. Wait a moment." for 429.
  • A 401 shows "Sign in first."; any other status shows "Couldn't save. Try again."; a fetch that throws shows "Couldn't reach the server. Check your connection."
  • Nothing in the offer blocks levelling up or closes the card.

Sign-in methods

Global constraints

  • Work happens in git worktrees under .claude/worktrees/. Commits follow Conventional Commits. No attribution to an AI anywhere.
  • Code style: 2-space indent, single quotes, no trailing commas, 100 columns.
  • Every Vitest test calls expect.
  • Signoff fails on server stderr, on timing crutches and on a retried flake. Each unit runs npm run lint, npm run check and the Vitest projects its files belong to before it hands back.
  • Port 4173 is shared by every session on this machine. A unit never kills a server it did not start; it waits.
  • Every agent runs every command in the foreground and never ends a turn while something it started is running.
  • Schema changes go through npm run db:generate. Nobody edits a migration.
  • No unit runs npm run signoff: its dataset step fails until the dataset is uploaded. closing runs it once, after the upload.
