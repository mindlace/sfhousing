Pool closing design

The step engine closes a pool that has had its last money and cannot pay a waiting project, so projects stop waiting for money that will never come.

Goal

Once sources end (finite-funding), the step engine's known limit would hold most affordable projects on the line to the window's end: an application waits on a spent pool. This unit carries out D13 of the incremental game design. It delivers:

  • A pool that is spent closes from the next month and is treated exactly as a pool switched off from that day: its programmes are in no bundle, and the applications that held it are re-made or lapse as on a re-pricing day.
  • A closed pool opens again when it receives a new arrival.
  • Each pool's open or closed state is part of the world, so the worker's rewind and copies restore it.
  • WorldOptions.poolClosing, true by default; the referee against the older engine runs with it false, and the older engine is unchanged.
  • MoneyView.closed and MoneyView.shut, and Details' line "{source}: ran out {Mon YYYY}".

// src/lib/sim/world/score/types.ts (TimelineView.money)
export interface MoneyView {
  /* the series as today, and: */
  /** Per pool id: the first day it was closed, or null. */
  closed: Record<string, Day | null>;
  /** Per pool id, by calendar month: true while the pool is closed at the end of that month. */
  shut: Record<string, boolean[]>;
}
  • A pool's last arrival is the last arrival the document in force gives it; a pool with a yearly inflow with no end has none.
  • A pool is spent in a month when the month begins after its last arrival, it has no loan out and holds no guarantee reserve, and that month's serving finds an application short on it.
  • A spent pool is closed from the first day of the next month, and stays closed until it receives a new arrival.
  • A closed pool is treated exactly as a pool switched off from that day: its programmes are in no bundle, and the applications waiting on them are re-made as on a re-pricing day.
  • Money returned to a closed pool stays in it and is never awarded.
  • A pool whose last arrival changes because the policy changed is judged again from the month the change takes effect; a closed pool that receives a new arrival is open again from that arrival's month.
  • The worker's rewind restores each pool's open or closed state with the world.
  • The older scenario engine keeps its behaviour: an application waits on a spent pool.
  • Details lists each closed source by its pool's label with the month it ran out: "{label}: ran out Mar 2030".
  • shut[id][i] is true from the calendar month the pool ran out (the month that found it spent) through the last calendar month before it opens again.
  • A pool's bar on the timeline reads empty in every month shut marks: what a closed pool still holds is never awarded.

Design

Shapes

F3 gives closedDay, WorldOptions and MoneyView.closed. This unit adds the following around them.

// src/lib/sim/world/score/types.ts
export interface MoneyRow {
  pools: {
    /* the fields as today, and: */
    /** The pool's first closed day, once the month that found it spent has been reached; absent reads as null. */
    closed?: Day | null;
    /** The pool is closed at the end of this calendar month; absent reads as false. */
    shut?: boolean;
  }[];
  /* the rest as today */
}
  • closedDay and the shut* columns are world columns: closedDay is in POOL_ROWS and every new pool row takes NO_DAY; the shut* columns grow like the line's side tables.
  • closedDay[q] is shutFrom of row q's closing whose shutTo is NO_DAY, and NO_DAY when there is none.
  • withFunding(f).step steps under f.beforeStep(world, statics, timeline) when f has it; withFunding(f).planDue plans under f.timelineOf(world, statics, timeline). createWorld is unchanged: a new world has no closings.
  • Both hooks return timeline itself for a world without funding columns or without a closing.
  • createFundingSystem gives both hooks. poolClosing only decides whether pools are ever closed; a world with no closing steps under timeline itself.

A pool's last arrival

The last arrival is read from the pool's definition in the frame in force: frame.finance.pools[fq] for the month being served (F3: "the last arrival the document in force gives it").

  • lastArrivalOf is null when any inflow is yearly with to: null and dollarsPerYear above 0. Such a pool never closes.
  • Otherwise it is the latest day, on or after asOf, on which an inflow with dollars above 0 arrives under inflowArrivals: a once inflow's day; a yearly inflow's last anniversary on or before its to, which may lie past the window.
  • A definition with no such day (no inflow, every inflow 0 dollars, every arrival before asOf) gives NO_DAY: it is before every month.
  • It is memoised per Pool object; a pool's definition objects are shared by the frames that hold them.
  • A pool's inflows from several spans of its policy: each span's definition is the one in force in its months, so the last arrival can change at a span's first month. A pool whose last arrival moves later is not spent until the month after the new last arrival.
  • A baseline pool scaled by a policy: its definition is buildFinance's scaled inflows, whose 0-scale runs give no inflow. The last arrival is read from them.
  • A pool switched off on a day, or whose policy is not in force: its programmes are not offered, so no application asks it and serving never finds one short on it. It cannot be spent while off.

When a pool is spent

The check runs in system 5, when poolClosing is true: inside serveLine's holdingReturns, after the scan has decided its last row and before the held money is released. Money arrived in system 2 of the same month, before it. The month's frame is ctx.frame, of the timeline the world steps under.

World pool row q, at frame pool index fq with definition def = ctx.frame.finance.pools[fq], is spent in month m when all of these hold:

  1. It is open: closedDay[q] === NO_DAY.
  2. The month begins after its last arrival: L = lastArrivalOf(def, asOf) is not null and L < ctx.firstDay. So a pool is never spent in the month its last money arrived.
  3. No loan is out and no guarantee reserve is held: no money row k < mN has mPool[k] === id[q] and mInstr[k] of INSTR_LOAN or INSTR_GUARANTEE. A loan committed and not yet spent counts as out.
  4. An application is short on it: some line row i with gone[i] === 0, whose lot is free, has a bundle (fm.bundleIds(bundle[i])) holding a programme of pool fq, and asksOf(fm.index, kind, bundle, protoId, units[i]).get(fq) is greater than serving's available money, availableOf(pools, q, def) - heldOf(pools, q). protoId is prototypeFor(stories[i], units[i]).id, as serving reads it.
  • The available money is serving's own view at the scan's end: money returned during the scan is held out of it, as serving held it out of every award test that month.
  • The ask is the whole bundle's, the first round of the award rule's leaving out.
  • The pools are judged in world pool row order; any number may be spent in one month.
  • Condition 4 may be found per award group of the line index at its largest live size (the ask grows with size); the result equals the test over every waiting row, and a test holds both to the same closings.
  • A spent pool's row takes closedDay[q] = ctx.lastDay + 1, the first day of the next model month, and a new shut row with shutFrom that day and shutTo NO_DAY.
  • Nothing else changes in month m: systems 6 and 7 run as today, under the month's frame.

A closed pool is a switched-off pool

Closing reuses the switched-off path whole. The world steps under closedTimeline, a view of the timeline in which each closed pool's programmes are not offered, so the frame id changes in the month a pool closes and today's frame-change code does the rest.

closed set of month k
The pool ids of the shut rows with shutFrom ≤ monthFirstDay(asOf, k) and either shutTo === NO_DAY or monthFirstDay(asOf, k) < shutTo.
  • frameAt(k) is the base frame when month k's closed set is empty.
  • Otherwise it is the base frame with finance replaced by a copy whose offered is 0 for every programme of a closed pool. Its pools, programmes, arrivals, slope and terms are the base frame's.
  • That frame's id is frameIdOf(`closed|${base.id}|${ids}`) (src/lib/sim/world/policy/intern.ts), ids being the closed set's pool ids sorted and joined with ",". Equal frames are one object: they are cached by the base frame object and ids.
  • changes() is the base's months, and every month k ≥ 2 whose closed set differs from month k − 1's, ascending, each once. It follows the base's list as the base compiles more months.
  • touched(k) is the base's for a month in the base's changes, and an empty Int32Array otherwise: closing changes no zoning.
  • readyThrough() is the base's.
  • A closed view is cached per base timeline and per shut history, so its memos (frameMoney, the rowless eligibility memo) live while the history is unchanged and a new closing gets a fresh view.
  • Derived frames are used only by the step, planning and the funding hooks. Readers outside the world (the score statics, the card, limits, lookups, the map stream) read the base timeline, as today.

So, in the month a pool closes:

  • The frame id differs from world.frame; system 1 runs: the core replans every free lot, and policyChanged re-makes every waiting row under the new frame. A row whose bundle held the closed pool is re-made on the bundle without it, or lapses when that bundle is empty or covers less than its level, its kind respelled from the month's first day (remakeRow).
  • From then on no bundle holds a closed pool's programmes: clocks, applications, re-makes and serving all read the offers of the frame.
  • A lot's funded clock splits at the closing month, as at any frame change, so its odds there are those of the bundle without the pool.
  • Money returned to a closed pool (a release or repayment) is booked as today and stays in it. No offered programme draws on it, so it is never awarded, and it does not open the pool.
  • The award rule is unchanged: a closed pool is never part of a bundle, so it is never asked.

Opening again

  • A closed pool stays closed until it receives a new arrival.
  • beforeStep, before month m = world.month + 1 is stepped, reads the base frame of month m. For each arrival with dollars above 0 whose pool is closed, it sets shutTo of that pool's open shut row to monthFirstDay(asOf, m) and closedDay to NO_DAY.
  • Then it returns closedTimeline of the updated history, so month m's frame offers the pool's programmes again and system 1 re-makes the waiting rows.
  • A shut row whose shutTo equals its shutFrom (closed and opened in the same month) is removed, keeping the order of the rest.
  • From the month it opens, closedDay holds NO_DAY.
  • After it opens, MoneyView.closed still holds the first day the pool was closed.
  • A pool opened again can close again later: a new shut row, and closedDay holds that closing's first day.
  • Only an arrival opens a pool. A policy edit that gives a closed pool a later arrival leaves it closed until that arrival's month.
  • A pool whose policy is switched off and on: while off it is never spent (above); a pool closed before the switch stays closed until an arrival comes.

Policy edits, rewind and copies

  • An edit applied with keep carries the world on under the new base timeline; its shut history comes with it, and the closed view is rebuilt on the new base. Each later month judges spending under the new frames' definitions.
  • An edit applied with restore clones a copy (month 0 today) and re-steps it quietly; the closings are made again, deterministically, from the world's state.
  • planDue after a restore plans under timelineOf, the view of the copied world's closings.
  • closedDay and the shut columns are in the world, so structuredClone copies them and the worker's rewind of the map stream needs nothing more.
  • The runner (src/lib/sim/world/runner/**) needs no change: ensemble.ts takes createFundingSystem()'s default.

The option and the older engine

  • createFundingSystem(opts) reads opts.poolClosing, default true.
  • With poolClosing false no pool is ever closed: the world steps and plans under its timeline itself, and an application waits on a spent pool, as the older engine's does.
  • runFunded (funding/test/fixtures.ts) gains poolClosing?: boolean, default true, passed to createFundingSystem.
  • The tolerance referee (tolerance.referee.spec.ts) runs poolClosing: false.
  • score/money.spec.ts's "rule 12 against today's engine" runs its world with createFundingSystem({ poolClosing: false }).
  • The ledger identities (referee-ledger.spec.ts) run with closing on: closing moves no money.
  • The older scenario engine (src/lib/sim/scenario/**) is unchanged; its known limit stands.

The money view

  • moneyRowsOf gives each pool entry of calendar month i closed: the shutFrom of that pool's first shut row in feed.world, when that day less 1 is on or before the last day of calendar month i; otherwise null. A world without funding columns gives null.
  • moneyRowsOf gives each pool entry of calendar month i shut: true when the pool has a shut row whose shutFrom less 1 is on or before the last day of calendar month i and whose shutTo is NO_DAY or later than that day; otherwise false. A world without funding columns gives false.
  • moneyViewOf gives shut (F3): for each pool id of the view, its rows' shut by calendar month, false where a row has none.
  • moneyViewOf gives closed (F3): for each pool id of the view, the last row's closed, null when absent.
  • So MoneyView.closed is the first day the pool was ever closed, through the view's last filled month. A pool opened again keeps it: it did run out then.
  • Chunks cut on a rewind (chunksBefore) cut closed and shut with the rows, and a chunk built from a re-stepped world reads its re-made history.
  • A row built without closed or shut (the page's zero rows in src/lib/timeline/chunk-log.ts) reads as null and false.

Details: "ran out"

/** One line per pool of `money` that ran out by the end of the calendar month starting `at`. */

  • A pool's day is money.closed[id] ?? null after that narrowing, and null for a money without closed.

One future

  • Closing reads only the world and the frames. It makes no draw and adds no seed or draw purpose.
  • Two runs of one document and dataset give the same closings, in the same months.
  • Grouped serving and the direct scan (grouped: false) give the same closings.

Cost

  • The check reads condition 1 and 2 first, which are per pool and cheap; it reads the money rows and the line only for a pool that passes them.
  • A closing month replans every free lot, as any money change does today.
  • funded-month.perf.spec.ts keeps its bar (90 µs a month, mean). It is measured on a quiet machine; a unit that cannot get one defers the measurement and says so.

Tests

Engine: src/lib/sim/world/funding/closing.spec.ts

On the mini city with money (fundedMini, moneyTimeline) and documents built for each case:

  • lastArrivalOf: a once inflow; a yearly inflow with to; to past the window; to: null gives null; a 0-dollar to: null inflow does not; 29 February anniversaries; every arrival before asOf and no inflow give NO_DAY; several inflows give the latest.
  • Spent: an added pool with one once inflow and an affordable grant programme, enough for one project. The next application finds it short in month m after the arrival's month: closedDay is monthLastDay(asOf, m) + 1, and one shut row is made. In the arrival's own month a short application closes nothing.
  • A pool with a loan money row (a loan programme's award, before and after construction) or a guarantee money row is not closed while the row exists, and is closed the first month after it ends that finds an application short.
  • A pool past its last arrival that no waiting application asks, or that every waiting application can be paid from, stays open.
  • A pool with a to: null inflow never closes, however short.
  • Exactly as switched off: world A (closing on) closes pool P from day D. World B, closing off, runs a document that switches P off from D (a baselineScale entry of 0 on a baseline pool; and, as a second case, an added pool's policy span ending the day before D). From D's month on, A and B send the same events (kinds, rows, days), write the same ledger and hold the same line rows.
  • Re-made and lapsed: in the closing month every waiting row whose bundle held P is re-made without it or lapses with its kind respelled from the month's first day; no row's bundle names P afterwards; no award asks P.
  • Money returned to a closed pool (a grant released by a project that exits before construction) raises its available money and is never awarded; closedDay is unchanged.
  • Opening again: an added pool with two spans, a once inflow in each, closes after the first span's money is spent and opens in the month of the second span's arrival: closedDay is NO_DAY from then, its programmes are offered, the shut row's shutTo is that month's first day, and it can close again later.
  • A pool closed and opened in the same month leaves no shut row.
  • An edit before the pool closes that gives it a later arrival (applied with keep): it does not close before the month after that arrival.
  • closedTimeline: base frames when nothing is closed; a closed pool's programmes have offered 0 and no other programme changes; ids differ from the base and are equal for equal content; changes() holds the closing and opening months and the base's, ascending; touched() is empty at a closing month; the view is the same object while the history is unchanged.
  • poolClosing: false: no shut row is ever made; an application waits on a spent pool to the horizon.
  • Grouped serving and grouped: false give the same closings and events.
  • Two runs of one seed give identical worlds; structuredClone of a world after a closing steps on identically to the original.
  • Restore: a world cloned at month 0, planned with planDue and stepped to month n, equals the world stepped straight to n, closings included.

Global constraints

  • Work happens in git worktrees under .claude/worktrees/. Commits follow Conventional Commits. No attribution to an AI anywhere.
  • Code style: 2-space indent, single quotes, no trailing commas, 100 columns.
  • Every Vitest test calls expect.
  • Signoff fails on server stderr, on timing crutches and on a retried flake. Each unit runs npm run lint, npm run check and the Vitest projects its files belong to before it hands back.
  • Port 4173 is shared by every session on this machine. A unit never kills a server it did not start; it waits.
  • Every agent runs every command in the foreground and never ends a turn while something it started is running.
  • Schema changes go through npm run db:generate. Nobody edits a migration.
  • No unit runs npm run signoff: its dataset step fails until the dataset is uploaded. closing runs it once, after the upload.
  • The dataset version changes in this build. The dataset is uploaded once, by closing, from the integration branch, after every unit has merged; no other unit uploads a dataset. reach-check builds one earlier to run the check and uploads nothing.
  • A unit that writes a hashed path regenerates the fixture dataset with npm run pipeline -- fixture and commits it.
  • WCAG 2.2 AA: every new control is at least 24 px and passes expectNoA11yViolations in light and dark.
  • Page text is short. No sentence says what something is not.
  • Nothing on the main screen says "RHNA". The goal is read from the Goal value, never from a constant.
  • The game's rules are read from src/lib/game/. No component compares a level to a number.
  • One future: no seed control, no band, no average over runs.
  • Published plans and policies, their ids and their pages keep working, including every policy published before this build.
  • A number that is a claim about the world carries its source and tier, in the existing Sourced, Unsourced and Evidence shapes.
  • A runtime dependency that ships in the bundle gets a credit in SOFTWARE. This build adds none.
  • CSP changes are interface changes. This build makes none.
  • Timing is measured only on a quiet machine. A unit that cannot get one defers the measurement and says so.
