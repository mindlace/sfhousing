Sim message log

A sim is an append-only log of changes to its rules. The rules, the page and every simulated month are computed from that log.

Intent

The owner asked for this, in these terms:

  • User input is recorded as a sequence of immutable messages. The state of the sim and of the page is a projection over them.
  • Follow planafoot's strategy: a websocket stream of messages, kept locally as well, with the consequence of an edit shown before the server answers.
  • Each sim (the thing that is saved and shared) has one consistent history, used for undo and redo.
  • The simulated months are a projection too. Editing an already-simulated year goes back to that month and simulates another future. Keeping every such variant shows how people explore the solution space.
  • Simulating is fast, so no world state is stored. What is stored is the changes to the ruleset.
  • No rule says what runs on the server and what runs in the browser.
  • Optimize for sharing and remixing. Memory is not the worry.
  • Adopt planafoot's gradual auth: a person is a user straight away, and signs in when and as they want.

Why now: timeline-ui is the last unit of the step engine, and it puts a new document (SimPolicy4) behind the same in-memory snapshot store /sim has today. Every page feature built after it would be built on that store.

Goals, non-goals, anti-goals

Goals

  • Every change to a sim's rules is one immutable commit in one ordered log per sim.
  • The ruleset is always the fold of that log. Nothing else holds rules.
  • An edit shows at once and survives a reload with no connection.
  • Undo and redo work across reloads and devices, to the depth of the whole log.
  • Every state a sim has ever been in can be named (sim id and position) and reopened.
  • A person is a user from their first edit, with no sign-up, and can attach a sign-in later.
  • Sharing is copying a link, with nothing to publish. Remixing is one commit, keeps the person's own sims, and records what it came from.
  • The logs of all sims can be read together to study how people explore: the shape of an exploration, the levers pulled, and histories that stop short.

Non-goals

  • Two people editing one sim at the same moment. The commit carries what that needs (an actor and a parent), and nothing more is built.
  • Roles, invitations or any way to give another account the right to edit a sim.
  • Email and Google sign-in, account deletion, and the clearing out of pseudonymous accounts nobody returns to. Each comes after this build.
  • Storing world states, results or anything else the engine computes.
  • Changing the engine or its messages (setPolicy, refill). The page querying a results projection held by the engine is separate work.
  • / (already an op list in Plan.ops) and /lesscars (no edits).
  • Recording what a person looked at. That is for a later, opt-in PostHog setup (Studying exploration).
  • Any screen for studying exploration. The data is read with SQL.

Anti-goals

  • A commit that changes after it is accepted, or a log with a gap or a second order.
  • An edit that is lost because the connection was down or the tab closed.
  • A second copy of the rules that can disagree with the log (a saved document, a cache treated as truth).
  • History stored as a moving head pointer. Planafoot tried it and dropped it.
  • A rule in the design or the docs about where the engine runs.

What exists today

  • Editing. PolicyStore (src/lib/sim-page/policy-store.svelte.ts) holds the policy plus undo and redo lists of whole-policy snapshots, in memory. Every editor calls store.apply((p) => p', label, coalesce?) with an inline closure. Nothing is serialisable, and a reload loses the history.
  • Saving. Autosave writes the whole document to one localStorage key, 500 ms after the last change.
  • Sharing. Publish inserts an immutable row in the D1 plan table, deduplicated by content hash, served at /s/<id>. A row has no owner, and a republish is an unrelated row.
  • Server. No Durable Object, no websocket. @planafoot/drizzle-cf-migrations already runs the D1 migrations (drizzle-cf.config.ts has one track, d1).
  • Identity. None. There are no accounts and no sessions.
  • Engine. The step engine gets the whole SimPolicy4 on each edit (setPolicy), finds the first month that differs (firstDifference), restores its month-0 copy and replays. A rerun is byte-identical for the same document, dataset version, app build and seeds. The future it replaces is discarded.
  • timeline-ui (plan written, not built) keeps PolicyStore, makes it generic over SimPolicy4, and adds undoTo and spanLens. The conductor's ledger records that it finishes on the current messages first.

Approaches

Three ways to give a sim a history
ApproachWhat it isTrade-off
A. Log of rule changes (picked) One Durable Object per sim orders and stores small commits. The browser applies each commit at once, keeps it locally and streams it over a websocket. Undo is a new commit. New server parts (a Durable Object, a websocket, a local database). A commit is a few hundred bytes, the history is linear, and every state is addressable.
B. Saved versions Keep the snapshot store and send each whole document to the server as a version. Least code. A painted policy is up to 262 KB per version, a version does not say what changed, and the page still has two copies of the rules.
C. Log with a moving head As A, but undo records a move of the head to an earlier commit, so the log is a tree. Keeps branches explicit. Planafoot built this and it went badly: the head is a second piece of state every reader must apply.
Decision (owner) Approach A. The owner proposed it, said the stored thing is "deltas in the ruleset", and ruled out C: "undo is copying an earlier state to the tip as a new commit".

Design

Terms

Sim
One log, with an id. The thing a person saves, shares and reopens.
Commit
One immutable entry in the log: an envelope and a list of changes.
Change
One addition, ending or deletion of an item in the ruleset.
Ruleset
The SimPolicy4, title and dataset version computed by folding the log.
Tip
The last commit. There is no other head.
Position
A commit's sequence number. A sim id and a position name one state for ever.

Changes

The ruleset is made of items that never change once added. This is the owner's rule from the timeline-ui ledger: "any offer by any source [is] immutable save truncation or deletion, so making a different offer ends the offer and starts a new one".

The change vocabulary
ChangeApplies toMeaning
addA policy, a span of a policy, a painted strokeThe item exists from this commit on.
endA spanThe span stops on a given day (truncation). Starting a different span on a policy ends the one in force.
deleteA policy, a span, a strokeThe item is gone as if never added.
setThe sim's title; a policy's label and on switchNames and switches, which are not offers.
  • R4. No change edits an item in place. Changing a band from 6 to 8 stories from the same day deletes the span and adds another, in one commit.
  • R5. A painted stroke is its own item, so a stroke costs its own bytes, not a copy of every stroke before it.
  • R6. The title joins the log. Today it sits outside PolicyStore and cannot be undone.
My call "Offer" is read as a span of a policy. A span has no id in SimPolicy4; a policy's spans do not overlap, so a span is named by its policy and start day.

Fold and diff

  • R7. fold(commits) gives the ruleset. It is one pure module, used by the browser and by the sim object. There is no second implementation.
  • R8. diff(a, b) gives the changes that turn ruleset a into b. For every pair, applying diff(a, b) to a gives b exactly (the same canonical text).
  • R9. The editors keep their pure edit functions (transit-edit.ts, funding-edit.ts, timeline-ui's spanLens). The store runs the function on the current ruleset and commits the diff. No editor writes changes by hand.
My call R9 keeps store.apply(change, label, coalesce?) as the editors' interface, so timeline-ui's page code moves over without rewriting each tab. What is stored is still values, per R2.

Undo and redo

  • R10. Undo appends a restore commit whose changes are diff(tip ruleset, earlier ruleset). After it, the ruleset equals the earlier one exactly. Nothing is removed from the log.
  • R11. Redo is the same: a restore to the state the last undo left.
  • R12. Which state undo and redo go to is computed from the tail of the log. No stack is stored. A new edit empties redo, as in any editor.
  • R13. Undo depth is the whole log, including after a reload and on another device.
  • R14. A restore to any position is the same operation. timeline-ui's undoTo (back to the last document the engine accepted) is a restore.
Five edits, two undos, one redo, then a new edit

Local first

  • R15. A commit is applied to the page and written to IndexedDB before it is sent. The page never waits for the server to show an edit.
  • R16. The page's ruleset is the fold of the confirmed commits followed by the pending ones. Confirmed commits come only from the stream.
  • R17. Pending commits survive a reload and are sent in order when the socket opens. Editing works with no connection for as long as it lasts.
  • R18. The sim object accepts a commit only when its parent is the tip. Otherwise it answers behind; the browser takes the newer commits, recomputes each pending commit as a diff against the new tip, and resends.
  • R40. Any number of tabs in one browser may edit one sim. Each tab has its own socket and sends its own commits; R18 puts them in one order, and every tab shows that order.
  • R19. A pending commit that no longer applies (its item was deleted elsewhere) is dropped, and the page says so.
  • R20. On first load after release, a document in the old localStorage autosave becomes a new sim whose first commit (system) holds it. The key is then removed.
Note Planafoot shows an edit before the server answers but keeps the pending edit in memory only. R15 and R17 go further, because /sim already survives a reload offline and must not lose that.

The sim object

  • R21. One Durable Object per sim, addressed by the sim id, holds the log in its SQLite storage: one row per commit, kept for ever.
  • R22. Its schema is a second track in drizzle-cf.config.ts. npm run db:generate builds its migration bundle and the object applies it on open with safeMigrate from @planafoot/drizzle-cf-migrations/do. Migrations are never hand-edited, as for D1.
  • R23. It uses the websocket hibernation API with an automatic ping reply, so an idle open sim costs nothing.
  • R24. D1 holds one row per sim (id, owner, created, last position, name, dataset version, commit count, what it was remixed from) and one row per commit's envelope (sim, position, kind, source, time, build, size), without the changes. Both are an index, for study and for listing a person's sims. They are rebuildable from the objects and never read to serve a sim's rules.
  • R41. The sim object writes the index after it accepts and broadcasts a commit, never before. A failed index write is retried and does not refuse or delay the commit.
  • R25. Appends are rate-limited per sim and a commit has a size cap. PUBLISH_RL (10 per minute) is for publishing and is not reused.

Accounts

Paused The owner paused this design on 2026-11-14 to port planafoot's auth, roles and invites into this project first, with quest renamed to sim. This section, the one-writer rule (R47) and Identity and sharing are to be rewritten on top of that port, which brings membership and invitations this design listed as non-goals.

This follows planafoot: onboarding with no barrier, an account that is pseudonymous until the person chooses otherwise, built on Better-Auth.

  • R44. A person gets a pseudonymous account at their first edit, with no email and no form (Better-Auth's anonymous() plugin). Reading a shared sim needs no account.
  • R45. A first edit made offline is kept as pending. The account is made at the first connection and the pending commits are sent under it.
  • R46. The Worker resolves the session and passes the account's id to the sim object. The object trusts only that; the browser never states who it is.
  • R47. A sim's writer is the account that sent its first commit. Only that account may append.
  • R48. A person can attach a sign-in at any time: a passkey, or a handle and password. Both keep the account pseudonymous. After that, signing in on another device brings their sims.
  • R49. Signing in to an existing account from a browser that already has a pseudonymous one joins the two, and the pseudonymous account's sims pass to the one that survives. Everything keys off a stable identity id that survives the join, as planafoot's user_identity does.
  • R50. Making accounts is rate-limited per address.
Decision (owner) Gradual auth as planafoot does it: "we get users straight away and allow them to auth when and as they want".
My call The account is made at the first edit, not on arrival, so a visitor who only looks, and a crawler, make none.
My call The first sign-in methods are a passkey and a handle with a password, because neither needs an outside service. Email needs a sender and Google needs an OAuth client; planafoot has both and they can follow.
My call From planafoot's identity model this takes the stable identity id and Better-Auth's own tables. It leaves out the history trail of handles and emails, which is there for abuse work this site does not have.

Identity and sharing

  • R29. The browser mints a sim's id at its first edit. The id is long and random; knowing it is what lets someone read the sim.
  • R30. Who may write is decided by the account (R47), not by anything the browser holds. A person signed in on two devices writes the same sim from both, in one order (R18).
  • R31. A share link names a sim and a position. It always shows that state, read-only, because the log does not change. Copying the link is the whole of sharing: the state is already on the server, or is sent as soon as there is a connection.
  • R32. Editing a sim you cannot write to starts a remix: a new sim whose first commit (system) holds the ruleset at that position and records the sim and position it came from. No separate step copies anything first.
  • R33. A remix is made locally and at once, like any commit, so it works offline from a link already open.
  • R34. A person holds any number of sims, each with its own address. The list of them belongs to the account, so it follows a sign-in to another device. A remix never replaces the person's current sim, as the single autosave slot does today.
  • R35. The D1 index row records what a sim was remixed from, so the tree of remixes can be read and counted without opening every log.
  • R42. A sim has a name the person can set at any time, as a commit. A new sim gets a default name; a remix starts with its source's name.
  • R43. From the list of its sims a person can open one, start a new one, rename one and remove one from the list. Removing takes the sim off the person's list; the log on the server stays, and its links still open.
  • R36. Existing /s/<id> links and their D1 rows keep working unchanged. Remixing one starts a new sim from its document.
Decision (owner) One writer per sim, with more than one tab open and editing in either. Sims are nameable so a person can have more than one. With accounts, one person's sims share the account's id, so they can be read together for study.
My call A remix's first commit holds the whole ruleset, not a pointer into the parent's log. A remix then never depends on another sim's object being reachable or taken down. The cost is that undo in a remix stops at its first commit; the page links to the parent for the history before it.

The engine and the variants

  • R37. The engine is fed as today: the store's ruleset, debounced 250 ms, through TimelineClient.setPolicy. Its messages do not change.
  • R38. No world state, series or result is stored anywhere. A variant is a position; reopening one folds the log to that position and simulates.
  • R39. This design says nothing about where the engine runs. The sim object does not run it, and nothing prevents a server-side run later.

What the page shows

  • The save state stays in the header's status slot, apart from the controls: saved, saving, or saved on this device while offline.
  • Undo and redo announce the commit's label, as today.
  • Publish becomes "copy link": there is nothing to upload, since the state already has an address.
  • A shared sim opens with the same editors. The first edit makes it the visitor's own remix and says so.
  • A remix names the sim it came from, with a link to it.
  • The sim's name sits in the header beside the save state. Tapping it opens the list of sims; nothing else about the list is on screen until then.
  • Signing in and the account pane are in the header's Menu. Nothing asks a person to sign in.
  • Tab, selection, scrubber position and map view stay local to the page and out of the log.

Studying exploration

The owner wants to classify the shape of an exploration, see which levers people pulled, and treat short change histories as a possible sign that a function is poorly exposed. No screen for this is wanted now.

  • The D1 index (R24) answers these with SQL: commits per sim, their kinds and sources in order, the time between them, undo and redo runs, remix trees.
  • The owner column groups one person's sims, so an exploration that runs across several sims can be read as one.
  • The full changes of a commit are read from its sim object when a question needs them.
  • What a person did in the page that changed no rule (which years and results they looked at) is not in the log. A later, opt-in PostHog setup records those actions and joins them to the log by sim id and position. Nothing for it is built here.

What leaves the browser

Decision (owner) Every edit is stored on the server from the first one, including edits later undone. Today nothing leaves the browser until Publish. No text announces the change: "everything is persisted" is how apps behave by default.
  • A commit stores no IP address. Its actor is the account's stable id, which names nobody until the person attaches contact details, and neither sign-in method in this build does.
  • Takedown stays manual: an operator deletes the sim object's storage and its index row.

Constraints

  • Starts after timeline-ui merges, and replaces the inside of its PolicyStore<SimPolicy4>.
  • A Durable Object class needs an export from the worker entry, which adapter-cloudflare's generated _worker.js does not have today.
  • The CSP is connect-src 'self'. If a supported browser does not admit a same-origin wss: under it, the change is an interface change (CLAUDE.md).
  • A Durable Object isolate has 128 MB and 10 GB of storage; a websocket message may be up to 32 MiB.
  • Better-Auth needs a secret in .dev.vars and in each environment, and its tables go through npm run db:generate like any schema change.
  • Any runtime dependency added to the bundle (for example an IndexedDB wrapper) gets a credit in src/lib/attribution.ts.
  • Vitest requires an assertion in every test; real Durable Object and R2 behaviour is tested in Playwright against workerd.

Testing

  • Core. Property tests: applying diff(a, b) to a gives b; a restore reproduces the earlier ruleset's canonical text; the undo and redo derivation matches a reference editor over random sequences of edit, undo and redo.
  • Accounts. A first edit makes one account and a second edit makes no other. A passkey or a password added on one browser signs in on another. Joining a pseudonymous account to an existing one moves its sims.
  • Sim object. Gapless positions; a duplicate id appends once; behind, invalid and not-writer refusals; resume from any position; migrate on open.
  • End to end. Edit, reload, undo back past the reload. Edit offline, reload, reconnect, and the commits arrive in order. Two tabs edit the same sim in turn and both show one order. A second sim is started, named and switched to without touching the first. A share link shows its position after later edits. Editing a shared sim starts a remix, leaves the visitor's other sims as they were, and the index records its source.

Builder check, unanswered

A fresh reader went through this document on 2026-11-14 as the builder would. The design was paused before these were sorted or answered. They are recorded as reported.

Questions, most important first

  • Dataset changes. Every load today reconciles the document against the current dataset and calibration (openSimDoc4, src/lib/timeline/sim-doc4.ts:238). If the reconciled result is the ruleset it must be a system commit, but a read-only viewer cannot append and the sim object has no calibration to validate with. If it is computed over the fold on each open, "the ruleset is always the fold" and R31 are false. Which is it?
  • What "recomputed against the new tip" means (R18). Replaying the pending commit's stored changes onto the new tip keeps the other tab's work. Diffing the new tip against the tab's intended state undoes it. The edit functions cannot be re-run after a reload, and a pending restore is undefined under either reading.
  • Joining accounts (R49). Planafoot does not join on a passkey or a password; its fuse runs only through onLinkAccount for email and Google, and a password deliberately does not trigger it (planafoot/src/lib/server/auth/password-pseudonymity.spec.ts:21-36). Which identity survives, and how does each sim's writer check follow?
  • Schema changes to SimPolicy4. A log kept for ever holds changes against today's shapes. Either fold keeps every past vocabulary and upgrades on read, or a system commit migrates the tip and older positions stop parsing.
  • The writer editing from an earlier position of their own sim. R31 makes a position link read-only and R32 makes an edit a remix only for someone who cannot write. For the writer: a restore then the edit, a remix, or a refusal?
  • Old positions re-simulate on the current build and dataset. Only one build is ever deployed, so the future someone saw cannot be reproduced exactly. If that matters, the plan needs pinned builds or stored results; if not, build is for study only.

Where this document is wrong about the repository or itself

  • R1: a coalesce run has no end signal today. It ends only when the next apply carries a different key (src/lib/sim-page/policy-store.svelte.ts:57-71). The store needs its own rule for when a draft becomes a commit, and whether an unfinished draft survives a reload.
  • The change vocabulary has no reorder, but timeline-ui adds "Move up" and "Move down" for policies and the kinds arrays are ordered. R8 cannot hold without one.
  • R24 says the D1 index is rebuildable, but removing a sim from a list (R43) and ownership passing on a join (R49) exist only in D1. Those rows are a source of truth and need a durability rule.
  • R22: npm run db:generate is hard-wired to generate d1 (package.json:27) and does not build a Durable Object track.
  • R20 assumes one old autosave key. After timeline-ui there are two, and sfhousing:sim:v1 is kept on purpose so an older tab keeps working (src/lib/timeline/sim-doc4.ts:315-319).
  • "timeline-ui (plan written, not built)" is out of date: tasks 1 to 3 are committed on step-engine/timeline-ui (ea21a9fb).
