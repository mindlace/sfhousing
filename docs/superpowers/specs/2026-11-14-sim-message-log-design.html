Sim message log

A sim is an append-only log of changes to its rules. The rules, the page and every simulated month are computed from that log.

Intent

The owner asked for this, in these terms:

  • User input is recorded as a sequence of immutable messages. The state of the sim and of the page is a projection over them.
  • Follow planafoot's strategy: a websocket stream of messages, kept locally as well, with the consequence of an edit shown before the server answers.
  • Each sim (the thing that is saved and shared) has one consistent history, used for undo and redo.
  • The simulated months are a projection too. Editing an already-simulated year goes back to that month and simulates another future. Keeping every such variant shows how people explore the solution space.
  • Simulating is fast, so no world state is stored. What is stored is the changes to the ruleset.
  • No rule says what runs on the server and what runs in the browser.
  • Optimize for sharing and remixing. Memory is not the worry.
  • Adopt planafoot's gradual auth: a person is a user straight away, and signs in when and as they want.
  • Take planafoot's 2.0 quest-graph model "to the level of complexity appropriate to this": people will add notes and other things to a sim later.
  • Read a sim with the shapes and the dataset as of the time it was made or shared, so the experience can change without breaking the past, and the "your sim is running on a new dataset" messages go.

Why now: timeline-ui is the last unit of the step engine, and it puts a new document (SimPolicy4) behind the same in-memory snapshot store /sim has today. Every page feature built after it would be built on that store. The sims ported from planafoot have a name and members and no content; this gives them one.

Goals, non-goals, anti-goals

Goals

  • Every change to a sim's rules is one immutable commit in one ordered log per sim.
  • The ruleset is always the fold of that log. Nothing else holds rules.
  • An edit shows at once and survives a reload with no connection.
  • Undo and redo work across reloads and devices, to the depth of the whole log.
  • Every state a sim has ever been in can be named (sim id and position) and reopened as it was.
  • A person is a user from their first edit, with no sign-up, and can attach a sign-in later.
  • A sim's members who may write (managers and editors) write one log, from any number of tabs and devices.
  • Sharing is copying a link, with nothing to publish. Remixing is one commit, keeps the person's own sims, and records what it came from.
  • The logs of all sims can be read together to study how people explore: the shape of an exploration, the levers pulled, and histories that stop short.

Non-goals

  • Merging two writers' edits beyond re-applying pending changes on the new tip (R18). No presence and no cursors.
  • New sign-in methods, or turning on password, passkey or Google. The port has them, off.
  • Notes. Only where they will go is designed (Shapes).
  • Storing world states, results or anything else the engine computes.
  • Changing the engine or its messages (setPolicy, refill). The page querying a results projection held by the engine is separate work.
  • / (already an op list in Plan.ops) and /lesscars (no edits).
  • Recording what a person looked at. That is for a later, opt-in PostHog setup (Studying exploration).
  • Any screen for studying exploration. The data is read with SQL.

Anti-goals

  • A commit that changes after it is accepted, or a log with a gap or a second order.
  • An edit that is lost because the connection was down or the tab closed.
  • A second copy of the rules that can disagree with the log (a saved document, a cache treated as truth).
  • History stored as a moving head pointer. Planafoot tried it and dropped it.
  • A share link that stops opening because someone left a sim or deleted their account.
  • A rule in the design or the docs about where the engine runs.

What exists today

  • Editing. PolicyStore (src/lib/sim-page/policy-store.svelte.ts) holds the policy plus undo and redo lists of whole-policy snapshots, in memory. Every editor calls store.apply((p) => p', label, coalesce?) with an inline closure. A coalesce run ends only when the next apply carries another key. Nothing is serialisable, and a reload loses the history.
  • Saving. Autosave (src/lib/sharing/autosave.svelte.ts) writes the whole document to sfhousing:sim:v1, 500 ms after the last change.
  • Sharing. Publish inserts an immutable row in the D1 plan table, deduplicated by content hash, served at /s/<id> (8 base58 characters). A row has no owner, and a republish is an unrelated row. /s/<id> opens on the document's dataset version, falls back to the current one when that is gone, and reconciles the timings on every load, with a notice when anything moved.
  • Server. No Durable Object, no websocket. @planafoot/drizzle-cf-migrations runs the D1 migrations: drizzle-cf.config.ts has one track, d1, and npm run db:generate runs generate d1 only (package.json).
  • Accounts, sims and invitations (ported from planafoot, docs/dev/auth.md). A stable identity (user_identity) with a survivor graph for fused accounts; pseudonymous accounts; magic link the only sign-in in staging and production, once mail is configured. A sim is a sim_index row (server-minted newId(), a title of at most 63 characters); roles (manager, editor, viewer) are grants in the capability_event ledger, and an invitation grants editor. A person may manage 5 sims; a sim whose last member leaves is deleted; onSimRosterChanged is a no-op seam. A sim has no content: nothing links it to /sim.
  • Engine. The step engine gets the whole SimPolicy4 on each edit (setPolicy), finds the first month that differs (firstDifference), restores its month-0 copy and replays. A rerun is byte-identical for the same document, dataset version, app build and seeds. The future it replaces is discarded.
  • timeline-ui is merged to main. It makes PolicyStore generic over SimPolicy4, records undoTo as an ordinary change, adds spanLens and Move up and Move down for policies, and saves under sfhousing:sim:v2 while keeping v1 for an older tab.

Approaches

Three ways to give a sim a history
ApproachWhat it isTrade-off
A. Log of rule changes (picked) One Durable Object per sim orders and stores small commits. The browser applies each commit at once, keeps it locally and streams it over a websocket. Undo is a new commit. New server parts (a Durable Object, a websocket, a local database). A commit is a few hundred bytes, the history is linear, and every state is addressable.
B. Saved versions Keep the snapshot store and send each whole document to the server as a version. Least code. A painted policy is up to 262 KB per version, a version does not say what changed, and the page still has two copies of the rules.
C. Log with a moving head As A, but undo records a move of the head to an earlier commit, so the log is a tree. Keeps branches explicit. Planafoot built this and it went badly: the head is a second piece of state every reader must apply.
Decision (owner) Approach A. The owner proposed it, said the stored thing is "deltas in the ruleset", and ruled out C: "undo is copying an earlier state to the tip as a new commit".

Design

Terms

Sim
One log, with an id, a name and members. The thing a person saves, shares and reopens.
Writer
A member whose role carries sim.write: a manager or an editor.
Commit
One immutable entry in the log: an envelope and a list of changes.
Item
A thing in a sim, with a shape and a key: a policy, a span, a painted stroke, the sim's name. Later, a note.
Shape
The declared form of a kind of item, with numbered versions, kept in the registry.
Change
One addition, ending, move, field set or deletion of an item.
Ruleset
The SimPolicy4, name and dataset version computed by folding the log.
Tip
The last commit. There is no other head.
Position
A commit's sequence number. A sim id and a position name one state for ever.

  • R1. A commit is one finished intent: a stroke, a released slider, a typed value. A drag shows live from a local draft. The draft becomes a commit when its coalesce key changes, when its field loses focus, or when the page is hidden. A draft still open when the page is hidden is committed then.
  • R2. A commit holds resulting values, never an instruction to recompute. A preset stores the numbers it resolved to, as it does today.
  • R3. The sim object refuses a commit whose changes do not fold to a valid ruleset: parsePolicy4 with asOf: null in its reconcile mode, so a preset retired later never makes an accepted sim refuse edits, and the existing size limits. The object holds no calibration, so alignment to the dataset's months is the author's check, as it is on the page today.
My call R1's three triggers, because a coalesce run has no end signal today and a draft open when the tab closes must not be lost. R3 checks structure only, because the object has no calibration and alignment is already checked where the edit is made.
My call source exists for the study of exploration (Studying exploration): which levers people pulled is read from it, without parsing labels or inferring from changes.
My call The hash chain replaces planafoot's state digest. Server and browser hold the same commits, so comparing one hash at the tip proves the browser's log is the server's.

Changes

The ruleset is made of items that never change once added. This is the owner's rule from the timeline-ui ledger: "any offer by any source [is] immutable save truncation or deletion, so making a different offer ends the offer and starts a new one".

The change vocabulary
ChangeApplies toMeaning
addAny itemThe item exists from this commit on, with its shape and fields.
endA spanThe span stops on a given day (truncation). Starting a different span on a policy ends the one in force.
moveAn item in an ordered list (a policy within its kind)The item takes a new place: first, or after a named sibling.
setA field the item's shape marks settable: the sim's name, a policy's label and on switchNames and switches, which are not offers.
deleteAny itemThe item is gone as if never added.
  • R4. No change edits an item in place. Changing a band from 6 to 8 stories from the same day deletes the span and adds another, in one commit. So does a later end or an earlier start; for a painted span that writes its strokes again.
  • R5. A painted stroke is its own item, so a stroke costs its own bytes, not a copy of every stroke before it.
  • R6. The title joins the log. Today it sits outside PolicyStore and cannot be undone.
My call "Offer" is read as a span of a policy. A span has no id in SimPolicy4; a policy's spans do not overlap, so a span is named by its policy and start day.

Shapes

Planafoot 2.0 stores a quest as a graph: every node and edge claims a shape from a registry, six kinds of event change them, an action groups events under one actor, and every event is read under the schema revision its writer attested (planafoot/docs/dev/quest-graph/model.md, vocab.md). This design takes what makes a later note a new shape in the same log, and leaves the rest.

What comes from planafoot's quest graph
Planafoot 2.0Here
A node claims its shape at genesisAn item is added with its shape's name; the commit's shapes gives the version.
A registry with lineage (succeeds)A registry in code: each shape's versions, each with a pure upgrade to the next. No version is ever removed.
Events read under the writer's attested revisionEach commit is read under its shapes and upgraded on read (R54).
An action groups events under one actorThe commit.
writeOnce facetsA shape marks which fields set may change. The rest are fixed, which is the offer rule.
Left outContent-hash shape ids and Merkle lineage; typed head tables generated from the registry; edges with cardinality and topology rules (a reference is a field holding another item's key); the door's closed-world checks; touch-based concurrency (R18 instead); undo by compensating actions (R10 instead); automation actors; code generation.
  • R57. Items of every shape live in the one log. The ruleset folds the shapes the engine reads; a shape it does not read (a note, later) is folded for the page and never sent to the engine. Adding a kind of thing is a new shape in the registry: no new store, table or frame.
  • R62. The registry is in use from the first commit; it is not kept for later. Revision 1 declares today's ruleset: the sim (its name); for each row of the where and what table of SimPolicy4 (transit, painted, category, routes, baseline, fund, terms; docs/dev/policy-timeline.md), a policy shape (its kind, where, label, preset, on switch and place in its list) and a span shape (from, to, what); and the painted stroke. A span names its policy and a stroke names its span, as fields. SimPolicy4 is not stored anywhere: it is what the fold assembles from these items for the engine.
My call One policy shape and one span shape per row of the table (R62), so a change to one what, which is where the schema has churned, is one shape's new version and one upgrade.
Decision (owner) "maybe we adopt the 2.0 quest-graph ish (to the level of complexity appropriate to this) - we're gonna wanna let people add notes and other things down the road". And the shape registry comes along: "the shape registry helps with schema evolution, and we've already seen a fair bit of that".
My call Shapes are versioned by number, and one registry revision names every shape's version. Planafoot hashes declarations for federation and cross-lineage comparison; one codebase with tens of shapes needs neither. Planafoot's 2.0 store is built but not yet in production, so nothing here depends on its code.

Fold and diff

  • R7. fold(commits) gives the ruleset. It is one pure module, used by the browser and by the sim object. There is no second implementation.
  • R8. diff(a, b) gives the changes that turn ruleset a into b, the order of every list included (move). For every pair, applying diff(a, b) to a gives b exactly (the same canonical text).
  • R9. The editors keep their pure edit functions (transit-edit.ts, funding-edit.ts, timeline-ui's spanLens and policy edits). The store runs the function on the current ruleset and commits the diff. No editor writes changes by hand.
My call R9 keeps store.apply(change, label, coalesce?) as the editors' interface, so timeline-ui's page code moves over without rewriting each tab. What is stored is still values, per R2.

Undo and redo

  • R10. Undo appends a restore commit whose changes are diff(tip ruleset, earlier ruleset). After it, the ruleset equals the earlier one exactly. Nothing is removed from the log.
  • R11. Redo is the same: a restore to the state the last undo left.
  • R12. Which state undo and redo go to is computed from the tail of the log, whoever wrote it. No stack is stored. A new edit empties redo, as in any editor; a jump counts as an edit. Undo stops at a system commit: an import, a remix's first commit, or a move to a newer dataset, since the rules before a move are aligned to the older dataset.
  • R13. Undo depth is the whole log, including after a reload and on another device.
  • R14. A restore to any position is the same operation. timeline-ui's undoTo (back to the last document the engine accepted) is a restore.
Five edits, two undos, one redo, then a new edit
PositionKindRestoresRuleset equals
1 to 5editS1 to S5
6restore (undo)4S4
7restore (undo)3S3

9editS4 plus the edit; redo is now empty, and undo goes to S4, then S3

The futures simulated from S5, S4 and S3 are all still reachable: each is a position in the log.

Decision (owner) With two writers, undo goes to the state before the tip, whoever made the tip (R12). It does not pick out the writer's own last commit.

Local first

  • R15. A commit is applied to the page and written to IndexedDB before it is sent. The page never waits for the server to show an edit.
  • R16. The page's ruleset is the fold of the confirmed commits followed by the pending ones. Confirmed commits come only from the stream.
  • R17. Pending commits survive a reload and are sent in order when the socket opens. Editing works with no connection for as long as it lasts.
  • R18. The sim object accepts a commit only when its parent is the tip. Otherwise it answers behind. The browser takes the newer commits, re-applies each pending commit's stored changes in order on the new tip, and resends. A pending restore keeps its target position; its changes are recomputed as diff(new tip ruleset, target ruleset).
  • R40. Any number of tabs, devices and writers may edit one sim. Each socket sends its own commits; R18 puts them in one order, and every socket shows that order.
  • R19. A re-applied change whose item no longer exists is dropped, and the rest of its commit stands. A commit left with no changes, or that no longer folds to a valid ruleset, is dropped. The page says what was dropped.
  • R20. On first load after release, the old autosave becomes a new sim whose first commit (system) holds it: sfhousing:sim:v2 if present, else sfhousing:sim:v1 opened with openSimDoc4. Both keys stay, so an older open tab keeps working, and a marker key makes the import run once per browser.
My call A pending commit stores its changes, not the state it meant, so re-applying it keeps the other socket's work. Diffing against an intended state would undo that work, and an edit function cannot be re-run after a reload. Both old autosave keys stay (R20) because timeline-ui keeps v1 for a tab opened before it.
Note Planafoot shows an edit before the server answers but keeps the pending edit in memory only. R15 and R17 go further, because /sim already survives a reload offline and must not lose that.

The sim object

  • R21. One Durable Object per sim, addressed by the sim id, holds the log in its SQLite storage: one row per commit, kept for good. Only an operator's takedown removes it (R43).
  • R22. Its schema is a second track in drizzle-cf.config.ts: sim, with its own drizzle-kit config (drizzle.sim.config.ts), dir: 'migrations/sim', a bundle (outFile, exportName) and a schemas.sim entry. package.json gains db:generate:sim, which runs generate sim. The object applies the bundle on open with safeMigrate from @planafoot/drizzle-cf-migrations/do. The track is append-only: it is never regenerated from scratch, because that re-stamps the baseline existing objects have applied.
  • R23. It uses the websocket hibernation API with an automatic ping reply, so an idle open sim costs nothing.
  • R24. sim_index is the D1 copy of what a sim's log says: its name (title), and new columns for what it was remixed from, its position count, its last change and its dataset version. A new sim_commit table holds each commit's envelope (sim, position, kind, what it restores, source, actor, time, build, dataset version, size), without the changes. Both can be rebuilt from the objects and are never read to serve a sim's rules. The membership grants in capability_event are not in any log and are the source of truth for who may write. The role folds join sim_index (sim-roles.ts), so a rebuild writes the index row before anything reads roles.
  • R41. The sim object writes the index after it accepts and broadcasts a commit, never before. A failed index write is retried and does not refuse or delay the commit.
  • R25. Appends are rate-limited per sim and a commit has a size cap. PUBLISH_RL (10 per minute) is for publishing and is not reused.
  • R53. The Worker reads the identity's role (foldSimRole) when it opens a socket and passes the object the identity and whether it may write. onSimRosterChanged (src/lib/server/sims/roster-hook.ts) tells the object to read the role of each open socket's identity again; a socket that loses write gets an access frame (the stream), and its pending commits become a remix (R32). The hook gains the environment as an argument, to reach the object's binding; its call sites (docs/dev/auth.md, Invitations) pass it, and the fuse becomes one (R49).
  • R58. A sim made without commits (on the /sims form, or before this build) folds to the default ruleset. The first time a writer opens it, the object appends a system commit holding its index name.
My call The log lives only in the object; membership lives only in D1, and the object learns of a change through the ported seam. The index row is a copy of the log; the grants are not, and are never rebuilt from anything.

Frames on the socket
DirectionFrameMeaning
Server to browserhelloFirst frame. Carries the server's build, so a stale tab can reload.
Server to browseraccess {write}After hello, and whenever this socket's right to write changes.
Browser to serverresume {after}Sent on every open: the last confirmed position the browser holds.
Server to browsercommitsCommits in order, exactly as stored. The answer to resume and the live broadcast are the same frame.
Browser to serverappend {commit}One pending commit.
Server to browserrefused {id, why}behind, invalid, not-writer, limit (the rate, or one commit's size: back off), full (the sim is at its commit-count or byte cap and takes no more commits: stop sending, keep the commit pending, offer a remix), newer (the commit was made under a shape revision this server does not know yet; the browser keeps it pending and sends it again) or gone (the sim was taken down, or the browser's position is past the tip).
  • R26. There is no separate acknowledgement. A pending commit is confirmed when it arrives on the stream with its id and a seq.
  • R27. A commit whose seq is not the next one is not applied; the browser sends resume.
  • R28. The log is the stream, so catching up is reading rows after a position. There is no replay cache and no snapshot to fall back to.
My call Appends go over the socket. Planafoot posts writes over HTTP and uses the socket only for the broadcast; a commit is already idempotent by id, so one channel is less to build.

Accounts

Accounts are the port of planafoot's (docs/dev/auth.md): Better-Auth for sessions and credentials, and the app's stable identity, roles and membership in D1. This design changes them only as R49, R51 and R52 say.

  • R44. A person gets a pseudonymous account when their browser first registers a sim (R51): startSim calls mintPseudonymousSession (Better-Auth anonymous(), with an @pseudonymous.sfhousing.invalid address that is never mailed). Reading a sim needs no account, and a visitor who only looks gets none.
  • R45. A first edit made offline stays pending. The account is minted at the first connection and the pending commits are sent under it.
  • R60. A signed-out browser that has signed in before (the sfh_known cookie) is not given a second account: POST /api/sims answers 401, the commits stay pending, and the save state offers sign-in. They are sent after it.
  • R46. The Worker resolves the session to locals.user.id, the stable identity id followed to its survivor (resolveSessionUser), and passes it to the object with the right to write (R53). The browser never states who it is.
  • R47. A sim's writers are its members whose role carries sim.write: managers and editors (src/lib/server/authz/ability.ts). A viewer, and anyone else with the link, reads.
  • R48. A person attaches a sign-in when they want. In staging and production the one method is the email magic link, in effect only once a mail provider is configured; until then the pseudonymous account is all there is. Password, passkey and Google are ported and off (AUTH_METHODS). Another device signed in to the same address lists the same sims, because the list is read from the ledger (R34).
  • R49. A magic-link sign-in from a pseudonymous session runs handleAccountLink. If the address is new, the pseudonymous identity survives with the new live row (applyUpgrade), and nothing changes for its sims. If the address already has an account, that account's identity survives (applyFuse): the pseudonymous identity gets superseded_by_id pointing at it, and its live row is deleted. Its grants stay where they are, and the role folds read them through the survivor (principalUnion), so the survivor writes every sim either identity could. Commits keep the actor they were appended with; superseded_by_id resolves it to the survivor. handleAccountLink gains a call to the roster hook for each sim of the absorbed identity.
  • R50. Minting is rate-limited per address: PSEUDO_MINT_RL, 5 a minute per CF-Connecting-IP, failing closed in production when the binding is missing.
  • R61. No account is reaped. The ported reaper (src/lib/server/reap/), which nothing calls, is removed, with its section in docs/dev/auth.md.
Decision (owner) No reaping. Removing the unused reaper code, rather than leaving it without a trigger, is my call: code that deletes accounts should not sit one cron entry away from running.
Decision (owner) Gradual auth as planafoot does it: "we get users straight away and allow them to auth when and as they want". In staging and production the only sign-in is the magic link, once mail is configured; pseudonymous accounts are always on.
My call The account is made at the first registration, not on arrival, so a visitor who only looks, and a crawler, make none. The port already works this way.

Identity and sharing

  • R29. The browser mints a sim's id at its first edit, in the format createSim uses (newId, a base58 UUIDv7, checked by isValidId), so a sim and a remix can be made offline. newId moves out of src/lib/server/ids/ so the browser can import it. Apart from its creation time the id is random; knowing it is what lets someone read the sim.
  • R51. The first connection registers the sim: the browser posts its id to POST /api/sims, then opens the socket. Registering again is a no-op for a writer of that sim and refused for anyone else, whose commits become a remix (R32). Changes: createSim takes the id and checks it with isValidId; it needs its own insert, because createSimRecord fails on an existing row and ensureSimRecord would make any caller a manager; startSim and the route take simId and an optional name, since checkSimTitle refuses an empty one and a new sim has the default name (R42); reseedHandleFromSim runs only when a name was given.
  • R52. A person may manage at most 1,000 sims (MAX_SIMS_PER_MANAGER, 5 today, and its copy in SIMS_COPY.quota). The ceiling stops one account, or a script holding one, from making objects and index rows without end. The rates do the real work: startSim gains MUTATION_REGISTERED_RL (120 a minute) keyed by identity, since an existing account has no limit on making sims today, and minting stays behind PSEUDO_MINT_RL (R50).
  • R30. Who may write is decided by the ledger (R47), never by anything the browser holds. A writer on two devices, or two writers, write the same sim in one order (R18).
  • R31. A share link names a sim and a position: /s/<simId>/<n>. Anyone with it reads that state, read-only, with no account and no membership. It shows the same state for good: the log does not change, and no member leaving or deleting their account removes it (R43). Copying the link is the whole of sharing.
  • R32. Editing a sim you cannot write to starts a remix: a new sim whose first commit (system) holds the ruleset at that position and records the sim and position it came from, in an envelope field remixOf that only a sim's first commit may carry. The object copies it to the index (R35). A writer editing from an earlier position of their own sim gets a restore to that position and then the edit, as two commits on that sim (R10); no remix.
  • R33. A remix is made locally and at once, like any commit, so it works offline from a link already open.
  • R34. A person holds any number of sims, up to R52, each with its own address (/sim/<simId>). Their list is the sims they are a member of (foldSimsForUser), so it follows a sign-in to another device. A remix never replaces another sim, as the single autosave slot does today.
  • R35. The index row records what a sim was remixed from (R24), so the tree of remixes can be read and counted without opening every log.
  • R42. A sim's name is a set on its name item, which every sim has from the start, at most 63 characters (SIM_TITLE_MAX, checked as checkSimTitle does). sim_index.title is its copy. A new sim gets a default name; a remix starts with its source's name.
  • R43. From the list a person can open a sim, start one, rename one and leave one (leaveSim). Nothing a member does deletes a sim. When its last member leaves, or deletes their account (deleteAccount removes its memberships), the sim stays with no members: its log and its sim_index row are kept, its links open as before, nobody can write it, and an edit starts a remix (R32). Its id cannot be registered again (R51), so nobody takes it over. removeSimMember (src/lib/server/sims/sims.ts) stops calling deleteSim when the roster is empty and deletes the sim's pending invitations instead. deleteSim is left for an operator's takedown: it also clears the object's storage and leaves a mark, so the id is never registered again and its links stop opening. A remix is unaffected by a takedown, because its first commit holds its whole ruleset.
  • R59. An invitation adds a member, as an editor (src/lib/server/invites/control-plane.ts). The new member writes to the same log from the next socket they open, in the one order. Membership changes are not commits: the log holds only the sim's content.
  • R36. Existing /s/<id> links (8 characters) and their D1 rows keep working unchanged. Remixing one starts a new sim from its document.
Decision (owner) One writer per sim, with more than one tab open and editing in either. Sims are nameable so a person can have more than one.
My call Writers are whom the ported ledger gives sim.write (R47): the owner's "one writer" predates roles and invitations, and a second rule beside the ledger would have to be kept in step with it. Two writers are ordered as two tabs are.

My call A remix's first commit holds the whole ruleset, so it never depends on another sim's object; the cost is that undo in a remix stops there, and the page links to the parent for the history before it.

The engine, datasets and the variants

  • R37. The engine is fed as today: the store's ruleset, debounced 250 ms, through TimelineClient.setPolicy. Its messages do not change.
  • R38. No world state, series or result is stored anywhere. A variant is a position; reopening one folds the log to that position and simulates.
  • R54. A commit is read with the dataset and shapes it records. Folding to a position reads each commit's changes under its shapes and upgrades them through the registry to the current shapes; the position is simulated on its last commit's dataset, which stays on R2 because published datasets are immutable. Opening a position never reconciles it against today's dataset, so a link shows what was shared, and the notices that a sim runs on another dataset go.
  • R55. Before a writer's first edit under a newer dataset than the tip's, the browser appends a system commit that moves the sim: its changes are what reconcilePolicy4 changes on the new dataset, and the page shows today's notices for what moved. Reading never moves a sim. A move to newer shapes is not a commit, because the upgrade on read gives the same ruleset every time.
  • R56. The engine is not pinned. An old position re-simulates on the current engine with its own dataset and shapes, so the future someone saw under an older engine is not reproduced exactly; build is kept for study. The engine's dataset loader keeps reading every dataset a log names, back to MIN_SIM_DATASET; a pipeline change that breaks an older dataset ships an upgrade in the loader, as a shape change ships one in the registry. A dataset may be pruned only once no commit names it, which sim_commit answers (R24); none is pruned for now.
  • R39. This design says nothing about where the engine runs. The sim object does not run it, and nothing prevents a server-side run later.
Decision (owner) The move to a newer dataset is automatic, on a writer's first edit under it (R55). The person is not asked. Old datasets stay as long as the site does; one can be pruned once nothing depends on it, and for now none is (R56).
My call R54 to R56 otherwise. A dataset move is a commit because the editors resolve presets against the page's dataset, so an edit made on a newer one must start from a ruleset moved to it. A shape move is not, because the upgrade is pure. The engine is not pinned because only one build is ever deployed.
Decision (owner) "being able to use the shapes/dataset as-of the time the sim was shared will make it easier to evolve the experience w/o worrying about breaking the past, and allow us to drop those 'your sim is running on a new dataset' messages we give now."

What the page shows

  • The save state stays in the header's status slot, apart from the controls: saved, saving, or saved on this device (offline, or waiting for sign-in, R60).
  • Undo and redo announce the commit's label, as today.
  • Publish becomes "copy link": there is nothing to upload, since the state already has an address.
  • A sim the visitor cannot write opens with the same editors. The first edit makes it the visitor's own remix and says so.
  • A remix names the sim it came from, with a link to it.
  • The sim's name sits in the header beside the save state. Tapping it opens the list of sims and a link to the member area; nothing else about either is on screen until then.
  • The header's account entry (Sign in, or the handle linking to /account) is as ported. Nothing asks a person to sign in except commits waiting on a known device (R60).
  • Tab, selection, scrubber position and map view stay local to the page and out of the log.

Studying exploration

The owner wants to classify the shape of an exploration, see which levers people pulled, and treat short change histories as a possible sign that a function is poorly exposed. No screen for this is wanted now.

  • The D1 index (R24) answers these with SQL: commits per sim, their kinds and sources in order, the time between them, undo and redo runs, remix trees.
  • The actor column, resolved through user_identity.superseded_by_id, groups one person's commits across sims, so an exploration that runs across several sims can be read as one.
  • The full changes of a commit are read from its sim object when a question needs them.
  • What a person did in the page that changed no rule (which years and results they looked at) is not in the log. A later, opt-in PostHog setup records those actions and joins them to the log by sim id and position. Nothing for it is built here.

What leaves the browser

Decision (owner) Every edit is stored on the server from the first one, including edits later undone. Today nothing leaves the browser until Publish. No text announces the change: "everything is persisted" is how apps behave by default.
  • A commit stores no IP address. Its actor is the stable identity id, which names nobody until the person signs in with an email. The address lives only in the D1 user row, and account deletion scrubs it.
  • Commits a deleted account made stay, in every sim, under its identity id, which now resolves to a tombstone.
  • A person cannot delete a sim. Leaving takes it off their list; its links still open (R43).
  • Takedown stays manual, and is the only way a sim is removed: an operator deletes it (R43).
Decision (owner) A deleted person's commits are kept, and a person cannot erase a sim. This project's privacy envelope and public surface differ from planafoot's: keeping sims is the greater virtue, and a sim discloses nothing particularly private.

Constraints

  • The log store replaces the inside of timeline-ui's PolicyStore<SimPolicy4>, which is on main.
  • A Durable Object class needs an export from the worker entry, which adapter-cloudflare's generated _worker.js (main in wrangler.jsonc) does not have today, and a binding and a new_sqlite_classes migration in both environments.
  • The CSP is connect-src 'self' (svelte.config.js). If a supported browser does not admit a same-origin wss: under it, the change is an interface change (CLAUDE.md).
  • The socket route sits under /api/sims, which is in SESSION_ROUTE_PREFIXES, so its session is resolved. It checks Origin as refuseUnlessSameOriginJson does for POST /api/sims.
  • A Durable Object isolate has 128 MB and 10 GB of storage; a websocket message may be up to 32 MiB.
  • Vitest requires an assertion in every test; real Durable Object and R2 behaviour is tested in Playwright against workerd.

Testing

  • Core. Property tests: applying diff(a, b) to a gives b, order included; a restore reproduces the earlier ruleset's canonical text; the undo and redo derivation matches a reference editor over random sequences of edit, undo and redo. A commit written under an older shape version folds to the same canonical text as its upgraded form (a fixture registry with two versions).
  • Control plane. A writer registering an id twice makes one sim; another account registering it is refused. A first registration mints one account and a second mints none; a known device gets 401. The 1,001st managed sim is refused. After a fuse the survivor writes the absorbed identity's sims. After the last member leaves, and after an account is deleted, the sim's links still open and an edit starts a remix. After a takedown they do not.
  • Sim object. Gapless positions; a duplicate id appends once; behind, invalid, not-writer and gone refusals; resume from any position; migrate on open; a role change ends write on an open socket.
  • End to end. Edit, reload, undo back past the reload. Edit offline, reload, reconnect, and the commits arrive in order. Two tabs edit the same sim in turn and both show one order. An invited editor's edit appears in the inviter's open tab. A second sim is started, named and switched to without touching the first. A share link shows its position, on its own dataset, after later edits. Editing a shared sim starts a remix, leaves the visitor's other sims as they were, and the index records its source.

Carried from the log core (unit 1, built; docs/dev/sim-log.md) to the units that call it:

  • Log store. A pending delete of a stroke that another writer has since repeated drops its whole commit today. The rule to build: with k deletes of one group of identical strokes in a commit, and t the highest repeat on the new tip, the i-th delete targets repeat t - k + i, and is dropped as gone when that is below 1.
  • Log store. Undo stops at a move to a newer dataset (R12), but a jump can name a position before one. Decide what such a jump does: refuse it, or restore and move in one commit.
  • Log store. reapply throws for a pending commit made under a newer shape revision than the build knows. The page offers a reload; the commit is kept.
  • Any unit that adds a shape version to the stroke. Turning a ruleset into items must then emit the newest fields, so that a folded state and one built from its ruleset hold the same items.
  • Every caller. An item read from the state is the stored one: treat it as read-only.

Carried from the sim object (unit 2, built; docs/dev/sim-object.md):

  • Control plane. Write the roster change, then call rereadRoles(), and handle its throw (a failed role read revokes nobody). Call it when the last member leaves too, or open writer sockets keep writing. Call takeDown() before deleting a sim's D1 rows. Add the end-to-end tests of a role change ending write on an open socket and of gone after a takedown.
  • Log store. Under npm run dev the socket never opens: Vite takes websocket upgrades for its own socket, and the object does not run there. Decide whether the page treats that as offline in dev or dev changes how it runs. The socket works under npm run preview.
  • Log store. Check a commit with fitsCommit (src/lib/sim-stream/limits.ts) before sending. On a refusal: limit backs off; full is permanent; newer keeps the commit pending and offers a reload; gone on a resume starts again. Send resume before pending commits, because a duplicate spends the rate budget. Reconnect with backoff: a sim whose stored rows no longer fold closes each append with an internal error.
  • Log store. Several readers resuming a very large sim at once are not bounded in memory or rate. Bound it (pages sent with backpressure, or a per-socket resume rate) once it is known how the runtime buffers outgoing frames.
  • Log store. Check that connect-src 'self' admits the socket in WebKit and Firefox; the end-to-end tests prove it in Chromium only.
  • Sharing. The index pass copies remixOf to the remixed_from columns once the field exists. A commit's actor id is visible to anyone with a sim's link.

Carried from the control plane (unit 3, built; docs/dev/auth.md, Registering a sim):

  • Log store. Register before opening the socket: the stream answers 404 until the sim is registered. Send a signed-out first registration one request at a time; two at once mint two accounts. On taken, start a remix. On 401 (a known device with no session), keep the commits pending and post the same id again after sign-in; the server holds nothing. A 500 without a code is safe to retry. Never show a sim's id before its registration succeeds, or someone else can register it first.
