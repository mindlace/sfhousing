Game core design

The game's rules, its saved games and their store, the win card, the level panel, and the root layout making and providing the store.

Goal

This unit implements the rules of the incremental game design as pure TypeScript, two components and the root layout's store script, behind the interfaces the contracts unit shipped as stubs. The pages (game-sim, game-shell) and the save sync (game-save) read the game only through them.

  • Levels and results: what beats a bar, and when Paint is won (G1).
  • Progress and banking, saved games with their default names, the store that holds them in localStorage, the win on offer, and the open game (G2).
  • What each level allows, the playable document, and the level a document needs (G3).
  • The player's standing from a seen result (G4).
  • The win card, the level panel with its saved-games list, and the game's words (G5).
  • The root layout's script that makes the store, or the open game under the e2e seam (X1), and provides it.

G1 Levels and results

// src/lib/game/levels.ts
import type { Day } from '$lib/timelapse/time';

import type { GoalOutcome } from '$lib/timeline/outcome';

export type Level = 1 | 2 | 3 | 4 | 5;
export const LAST_LEVEL: Level = 5;

/** What the months reached so far show: `{ kind: 'reached'; on }` or `{ kind: 'missed'; short }`. */
export type Result = GoalOutcome;

/** The result to beat: the day a banked result reached the goal. */
export interface Bar {
  on: Day;
}

export function beats(seen: Result, bar: Bar): boolean;

/** Paint is won: capacity is at least the goal's amount. */
export function paintWon(net: number, amount: number): boolean;
reached.on
The first day of the calendar month in which the goal's amount is first met, as readGoal gives it.
  • beats(seen, bar) is true when seen reached the goal and seen.on is in an earlier calendar month than bar.on.
  • It is false in every other case: a tie never beats, and a missed result never beats.
  • paintWon(net, amount) is net >= amount.
  • Only a reached result is ever banked, so a bar is always a date.

Holds { v: 1, current: string, saves: SaveEntry[] }.
saveKey(id)
Holds one GameSave. For the current game its plan and policy are stale: the records under sfhousing:plan:v1 and sfhousing:sim:v2 are the truth.
  • barOf is { on: banked[level - 1].on } at levels 3 to 5.
  • levelUp from level 1 takes null and banks nothing.
  • levelUp from levels 2 to 4 stores the day under the level being left and adds one to the level.
  • levelUp at level 5 stores banked[5] and keeps the level at 5.
  • The page calls won() when a win card first shows.
  • allowed is allowedAt(progress.level).
  • While open is true no page shows a game part: no level cell, no win card, no bar or "To beat" flag, no locked lane, no reworded outcome message, no Remix button, and no offer is set. The pages read open; they never compare allowed with ALL_ALLOWED.
  • The page calls setOffer with the win while its seen result wins the level, and with null on any edit and when it unmounts. The offer is kept in memory only.
  • The store's levelUp() banks the offer with the pure levelUp, clears the offer, and stores the game. The win card and the level panel both call it.
  • The page that set the offer reacts to the level changing: /sim returns the clock to today, and Paint opens /sim.
  • The page calls touched() after its autosave writes a record key. The store sets the current game's savedAt and calls sync.changed(currentId).
  • On first construction with no SAVES_KEY, the store makes one saved game at level 1 whose plan and policy are whatever the two record keys hold.
  • newGame, switchTo and remix first copy the two record keys into the current game's stored save, then write the new current game's plan and policy into the two record keys. remove of the current game removes its save without copying it out, then writes the new current game's plan and policy into the two record keys.
  • After newGame, switchTo or remove answers ok, the caller loads the new current game's page with a full page load: / at level 1, /sim above it.
  • After remix answers ok, the caller loads / for a plan and /sim for a policy, with a full page load.
  • remix's record is the text the page's autosave holds under the record key for the published document. The caller builds it with the codec the page already uses, so the store never reads inside a plan or a policy.
  • remix of a policy copies the current game's progress and plan; remix of a plan copies the current game's progress and policy. The new game's name is defaultSaveName({ kind: 'remix', title }).
  • newGame, remix and adopt answer full and change nothing when they would pass MAX_SAVES.
  • rekey of the current game leaves it current, keeps the offer and needs no page load: the records and the progress are untouched. The save sync uses it when it keeps both sides of a conflict (S2).
  • A write that the browser refuses answers storage and leaves the stored games as they were.
  • remove of the current game makes the most recently changed other game current; with none left it makes a new game.
  • rename trims the name, cuts it at SAVE_NAME_MAX, ignores an empty one, and sets nameIsDefault false.
  • defaultSaveName gives "Game, 22 Nov", "Remix of {title}" or "{name} (this device)", and adds " (2)", " (3)" while the name is in taken.
  • The store calls sync.changed(id) after every change to a saved game and sync.removed(id) after a remove.
  • A stored value that will not parse is copied to sfhousing:save:corrupt:<ISO time> and left out of the list.
  • With storage: null the store keeps one game in memory.
  • useGame() outside a provider returns openGame(), so a component test that provides no game sees every control.
  • Only the root layout calls provideGame. It makes the save sync with createSaveSync (S2), constructs the store with it, calls sync.attach(store) and provides the store.
  • When e2eOpen (X1) is true, the root layout provides openGame() instead and makes no sync.
  • The root layout's script that makes and provides the store belongs to game-core.

  • allowedAt(1) and allowedAt(2) have no kinds.
  • allowedAt(3) has permitting; allowedAt(4) adds zoning; allowedAt(5) adds money with money: 'given'.
  • ALL_ALLOWED has all three kinds and money: 'all'. No level in this round returns it.
  • The published view at /s/<id> runs under ALL_ALLOWED, so playable returns its document unchanged (D5).
  • runs is false for a kind not in a.kinds.
  • runs is false for a money policy that is not given while a.money is 'given'.
  • playable returns the document with only the policies that run, in their order, and returns the same object when nothing is removed.
  • Every money policy that addPolicy makes from a funding preset carries the preset's id in preset and the preset's label as its label.
  • The schema 4 parser accepts null or a preset id of 1 to 60 characters in a money policy's preset. Zoning and permitting are unchanged.
  • A money policy stored or published before this build has preset null, so it is not a given measure. It runs in the published view and is locked in a game.
  • An edit that changes what a given measure pays sets its preset to null.
  • isGiven is false for every zoning and permitting policy.
  • isGiven does not check the id against the presets on offer. A hand-made document can carry any id on any pool; nothing ranks one player against another, so that is accepted.
  • simLocked is true exactly at level 1. Pages call it and needsHigher; no page compares a level itself.
  • levelNeeded of a document with no policies is 2.

S2 The browser's save sync

// src/lib/game/save-sync.svelte.ts
export type SyncState = 'local' | 'saving' | 'saved' | 'offline' | 'sign-in' | 'full';

export interface SaveSync {
  /** Reactive. */
  readonly state: SyncState;
  /** Reactive: the account as the server last answered (S1's `AccountLine`); null until it has. */
  readonly account: AccountLine | null;
  /** The saved game `id` changed. */
  changed(id: string): void;
  /** The saved game `id` was deleted in this browser. */
  removed(id: string): void;
  /** Bring the account's saved games here and send this browser's there. */
  pull(): Promise<void>;
  /** The store saved games are read from and adopted into. Called once by the root layout. */
  attach(store: GameStore): void;
}

export function createSaveSync(opts: {
  storage: Storage | null;
  fetchFn: typeof fetch;
  /** Whether the root layout's `user` is set now. */
  signedIn: () => boolean;
}): SaveSync;
  • state is local until this browser has a session.
  • changed(id) sends nothing while this browser has no session and the game's firstWinAt is null.
  • When the sync attaches with no session, every saved game that has firstWinAt set and has not been sent since it last changed is queued to send, so a first win whose send never went still makes the account.
  • changed(id) debounces to one PUT per saved game per 2 seconds, with the save read from the store at send time.
  • The browser keeps each saved game's last seen rev under sfhousing:saves:revs.
  • A 409 keeps both: the browser's version is stored as a new saved game with a new id and the name defaultSaveName({ kind: 'conflict', name }), the account's version is adopted under the old id, and the new saved game is sent.
  • When the old id was the current game, the browser's version stays current under its new id, so nothing changes under the player's hands.
  • A 410 keeps the saved game in this browser under a new id and sends it again: a change made here is never lost to a delete made on another device (D8).
  • pull() lists the account's saved games. It fetches and adopts those this browser lacks, and those it holds unchanged at an older rev. It removes those listed under removed that are unchanged here. It sends those the account lacks.
  • pull() runs once on load when signedIn(), and again when signedIn() turns true.
  • account is set from every answer that carries an AccountLine. After the PUT that made the account, the header shows the handle from it. The sync never invalidates page data: a page keeps its playhead, its card and its undo history.
  • Once a PUT has answered 200 the sync treats this browser as having a session, whatever signedIn() says.
  • The root layout calls createSaveSync once and gives the result to the store (G2). Components reach it as useGame().sync.
  • A network failure sets offline and the next changed tries again.
  • A 401 sign_in sets sign-in and stops sending until the page loads signed in.
  • A 422 too_many, or the store answering full, sets full.
  • The stub shipped by contracts has state local, a null account, and does nothing. game-save replaces the body of createSaveSync; no caller changes.

Design

Levels and results

  • beats(seen, bar) compares calendar months with utcParts: seen.on's year and month against bar.on's, year first.
  • The day within the month never matters: a result on any day of June 2057 ties a bar of 1 June 2057.
  • paintWon(net, amount) is net >= amount.

Progress and banking

  • NEW_GAME is { v: 1, level: 1, banked: {}, firstWinAt: null }. Every function that starts from it copies it; nothing mutates it.
  • barOf(p) is { on: p.banked[p.level - 1].on } at levels 3 to 5, and null when that entry is missing.
  • barOf is null at levels 1 and 2.
  • roundComplete(p) is true when the level is 5 and banked[5] is present.
  • levelUp(p, banked) returns a new Progress and never mutates p.

Saved games

saves.ts imports values only by relative path, and only from modules that have no $lib value import, because e2e/helpers/game.ts loads it under Playwright. Its one value import is isValidId from ../ids/base58.

parseGameSave(json) returns a new GameSave holding only the known fields, or null. It returns null unless every rule holds:

  • json is a plain object with v equal to 1.
  • id is a string for which isValidId is true.
  • name is a string equal to its own trim, of 1 to SAVE_NAME_MAX code points.
  • nameIsDefault is a boolean.
  • savedAt is a string whose Date.parse is finite.
  • plan and policy are each a string or null. Their contents are not read.
  • progress is a plain object with v equal to 1 and level an integer from 1 to 5.
  • progress.firstWinAt is null or a string whose Date.parse is finite.
  • progress.banked is a plain object whose keys are exactly the levels from 2 up to level - 1, plus "5" optionally when level is 5.
  • Each banked value has on, an integer of at least 0; datasetVersion, a non-empty string; and at, a string whose Date.parse is finite.

Unknown fields at any depth are dropped from the result.

The store's storage

// under SAVES_KEY ('sfhousing:saves:v1'), most recently changed first
interface SavesIndex {
  v: 1;
  /** The id of the current game. */
  current: string;
  saves: SaveEntry[];
}
// under saveKey(id) ('sfhousing:save:<id>'): one GameSave as JSON
// under 'sfhousing:save:corrupt:<ISO time>': the raw text of a value that would not parse
  • The index is valid when it is a plain object with v 1, a string current, and saves an array of entries with distinct ids, each with a string id, a string name, a boolean nameIsDefault, a string savedAt and an integer level from 1 to 5.
  • Each entry repeats its save's id, name, nameIsDefault, savedAt and progress.level. Where an entry and its save differ, the save wins and the index is rewritten.
  • A GameSave's plan is the raw text stored under sfhousing:plan:v1, the whole LocalPlanRecord JSON, or null when the key is absent. policy is the same for sfhousing:sim:v2.
  • "Writing a game's records" means: setItem('sfhousing:plan:v1', save.plan), or removeItem when it is null; then the same for sfhousing:sim:v2 and save.policy.
  • A corrupt key that is already taken uses the ISO time one millisecond later, until free.

A game's played time is the latest of its save's savedAt and, for the current game only, the savedAt of each of the two records whose text parses as JSON with a string savedAt of finite Date.parse.

Constructing the store

The store reads storage once, when it is constructed, and keeps every saved game in memory. After that it writes through and never reads the index or a save again; it reads the two record keys whenever it copies or reports the current game.

  1. With storage null, or when any read of storage throws during construction (a getItem of the index, a save, a record key or a rebuilt key, or the key listing of step 4), the store is in memory mode: one game, at NEW_GAME, with a new id, the default new name, null plan and policy, and savedAt now. When the throw comes after construction has set or removed a key, the store first puts back every such key as in step 8, ignoring throws while it does, so storage holds what it held before construction. After that it writes nothing, ever, and a later load tries construction again. Reason: a storage that failed one read is not trusted for the rest, and treating the failed key as absent would rewrite the index without a game the player still has.
  2. With no value under SAVES_KEY, the store makes the first game: a new id, the default new name with nothing taken, nameIsDefault true, NEW_GAME, the raw text of sfhousing:plan:v1 and sfhousing:sim:v2 as plan and policy (null where absent), and savedAt now. It writes the save, then the index. It does not touch the record keys or sfhousing:sim:v1.
  3. When the first game's writes are refused, the store is in memory mode with that game, which keeps the plan and policy it read.
  4. With an index that is not valid, the store copies the raw index to a corrupt key and rebuilds: every key that starts with sfhousing:save: and not with sfhousing:save:corrupt: is read as a save. A value that parses and whose id equals the rest of its key after sfhousing:save: becomes an entry. Every other value, one that will not parse or whose id differs from its key's, is moved aside as in step 5. Because each key holds at most one save and its id is the key's, the entries' ids are distinct. Then the store makes a new game from the two record keys as in step 2, with the found games' names taken, and makes it current. The list may then hold more than MAX_SAVES games.
  5. With a valid index, the store reads saveKey(id) for each entry. A save that is absent, will not parse, or has a different id is left out of the list. Its raw text, when there is one, is copied to a corrupt key, and its key is removed.
  6. When the current game was left out in step 5, or current names no entry, the store makes a new game from the two record keys as in step 2 and makes it current.
  7. When anything was left out, added or corrected, the store rewrites the index.
  8. When a write in steps 4 to 7 is refused, the store puts back every key construction had already set or removed (ignoring throws while it does), so storage holds what it held before construction. The store is then in memory mode with the saved games it read and made, the current one as steps 4 to 6 chose it, its plan and policy as read. A later load tries construction again.
  • A level 1 game made from earlier record keys keeps them as its plan and policy: a plan or policy saved before the game existed becomes the first saved game, at level 1. The store gives it no other level and banks nothing for it; its policies run as its level unlocks their kinds (G3).
  • Two tabs share one storage. Each keeps its own memory, and the last write wins, as autosave does today.
  • The offer is null after construction.

Changing the store

A change is one sequence of writes. The store remembers the old value of every key it will set or remove. When a write throws, it puts back every key it had already written (ignoring throws while it does), keeps its memory as it was, calls no sync method, and answers { ok: false, reason: 'storage' }.

Before the current game stops being current through newGame, switchTo or remix, the store "copies it out": it writes the current game's save with plan and policy read from the two record keys and savedAt set to its played time. remove of the current game does not copy it out: the save is removed in the same change, and a delete never needs a write that storage could refuse for want of space.

Whenever a change writes the two record keys (a game that becomes current, and adopt of the current game's id) and sfhousing:sim:v1 holds a value, the store removes that key in the same change. When sfhousing:sim:v2 was absent before the change, it first copies the v1 text to sfhousing:sim:corrupt:<ISO time>. Without this, opening /sim would carry the old schema 3 policy into every new game.

Memory mode follows the same rules, except:

  • newGame, switchTo of another id, remix, rekey, remove and adopt answer storage and change nothing.
  • won, setOffer, levelUp, touched and rename change memory and call the sync as above, and write nothing.

Reading the store

  • progress, allowed, currentId, offer and saves are reactive ($state or $derived), and replaced, never mutated, on each change.
  • sync is the SaveSync given to the constructor, the same object for the store's life.
  • saves is one SaveEntry per saved game, recomputed after construction and after each change.
  • saves is ordered by savedAt, latest first, with the current game's played time in place of its savedAt. Equal times order by id.
  • read(id) of an id not in the list is null.
  • read(id) of another game is a deep copy of its save as stored.
  • read(id) of the current game is its save with plan and policy read from the two record keys now, and savedAt its played time. When reading a record key throws, the stored copy is used.

The open game, and providing the store

  • openGame() returns a new store in memory mode with one game named "Game" at { v: 1, level: 5, banked: {}, firstWinAt: null }, allowed equal to ALL_ALLOWED, open true, and a do-nothing sync whose state is 'local' and whose account is null.
  • open is true only for a store made by openGame(), and false for every store made with new GameStore. It never changes during a store's life.
  • While open is true no page shows a game part. Pages read open; none compares allowed with ALL_ALLOWED.
  • Every transition on the open game refuses as memory mode does: newGame, switchTo of another id, remix, rekey, remove and adopt answer storage.
  • won, setOffer, levelUp, touched and rename work in memory. levelUp() with an offer completes the round, since the open game is at level 5.
  • openGame uses a constructor path private to the module; the public constructor always gives a level from storage or NEW_GAME.
  • provideGame(store) sets the store in Svelte context under a private key.
  • useGame() returns that store. Outside a provider it returns a new openGame() for each call.

The root layout's store script

This unit writes the part of src/routes/+layout.svelte's script that makes and provides the store. The rest of the layout is unchanged in this build: SiteHeader reads the game itself with useGame(), so no other unit writes the layout.

<script lang="ts">

  import { browser } from '$app/environment';
  import { e2eOpen } from '$lib/game/e2e';
  import { createSaveSync } from '$lib/game/save-sync.svelte';

      storage,

  • Under the e2e seam (e2eOpen true) the layout provides openGame() and makes no sync.
  • createSaveSync is called at most once per document, and sync.attach(store) once; the root layout is never remounted by a client navigation. What the sync does on attach is game-save's.
  • The layout's existing onMount is unchanged.

The rule every unit relies on, until mounted:

  • On the server and in the first client render, nothing game-specific shows. The server's store is the open game and the browser's may be at any level, so the two renders would otherwise differ.
  • A component that renders markup depending on the game (the level, the bar, an offer, the saved games, a lock, the locked page, a game-only control, the win card) keeps its own mounted flag, set true in its onMount, and renders that markup only while the flag is true.   • Scripts, effects and onMount may read the store at any time in the browser: it is the real one from the layout's init.
  • WinCard and LevelPanel are mounted only by components that follow this rule, so they keep no flag of their own.

Rename, in place:

  • "Rename" replaces the row's name with a text field labelled "Name" (aria-label), holding the name, with maxlength 60, its text selected and focused. The row's two buttons hide while it is open.
  • Enter, or focus leaving the field, calls game.rename(id, value) and closes the field. An empty value leaves the name as it was, because rename ignores it.
  • Escape closes the field without renaming, and stops the event so the pop-over stays open.
  • After the field closes, focus returns to the row's "Rename" button.

Delete, asked once:

  • "Delete" replaces the row's buttons with the line "Delete {name}?" and two buttons: "Delete" (BUTTON_PRIMARY) and "Cancel" (BUTTON). Focus moves to "Cancel".
  • "Cancel", or Escape inside the row, puts the row back, stops the event, and returns focus to the row's "Delete" button.
  • The confirming "Delete" calls game.remove(id).
  • For the current game, on ok, the panel loads the new current game's page.
  • For another game, on ok, the row goes and focus moves to "New game".
  • Opening rename or delete on one row closes any other row's rename or delete first, without renaming or deleting.

The open game:

  • Under a store whose open is true the panel renders nothing. The header shows no level cell there, so it is never opened.

Errors:
