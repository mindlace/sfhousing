Shared pipeline cache

One cache per machine for the pipeline's point-in-time downloads, and a boxes that skips work it has already done.

Why

The hour of compute is boxes (about 54 minutes, single-threaded). Behind it is the LiDAR data it reads, which takes about 68 minutes to fetch. Both are wasted on most branches, for two reasons:

  • The cache lives in each worktree. pipeline/.cache sits inside each worktree, so every new worktree starts empty. One worktree, building-steps, holds 70 GB of it: 59 GB of EPT, 7.6 GB of lidar-work and 3 GB of raw.
  • boxes never checks for earlier work. It normalises and rebuilds in full even when its code, config and inputs are unchanged.

The files in the cache are point-in-time references and content-addressed: raw/<sha256>, and the boxes artifact's upstreamVersion hashes its code, config and inputs. One shared copy is therefore safe.

Goals and non-goals

  • Goal: a new worktree builds without downloading anything again, as long as this machine has fetched it once.
  • Goal: boxes finishes in seconds when it has already been run for its exact code, config and inputs. It runs in full only when one of those changed.
  • Goal: the 70 GB already on disk is moved into the shared cache, not fetched again.
  • Non-goal: caching the stages inside build (about 4.5 minutes) or changing how the dataset version is computed.
  • Non-goal: fetching cache misses from R2, or sharing the cache between machines or with CI.
  • Non-goal: making boxes itself faster.
  • Anti-goal: a cache hit that gives a different dataset version or different bytes than a cold run. A skip must restore exactly the lock entry a full run would write.

Approaches

Decision The owner picked A.
  • A. A shared local cache, and boxes skips work it has already done (picked). This removes the hour on every branch whose boxes inputs are unchanged, at the cost of some path plumbing and one index.
  • B. A, plus a fallback to R2 on a cache miss. This helps a second machine or CI, but adds upload logic and storage. Deferred until a second machine needs it.
  • C. A, plus caching each build stage separately. This saves at most about 4 minutes and makes the version scheme harder to reason about. Rejected.

Design

Where the cache lives

The pipeline resolves its cache root in one function, cacheRoot():

  1. SFH_CACHE_DIR, if it is set, for example to point at an external drive.
  2. Otherwise $XDG_CACHE_HOME/sfhousing.
  3. Otherwise ~/.cache/sfhousing.

Every path that is hard-coded today derives from cacheRoot(). These include pipeline/cli.ts:27, steps/fetch.ts:21, sources/lidar.ts:36 and scripts/data-transit.ts:31.

The code hash keeps excluding pipeline/.cache. The shared root lies outside the repo, so nothing it holds can affect the dataset version.

Safe writes from several worktrees

  • Files in the shared cache are written to a temp name in the same directory, then renamed into place. A reader never sees a half-written file.
  • A file whose sha256 name is already present is not written again.
  • boxes holds an exclusive lock file per key (boxes-index/<key>.lock) while it runs. A second run for the same key waits for the first, then takes the skip.

The skip in boxes

  1. After verifying the raw files, boxes computes the key from its inputs. The key is the full upstreamVersion (code, config and input hashes) that a full run would write.
  2. If boxes-index/<key>.json exists and every file it names is present in raw/ with the right sha256, boxes writes that stored lock entry into sources.lock.json. It prints "boxes: reused <key>" and exits 0.
  3. Otherwise it runs in full, as it does today. When it finishes, it writes boxes-index/<key>.json with the exact building-boxes lock entry it put in the lock.
  4. --force skips the check and runs in full.

A reused entry is byte-for-byte the one a full run with the same key wrote. The lock, and so the dataset version, comes out the same either way. If the entry's retrievedAt stays as the original run's date, the version's date stays stable as well.

Moving the existing caches

  • A new command, npm run pipeline -- cache import <dir>, moves the shared directories of an old pipeline/.cache into the shared cache.
  • On the same volume it renames rather than copies. It checks the sha256 of every raw/ file it moves, skips files the shared cache already has, and leaves the per-worktree directories where they are.
  • When the old directory holds a building-boxes artifact in raw/, the command also writes its boxes-index entry. The 54 minutes already spent then count as earlier work.
  • Any pipeline command that finds a local pipeline/.cache/raw, ept or lidar-work prints one line naming the import command.
  • The builder runs the import once on this machine for every worktree that has a cache, starting with building-steps.

Left to the builder

  • The exact contents of the boxes-index file, as long as it holds the full lock entry and the list of sha256 files it depends on.
  • How fixture builds and pipeline tests point at a temp cache root, so tests never touch the developer's shared cache.
  • Updating docs/dev/pipeline.md and docs/dev/building-boxes.md: the cache location, SFH_CACHE_DIR, the skip, --force and cache import.
Note These calls were mine, not the owner's: the default location ~/.cache/sfhousing; keeping derived/, review/ and lidar-venv/ in each worktree; the lock file per key; and the import being a command rather than an automatic move.
