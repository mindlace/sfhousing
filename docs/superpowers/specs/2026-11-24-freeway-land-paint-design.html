Freeway land in Paint

Paint refuses a lot on the freeway-land list while its freeway stands, and can open it once a plan removes that freeway.

Why

The owner saw Paint draw new buildings straight over the Central Freeway between Market and Duboce (lots 3502112, 3513071, 3513074 and their neighbours). These lots are on the freeway-land list (pipeline/enrichment/freeway-land.json). That list is checked before the road-like rule and skips it on purpose, because freeway land, unlike a road lot, has a future as housing once its freeway comes down (each segment's removedBy).

The scenario step zeroes freeway land in parcels.bin, so /sim never builds there. The chunk records (60_attributes.sql) leave eligible=1 on all 559 catalog lots, and Paint's applyOp (src/lib/plan/resolve.ts) checks only rec.eligible. Paint therefore counts and draws about 32.8k homes of room on land under standing freeways.

Goals and non-goals

  • Goal. Paint never builds on a catalog lot whose freeway stands. Because nothing removes a freeway today, that is all 559 lots.
  • Goal. The data says which removal frees each lot, so a later unlock that brings back freeway removal (the incremental game's rebuilt less cars) opens the lots without a new dataset format.
  • Non-goal. A freeway-removal control in Paint, or any change to the plan schema. The set of removed freeways is an input that is empty until that unlock.
  • Non-goal. Changing the road-like rule, its thresholds or road-lots.json. Freeway land stays on its own path.
  • Anti-goal. Making catalog lots ineligible in the chunk record. That would close them permanently and lose the route to freed land.

Approaches

  • A. Chunk eligible=0 for catalog land. A one-line SQL change. Paint would match /sim, but freed freeway land could never be painted.
  • B. A per-lot freeway field in the chunk, and Paint gates on it. A chunk column and client check. It keeps the lots open to a future removal. Picked by the owner.

Design

Data

  • The chunk gains an optional sparse column fw, shaped like rl: [row, removedBy | null][], strictly increasing rows, absent when empty. The value is the catalog segment's removedBy, or null for a freeway that stays.
  • The decoded ParcelRecord gains an optional freeway field holding that value (present only on catalog lots).
  • eligible is unchanged. The decoder rejects an fw row that is also underwater or road-like, since the sets are disjoint.
  • A build check confirms the fw rows match the catalog exactly (every catalog lot in a chunk, with its segment's removedBy, and nothing else).

Paint

  • The resolver takes the set of removed freeways (removedBy keys), empty by default. A lot with freeway set counts as ineligible unless its value is non-null and in that set. It is counted in coverage.ineligible like other unbuildable land.
  • The headline "Room for N homes", the Level 1 bar and the map's built boxes follow from the resolver, so they drop the freeway land with no change of their own.
  • A dataset without fw (older published plans) resolves exactly as before.

Dataset

This changes the dataset version. The branch regenerates the fixture, builds the live dataset, runs scripts/level2-check.ts on it, and uploads before signoff (docs/dev/pipeline.md, "Finishing a branch that changes the dataset"). Docs: pipeline.md "Freeway land" (drop "the chunk records are unchanged"), data-serving.md or the chunk's doc for fw, and game.md if it states Level 1's room.

Left to the builder

  • How the removed set reaches the resolver (a parameter on resolvePlan/applyOp defaulting to empty).
  • Whether Level 1's goal is still reachable on the live dataset with the room removed; if not, stop and report before changing the goal.
