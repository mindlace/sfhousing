# `finance-levers`: the funding documents and their compile path

Package: `sim-financing` ([design](../design/2026-11-09-1911-sim-financing.md), approved 2026-11-09 and amended the same day; [evidence digest](../research/2026-11-09-financing-evidence.md)). This spec decides the behaviour of rows F7, F15, F16 and F17 and builds against F1, F4, F5, F6, F8, F9 and F12. It runs in step 4 of the design's dependency order, after `finance-engine` and after `finance-score` (both edit `scenario-host.ts`, so they run in sequence), and ships in Release 2. It follows the design as amended at reconciliation (OD-F10, rows F5, F7 to F9, F12, F15 to F17).

Terms used throughout:

- **Lever document**: `SimLevers` (`src/lib/sim/levers/types.ts:49-58`), what the worker runs.
- **Policy**: `SimPolicy` (`src/lib/sim-page/policy.ts:57-66`), what the page edits and stores.
- **Stored document**: `SimDoc` (`src/lib/sim-page/sim-doc.ts:40-46`), a policy plus its dataset version and title, as autosaved, published and remixed.
- **Baseline**: the dataset's `Calibration.baselineFunding` (F12), as `buildSimInput` puts it on the base input's `finance` (F9).
- **Added**: the user's own pools and programmes (`FinanceLevers.pools`, `.programmes`).
- **`asOf`**: the calibration's start day (`src/lib/timelapse/types.ts:74`); the simulation's first day.

## 3. Global constraints

- **Evidence hierarchy.** Every number the simulation uses carries a `Provenance` with its tier and source, and the interface can show both. A value that cannot be sourced is `Unsourced` with a reason; what depends on it is unavailable, or runs on a value labelled "custom, not sourced" that the user typed. No tier 3 or 4 number is presented as data.
- **Money never decides alone.** A funded project needs a lot the user's zoning makes hostable and free, takes its size from the same draw, and passes through the same stage tables as every other project. Only a fully funded project is exempt from drop-out (R6).
- **Deterministic and paired.** A run is a pure function of (dataset, levers, seed). The plan and the twin share draws: no existing draw purpose changes, and a lot's draws do not depend on the order lots are processed in.
- **No public money means no change.** With `finance` absent, the engine's output is identical, schedule for schedule, to its output before `finance-engine` under the same `market`. A test asserts it. The site's default is not that case: it runs the baseline funding.
- **The engine is in the dataset version.** `src/lib/sim/scenario`, `src/lib/sim/levers`, `src/lib/scoreboard`, `src/lib/timelapse` and `pipeline/` are hashed into the dataset version. The finance model shapes published data too, because the `/lesscars` build step runs the baseline funding: `src/lib/sim/finance/` (the functions and constants of F4 and F8) is added to the hashed paths in `pipeline/lib/version.ts` by `market-baseline`, the first subsystem whose pipeline code imports it. Any change in a hashed path needs a dataset build and upload before signoff ([pipeline.md](../../dev/pipeline.md), "Finishing a branch that changes the dataset"). The page's code stays outside them, in `src/lib/sim-page/`.
- **Goldens change only at the two releases.** The pipeline fixture goldens, the lesscars fixture goldens and `fixture-0` are regenerated by their documented commands for Release 1 (`market-baseline` with `finance-data`) and for Release 2 (`finance-engine`, when the default starts running the baseline funding), each reviewed as an engine or data change. The fixture build emits a fixture market model and fixture baseline funding, labelled tier 4, so the page and its e2e tests have both. `golden-seed1.json` and `model-golden.json` (the mini city and the small calibration, which have no market model and no funding) never change: they are the lock on "no public money means no change".
- **Open data only.** The dataset stays ODbL and PDDL. New sources go in the lock and the attribution list.
- **Worker-safe and client-side.** The simulation stays in the worker; nothing here adds a server computation or a binding. Shared policies stay in the `plan` table's `body`: no migration.
- **Stored documents keep loading.** A schema-2 policy, saved locally or published, opens with default funding. It is never treated as corrupt.
- **Constant dollars.** Every dollar figure is in the dataset year's dollars except bond repayment, which is nominal and labelled.
- **House rules.** Svelte 5 runes, Tailwind 4, colocated Vitest with `expect.requireAssertions`, Playwright e2e, WCAG 2.2 AA, compact results with detail on demand, status apart from controls, Conventional Commits, work in worktrees, signoff as the only merge gate.

## 4. Behaviour

### 4.1 `FinanceLevers` validation (F7)

`parseFinanceLevers` uses the house guards (`record()` rejects unknown and missing keys, `types.ts:95-108`) and throws `LeverFormatError(path, message)` on the first bad field. Paths are relative to the lever document (`finance.pools[2].inflows[0].day`); under a policy the same error is re-pathed to `funding.…` by `viaLevers`, and under a stored document to `/policy/funding/…` by `pointer` (`sim-doc.ts:108-114`). Every bound below that is not a law, a source or another row is a numerical sanity bound (tier 4) that no sourced value comes near; each is named.

**Checks shared with the dataset.** The checks a baseline pool and an added pool have in common are written once, in `finance-data`'s `checkPool(v, path)`, exported from `src/lib/timelapse/model.ts` (`finance-data` section 4.6). `parseFinanceLevers` calls it after its own key check (`record()`) and before the added-only rules below. It throws `CalibrationFormatError` (`model.ts:468-476`), whose message is `<path>: <message>`, the same form as `LeverFormatError`'s (`types.ts:78-85`); `parseFinanceLevers` rethrows it as `new LeverFormatError(e.path, e.message.slice(e.path.length + 2))`, so the text reaches the user unchanged. The rows marked "shared" in the table are its checks; their messages are `finance-data`'s. `checkProgramme` is **not** used for added programmes: it validates the baseline and stays grants-only, with `minHomes` of at least 1 and a complete pool list. An added programme may be a loan or a guarantee (F6), may have `minHomes` 0, and may name a baseline pool the parser cannot see, so `parseFinanceLevers` applies the programme rows of the table itself, with `finance-model`'s `validateInstrument` (its section 4.4) for the instrument and the tiers sum tolerance of `model.ts` (10⁻⁹, `model.ts:478`, `541-545`).

- **A day** is an integer from 10957 (2000-01-01) to 47482 (`LAST_DAY`, 2100-01-01) in the house `Day` (`src/lib/timelapse/time.ts:7`). Tier 4 bound. The parser cannot see `asOf`, so it does not compare with it (section 4.6).
- **An id** matches `^[a-z0-9][a-z0-9-]{0,39}$` (F7, F12). **An added id** also starts `u-` (F7). Baseline ids never start `u-` (F12), so the parser can tell, without the dataset, whether a reference names an added or a baseline pool, and an added id can never equal a baseline id.
- **Terms.** Each typed term is checked by calling `resolveTerms` with that key alone, inside `try`; a `RangeError` becomes `LeverFormatError('finance.terms.<key>', e.message)`. The ranges are `finance-model`'s input bounds, not evidence, and carry no tier; this spec does not copy them into code. A typed term is kept even when it equals the sourced value: what the user typed is labelled "custom, not sourced" (F7).
- **A term an instrument needs** (F8, `missingTerms`) is **not** a parse rule. `MARKET_TERMS` is code, and a later release may un-source a term; a stored policy must not turn corrupt when it does (global constraint "Stored documents keep loading"). Missing terms are handled where they matter: dropped on load with a report entry (section 4.5), refused at publish (section 4.3), and guarded in `buildFinance` (section 4.4).
- **Bounds and their tier**: dollars up to $100 billion (ten times the Charter's general-obligation limit, about $10.6 billion, BLA 2026 p. 104, verified), bank leverage up to 10, 80-character labels: tier 4 sanity bounds. A pool's debt rate (above 0, at most 0.25) and term (1 to 40 years) are F5's, checked by `checkPool` with the same bounds `debtService` uses; `minHomes` (0 to 10,000) and every instrument bound are F6's, the instrument through `validateInstrument`. The 12, 12, 24 and 24 limits are F7's.
- `DEFAULT_LEVERS.finance` is a fresh `{ baselineScale: [], pools: [], programmes: [], terms: {} }`; `DEFAULT_POLICY.funding` is a separate fresh copy, so no caller can mutate one through the other.

**Size.** At the limits a `FinanceLevers` serialises to about 25 KB (estimate: 12 pools of 12 yearly inflows at about 90 bytes each, about 13 KB; 24 programmes at about 330 bytes, about 8 KB; 24 scale entries at about 50 bytes; five terms; tier 4 arithmetic, checked by a test on `maxFunding()`, section 6, which asserts under 32,768 bytes). That fits beside strokes inside the existing `MAX_PLAN_BYTES` of 262,144 (`src/lib/plan/constants.ts:8`), which `simDocProblems` already checks on the whole canonical document (`sim-doc.ts:95-96`). The limits are not changed; a policy whose strokes and funding together pass the cap gets the existing `too-large` error and "Autosave off" path.

**Parsing.** `parseSimDoc(text, mode)` (`sim-doc.ts:121-162`):

3. 6. Publishing a schema-2 policy after it has been upgraded produces a new row: the canonical body differs, so the hash dedupe (`publish.ts:98-102`) does not find the old one. The old row and its link are untouched.

**Knowing that a document was upgraded.** `schemaOfText(text)` returns the integer `schema` of the JSON text, or null. On each path the result's schema is compared with the text's:

The handoff branch does the same with the handoff text.

The page passes it to `SimRoute` and `SimPage` as a new prop `upgradedFrom`, which `SimPage` puts into the `restoreSimDoc` call that builds `opened` (`SimPage.svelte:174-180`).
- **Remix.** `/s/<id>` remixes `SIM_CODEC.publishable(data.doc)`, already schema 3, so the local copy is schema 3. The hand-off state gains `upgradedFrom: data.upgradedFrom` (`src/routes/s/[id]/+page.svelte:41`, `src/app.d.ts:12`), and `SimPage.restore()` passes `r.upgradedFrom ?? remix?.upgradedFrom` to `restoreSimDoc`.

### 4.4 `applyLevers`, the plan and the twin (F17)

**`bare()`** (`apply.ts:44-48`) keeps stripping only `newProjects` and `inFlightScale`. `market` and `finance` pass through `applyPolicies` (it spreads the input, `policy.ts:44`) and `bare()`. A test asserts both survive `baseZoning` and the timer ops by identity.

**`planOf`** (`apply.ts:51-68`) sets `finance: buildFinance(base.finance, levers.finance, base.asOf)` on the returned plan, after the existing fields.

**`buildFinance(base, f, asOf)`**:

1. **No baseline finance** (`base` undefined: the dataset lacks `baselineFunding` or `market`, so `buildSimInput` set none, F9). Return undefined, whatever `f` holds. The funding is kept in the policy but not used, and the loader reports it (`unusable`, section 4.5) for `funding-ui`'s notice. Reason: without a market model there is no slope, so no programme can be priced (F2); refusing the levers instead would leave a policy from a newer dataset unable to run on an older one.
2. **Empty `f`** (no scale entry, no added pool or programme, and no typed term): return `base` itself (the same object), so a run with no funding changes has an input identical to the twin's baseline, and the memoised precompute is shared. This is exact: `base.terms` is `resolveTerms(MARKET_TERMS)` (F9), which equals `resolveTerms(MARKET_TERMS, {})`.
3. **The id check** (F7's "against the baseline"), in this order, throwing `LeverFormatError` with these paths and messages:
   - `finance.baselineScale[i].pool`: `no baseline pool <id> in this data`;
   - `finance.programmes[i].pool` (not starting `u-`): `no baseline pool <id> in this data`.
     Added ids start `u-` and baseline ids never do (F7, F12), so no added id can collide with a baseline id and there is no collision check.
4. **Terms.** `terms = resolveTerms(MARKET_TERMS, f.terms)` (F17). Then every programme, baseline and added, whose `missingTerms(instrument, terms)` is non-empty throws `LeverFormatError('finance.programmes[<i>].instrument', '<instrument kind> needs <key>, which is not sourced')` (for a baseline programme the path names `base.programmes[<i>]`; baseline programmes are grants, F12, and need no term). A guard: the page drops such programmes on load and never sends one.
5. **Scale the baseline pools.** For a baseline pool with no scale entry, the pool object is kept as it is. For one with entries, `scaleAt(d)` is the `scale` of the latest of its entries with `from ≤ d`, or 1 when none (F7). The pool's entries cut time into **runs**: run 0 from `asOf` to the day before the first entry, then one run from each entry's `from` to the day before the next, the last run open. Arrivals are always taken from `inflowArrivals(inflow, lo, hi)` (F5, `finance-engine`), called with a run's window as `lo` and `hi` (`lo` never below `asOf`; `hi` the run's last day, or `LAST_DAY` for the open run), so the plan receives exactly the arrivals the engine would and none before `asOf`. Then:
   - **A capped pool.** A `once` inflow becomes a `once` inflow on its arrival day of `Math.round(dollars × scaleAt(day))` dollars, dropped when it has no arrival or comes to 0. A `yearly` inflow becomes, for each bounded run at a scale above 0, one `once` inflow per arrival of `Math.round(dollarsPerYear × scale)` dollars; and for the open run at a scale above 0, a `yearly` inflow `{ from: a, to: inflow.to, dollarsPerYear: Math.round(dollarsPerYear × scale) }`, where `a` is the run's first arrival that falls on the inflow's own month and day, with any arrival of the run before `a` as a `once` inflow. Reason: a yearly inflow first due on 29 February arrives on 28 February in common years (F5); restarting it from a 28 February would move its leap-year arrivals by a day, so it restarts only on a true anniversary. Arrivals that come to 0 dollars are dropped. The new inflows are in day order.
   - **An uncapped pool** has no inflows (F5); a scale above 0 leaves it on (F7).
   - **Off spans.** For every baseline pool, capped or uncapped, each maximal stretch of entries at scale 0 gives one `off` span `{ pool, from, to }`: `from` is the first such entry's `from`, `to` the day before the next entry above 0, or null when there is none (F7, F9 `off`, `to` inclusive). Spans are not clipped at `asOf`: a span that starts earlier is simply in force from the first simulated day. A capped pool's arrivals inside a span are already 0 and dropped, so nothing arrives while it is off and what it holds stays unspent; the engine takes its programmes out of every bundle on those days (F9 (b)). Programme ids are never split or renamed.
6. **Concatenate**: pools are the baseline's in dataset order, then the added ones in document order; programmes likewise (added programmes are copied as they are, including those on baseline pools, which F7 allows); `off` is `base.off` (empty, F9), then the new spans by baseline pool order and then by `from`. `slope` is `base.slope`; `terms` is step 4's. Added pools are passed as written: an added inflow dated before `asOf` is never received because the engine's `inflowArrivals` clips it (F5, `finance-engine` section 4.3), the same function and the same rule as step 5. The result is a new object; `base` is never mutated.

**The twin.** `twinInput` (`apply.ts:78-97`) is unchanged in form. Its `'preFzp'` twin is `bare(applyPolicies([baseZoning], base))`, which carries `base.market` and `base.finance`; its `'fzp'` twin is `planOf(base, ctx, DEFAULT_LEVERS, r)`, whose empty `finance` returns `base.finance` by identity (step 2). So both twins run the unscaled baseline on the sourced terms, with no `off` span, under the same market, as F9 and F17 require, and the memo key stays (base, ctx, compare): the twin depends on the levers only through `compare`. Typed terms reach the plan only.

**`compare`.** `compileLevers` keeps `compare: isDefaultPolicy(p) ? 'preFzp' : 'fzp'` (`policy.ts:558`). `isDefaultPolicy` stays a canonical-JSON compare of the whole policy with the timing snapshot stripped (`policy.ts:123-126`); since `funding` is part of the policy, any scale entry, added pool, added programme or typed term makes the policy non-default, so a funding-only policy is compared with FZP as written on the baseline funding (F15). A typed term alone changes the plan (for example `lossOnExit`, which the engine applies to the baseline's grants too, F9 (h)), so it is rightly not default. Publish refuses the default policy as today (`empty_plan`) and accepts a funding-only one.

**`compileLevers`** adds `finance: structuredClone(p.funding)` (a deep copy, as `protect` is copied today). It does not reconcile; reconciliation happens on load (section 4.5) and the editor only offers pools the dataset has.

**`LeverInputs`, `LeversResponse` and `references`** are unchanged.

**The worker.** `initScenario` and `setLevers` parse with `parseSimLevers` as today; a schema-2 or malformed `finance` is a `bad-request` with `levers <path>: <message>` (`load.ts:78-85`). The baseline check runs where the baseline is known: `applyLevers` in `leverStep` (`scenario-host.ts:908`). `leverStep` wraps that call; on a `LeverFormatError` it posts `{ type: 'error', rev: p.rev, code: 'bad-request', message: 'levers ' + e.message }`, sets `lw.pending = null`, and leaves `w.loaded`, `w.run` and the band as they were, so the previous revision stays in force; a session whose first revision fails runs nothing until the next `setLevers`. Any other error still ends the session as `internal` (`scenario-host.ts:753-757`). The client already ends a revision on an error carrying its own rev (`scenario-client.ts:459-466`). The page never sends such levers (it reconciles on load and offers only the dataset's pools), so this path is a guard, tested in the host.

### 4.5 Reconciling funding on load, and the loader's report (F15)

**The report.** F15 leaves its shape to this spec. It is fixed here, for `funding-ui` to consume (`src/lib/sim-page/funding-reconcile.ts`):

```ts
export interface FundingLoadReport {
  /** 2 when this load upgraded a schema-2 document (it now carries DEFAULT_POLICY.funding). */
  upgradedFrom: 2 | null;
  /** baselineScale entries removed because the data has no such baseline pool, in document order. */
  droppedScales: { pool: string; from: Day }[];
  /** Programmes removed, in document order. */
  droppedProgrammes: {
    id: string;
    label: string;
    pool: string;
    /** 'pool': names a baseline pool the data lacks. 'term': needs a market term that is
     *  neither sourced nor typed (F8). */
    reason: 'pool' | 'term';
    /** The first missing term, for reason 'term'; null otherwise. */
    term: TermKey | null;
  }[];
  /** The data cannot run money (no `market` or no `baselineFunding`) and the funding left after
   *  the drops is not DEFAULT_POLICY.funding: it is kept but not used (section 4.4 step 1). */
  unusable: boolean;
}
```

`restoreSimDoc(r, cal, remixFrom)` (`sim-session.ts:46-79`) returns `{ doc, notices, funding: FundingLoadReport }`. With `cal` null, reconciliation is skipped as today (`sim-session.ts:55`) and the report is `{ upgradedFrom, droppedScales: [], droppedProgrammes: [], unusable: false }`. `restoreSimDoc` adds no funding notice: `funding-ui` turns the report into its notices (`funding-added` from `upgradedFrom`, `funding-dropped` from the two lists, `funding-off` from `unusable`; `funding-ui` section 4.15), owns their text, and places them in the notice order.

**`reconcileFunding(f, cal)`** runs when `cal` is not null, after the schema upgrade and beside `reconcileTiming`. It never rejects a document and returns the same `funding` object when nothing changes, so a reload does not nag (the house rule, `reconcile.ts:6-7`). The data's baseline pools are `cal.baselineFunding?.pools ?? []`.

- A `baselineScale` entry naming a pool that is not among them is removed and listed in `droppedScales` (F15).
- A programme whose `pool` does not start `u-` and is not among them is removed, `reason: 'pool'` (F15). A programme on an added pool is never removed for its pool.
- A programme whose instrument needs a term that `resolveTerms(MARKET_TERMS, f.terms)` leaves null is removed, `reason: 'term'`, `term` the first of `missingTerms` (F8: such an instrument "cannot be compiled"). This needs no calibration, but runs here so that one report carries every drop.
- `unusable` is true when `cal.market` or `cal.baselineFunding` is absent and the reconciled funding differs from `DEFAULT_POLICY.funding` (canonical JSON). Added pools, their programmes and typed terms are kept.

On `/sim` the reconciled document is what the autosave writes next; on `/s/<id>` the stored row is never changed.

### 4.6 Dated values and a dataset that moves forward

Days in a policy are absolute and are never rewritten when the dataset's `asOf` moves. The rules:

- Money dated before `asOf` never arrives (F5; section 4.4 step 5 for scaled baseline pools, the engine's `inflowArrivals` for every other pool). Reason: the simulation starts at `asOf`; money before it is history, and history is what the dataset's records hold. Shifting the user's dates would change what they wrote.
- A programme with `from` before `asOf` is active from `asOf`; one whose `to` is before `asOf` is never active (`finance-engine` section 4.3).
- A scale entry with `from` before `asOf` applies from `asOf` (the latest entry at or before a day applies); an `off` span that starts before `asOf` is in force from `asOf`.
- No notice: the document did not change. Instead `pastItems(f, asOf)` returns `{ pools, programmes, inflows }`: `pools`, the ids of added pools none of whose inflows has an arrival on or after `asOf` (`inflowArrivals(inflow, asOf, LAST_DAY)` empty for each); `programmes`, the ids of added programmes whose `to` is before `asOf`; `inflows`, one `{ pool, index }` for each inflow of an added pool that has no arrival on or after `asOf` (`index` its position in that pool's `inflows`), each list in document order. `funding-ui` marks them "before the simulation starts: not counted".

### 4.7 Presets (F16)

`fundingPresets(cal)` (`src/lib/sim-page/funding-presets.ts`) builds the list against the page's calibration, because the presets refer to baseline pool ids and to `asOf`. Sources and their provenance live in `funding-sources.ts`, in the `Sourced`, `Unsourced` and `Evidence` shapes (`src/lib/sim/finance/evidence.ts`, re-exported from `timing-sources.ts`, F4). The module is page code, outside the dataset-version paths: presets shape only a policy, never published data.

**Availability.** A preset is offered (`available: true`) when all of these hold, else `available: false` with the first failing reason:

1. every number it presents as a fact is `Sourced`;
2. every market term its instruments read is `Sourced` in `MARKET_TERMS` (`missingTerms(inst, resolveTerms())` is empty, F8), so its grant-equivalent is sourced; reason `The market terms this loan is valued against are not sourced: <term>`. Presets never type a term;
3. an enacted measure it models is certified (OD-F3); reason as listed;
4. the calibration has baseline funding and a market model; reason `This data has no funding model.`

Numbers a preset leaves to the user (a bond's date, a loan's share of cost, a federal amount) are **starting values**: each has a stated default and tier, and `funding-ui` labels them as below. They do not block availability.

**Shared pieces.**

**What each preset does under the fill rule (OD-F10, F8).** `fundBundle` (F8) fills three tiers in order: `federal` pools, then `state` pools, then the City's (`bank`, `dedicatedTax`, `generalRevenue`, `goBond`, `cop`). Within each tier, its loans and guarantees count first, then its grants; each grant pays its full `share × uncoveredPerHome` when the tier's grants fit in what remains, and otherwise the same fraction of its share, so that the tier covers exactly what remains. The award (F9 (c)) leaves out programmes whose pools cannot pay and prices the rest again. The figures below use `finance-data`'s expected live baseline (its section 4.6, tier 1 and 2 arithmetic): grant shares `federal-tax-credits` 0.51433, `state` 0.137419, and six City pools summing to 0.348251 (`city-ocoh` 0.072329, `city-impact-fees` 0.051791, `city-redevelopment` 0.00893, `city-general-fund` 0.054619, `city-housing-trust-fund` 0.040778, `city-debt` 0.119804), together 1 of the $861,525 uncovered, so $300,027 a home is the City's part; the capped pools fully fund about 780 homes a year at the City pools (every City pool gives the same quotient) and about 1,267 at the state pool. The slope is about 1.75 (design OD-F11, tier 2). "Binds" means the line of waiting affordable applications is longer than that money serves. These are illustrations of the rule on the baseline (tier 2 arithmetic), not run results; the run decides.

- **`housing-bond`** (an added `goBond` grant, share 0.348251). The City tier's grants now sum to 0.696502 against 0.348251 remaining, so every City grant, the bond's included, pays half its share: the bond about $150,014 a home and each baseline City pool half its part. Every City source is relieved, and the City's cost per home stays $300,027, so homes rise by about the added dollars over that cost, $410,442,573 ÷ $300,027 ≈ 1,368 homes over the bond's life (tier 2). While both are paying, the City pools could fund about 1,560 homes a year, so the state's 1,267 a year becomes the bound and sets the pace. When the bond is spent it is left out and the baseline pools pay their full shares again. It does not change odds: the default affordable bundle is already certain.
- **`general-revenue`** (an added `generalRevenue` grant, share 0.348251, $36,700,000 a year). The same as the bond, from its first day: every City grant pays half its share while the added pool has money, and homes rise by about $36,700,000 ÷ $300,027 ≈ 122 a year (tier 2), to about 902 a year, below the state's 1,267, so the City still binds and all the added money is used.
- **`htf-2026`** (unavailable): as `general-revenue`, with its own amounts.
- **`revolving-fund`** (an added loan to `market` projects). Market projects have no baseline programme (F12), so the bundle is the loan alone, counted first. On prototype B ($736,700 cost, $217,000 uncovered; design section 2, tier 1) its grant-equivalent is 0.10 × 736,700 × (0.085 − 0.06) × 1.917 × 0.55 ≈ $1,942 a home (`MARKET_TERMS`: `constructionRate` 0.085, tier 3, and `constructionYears` 1.917, tier 2, `finance-model` section 4.3; `AVERAGE_DRAWN` 0.55, F8, ruling R11, tier 4 assumption); coverage about 0.009; odds shift 1.75 × 1,942 ÷ 736,700 ≈ 0.0046, about 0.5% more starts on a reached lot (tier 2 arithmetic). The pool still commits the whole principal, $73,670 a home, at the start (F9 (g)), so $100 million is out to about 1,357 homes at once. The grant tiers do not touch it.
- **`public-bank`** (an added loan to `affordable` projects). Loans count first: 0.10 × 954,127 × (0.085 − 0.0613) × 1.917 × 0.55 ≈ $2,384 a home (`AFFORDABLE.costPerHome` $954,127, tier 1; `AVERAGE_DRAWN` 0.55, F8, tier 4). The City tier then covers $297,643 in place of $300,027, so every City grant pays about 0.992 of its share, and the City pools stretch to about 780 × 300,027 ÷ 297,643 ≈ 786 homes a year while the bank lends (tier 2): a small gain, because a loan's saving is small. The bundle was already certain, so odds do not change. When the bank is short it is left out and the grants alone still cover the whole cost, so the award never waits for it.
- **`state-off`** (`off` span on `state`). From its day the state programme leaves every bundle. The City tier's grants then fit in what remains and pay their full shares, so affordable coverage is 1 − 0.137419 = 0.862581: funded affordable projects are no longer certain and start only by chance, at the affordable start's log-odds plus 1.75 × 0.862581 × 861,525 ÷ 954,127 ≈ 1.36 (F9 (a)). Waiting applications are re-made on that day; their coverage falls, so they lapse and are drawn again (F9 (b)). The state pool's balance stays unspent.
- **`state-double`** (state inflows × 2). This preset still buys no homes on the baseline, and the reason is the tiers. The state tier's one grant fits in what remains, so it pays its full share, 0.137419 of each home, and never more. The City tier must still cover the City's $300,027 a home from City money, which binds first (about 780 a year against the state's 1,267). Extra state money cannot pay the City's part, so it accumulates. It adds homes only beside money that makes the state the bound: added City money past about 1,267 a year, or `federal-support`. The preset's description says so.
- **`federal-support`** (an added `federal` grant, share 0.348251, $150,000,000 a year). The federal tier's grants, 0.51433 + 0.348251 = 0.862581, fit in what remains and pay in full; the state then pays its 0.137419, and nothing remains for the City tier, so every City grant is scaled down to 0 while the added pool has money. It funds about $150,000,000 ÷ $300,027 ≈ 500 homes a year without City money, on top of the City's 780, until the state's 1,267 a year binds (tier 2 arithmetic). This is the design's "the City's share of a home falls" (section 3). A smaller federal amount scales the City grants down by the same fraction rather than to 0.
- **`federal-credits-off`** (`off` span on the uncapped federal pool). The state and City grants fit and pay their full shares; affordable coverage falls to 1 − 0.51433 = 0.48567; funded affordable projects start only by chance, at a shift of about 1.75 × 0.48567 × 861,525 ÷ 954,127 ≈ 0.77; waiting applications lapse and are drawn again, as for `state-off`.

So these are `'custom'` from the start: every default date (`nextFiscal`, `nextCalendar`, `federal-support`'s year) and every `to: null`; `federal-support`'s amount; `revolving-fund`'s `costShare`, `rate` and `minHomes`; `public-bank`'s `costShare` and its inflow days; every `requiredReturn: null`. `FundingPreset.provenance` lists, in this table's order, one entry per distinct source above for that preset.

### 4.8 What changes on screen

Nothing this spec renders. The loader's report (section 4.5) feeds `funding-ui`'s notices, and everything else visible belongs to `funding-ui`.

## 5. Seams

- **Market scenarios and a market control (R7).** This spec adds nothing to `SimLevers` or `SimPolicy` for the market: the market is the world, not the policy. It keeps the seam open by passing `base.market` through `bare()`, `applyPolicies`, `planOf` and both twins unchanged (a test asserts identity). Typed `terms` are not dated, so a scenario that varies terms over time would need a new field. A later scenario control would be a new optional policy field in a later schema; the loader pattern of section 4.3 is the template.
- **The pipeline and drop-out (R1, R8).** Nothing here reaches pipeline rows: `Programme.reach` is a `ProjectKind`, and this spec adds no field that names a stage or a project. Nothing more.
- **A rent model (R4).** `tiers` are shares of homes by income tier only; no rent or price field is added. Nothing more.

## 7. Acceptance criteria

6. A scale or a programme naming an unknown baseline pool fails in `applyLevers` with `LeverFormatError`; the worker reports it as `bad-request` on its rev and keeps the previous revision (F7, F17).
7. Scaling follows the latest entry at or before each arrival; a scale of 0 on any baseline pool, capped or uncapped, gives an `off` span until the next entry above 0 and no arrival in it; no programme id is split or renamed (F7, F9 `off`, F17).
8. Every arrival in `plan.finance` comes from `inflowArrivals` (F5), none is before `asOf`, and `buildFinance` defines no arrival arithmetic of its own (F5; section 4.6).
9. `LeversResponse` is unchanged (F17).
10. `SimPolicy`, `SimDoc` and `SimLevers` are schema 3; `compileLevers` copies `funding` to `finance`; a funding-only policy compiles with `compare: 'fzp'` and can be published (F15).
11. Every stored schema-2 fixture opens on autosave, `/s/<id>` and Remix with default funding and `upgradedFrom: 2` in the report, and never as corrupt or 500 (F15; global constraint "Stored documents keep loading").
12. Publish writes schema 3 only and refuses schema 2 with 422 `unsupported_schema` (F15).
13. A baseline id the dataset lacks is dropped on load and listed in the report; a programme with a missing term is dropped and listed with its term; `FundingLoadReport` has exactly the shape of section 4.5 (F15).
14. The preset list is the table of section 4.7; every available preset's numbers carry a provenance with a tier, every unavailable one a reason, the tier 4 starting values are labelled "custom, not sourced", and preset ids are `u-<presetId>-<n>` (F16; global constraint "Evidence hierarchy").
