Sim log store: the plans after the core

Unit 4 of the sim message log is four plans, each merged with /sim working for a person on main and on staging. Plan 1 is written in full: 2026-11-15-sim-log-store-1.html. These are outlines of plans 2 to 4.

Why it is cut here

The four plans
PlanDeliversWhat a person sees after it merges
1. Store coreThe local log, the dataset rule, authoring, drafts, IndexedDB, LogStore and DocStore; the delete re-apply rule; the four log linesNothing changes
2. SyncRegistration, the socket client, tab claims, the server's resume bound, the account-deletion boundNothing changes on /sim; deleting an account in very many sims finishes in several requests
3. The page/sim on the store, the autosave import, the save state, the notices, the end-to-end tests/sim saves to the server from the first edit; undo survives a reload; the old autosave is imported
4. As-of readsA sim opens on its tip's own dataset (R54)No "running on a new dataset" notice on opening; the move happens at the first edit
  • The core (plan 1) is where correctness lives: re-applying, restores, history, persistence order. It is reviewable alone with Node tests and no page or socket in the way, and it is dead code until plan 3, so it cannot break /sim.
  • The socket and registration (plan 2) are the second risk: a protocol state machine, backoff, the two-tab rules and two server bounds that must merge before browser registration ships (sim-object.md and auth.md say so). They are testable in Node against fakes; the real socket is proved end to end in plan 3, where a page drives it.
  • The page switch (plan 3) is one plan because a half-switched /sim (store without socket, or socket without import) would lose a person's autosave or show "saved" when it is not. It needs 1 and 2.
  • R54 (plan 4) changes how the page loads data and runs the engine on an older dataset. It is separable: until it lands, plan 3 shows a sim on today's dataset with today's reconcile notices on opening (what /sim does now) and appends the move commit (R55, built in plan 1) at the first edit.

Plan 2: registration, the socket and tabs

Goal
A SimSync per open sim per tab that registers the sim, keeps one socket, resumes, sends pending commits one at a time and feeds LogStore.receive; tabs claim the pending commits of tabs that closed; the server bounds resumes and account deletion. No page change.
Needs from plan 1
LogStore's socket side (setServerDataset, receive, head, dropPending, subscribe, written, simId, pendingCount, stopped, local), open(simId, { claim }) and claim(owners), SimDb.setRegistered, test/commits.ts's FakeObject.

Tasks

  1. hello carries the server's dataset. {"type":"hello","build":…,"protocol":1,"dataset":"<version>"}, from the open header's datasetVersion (sim-object.ts:112); optional in ServerFrame, PROTOCOL stays 1. The browser calls LogStore.setServerDataset on it, before anything is sent (plan 1's head() is null until then, and its dataset rule needs it: plan 1, the dataset rule). A hello without it leaves the store unable to author on a sim on another dataset ('unknown-dataset').
  2. Bound resumes on the server. A resume answer stops after LIMITS.resumeBytes (8 MiB proposed) of stored bodies, its last frame {"type":"commits","commits":[…],"more":true}; the browser sends the next resume after the last seq it got. An object-wide resume budget (a byte bucket, 32 MiB burst, refilled at 4 MiB a second, proposed) refuses a resume limit with id: null when spent; the browser backs off. PROTOCOL stays 1 (the field is additive and the store is its only reader besides e2e/helpers/sim-socket.ts). Node tests in log-host.spec.ts, an e2e of a two-page resume in e2e/sim-object.spec.ts, sim-object.md.
  3. Bound account deletion. deleteAccount removes at most a fixed number of memberships per request (50 proposed) and answers whether more remain; the account route answers 202 { more: true } until the last pass tombstones the account; the account page repeats the request while it says more. auth.md, Deletion.
  4. Registration client. registerSim(fetchFn, simId): POST /api/sims with content-type: application/json and { simId } (no title: the default name, R42), mapped to ok, sign-in (401), taken (409), quota, retry (429, 500 with failed, session or no code, a network error) and bug (400 invalid_id, 415, 403). Single flight across tabs with the Web Lock sfh-register, so a signed-out first registration is never sent twice at once (auth.md). ok calls setRegistered.
  5. The socket machine. A pure SocketMachine (events in, actions out) and a thin SimSocket on the browser's WebSocket: open /api/sims/<id>/stream only after registration; on hello note the build; on access note write; send resume { after: tipSeq }; send the head only after the first commits frame of the resume answer and only while write; one append in flight; behind sends again once the tip moved past the refused parent; invalid calls dropPending; not-writer waits for access { write: true }; limit backs off; full stops sending; newer stops and asks for a reload; gone on a resume restarts from 0, on an append stops; a gap from receive sends resume. Reconnect after any close but 4410 with backoff from 1 s, doubling, capped at 30 s, ±20% jitter; a connect that has no hello in 10 s counts as a failed attempt. A text ping every 30 s while visible. Close codes as sim-object.md.
  6. Tabs. Each tab holds the Web Lock sfh-tab:<tabId> for its life. At open, and when a BroadcastChannel('sfh-sim') message says a tab closed (pagehide), a tab claims the pending records of owners whose lock is not held (navigator.locks.query()) with LogStore.open(simId, { claim }) or, mid-session, LogStore.claim(owners), which re-apply them after its own with new n. A tab whose record another took learns it from the write's lost and never sends it (plan 1). Without Web Locks a tab claims nothing it did not make, except at open, where it claims every owner (a duplicate costs a rate token, not the log).
  7. SimSync and the save state. Ties the store, registration, the socket and tabs; does nothing under dev (decision below). A pure saveState(input) for plan 3: saved (nothing pending: every commit the server confirmed counts as saved, with or without local storage), saving, device (pending stored, not connected; never while local is 'failed'), unsaved (local storage unavailable or failed and commits not yet confirmed: never saved on this device), sign-in (401), no-write (the socket lost write, below), stopped (the store's 'stale', 'unknown-dataset', 'future'; the socket's newer, full, gone).
  8. Losing write. Pending commits becoming a remix (R32, R53) waits for the sharing unit. Until then a socket that gets access { write: false }, or not-writer, keeps its pending commits stored and unsent and the save state says so. The sharing unit needs a way to re-home a sim's pending records to a new sim id in one IndexedDB transaction; this plan does not build it.
  9. Docs. sim-store.md (the sync side), sim-object.md (the resume bound), auth.md (deletion passes, registration's browser side).
  10. The socket's contract with the store (docs/dev/sim-store.md, The interfaces). setServerDataset on every hello; receive(simId, commits) for every commits frame, a confirmation included, with the id of the sim whose socket it came from (a frame for another sim, or one during open, is ignored as { kind: 'stale', why }); dropPending(id) on invalid (a refused move or alignment commit stops the store 'stale', so the page offers a reload); head() only when ready and never during open, asked again after each receive and each subscriber call, since a landed write tells the subscribers; one append in flight; claim and open(simId, { claim }) only for owners whose lock is free. LogStore.open rejects when the read fails and the store then stays not ready: plan 2 decides whether to retry.
  11. Opening the database. Pass onVersionChange to openSimDb: a newer build's tab closes this tab's connection and every later write rejects, so the store goes local: 'failed'. openSimDb answers null for no storage and for a version error (an older build's tab after a newer build upgraded the database), which look the same today; plan 2 or 3 tells them apart if the page is to say "reload".
  12. Known edges of the store, left as they are. The store's receive answers stale both for commits it already has and for a frame it ignored (the ignored case carries why); rename it when the first caller is written if that reads badly. A move discarded while a newer build's commits are held behind it deletes the move's record, so a held restore that targeted it is dropped as target-gone (reported) when the newer build retries: it needs two builds and a dataset release at once. Firefox has not run the IndexedDB suite.

Decisions it will make

  • npm run dev (carried item): under dev the page registers nothing and opens no socket; commits stay pending and the save state says saved on this device. Developers lose server sync, cross-tab confirmation and undo across devices in dev, and use npm run preview for those. Reason: Vite takes the upgrade and never answers (sim-object.md, Running it), and minting accounts from dev against a local D1 has no use.
  • The resume bound (carried item): Cloudflare's WebSocket API documents no bound on, or signal for, outgoing data queued by send() (Workers WebSockets: send is "Send a message to the other WebSocket in this WebSocket pair", and the only size limit stated is for received messages); there is no bufferedAmount to wait on. An object has 128 MB (spec, Constraints) and a sim up to 64 MiB, so two whole-sim resumes at once could exhaust it. Hence a per-request byte cap with demand from the browser, plus an object-wide budget. Plan 2 checks the workerd source for any send-side buffering limit before fixing the numbers.
  • Account deletion (carried item): bounded per request as above, because browser registration (plan 3) makes accounts in hundreds of sims likely.
  • One append in flight, not a window: a refusal then always names the head, and the sustained rate (2 a second) is the real limit, not round trips.
  • Two tabs (carried item): each sends only its own pending commits (plan 1, decision 22), so no commit is sent by two tabs at once and no tab re-applies another's; a closed tab's commits are claimed through the lock check, atomically in IndexedDB.
  • hello.build: a mismatch with the page's release keeps the tab working (the object accepts any build's commits it can fold) and tells plan 3 to offer a reload.
  • Whether the browser compares the tip hash after a resume (plan 1, decision 26).

Plan 3: /sim on the log

Goal
Replace PolicyStore and Autosave on /sim with LogStore and SimSync; import the old autosave; show the save state and the notices; prove it end to end.
Needs
Plan 1 (the store), plan 2 (sync, the save state, the dev rule).

Tasks

  1. The autosave import (R20). Pure importAutosave(storage, ds): sfhousing:sim:v2 if present, else sfhousing:sim:v1 opened with openSimDoc4; the result through checkRuleset (sim-log.md, Rules for callers); one system commit (sim.import, label "Imported") made with plan 1's LogStore.importContent(content, marker), which writes the commit and a marker compare-and-set in one transaction, so two tabs opening at once import once. The marker is the IndexedDB meta row import, { simId, v2SavedAt, v1SavedAt }. Both keys stay. An older open tab keeps writing its key; on a later open, a record newer than the marker's is imported again as a new system commit on the current sim, so its late edits are not lost. A default policy with no title imports nothing (no sim, I6). With local storage failed an import cannot record its marker (importContent answers 'imported' with none), so each page load would import the same autosave again: the plan decides what to do about it.
  2. The page on the store. SimPage opens the current sim (meta current) before TimelineMode mounts, as it opens the autosave today; the title is store.name (R6) and Publish uses it; align is reconcilePolicy4 with today's notices; settle() on focus leaving the inspector, on visibilitychange to hidden, on pagehide, in beforeNavigate and on the page's teardown (a draft open at close is committed in memory; its write is best effort); a source code per control. Inspector.svelte:50, InspectorHost.svelte and the page switch their store props from the class PolicyStore<SimPolicy4> to plan 1's structural DocStore. DocStore has no reset: SimPage stops calling PolicyStore.reset to load a document, and a load becomes LogStore.open (a sim) or importContent (an autosave or a shared text). The engine is fed as today: store.policy through PolicySync and the 250 ms debounce to TimelineClient.setPolicy (R37).
  3. The save state. In the header's status slot, apart from the controls: "Saved", "Saving…", "Saved on this device" (details on tap: offline, or a sign-in link for R60), and, when local storage is unavailable or failed, a state that never says "on this device" while commits wait ("Not saved yet", details: this browser cannot keep it; it saves once sent); once the server has confirmed them it reads "Saved". Announced politely when it changes, as SaveIndicator is.
  4. Notices. Dropped re-applied changes or commits (R19, with each DropReport's reason); a stale page ('stale': reload offered); an unknown server dataset ('unknown-dataset': reconnect to edit); a newer build's commit ('future') or newer (reload); one notice for each refusal the store sets: 'invalid', 'too-large', 'queue-full' (short notice, edits refused until some are sent) and 'stopped' (a draft that could only be settled once the store was stopped, so it went); full; gone; lost write (pending kept, not sent); a build mismatch (reload offered). Terse; details on tap.
  5. /s/<id> and Remix. The read-only view keeps an in-memory store (old links open unchanged, R36). Remix starts a new current sim whose first commit holds the shared document. Plan 1's store cannot do that in a browser that already has a current sim: a new sim's first write asks to become the current sim, and when one is already current the store adopts it (decision 28, right for two fresh tabs), so open(null) plus importContent would write the shared document into the person's existing sim; setMeta refuses the current-sim key, and current: false leaves the remix unreachable from /sim. This plan adds an operation that creates a new sim and makes it the current one in one write, replacing the pointer, designed so the two-fresh-tabs rule still holds, and Remix uses it. Until it lands the store cannot start a second sim in a browser that already has one.
  6. Test handle and end-to-end. window.__sfhSimStore (VITE_E2E): sim id once registered, tip seq, pending count, save state, socket state. Specs: edit, reload, undo back past the reload; offline (context.setOffline) edit, reload, reconnect, commits in order; two tabs editing in turn show one order; an invited editor's edit appears in the inviter's tab; an existing v2 and a v1 autosave are found on first open; a visitor who only looks sends no request to /api/sims. All wait on the handle, frames or responses.
  7. CSP in WebKit and Firefox (carried item). One spec that opens the sim socket under the real CSP, run once in Playwright's WebKit and Firefox (projects added to playwright.config.ts that match only that spec, so CI and signoff are unchanged). If either refuses connect-src 'self' for wss:, stop and ask the owner: a CSP change is an interface change. If the engines cannot run here, the plan names what is unverified and the owner's check (open /sim in Safari and Firefox, edit, and see "Saved").
  8. The browser check. It includes Firefox, which cannot be launched on the machine that built plan 1 ("Could not find profile folder"), so plan 1's IndexedDB suite (SFH_BROWSER=firefox npx vitest --run --project client src/lib/sim-store) has run only in Chromium and WebKit; a real quota error was not tried in any engine. The page also asks for persistent storage (navigator.storage.persist()) so that a device's pending commits are not evicted.
  9. Docs. sim-page.md, plan-sharing.md (the autosave retired on /sim, its keys kept), sim-store.md, auth.md.

Decisions it will make

  • What a person's work is at the moment this ships: the autosave is imported on first open, with nothing to press; the keys stay.
  • The exact save state copy and when each shows; what is logged versus shown.
  • The source code of each control.
  • What an out-of-date tab (its database connection closed by a newer version, or a version error at open) and a browser with failing storage (local: 'failed', or no database) see: the store still hands commits out to be sent and never says they are stored on the device.
  • Where settle() is called: on focus leaving, on hiding, on pagehide, in-app navigation and teardown. A draft open when the tab closes is committed in memory and its write is best effort; another tab's claim, a foreign commit or a withdrawn import can still split one drag into two commits.
  • How a draft on a numeric field interacts with the focus rule in each editor (stories steppers, band distances, route stage months, funding fields: all coalesced today).
  • Everything is persisted from the first edit with no text announcing it (owner decision); a visitor who only looks gets no account and sends nothing (R44, I6).
  • Behaviour that must not regress, each with a named test: every editor on /sim still edits (e2e/sim.spec.ts, sim-timeline.spec.ts, sim-funding.spec.ts); undo and redo still work and announce; the engine is fed as today; an existing autosave is found; / and /lesscars untouched; old /s/<id> links open (sim-share.spec.ts).

Plan 4: reading a sim on its own dataset

Goal
R54: /sim opens a sim on the dataset of its tip, not today's, with no reconcile and no "new dataset" notice on opening; the first edit moves it (R55 and the dataset rule, already built: only a page that knows it is current moves a sim) and the page then runs on today's dataset.
Needs
Plan 3.

Tasks

  1. Load the manifest and calibration of a given dataset version (every published version stays on R2, R56) and run the engine on it; the page holds "the dataset in use" as state, not as the layout's.
  2. Switch to today's dataset after the move commit, re-running the engine.
  3. Remove the open-time reconcile notices on /sim; keep the move's notices.
  4. e2e with a second fixture dataset: a sim made on fixture-0 opens on it after the current version changes; an edit moves it.
  5. Docs.

Decisions it will make

  • A sim whose dataset is older than MIN_SIM_DATASET, or whose data cannot load: open on today's with a move at the first edit, or say it cannot be shown.
  • Whether the editors are offered before the older dataset's data has loaded.
  • How it shares the loader with unit 5's share links (/s/<simId>/<n>), which need the same as-of read.
