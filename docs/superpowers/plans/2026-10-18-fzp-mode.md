# fzp-mode (`/fzp` timelapse page) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the read-only `/fzp` page: map plus time scrubber, time-aware scoreboard and chart, ghost-state legend, project card, "Where these numbers come from" dialog, reroll with the seed in the URL, the header mode links and the attribution changes.

**Architecture:** Pure TypeScript view logic in `src/lib/fzp/*.ts` (time, format, labels, seed, playback, score-view, chart, card, provenance, summary requests), unit-tested in the Vitest server project. Svelte 5 components in `src/lib/fzp/*.svelte` render that logic, with `FzpMode.svelte` composing `SimMap` and timelapse-sim's `ScenarioClient` (no `BrushEditor`). The route `src/routes/fzp/` loads the manifest and calibration; everything downstream of the worker reads only `TimelineScore` and `ProjectCard`.

**Tech Stack:** SvelteKit 2, Svelte 5 runes, Tailwind 4, Vitest (server + browser client projects), Playwright, fast-check, axe.

**Spec:** `docs/superpowers/specs/2026-10-16-fzp-mode-design.md` (authoritative; every copy string the plan cites by section is copied verbatim from there). Design: `docs/superpowers/design/2026-10-16-1903-fzp-timelapse.md`.

## Global Constraints

Copied verbatim from spec §3:

- **Evidence hierarchy** (above). No number reaches the simulation without a tier and a source. A tier-3 or tier-4 number is never presented as data.
- **Data quality** (reappraisal 1). Live sources are not assumed clean. Every pipeline rule that nulls, replaces, defaults or drops a source value is a registered T14 rule with a tier, a label and counts in every build. A replaced parcel value sets its `imputed` bit, and a changed record carries the rule's id in `quality`. A value a rule wrote is never presented as a record.
- **Determinism.** The same `datasetVersion` and seed always give the same future, on every machine. The representative seed is chosen deterministically: the run whose final `completedNet` is the median of the N band runs.
- **Honesty of numbers.** The mode is labelled a *simulation*. The scoreboard shows the shown run and the p10–p90 band. Pipeline and new-FZP units are separate lines. Actual completions since the RHNA period start are counted and labelled as actual. Units lost to dead projects are shown.
- **Time scrubbing performance.** At 60 fps on a 2022-era laptop with the whole city's timeline loaded, per-frame JS during scrub or playback is O(1) in project count. A reroll reaches a full new timeline (the shown run, to 2050) within 3 s off the main thread. The p10–p90 band may fill in progressively afterwards; the UI marks it as provisional until it is complete.
- **First paint.** `/fzp` must not require loading every parcel chunk. The whole-city score comes from `parcels.bin`, `projects.json` and `calibration.json`. Geometry streams with the viewport, as on `/`.
- **The editor is unchanged.** `/` and `/p/:id` behave exactly as before. FZP mode is additive. The one intended exception is the shared header, which gains the mode links ("Paint" / "Timelapse") and shortens the brand to "SF Housing" below 640 px so the links fit at 375 px.
- **Map budgets in FZP mode.** Two deck layers per cell are allowed for timeline cells: translucency needs them. This is an exception to map-view's one-layer-per-cell rule, so a `bench:map` timeline scenario must pass the same p95 frame bar. The existing-building catch-up stays within 2,000 feature-state changes per frame.
- **Accessibility.** WCAG 2.2 AA as in `docs/dev/accessibility.md`. The scrubber is a labelled slider: arrow keys step a month, Page Up/Down a year. Reduced motion stops autoplay, but scrubbing still works.

Project and run constraints (repo CLAUDE.md, conductor carry-forwards):

- 2-space indent, single quotes, no trailing commas, 100 columns. Conventional Commits. Vitest runs with `expect.requireAssertions`: every test calls `expect`.

## Review Focus

1. **Negative plan-effect values on the chart.** Early `planEffect` values are negative (spec §4.5 5a); a y axis fixed at 0 would draw them outside the plot. Expected: the y domain extends below 0 when any drawn series is negative (Task 2 test `chart domain extends below zero`).
2. **Crash while a card request is in flight.** `ScenarioClient` resolves pending summaries with `null`, which would read as "still loading for this area". Expected: "Details unavailable" (Task 9 test `pending request at crash shows Details unavailable`).
3. **Scrubbing back before a project's first stage with its card open.** Expected: the re-request answers with no `project` and the card reads "No project on this parcel at this date."; `cardStatus` returns `null` and never throws (Task 3 test `cardStatus is null before the first stage`; Task 9 FzpMode test `scrub back before the project shows No project`).
4. **Viewport crossing 768 px with the mobile sheet open.** Expected: the sheet closes, and the map inset returns to scrubber + scorebar (Task 7 test `sheet closes when the viewport widens`).
5. **Retry when the manifest or calibration reload fails again.** Expected: phase stays `failed` with Retry still offered; no `initScenario` is sent (Task 9 test `retry with a failing reload stays failed`).
