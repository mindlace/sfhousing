Sim log core plan

Unit 1 of the sim message log: commit and change types, parsers, fold, diff, re-apply, the undo and redo derivation, the hash chain and the shape registry at revision 1. Pure TypeScript, no I/O.

For agentic workers REQUIRED SUB-SKILL: use superpowers:subagent-driven-development to implement this plan task by task. Steps are checklist items; progress is kept in the workspace ledger, not in the plan.

Overview

Goal
One pure module, src/lib/sim-log/, that the sim object (unit 2) and the browser log store (unit 4) both use to parse commits, fold a log to a ruleset, check it, diff two rulesets, re-apply pending changes on a new tip, derive undo and redo targets, and chain commit hashes.
Architecture
A ruleset ({ name, policy: SimPolicy4, datasetVersion }) is flattened into keyed items of 16 shapes (the sim, a policy and a span per where row, the painted stroke). A change acts on one item. LogState holds the items of a folded log, applies a commit atomically (upgrading each change from the commit's shape revision), and assembles the SimPolicy4. diff flattens two rulesets and emits the changes between them, list order included. Undo and redo are a two-stack replay over the log's kinds. Hashes are SHA-256 over canonical text.
Tech Stack
TypeScript, Vitest (project server, Node environment), fast-check 4 (already a dev dependency, package.json:98). No new dependency.

Decisions made in this plan

  1. Directory. src/lib/sim-log/, flat, with test helpers in src/lib/sim-log/test/. Specs are *.spec.ts and run in Vitest project server (vite.config.ts:53-61: src/**/*.{test,spec}.ts, Node). Reason: the module is pure, and Node has crypto.subtle and TextEncoder like the browser and workerd.
  2. Item keys. The name item is sim; a policy p:<policyId>; a span s:<from>:<policyId>; a stroke k:<digest>, where the digest is digest128 (MurmurHash3 x86_128, src/lib/sim/world/policy/intern.ts:111) of canonicalJson of the stroke's fields, and the n-th identical stroke in one span gets ~n (n >= 2). Reason: a key is a pure function of content, so diff of two rulesets names the same keys the log holds; content keys let two tabs' strokes into the same brush both survive re-application. from is digits, so the span key parses unambiguously whatever the policy id holds (ids are any 1 to 80 characters, parse4.ts:255-258). Checked against timeline-ui's in-place edits (docs/dev/timeline-ui.md on step-engine/timeline-ui, "Edits in place on an offer"): each is a set (pool name is the policy label) or a span replaced (R4), and the programme set written to every span replaces every span.
  3. Brushes are named by their strokes. R62 lists a stroke and no brush shape. A stroke's fields are { span, brush, kind, stories, path, radiusM }; a painted span's brushes are assembled from its strokes in list order, grouped by brush id in order of first appearance. Reason: timeline-ui's appendStroke joins a stroke to the last brush and removeCustomBrush merges neighbours (git show step-engine/timeline-ui:src/lib/sim-page/stroke-adapter.ts, lines 29-63); both are stroke adds and deletes here, and a stroke costs its own bytes (R5). Consequence: a brush with no strokes cannot be stored (see 4).
  4. Log form. A ruleset with an empty brush is not in log form. toLogForm drops empty brushes; diff throws RangeError when its target is not in log form. Reason: an empty brush has no lots and no effect (paintEdits, src/lib/sim-page/policy.ts:511-527), and the editors never make one; imports (unit 4, R20) call toLogForm.
  5. The name item always exists. It is not added or deleted; only set applies. Unset, the name is DEFAULT_SIM_NAME = 'Untitled sim'. Reason: R42 makes the name a set, and R58 folds a sim without commits to the default ruleset. Unit 5 may reword the default only by a new shape version, since it is part of the fold's output for every old position.
  6. Delete cascades. Deleting a policy deletes its spans and their strokes; deleting a span deletes its strokes. Reason: #tbl-changes says "gone as if never added", and a span cannot exist without its policy. diff emits only the topmost delete.
  7. end only truncates. Valid when the new to is on or after from and before the current to (or the span had none). Extending a span or moving its start is a delete and an add (for a painted span, its strokes are added again). Reason: the owner's rule, "immutable save truncation or deletion" (#sec-changes).
  8. Commit id. The sim id's format: a base58 UUIDv7 (newId, isValidId). Task 1 moves src/lib/server/ids/base58.ts to src/lib/ids/base58.ts and leaves a re-export at the old path, which is R29's move. Reason: the parser runs in the browser, which cannot import $lib/server; one id format for sims and commits; no call site changes.
  9. Hash. hash = sha256Hex(prevHash + commitText(commit)) with sha256Hex from src/lib/sharing/hash.ts:1-4; the first commit's prevHash is GENESIS_HASH, 64 zeros. Asynchronous; fold, diff and re-apply stay synchronous and never hash. Reason: already in the repo and in every runtime; the chain is computed once per accepted commit and checked once per load.
  10. Canonical text of a commit. canonicalJson (src/lib/sim-page/policy.ts:445) of every field but hash. No field is ever undefined: absent values are null (restores) or absent keys (after on an unordered add). commitText throws on undefined or a non-finite number. Reason: canonicalJson(undefined) yields the text undefined, which is not JSON.
  11. restores. { position, as: 'undo' | 'redo' | 'jump' }. jump is R14's restore to any position (timeline-ui's undoTo) and R32's restore before an edit. Reason: #tbl-commit names only undo and redo, but R14 needs a third, and timeline-ui records undoTo "as an ordinary change" (#sec-today), which is how jump counts in the derivation.
  12. Undo and redo derivation. A two-stack editor replayed over the log: an edit or a jump pushes the current position on undo and empties redo; an undo restore pops undo down to its target and pushes the current position on redo; a redo restore the reverse. A system commit empties both stacks. A restore whose target is not on its stack counts as a jump. Reason: it reproduces #tbl-undo exactly; undo stops at an import, a remix's first commit and a dataset move (restoring a ruleset aligned to an older dataset onto a newer one would break R55); a restore re-applied on a moved tip keeps its declared target (R18).
  13. Validity is structure only. checkRuleset runs parsePolicy4(policy, { asOf: null, presetLayer: 'reconcile' }) and simDoc4Problems (src/lib/timeline/sim-doc4.ts:74). Reason: R3 says "checks structure only"; strict mode also checks preset availability (policy.ts:262-284), so a preset retired later would make every edit on an accepted sim refused.
  14. A commit has at least one change. Reason: R19 drops a commit left with none, so none is ever stored.
  15. Re-apply beyond R19. An add whose key exists is dropped (exists); an end that is no longer a truncation is dropped (not-truncation); an add or move whose after sibling is gone is kept and placed last in its list. Reason: the first two would otherwise make the whole commit invalid; the third keeps a new policy that another writer's delete only displaced.
  16. Structural roles belong to the shape name. A shape's key rule, parent, list and whether end applies are fixed per name in code (items.ts). A shape version changes fields only, with a pure up. Reason: diff and assembly are code over the current versions; a change of structure is a new shape name.
  17. Envelope limits. label at most 200 characters; build 1 to 64; source matches /^[a-z][a-z0-9-]*(\.[a-z0-9-]+)*$/, at most 64; a key at most 256; at is milliseconds since the epoch. Reason: none are page text limits; they only stop junk. The per-commit size cap is unit 2's.

Rules the parsers enforce

  • Exact key sets (unknown key: path is that key, "unknown key"; missing: "missing"). add may carry after or not; every other op has a fixed set: end {op,key,to}, move {op,key,after}, set {op,key,field,value}, delete {op,key}.

  • Draft: id passes isValidId; parent integer >= 0; kind one of the three; label string of at most LABEL_MAX; restores is non-null exactly when kind === 'restore', with position an integer from 0 to parent and as one of the three; datasetVersion matches DATASET_VERSION_RE; shapes integer >= 1; build 1 to BUILD_MAX; source matches SOURCE_RE, at most SOURCE_MAX; changes a non-empty array (decision 14).
  • Stored commit: the draft's rules, plus seq integer >= 1 with parent === seq - 1 (path parent; R18 accepts only on the tip), actor 1 to 64 characters, at a safe integer >= 0, hash matching /^[0-9a-f]{64}$/.

Algorithm

A = flatten(a); B = flatten(b)
same(k): k in A and B, same shape, fields equal (canonicalJson) except
         the shape's settable fields, and for a span `to` when B.to is a truncation of A.to
         (B.to !== null and (A.to === null or B.to < A.to))
survives(k): same(k) and (parentOf(B[k]) is null or survives(parent))
1. deletes  for k in A in flatten order, not survives(k), and its parent survives or has none:
            { op: 'delete', key: k }                  (a cascade removes the rest)
2. by level policies, then spans, then strokes:
   listed   for each list L of that level in B, in B order:
              stable = longest increasing subsequence of the surviving keys of L,
                       taken in A's list order and ranked by their index in B's list
              prev = null
              for k in B's list L:
                if not survives(k): { op: 'add', key: k, shape, fields: B[k].fields, after: prev }
                else if k not in stable: { op: 'move', key: k, after: prev }
                prev = k
   spans    for each span k in B, not survives(k): { op: 'add', key: k, shape, fields }
3. sets     name first (key 'sim'), then each surviving item's settable fields that differ
4. ends     each surviving span whose `to` differs: { op: 'end', key, to: B.to }

/** R19: re-apply one pending commit's stored changes on `tip`. Never mutates `tip`. */
export function reapply(tip: LogState, input: FoldInput): Reapplied;

Walk the changes in order on a clone of tip, applying each kept change as you go, so a later change sees an earlier one. A change is dropped as gone when its item (for end, move, set, delete) or its parent (for add) is missing; as exists when an add's key is taken; as not-truncation when an end no longer shortens the span. An add or move whose after is not in the list is kept with after set to the list's last key (null when empty). Kept changes are returned as written (still under input.shapes) apart from that re-anchoring. None kept: empty. A kept change that still fails, or a result that fails checkRuleset: invalid. A pending restore is not this function's job: unit 4 recomputes it as diff(new tip ruleset, target ruleset) (R18).

Algorithm (decision 12)

undo = [], redo = [], cur = 0
for e in log:
  if e.kind is 'system':                       undo = []; redo = []
  else if e.kind is 'edit' or e.restores.as is 'jump': undo.push(cur); redo = []
  else if e.restores.as is 'undo':
    i = undo.lastIndexOf(e.restores.position)
    if i < 0: as jump   else: undo.length = i; redo.push(cur)

    i = redo.lastIndexOf(e.restores.position)
    if i < 0: as jump   else: redo.length = i; undo.push(cur)
  cur = e.seq
