Pool closing implementation plan

The step engine closes a spent pool, opens it again on a new arrival, and the money view and Details say when each source ran out.

For agentic workers REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps are checklist items; progress is kept in the workspace ledger, not in the plan.

Overview

Goal
A pool that has had its last money and cannot pay a waiting application closes from the next month, exactly as if switched off that day; it opens again on a new arrival; MoneyView.closed and MoneyView.shut carry it, and Details prints "{label}: ran out {Mon YYYY}".
Architecture
The world gains closedDay and a shut history (world columns, so structuredClone, rewind and copies carry them). System 5 closes spent pools at the end of serving. Two optional hooks, beforeStep and timelineOf, make withFunding step and plan under closedTimeline: a view of the base timeline whose frames do not offer a closed pool's programmes. The frame id changes in the closing month, so today's frame-change code (replan, policyChanged, remakeRow) does the re-making. The older scenario engine is untouched; the comparisons with it run with poolClosing: false.
Tech Stack
TypeScript, Svelte 5 (runes), Vitest (projects server and client), axe-core in the client project.

export type Inflow =
  | { kind: 'once'; day: Day; dollars: Dollars }
  | { kind: 'yearly'; from: Day; to: Day | null; dollarsPerYear: Dollars };
  • Pool has no uncapped field. A pool can pay only from what it has received.
  • The baseline's federal pool has kind federal and one yearly inflow of the ceiling.
  • A baseline pool's inflows follow its source's bound (F1). A yearly inflow has to: null only for a bound of kind none.
  • A stored or published document whose pool carries uncapped loads with the field ignored.
  • A published plan or policy runs on its own dataset while that dataset exists, and every dataset built before this build has uncapped: true on its federal pool. The calibration loader reads such a pool as one yearly inflow of LEGACY_UNCAPPED_DOLLARS (100 billion dollars) from the dataset date with no end, and never refuses the calibration.
  • Where the yearly amount of such a pool is shown, it reads "No ceiling". So a policy published before this build plays as it did.
  • isNoCeiling(dollars) in src/lib/timelapse/model.ts is the one test for such a pool: a yearly amount at or above LEGACY_UNCAPPED_DOLLARS.
  • A scale entry on the federal pool scales its ceiling, as on any pool; 0 switches it off.
  • Inflow, Programme, Instrument, the award rule, the line and fundBundle are unchanged.

Removed: Pool.uncapped, the "no limit" text for anything but an older dataset's pool, the on/off-only editor for the federal pool, the uncapped sets passed to the money results.

// src/lib/sim/world/score/types.ts (TimelineView.money)
export interface MoneyView {
  /* the series as today, and: */
  /** Per pool id: the first day it was closed, or null. */
  closed: Record<string, Day | null>;
  /** Per pool id, by calendar month: true while the pool is closed at the end of that month. */
  shut: Record<string, boolean[]>;
}
  • A pool's last arrival is the last arrival the document in force gives it; a pool with a yearly inflow with no end has none.
  • A pool is spent in a month when the month begins after its last arrival, it has no loan out and holds no guarantee reserve, and that month's serving finds an application short on it.
  • A spent pool is closed from the first day of the next month, and stays closed until it receives a new arrival.
  • A closed pool is treated exactly as a pool switched off from that day: its programmes are in no bundle, and the applications waiting on them are re-made as on a re-pricing day.
  • Money returned to a closed pool stays in it and is never awarded.
  • A pool whose last arrival changes because the policy changed is judged again from the month the change takes effect; a closed pool that receives a new arrival is open again from that arrival's month.
  • The worker's rewind restores each pool's open or closed state with the world.
  • The older scenario engine keeps its behaviour: an application waits on a spent pool.
  • Details lists each closed source by its pool's label with the month it ran out: "{label}: ran out Mar 2030".
  • shut[id][i] is true from the calendar month the pool ran out (the month that found it spent) through the last calendar month before it opens again.
  • A pool's bar on the timeline reads empty in every month shut marks: what a closed pool still holds is never awarded.

Review Focus

Five failure modes the spec implies and its test list does not pin, most likely first. Each has its test in the owning task.

  1. A closed view that reads the live world. If closedTimeline reads pools at frameAt time rather than a snapshot taken when built, a later closing rewrites the frames of months already stepped, frameAt(month - 1).id stops matching world.frame, and policyChanged re-makes every waiting row every month. Expected: a view built before a closing keeps its frames. Test: Task 2, "a view is a snapshot".
  2. A world without funding columns. A timeline with no money (finance null in every frame) stepped through withFunding(createFundingSystem()): beforeStep and timelineOf must return the timeline itself without calling fundOf (which throws, columns.ts:203-207). Expected: the run steps as before. Test: Task 3, "a world without money steps under its own timeline".
  3. Two worlds on one base timeline. The plan and its twin, or two copies, can share a base timeline with different shut histories. A cache keyed on the base alone would hand one world the other's closed set. Expected: each history gets its own view, the same object each time it is asked for. Test: Task 2, "two histories over one base".
  4. The next frame not ready. beforeStep reads frameAt(world.month + 1) to open pools again; past readyThrough() that frame does not exist. Expected: step throws its RangeError as today and the world, its shut history included, is unchanged. Test: Task 4, "beforeStep past readyThrough".
  5. A closed pool missing from a later frame. A policy edit applied with keep can drop a closed pool's id from the frames. Expected: the closed view and beforeStep skip shut rows whose pool the frame does not hold, no throw, and the other closed pools still lose their programmes. Test: Task 2, "a closed pool the frame does not hold".

    /** The last day `pool` receives money under this definition; null when it never stops. */
export function lastArrivalOf(pool: Pool, asOf: Day): Day | null;
/** `timeline` with the world's closed pools' programmes not offered; `timeline` itself with none. */
export function closedTimeline(timeline: PolicyTimeline, pools: FundPools, asOf: Day): PolicyTimeline;

Pinned behaviour (spec sec-design-last, sec-design-closed):

  • lastArrivalOf: null when some inflow is yearly, to: null, dollarsPerYear > 0. Otherwise the latest day on or after asOf on which an inflow with dollars above 0 arrives under inflowArrivals (a yearly inflow read through its own to, which may lie past the window); NO_DAY when there is none. Memoised per Pool object (WeakMap; builder's call to key the inner value by asOf, since one worker can hold two datasets).
  • Closed set of month k: the pool ids of shut rows with shutFrom <= monthFirstDay(asOf, k) and (shutTo === NO_DAY or monthFirstDay(asOf, k) < shutTo).
  • frameAt(k): the base frame when the set is empty, or when no pool of the set is in the base frame's finance.pools; else the base frame with finance replaced by a copy whose offered is 0 for each programme of a closed pool, pools, programmes, arrivals, slope and terms the base's. Its id is frameIdOf(`closed|${base.id}|${ids}`), ids the closed ids present in the frame, sorted, joined with ,. Derived frames are cached in a module WeakMap<PolicyFrame, Map<string, PolicyFrame>> keyed by the base frame object and ids.
  • changes(): the base's months and every month k >= 2 whose closed set differs from month k - 1's, ascending, each once; recomputed when the base's changes() array is another object or another length. touched(k): the base's for a month in the base's changes, else new Int32Array(0). readyThrough(): the base's.
  • The view is a snapshot: it copies the shut rows (pool id, from, to) when built and never reads pools again.
  • Cache: builder's call, WeakMap<PolicyTimeline, Map<string, PolicyTimeline>> keyed by the base and a signature of the shut rows (id:from:to joined), holding the last 8 views per base, oldest dropped. Reason: the plan world and its twin may share a base (Review Focus 3) and alternate every month, and an unbounded map grows with every closing.
