Sim log store, plan 2: registration, the socket client and tabs

Unit 4 of the sim message log, second of four plans: the server's hello carries its dataset, resumes and account deletions are bounded, and a browser library (src/lib/sim-sync/) registers a sim, keeps one socket per sim, sends the store's pending commits one at a time, claims the work of closed tabs and states the save state as data. No page changes: /sim keeps its old store until plan 3.

For agentic workers REQUIRED SUB-SKILL: use superpowers:subagent-driven-development to implement this plan task by task. Steps are checklist items; progress is kept in the workspace ledger, not in the plan.

Everything plan 3 needs to put /sim on the log, short of the page: server changes that must merge before browser registration ships (the dataset in hello, a bounded resume, a bounded account deletion), four small additions to plan 1's store, and a SimSync per tab that ties registration, the socket, tabs and the save state together, tested in Node against fakes and, for Web Locks and BroadcastChannel, in real Chromium.

Review Focus

  1. An append answered by silence. The object sends no frame for a duplicate id (decide.ts:46, sim-object.ts:173-178). The client's one in-flight append must still resolve, from the stored copy on the stream. That holds only because nothing is sent before the resume answer ends with more: false on that connection. Try to make the client send early (after a gap, after a store open, after a reconnect) and leave an append in flight for ever. Pinned by Task 8, S10, and Task 7, C7 and C10.
  2. A frame or a send for the wrong sim. The store's sim changes under a live socket: open of another sim, adopting the current sim, a withdrawn import. Late events of a stopped socket, a registration answer for the old sim, a head() of the new sim on the old socket. Pinned by C17, C18, S13 and Task 11, Y9 and Y10.
  3. The capped resume and the resumed mark. A socket is marked resumed only when an answer reaches the tip; a resumed socket that resumes again gets live frames between pages. Look for a commit stored between the last page read and the mark, a socket that never gets live commits, and a budget refusal mid-answer. Pinned by Task 2's host tests and C7, C9, C22.
  4. Registration of a look that becomes an edit, and taken. No socket may feed another person's commits into a sim this device minted; an ok must bring write to a socket opened signed out. Pinned by Y6, Y8 and the registration table.
  5. The save state. It must never say saved while anything is pending or held, and never "on this device" while storage has failed; and the account-deletion loop must end. Pinned by Task 10's property and rows, Task 3's pass tests and the pane's pass cap.

Invariants

Each holds after every public call of SimSocket, SimSync and TabPresence returns. The store's I1 to I12 (docs/dev/sim-store.md, Invariants) still hold; this plan adds no way around them. Tests name the ones they pin.

  1. S1, one in flight, after the resume. A socket has at most one append unanswered, and sends none on a connection until a resume answer on it ended with more: false and no other resume is outstanding.
  2. S2, only what the store hands out, for its own sim. Every append is store.head() read at the moment of sending, and is sent only when store.ready and store.simId equals the socket's sim.
  3. S3, frames go to the sim they came from. Every receive names the socket's sim id; a socket whose sim is no longer the store's is stopped; events of a stopped or replaced socket are ignored.
  4. S4, the client never confirms or discards on its own. A commit leaves pending only through store.receive (the store's I4) or store.dropPending on an invalid refusal naming it. not-writer, limit, full, newer, gone, a close, taken, sign-in and quota leave every commit pending and stored.
  5. S5, registration only for the device's own work. POST /api/sims is sent only when the store says 'needed' (the sim is stored here, or storage is unavailable or failed for a sim this store minted) and the sim has something to send (pending, or stopped with held commits); never for a look; one request at a time per browser.
  6. S6, no socket without a registered or foreign sim. A socket is open only when the store says 'done' (registered) or 'none' (a sim with no record on this device: a look), and never after taken.
  7. S7, dev sends nothing. With live: false no fetch is made and no socket is opened.
  8. S8, claims only from gone tabs. Pending records are claimed only from owners whose tab lock is free, never from this tab; without Web Locks, from every other owner, at open only.
  9. S9, the save state is honest. Never saved while pendingCount > 0 or stopped is set; never device while local is 'failed'.
  10. S10, every wait is the clock's. Every timer goes through the injected Clock; reconnect delays follow backoffDelay; nothing reconnects after 4410, an append refused gone, a resume refused gone or another protocol.

Decisions

  1. Send only after the resume completes (S1). A duplicate append gets no frame (decide.ts:46; sim-object.ts:173-178 answers only a refusal). On a connection whose resume reached the tip, every stored commit has reached the socket before any append it sends is processed (the answer and the live broadcast are in one serialized order, log-host.ts:239-246), so an in-flight id that is a duplicate always arrives on the stream and resolves the append. Confirmed with the prototype (What was run, case 6).
  2. A resume answer ends with more. The last commits frame of every resume answer carries "more": false (caught up) or true (capped: send the next resume); live frames and the other frames of an answer carry none. PROTOCOL stays 1: the field is additive and the e2e helper reads only commits. Reason: today an answer has no end marker (sim-object.md, Resume), so a client cannot tell when it may send (decision 1).
  3. The resume bound. An answer holds at most LIMITS.resumeBytes (8 MiB) of stored bodies (always at least one commit); an object-wide byte budget (a RateBucket of 32 MiB, refilled at 4 MiB a second) pays for each 500-row page as it is read; a spent budget refuses the first page {"type":"refused","id":null,"why":"limit"} and cuts a later one with more: true. The browser asks for the next page only after the last frame of the previous one, so one socket never has more than about 9 MiB queued. Reason: workerd queues send() without limit or bufferedAmount (checked, What was run), the object has 128 MB and a sim up to 64 MiB. The numbers are a proposal: 32 MiB of queued frames plus a 64 MiB fold fits 128 MB.
  4. A socket is marked resumed when an answer reaches the tip (more: false), not at its first page as today (sim-object.ts:153-157). Within the serialized section no commit can be stored between the last page read and the mark, so I7 of the object still holds; a capped answer gets no live frames until it catches up. A socket already resumed stays resumed.
  5. A resume refused gone halts as diverged. The outline said "restarts from 0"; the store cannot: receive skips seqs at or below its tip (local-log.ts, The log), so a resume from 0 would apply nothing. A resume past the tip means the device's log is not this sim's (a takedown closes sockets 4410 first): the socket stops, the commits stay, the save state says why.
  6. One SimSocket class with injected ports, not a pure reducer plus a driver. A pure machine would need the store's head and tip passed in on every event and receive's answer fed back as another event; with the socket constructor, the clock and the store injected, the class is as deterministic in tests and half the surface. Departs from the outline's SocketMachine; the state table below is the contract.
  7. What the device knows decides registration. Plan 1's store keeps registered on the sim record but does not expose it, nor the confirmed tip (the resume needs it), nor which tabs own records (claims need it). Task 4 adds LogStore.tipSeq, LogStore.registration ('none' | 'wait' | 'needed' | 'done'), LogStore.markRegistered(simId) and SimDb.pendingOwners(simId). A device that recorded the registration never posts again, so a person whose session has expired is not told taken for their own sim (a signed-out repeat of an id in use is 409).
  8. Registration answers. ok records it (markRegistered) and connects, reconnecting a read socket that could not write. sign-in: keep, no socket, post again on retryRegistration() or the next load. taken: keep on the device, unsent, stop any socket (never feed another sim's commits into this one); the sharing unit turns them into a remix (R32, R53). quota: keep, report, post again on retryRegistration() or the next load. retry (429, 5xx, network): back off as the socket does; online retries at once. bug (400, 403 without quota, 415, anything else): stop and log the status and code.
  9. Every registration is single-flight through the Web Lock sfh-register (without Web Locks, a promise chain in the tab). The client cannot tell whether it is signed in, and a serialized repeat costs nothing.
  10. Tabs wait on each other's locks. Each tab holds sfh-tab:<tabId> for its life. At open, owners of the sim's pending records whose lock is free (locks.query()) are claimed through store.open(simId, { claim }); for each owner still alive, and each tab heard on the BroadcastChannel('sfh-sim') ({ type: 'here', tabId, reply }), the tab requests that tab's lock, which is granted only when it is gone, then claims its records with store.claim([owner]). Departs from the outline's pagehide message plus query(): the lock is still held when pagehide fires, so the query would race it; waiting on the lock needs no polling. Tab ids are never reused, so a free lock means gone for good.
  11. Without Web Locks (all current browsers have them: Chrome 69, Safari 15.4, Firefox 96) a tab claims every other owner's records at open and nothing later (the outline's rule): a live tab whose records are taken learns it from its next write (lost) and the claimer sends them, at the cost of rate tokens, never of a commit.
  12. Dev is an option. SimSyncOptions.live: plan 3 passes !dev from $app/environment. With live: false nothing is fetched or opened, tabs and claims still run (they are local), and the save state is device with why dev. Reason: the library must not import $app/*, and import.meta.env.DEV is true under Vitest, which would switch off every test.
  13. The backoff resets on progress, not on hello. A confirmed append, or reaching live with nothing to send, resets it. A sim whose stored rows no longer fold closes every append 1011 (sim-object.md, Close codes): resetting on hello would loop every second.
  14. Network signals. offline closes the socket and waits; online connects at once (and retries a registration at once). visible while waiting connects at once; visible while the socket cannot write (a not-writer hold, or access said write: false) reconnects (SimSync does it), so a sign-in made in another tab gives this socket write. A text ping every 30 s while visible; a connection with no hello in 10 s is a failed attempt. The object's hibernation is invisible to the client: the socket stays open and its attachment keeps resumed.
  15. Holds and halts. full and newer hold sending for the life of the SimSocket (across reconnects); not-writer and limit are cleared by a new connection. Halts (gone, diverged, protocol) close the socket for good.
  16. hello.build different from the page's build is reported (buildMismatch) and changes nothing else (outline). No tip-hash check after a resume (plan 1, decision 26): nothing to compare against without another protocol field, and a mismatch would be a server bug the chain already guards (sim-object.md, I2).
  17. SimSync.open does not retry a store open that rejects (p2-store-contract): a failed IndexedDB read is a closed connection or a broken database, which a retry does not mend. It rejects, and plan 3 offers a reload. openSimDb's null for a version error stays indistinguishable from no storage (p2-db-open): what the page says is plan 3's.
  18. The save state is four kinds and a reason: saved, saving, device (saved on this device only), unsaved (not saved anywhere yet), with why for the details on tap. Ordering in the save state table. An open draft is not pending and does not change it.
  19. Account deletion is bounded per request. deleteAccount leaves at most 50 sims per call and answers { more }; the route answers 202 { more: true } without signing out until the last pass, which closes the account as today; the pane repeats while it gets 202, at most 100 passes (5,000 sims) before it shows the network error and the person retries. Each pass is about ten D1 queries per sim, well under the per-request limit.
  20. No client end-to-end test in this plan. No page drives SimSync until plan 3 (the outline puts the real socket's proof there, with the page's specs). Playwright here covers the server changes (Tasks 1 and 2). Web Locks and BroadcastChannel are proved in real Chromium (Task 9).
  21. fitsCommit is not re-checked before sending. The store makes a commit pending only after fitsCommit (its I7), so every head() fits; re-checking would add a second refusal path with no case behind it.

For the owner

What a person will see or can lose once plan 3 puts this on /sim, most important first.

  1. An edit can be stuck on one device as "taken". If a first, signed-out registration reaches the server but its answer is lost (the network drops at that moment), the server made the sim and an account whose session cookie never reached the browser. The retry is signed out and the id is in use, so the server says taken. The person's edits stay on that device, unsent, and the page says so, until the sharing unit can turn them into a remix (R32). Rare, and nothing is deleted. See question 1.
  2. A pseudonymous person whose session has expired keeps editing on the device only. The device knows the sim is registered, so it opens the socket, which is read-only signed out: edits stay on the device and the save state says "saved on this device" (no write). A pseudonymous account has no way back in. Nothing is lost; until unit 5 it is not sent either. See question 2.
  3. Write taken away (removed from a sim, or the last manager left): edits stay on the device, unsent, "saved on this device"; they are sent if write comes back. The remix of R53 waits for unit 5.
  4. Under npm run dev nothing reaches the server; the page says "saved on this device". Use npm run preview to see saving.
  5. A very large sim opens in 8 MiB pages, and when many tabs open large sims on one object at once the later ones wait for the budget (4 MiB a second). A 64 MiB sim takes at least 8 round trips.
  6. Old browsers without Web Locks: a second tab takes over the first tab's unsent edits at open; the first tab stops showing them until they come back confirmed. Nothing is lost.
  7. Deleting an account in many sims takes several requests; the button stays busy throughout.
  8. A tab on an older build keeps saving; plan 3 can offer a reload from buildMismatch.

Open questions

  1. Question A lost first answer turns the person's own sim into taken (For the owner, 1). Accept until unit 5's remix re-homes the edits, or make registration recoverable now (for example the browser sends a one-time proof it minted, kept with the sim, and the server answers 200 to the same proof)? Recommendation: accept for now. It needs a lost response at the one moment that matters, loses nothing, and unit 5's remix is the general cure; a proof is a new credential to store and check.
  2. Question A pseudonymous session that expires leaves the device unable to write its own sims (For the owner, 2).
