Mail setup plan

Runs the mail-setup runbook (SES identity, DNS, IAM, secrets, proof mails) and writes the mail section of docs/dev/deploy.md.

For agentic workers REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps are checklist items; progress is kept in the workspace ledger, not in the plan.

Overview

  • Goal: sign-in mail from sfhousing.mindlace.net deliverable through Amazon SES on staging and production, proved by one real mail each, and documented.
  • Architecture: no application code. Tasks 1 to 4 are outward-facing runbook steps that the operator runs itself, in the foreground, exactly as the spec's numbered subsections write them: they handle secrets and the owner's test address, which never pass to a subagent. Task 5 is the one repository change, docs/dev/deploy.md, implemented and reviewed through subagent-driven development.
  • Tech stack: aws CLI (sesv2, iam, sts), npx wrangler secret, dig, curl, Markdown + Prettier.
  • Spec: docs/superpowers/specs/2026-11-22-mail-setup-design.html, read from the package worktree /Users/mindlace/Projects/sfhousing/.claude/worktrees/incremental-game.

Global constraints

Interface rows: this unit needs none and produces none.

From the spec's Rules for the operator (verbatim):

  • Every command runs from the unit's worktree, in the foreground.
  • No secret value is ever printed, logged, written to a file, put in a commit or put in the handback. The access key is passed from aws to wrangler inside one shell command.
  • The AWS account id is never printed whole. Commands that need it read it into a shell variable in the same command.
  • The test address is never written to a file, a commit, a doc or the handback. The handback says "an address the owner named".
  • No SES identity, IAM user, key or DNS record other than those named here is created, changed or deleted. The planafoot user, its policy and its keys are never touched.
  • Secrets go on an environment only after the identity reads verified, because SES refuses mail from an identity that is not verified.
  • The DNS step is the one wait.

From the design's global constraints (verbatim, those that apply):

  • Work happens in git worktrees under .claude/worktrees/. Commits follow Conventional Commits. No attribution to an AI anywhere.
  • Code style: 2-space indent, single quotes, no trailing commas, 100 columns.
  • Signoff fails on server stderr, on timing crutches and on a retried flake. Each unit runs npm run lint, npm run check and the Vitest projects its files belong to before it hands back.
  • No unit runs npm run signoff: its dataset step fails until the dataset is uploaded. closing runs it once, after the upload.
  • Page text is short. No sentence says what something is not.

Review focus

  • A key id, secret, account id or the test address leaking into the diff or a doc example: Task 5's review greps the diff for AKIA, 12-digit numbers and @ addresses other than noreply@sfhousing.mindlace.net.
  • A doc command that runs against the wrong environment: every block in Sign-in mail starts with the environment prelude, and production carries no --env.
  • The deploy.md edit straying outside the mail section's boundary (the takedown section and the other Worker bullets belong to closing).
  • DKIM CNAMEs added proxied: the doc states the "DNS only" rule beside the table.
  • A rotation leaving two keys: the doc's rotation keeps the three steps, ending in the delete.

Task 1: SES identity, DNS records, verification

Operator-run. Spec §sec-design-identity, §sec-design-dns, §sec-design-wait, §sec-design-relay.

  1. Create the identity with Easy DKIM 2048 and keep the three tokens (spec step 1, first block).
  2. Set MAIL FROM mail.sfhousing.mindlace.net with USE_DEFAULT_VALUE (spec step 1, second block).
  3. Hand back partial, "waiting on owner: DNS records and a test address", as a question file holding the six records with the tokens filled in.
  4. On the owner's answer, check each record with dig against the table (spec step 3); a wrong record goes back alone.
  5. Read the identity state; go on only at sending true and identity, DKIM, MAIL FROM SUCCESS. PENDING hands back "waiting on SES verification"; FAILED stops and is reported.

Task 3: Staging key, secrets and proof mail

Operator-run. Spec §sec-design-staging, §sec-design-proof, §sec-design-rollback.

  1. With E=staging, run the step 5 block; npx wrangler secret list --env staging lists BETTER_AUTH_SECRET, SES_ACCESS_KEY_ID, SES_SECRET_ACCESS_KEY.
  2. /signin on the staging host contains sendLink at least once.
  3. POST sendLink with the owner's address; the answer is JSON with "type":"success". A 500 is read under the bounded tail; an unfixable one runs Rollback for staging and is reported.

Task 4: Production key, secrets and proof mail

Operator-run, only after Task 3's POST answered success. Same steps as Task 3 with E=production (no --env).

  1. Step 5 block; npx wrangler secret list lists the three names.
  2. /signin on sfhousing.mindlace.net contains sendLink.
  3. POST sendLink; "type":"success".
  4. Step 7 checks: each user's list-access-keys prints exactly one Active; SES_FROM in wrangler.jsonc unchanged.
