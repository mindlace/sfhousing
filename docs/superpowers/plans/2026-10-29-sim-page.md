# /sim Page, Zoning Layers and Brush UI (Plan 3 of 5) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A `/sim` page that runs the plan-2 lever engine: `/fzp` routes to it, the user toggles stock zoning layers and the comparison twin, paints a user zoning layer with freehand, transit, street and area brushes, protects lots by category or by brush, and sees the simulation go out of date and come back.

**Architecture:** The page keeps a **policy recipe** (`SimPolicy`: stock toggles, an ordered list of brushes with their parameters, protections), compiles it to plan 2's `SimLevers` once every brush's lot set is known, and sends it with `setLevers`. Brush lot sets are resolved **in the worker**, which already holds `parcels.bin` and `policy.bin` citywide; it fetches `frontage.bin`, `transit.json` and `neighborhoods.geojson` lazily on `/sim` only. The `/fzp` page composition (`FzpMode`) gains a `levers` input and the posted lookups. `/sim` needs a dataset with `policy.bin`; production is moved to one (`2026-10-29-0fd62c4d`) before the redirect can reach it (Task 0B). The editor's `BrushController` drives freehand strokes through a small adapter, unchanged in behaviour on `/`.

**Tech Stack:** SvelteKit 2, Svelte 5 runes, Tailwind 4, deck.gl overlay layers, KDBush (already a dependency), worker-safe TypeScript in `src/lib/sim/`, Vitest (`server` and `client` projects), Playwright.

**Spec:** `docs/superpowers/specs/2026-10-28-sim-policy-levers-design.md`. Read all of it, especially Goals 1, 2 and 5, both rounds of partner rulings (round 2 rulings 1, 5 and 7), "Calls made after the builder check" (Defaults, Density, Where yields come from), "Left to the builder", "Carried from plan 1" (Plan 3 items) and "Carried from plan 2" (Performance). Read it with `docs/dev/sim-levers.md` (the engine, its protocol, "Notes for plans 3 and 4"), `docs/dev/fzp-mode.md` (request flow, the T9 lookups seam, e2e notes), `docs/dev/pipeline.md` ("Street frontage", commercial corridor) and `docs/dev/accessibility.md`.

## Plan sequence

This is plan 3 of 5. Plans 1 (data layers) and 2 (policy engine, branch `sim-policy-engine`, unmerged) are done. Plan 4 owns the permitting timeline UI, presets, stage floors and route shares. Plan 5 owns publishing, local autosave of the policy, and size limits on the lever document. This plan leaves two seams for them: `SimPolicy.timing` (carried through, never edited here) and `parseSimPolicy` (the document plan 5 saves and publishes).

## Calls made in this plan

Each is the builder's call unless marked otherwise, with its reason.

1. **A recipe document over `SimLevers`.** The page edits `SimPolicy` (brush parameters), not lot lists. `SimLevers.user` stays plan 2's lot lists, compiled from the recipe. Reason: a citywide rule brush is tens of thousands of ids; the recipe is small, editable after the fact ("change the arterial brush to 8 stories"), and is what plan 5 should publish.
2. **Brush resolution runs in the worker** (`resolveBrush`, `brushCatalog` requests). Reason: the worker already holds `parcels.bin` and `policy.bin` for every lot; the main thread would have to fetch them a second time.
3. **Freehand covers what the editor covers:** a lot whose label point is within the radius of the stroke path (`createParcelIndex().covered`, `src/lib/plan/parcel-index.ts:85-101`), over `parcels.bin`'s `labelPoint`. Every brush resolves to **scenario-eligible lots only** (`parcels.eligible`). Reason: same behaviour as `/`, and ineligible lots carry no yield.
4. **Brush order:** the brush list is the user layer's order, and a later brush wins (plan 2's edit order). Brushes can be moved up and down. An **erase** brush removes its lots from every earlier brush. A transit brush with several bands compiles outermost band first, so the inner band wins.
5. **Density defaults** (spec "Calls made": raise defaults to limits off): `raise` starts with density limits off; `lower` and `set` start with limits on. The user can change either.
6. **Stories range in the UI** is the editor's 1 to 80 (`STORIES_MIN`, `STORIES_MAX`, `src/lib/plan/constants.ts:3-4`). Reason: one brush vocabulary across `/` and `/sim`; plan 2 accepts 0 to 255.
7. **Transit stop types** (tier noted per type), from `transit.json` patterns:
   - `regionalRail`: a stop on a `heavy-rail` or `commuter-rail` pattern (BART, Caltrain). Tier 0.
   - `metro`: a stop on a `light-rail` pattern (Muni Metro). Streetcar (F) and cable car are not Metro. Tier 0.
   - `rapidBus`: a Muni stop on a route whose id ends in `R` (live: 5R, 9R, 14R, 28R, 38R; SFMTA's Rapid naming). Tier 1.
   - `frequentBus`: a bus stop whose summed peak trips per hour over its bus patterns is at least `FREQUENT_BUS_TPH = 6` (every 10 minutes or better). Tier 3 if the implementer cites SFMTA's frequent-network definition, otherwise tier 4 with a comment saying so.
   - Distance is straight-line from the lot's label point to the stop (tier 4: SB 79 measures from the parcel edge, and `parcels.bin` has no outline). Default bands: 1/4 mile (402 m) and 1/2 mile (805 m), SB 79's band edges, each with its own height.
8. **Area by neighborhood** is the label point in a `neighborhoods.geojson` polygon (the same 41 analysis neighborhoods the map draws). Tier 3: the chunk records carry DataSF's `analysis_neighborhood`, which can differ at polygon edges. A `neighborhood` column in `policy.bin` is the exact fix at the next dataset bump.
9. **Area by zoning district** lists the components of `policy.useDistricts` (split codes broken at `|`), grouped by family (`RH-1(D)` under `RH-1`). Choosing a family chooses its members; a lot matches if any component of its code is chosen.
10. **Commercial corridor** is plan 1's composition exactly (`docs/dev/pipeline.md`, "Street frontage"): arterial frontage intersected with `isNeighborhoodCommercial`. CRNC is not counted (Open question 1).
11. **Protect brush** is the freehand stroke with a "Protect" or "Unprotect" tool; the lot list is the union of protect strokes minus later unprotect strokes, in order. Category protections (rent control, historic A/A\*, newer than N years) are toggles. Reason: spec Goals 2, "Protections".
12. **Map feedback:** lots in the user layer and brushed-protected lots are drawn as dots at their label points (deck `ScatterplotLayer`), coloured by mode, with protected lots outlined so colour is never the only signal. No height-map choropleth (Open question 3). Overlay layers are shared through a small multiplexer, because `setOverlayLayers` takes one list (`src/lib/map/SimMap.svelte:328-333`).
13. **Map lookups on `/sim`:** the map gets the posted `lookups.fresh`; cards pick `inFlight` or `fresh` per project. Reason: `setTimelineLookups` takes one set (`src/lib/map/types.ts:94-98`) and most bars over the horizon are new projects. Under an `'all'`-reach timer the map's bars for in-flight projects are approximate; that is plan 4's, which adds timers (documented in `docs/dev/sim-levers.md`).
14. **`/fzp` redirects with 307** to `/sim` with the query kept and `start=fzp` added. `start=fzp` opens `FZP_COMPAT_LEVERS` (stock FZP, compare pre-FZP, empty user layer: spec "Defaults"). Reason: 307 is temporary, so the route can change again without cached permanent redirects.
15. **No local persistence in plan 3.** The policy lives in memory; plan 5 adds autosave and publishing on `parseSimPolicy`. Reason: the spec puts "saved locally" with publishing ("`/sim` policies are publishable").
16. **No missing-data fallback** (partner decision, 2026-10-29). `/sim` always initialises with levers. A dataset without `policy.bin` gets the worker's existing `scenario-missing` answer, which the page already shows as "The simulation data for dataset … is missing or damaged" with Retry (`FzpMode.svelte:557-571`). Production is brought onto a dataset with `policy.bin` and `frontage.bin` first (Task 0B), and a config test keeps it there (Task 6). Within a supported dataset, a brush kind whose optional file failed to load (`frontage.bin`, `transit.json`, `neighborhoods.geojson`) is disabled with its reason; the rest of the page works.
17. **Names kept:** `src/lib/fzp/`, `FzpMode`, the `fzp-*` test ids and `window.__sfhFzp` stay. Reason: no rename churn in a plan that already changes the route; the debug hook gains a `levers` field.
18. **Lever sends are debounced 250 ms** after the last policy change once all lots are resolved (tier 4 UI choice). The worker already lets the latest `setLevers` win.
19. **A need whose cell has loaded but whose record is absent** is filled with a zero, non-hostable row and warned once (Task 11). Reason: a lot with no chunk record cannot be massed in the run anyway, and the alternative is a page stuck "updating" forever (plan 2 carried guard).
20. **Performance gate:** if the recompute for "every RH-1 lot raised to 4 stories" takes more than 20 s on the dev machine after Task 11's fix, stop and report: the per-lot yield-table fallback is a pipeline change and a dataset bump (spec "Where yields come from").

21. **Protected lots keep the stock-blend envelope for projects already in the pipeline** (partner ruling 2026-10-29 makes protection "not redevelopable"; this detail is the builder's). The engine reads `hostable` only to gate new initiation (`src/lib/sim/scenario/input.ts:268`, `:294`), so a protected lot hosts no new project while its in-flight project runs on as filed. The user layer's edits do not apply to protected lots, so no `Need` is made for them.
22. **Local Program forcing after the switch** (partner ruling 2026-10-29) is per lot and per period. A Local Program lot is forced onto streamlined when `localProgramStreamlined` is set and either `fzp` is on, or `currentLaw` is on and the period's current law for that lot is not SB 79's row. So after the switch, a lot where SB 79 wins the after-switch current law follows the route shares, unless the FZP map layer is also on (the spec ties forcing to the FZP stock layer: "Calls made", Density).

## Global Constraints

- **Spec anti-goal:** "A policy that skips the simulation. No user setting may decide directly how much gets built." Brushes change envelopes only, through `SimLevers`.
- **Spec anti-goal:** "Making the hard choices invisible. Protections and their trade-off (fewer sites) must be visible in the score." The score panel shows the protection capacity line whenever any lot is protected.
- **Protection means "not redevelopable"** (partner ruling 2026-10-29, spec round 1 as amended): a protected lot, by category or by brush, is not hostable under any layer, and its capacity drops out entirely.
- **Spec Goal 1:** "`/fzp` keeps working by routing to `/sim`, with query parameters such as `?seed=` preserved. `/` stays the brush editor." `/` behaves identically: `e2e/brush.spec.ts` and the `src/lib/brush/` specs pass with at most type-only changes.
- **Spec Defaults:** "`/sim` opens with current law on: FZP + the SF alternative plan (§207.11) + 'SF as observed' timers. `planEffect` starts at zero and reads 'your policy versus current law'." `/fzp` → `/sim` links open with pre-FZP comparison and an empty user layer.
- **Determinism:** "deterministic in `(dataset, levers, seed)`". Brush resolution is a pure function of the dataset and the query; the compiled `SimLevers` depends only on the recipe.
- **The data reaches production before the redirect does** (partner decision 2026-10-29). Task 0B promotes `2026-10-29-0fd62c4d` to production through its own `data:` PR and release before any plan-3 code merges, and Task 6's config test fails the branch if production's `PUBLIC_DATASET_VERSION` predates it. Code that ships before plan 3 merges (plan 2, on `main`) must keep parsing manifests with and without the optional keys, as plan 1 required.
- **`/` changes are minimal** (spec non-goal "Changes to `/` beyond what is needed to reuse its brush code"):
  - `BrushControllerDeps` types and an optional-preview branch in `BrushController`;
  - the stories and radius pop-overs moved out of `BrushToolbar` into components both pages use (Task 8);
  - **an allowed shell change** (layout ruling 2, 2026-10-29): the phone header menu and a pinned header slot in `SiteHeader` / `header-actions.svelte.ts`, which `/` shares (Task 6B).

  `e2e/brush.spec.ts` must pass; phone e2e tests that click header items open the menu through one helper.
- **WCAG 2.2 AA** (`docs/dev/accessibility.md`): every control keyboard-operable with a visible label, targets at least 24x24 px, no horizontal scroll at 375 px, and every drag (freehand) has a non-drag alternative (rule brushes, and the keyboard stamp `BrushController.stampAtCenter`).
- **Evidence hierarchy:** every new constant (`FREQUENT_BUS_TPH`, `RAPID_ROUTE`, band defaults, `PERF_GATE_MS`) carries its tier and source in a comment.
- **No CSP change, no new dependency.** Runtime dependencies are unchanged, so `src/lib/attribution.ts` is unchanged.
- **Stack and style:** Svelte 5 runes, colocated Vitest, `expect.requireAssertions` (every test calls `expect`), 2-space indent, single quotes, no trailing commas, 100 columns. Worker modules (`src/lib/sim/**`) are zod-free, DOM-free and `$app`-free.

## Review Focus

1. **Old `/fzp` links and history after the redirect.** Bookmarks with `?seed=N`, an invalid seed, unknown parameters, and Back or Forward onto an entry written before or after a reroll must all land on the same future `/fzp` showed, with the URL cleaned as `/fzp` cleaned it (`src/routes/fzp/+page.svelte:31-48`). Task 6 tests `redirect keeps every parameter` and `an invalid seed is cleaned on /sim`; the Task 12 e2e `Back after a reroll`.
2. **Brushing faster than lots resolve and levers recompute.** Five strokes in a second, a toggle mid-resolve, a reroll while resolving. Only the latest recipe reaches the worker, `leversPending` clears exactly once the latest revision is current, and a `levers` message below a reroll barrier is not dropped. Task 1 tests `reroll while resolving keeps the status` and `load failure clears pending`; Task 6 test `only the latest recipe is sent`.
3. **A brush that resolves to nothing, or to the whole city.** Zero lots (a street name with no frontage, a district family with no eligible lot) must say "0 lots" and send no edit. Every RH-1 lot must not freeze the page: resolution is in the worker and the recompute is budgeted. Tasks 3 (`an empty brush compiles to no edit`), 4 (`district family`) and 11 (bench).
4. **Erase and protect interacting with order.** Erase after a raise removes those lots; a raise after the erase paints them again; protection beats every brush (the lot is not hostable whatever the user layer says), and unprotecting a lot that a category still protects leaves it protected. Task 3 tests `erase removes from earlier brushes only` and `protection wins over a later raise`; Task 1B test `a protected lot is not hostable after a raise`.
5. **A worker crash or chunk failure while a brush is resolving.** Pending `resolveBrush` promises resolve with `{ ok: false, reason: 'no-session' }`, the brush shows "Couldn't find lots: Retry", and failed recompute cells show the existing chunk Retry. Task 5 test `crash resolves pending brush requests` and Task 8 test `a failed brush offers Retry`.

### Task 1: Lever status rules and the load-failure fix

**Files:**
- Modify: `src/lib/sim/scenario-client.ts:109-136`, `:261-273`
- Create: `src/lib/sim-page/lever-status.ts`
- Test: `src/lib/sim/scenario-client.spec.ts`, `src/lib/sim-page/lever-status.spec.ts`

**Interfaces:**
- Consumes: `LeversResponse` (`src/lib/sim/scenario/types.ts:113-129`), `LeverCapacity`, `LeverLookups`.
- Produces:

```ts
// scenario-client.ts: new private #sessionRev (the latest initScenario rev). An error with
// rev >= #sessionRev clears #leversRev when it ended the session: code !== 'bad-request', or
// rev === #sessionRev. (Carried note "Plan 3, load failure": a load error is posted at the
// initScenario rev, below a setLevers sent before load.)

// lever-status.ts
export type LeverStatus =
  | { kind: 'off' }                                        // /fzp path: no levers
  | { kind: 'resolving'; rev: number; done: number; total: number; failedCells: string[] }
  | { kind: 'current'; rev: number; lookups: LeverLookups; capacity: LeverCapacity }
  | { kind: 'failed'; rev: number };
export interface LeverStatusState { sentRev: number | null; status: LeverStatus }
export function leversSent(s: LeverStatusState, rev: number): LeverStatusState; // -> resolving 0/0
export function leversMessage(s: LeverStatusState, m: LeversResponse): LeverStatusState;
export function leversError(s: LeverStatusState, rev: number): LeverStatusState;
```

  `leversMessage` keeps a message with `m.rev >= sentRev` and drops an older one. It never consults the timeline barrier, so a reroll does not make lever messages stale (carried note "Plan 3, reroll while resolving"). `current` with `m.rev >= sentRev` sets `current`. `leversError` with `rev >= sentRev` sets `failed`.

- [ ] **Step 1: Failing tests.**
  - Client, `load failure clears pending`: `initScenario(m, h, null, DEFAULT_LEVERS)` (rev 1), `setLevers(...)` (rev 2), worker posts `{ type: 'error', rev: 1, code: 'scenario-invalid' }`. Expect `leversPending` false.
  - Client: `{ type: 'error', rev: 3, code: 'bad-request' }` for a reroll at rev 3 after `setLevers` at rev 2 leaves `leversPending` true until rev 2's `current`.
