Funding award rule: implementation plan

Award what the pools can pay now (R1), give a fully funded bundle the ordinary odds (R2 and its riders), close a pool only when no waiting ask fits (M4), and add the money monotonicity check that proves more money never builds fewer homes.

For agentic workers REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps are checklist items; progress is kept in the workspace ledger, not in the plan.

Overview

Goal
Adding any offered funding preset to any set never lowers net, funded or affordable homes at Dec 2035, 2040, 2045, 2055 or 2060 by more than 5 homes, and scripts/money-monotone.ts fails when it does.
Architecture
The award rule (awardSet, awardPasses in src/lib/sim/scenario/funding.ts) is shared by both engines, so R1 is one change. The certain hazard and the first-day rule live twice, in the step engine's clocks (world/funding/clocks.ts) and the old scenario engine (scenario/funded.ts); both change together so the tolerance referee and the kernel equivalence test keep holding. The odds-shift clamp is applied at those two call sites through one helper in scenario/funding.ts, never in src/lib/sim/finance, which is hashed into the dataset version. The closing fix is a separate commit in world/funding/closing.ts. The monotonicity check is a script over a real dataset, run by hand; the dataset-free property test is what signoff enforces.
Tech Stack
TypeScript, Vitest (server project for engine and scripts/**/*.spec.ts, client project for the browser goldens), tsx for scripts, the timeline host (src/lib/sim/world/host.ts) driven from Node.
Spec
2026-11-25-funding-award-rule-design.html. Owner rulings of 2026-11-25: R3 (with its three riders), current law moving is accepted, and current law covers only what exists today.

Review focus

  1. Grouped serving under the new rule. The grouped line bisects each group's largest passing size (line.ts:197, serve.ts:172-186), which needs "passes" to stay monotone in units. A partial award must not break the scan/grouped equivalence. Pinned in Task 2 (t2-s6): line.spec.ts's 500 random lines also count awards whose set is shorter than the bundle, and that count is above 0.
  2. A certain bundle awarded a partial set. A reader expects "fully funded" only when the money awarded covers the whole cost. Such a project is not certain: it can exit, it takes pathwayForNew, it is revised. Pinned in Task 2 (t2-s1): the world engine's rewritten rule 16 test asserts projects.certain[row] === 0 for the partial awards, and the old engine's stack test asserts funding.certain === false.
  3. A bundle worth nothing. Today a bundle that every pool can pay is awarded whatever its level, even 0 (funding.ts:402: below(0, 0) is false). Under the fallback no set at level 0 is awarded, whole or partial, and the lot keeps its ordinary start; awardPasses must agree on the whole-bundle case it used to short-cut (:486). Pinned in Task 2 (t2-s1).
  4. Loan coverage above 1 on the market kind. revolving-fund lends to market lots; after the clamp its odds equal those at coverage 1, the rate is finite, and a market funded start is still never later than the ordinary one. Pinned in Task 3 (t3-s8).
  5. The old engine's skip shortcut. Certain lots had an Infinity skip bound (funded.ts:686-689); without certainty the bound is finite and more lots are passed over on one draw. Runs with the shortcuts on and off must stay identical. Pinned in Task 3 (t3-s4): funded.spec.ts's noShortcuts comparisons run on a finance input whose affordable bundle reaches level 1.
