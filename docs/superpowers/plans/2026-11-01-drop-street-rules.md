# Drop Street-Based Zoning Rules Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `/sim` offers only Transit rules; the app stops fetching `frontage.bin`, the pipeline stops building it, and a saved policy holding street rules still opens without them.

**Architecture:** A removal in dependency order. Task 1 removes the `street` rule kind from the policy model and the rule UI together (they share `ZoningRule`), with a silent drop in `'reconcile'` parsing. Task 2 removes the `street` brush query and the frontage file from the brush engine, the scenario host and loader, and the benchmark. Task 3 removes the frontage step, V34, the T14 rule and the `datasf-streets` source from the pipeline, deletes the shared frontage codec, and regenerates the fixture dataset and the mini goldens with the real pipeline. Task 4 updates the live docs. Each task leaves `npm run check` and its test projects green.

**Tech Stack:** SvelteKit 2, Svelte 5 runes, TypeScript, Vitest (server, client, pipeline projects), Playwright, DuckDB pipeline (tippecanoe, pmtiles installed).

**Spec:** `docs/superpowers/specs/2026-11-01-drop-street-rules-design.md` (approved, binding). Read it before each task.

## Global Constraints

- Policy schema stays `2`. No schema bump, no migrator, no notice, no dropped-rule count.
- `parseSimDoc(…, 'reconcile')` (what `SIM_CODEC.load` uses): a stored rule with `kind: 'street'` is dropped silently; every other part of the policy loads as before; other unknown kinds still fail as they do now.
- `strict` parsing (publishing) still rejects `kind: 'street'` with `bad-field`.
- The app manifest schema keeps accepting the optional `scenarios.fzp.frontage` key, so older datasets (live `2026-10-29-14e0eccb`) still validate; nothing reads it.
- Invariants are V1 to V33 afterwards. V34's number is retired, not reused.
- `fixture-0` and `pipeline/test/fixtures/mini/golden/` are regenerated by the real pipeline only; never hand-edit them.
- Do not edit historical plans and specs under `docs/superpowers/`, or `CHANGELOG.md`. Do not touch `LOT_FRONTAGE_M` in `src/lib/generator/`.
- No dataset rebuild, no upload.
- Code style: 2-space indent, single quotes, no trailing commas, 100 columns. Vitest runs with `expect.requireAssertions`: every test calls `expect`.
- Conventional Commits. Never `cd … && cmd` compounds.

## Review Focus

1. An autosave holding a transit rule, a street rule, paint, protections and timing restores everything but the street rule, and the next autosave omits it (tests: Task 1 Steps 1 and 5).
2. A dataset manifest that still names `scenarios.fzp.frontage` still validates and loads `/sim` (tests: Task 2 Step 1; `fixture-0` still names it during Task 2's e2e run).
3. The brush catalog no longer fetches `frontage.bin`, even when the manifest names it (tests: Task 2 Steps 1 and 6).
4. The attribution page no longer lists DataSF Streets but lists the rest (test: Task 3 Step 1).
5. Transit rules still resolve with the catalog's transit and neighbourhood files, including the file-once cache and 5xx retry now exercised by transit queries (tests: Task 2 Step 1; e2e transit rule in `e2e/sim.spec.ts`).

Decisions in this task:
- The drop rides on the existing `presetLayer: 'reconcile'` mode rather than a new option (builder's call: `parseSimDoc` already maps `load` to it, and the spec ties the drop to `parseSimDoc(…, 'reconcile')`). Update the JSDoc of `parseSimPolicy` and `parseSimDoc` to say so.
- The drop checks only `kind`, not the dropped rule's other fields (builder's call: validating them would keep `STREET_CLASSES` alive for data we throw away).
- Paths in errors keep the stored index: with `rules: [street, badTransit]` the error is at `rules[1]…`. A dropped rule's id does not take part in the duplicate-id check.
- "Add transit rule" uses `aria-disabled="true"` plus `aria-describedby` on its reason while `transitUnavailable` is non-null, and its click does nothing then (builder's call: a `disabled` button drops out of the tab order, so `afterRemove`'s focus on the add button, WCAG 2.4.3, would fail while the catalog loads; the form's Save button already stays enabled for the same reason). The reason text shows under the button, as the old menu items did. The `data-brush-add` attribute stays.
- `RuleKind`, `RULE_KINDS` and `ruleKindOf` are deleted outright (the simpler option the spec allows).
