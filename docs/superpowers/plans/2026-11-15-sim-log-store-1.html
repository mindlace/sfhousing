Overview

Goal
Build, test and document the browser's log store so that plan 2 (the socket) and plan 3 (the page) only wire it: a pure LocalLog that folds confirmed then pending commits and re-applies pending ones on a new tip without ever moving a sim to another dataset than its fold's; pure authoring of edit, restore, move and import commits; a pure dataset decision; a durable SimDb on IndexedDB; and a LogStore that satisfies a structural interface both it and today's PolicyStore meet. Review Focus

  1. A tab opened before a release, re-applying its pending commits over another writer's move to the new dataset. The fold must stay on the new dataset; the old tab must stop authoring and keep its commits unsent. Pinned by Task 5's "never re-stamps a commit onto an older dataset than the fold's" and Task 9's "stops as stale after a foreign move".
  2. A co-writer's commit arriving in the middle of a drag. The draft is committed first, then re-applied with the rest. Pinned by Task 9's "a foreign commit ends an open draft".
  3. Two fresh tabs making their first edit at once. One sim, both edits in it. Pinned by Task 10's "two fresh stores over one database make one current sim".
  4. A tab whose pending row another tab claimed. It must not put its owner back, and must not send the commit. Pinned by Task 7's contract "a put of a record another owner holds is lost, not written" and Task 10's "forgets pending commits another tab took".
  5. IndexedDB failing mid-session (quota, an aborted transaction). The edit stays, is still sent, and the store never reports it stored. Pinned by Task 7's "a write whose transaction aborts rejects and writes nothing" and Task 10's "a failed write sends the edit and never reports it stored".

Invariants

Each holds after every public call returns. A task's tests name the ones they pin.

  1. I1, the page is the fold. With no draft open, LogStore.policy and name are content-equal to LocalLog.ruleset(): the fold of the confirmed commits followed by the pending ones (R16). With a draft open they are the editor's output on top of that fold, and nothing else.
  2. I2, stored before sent while storage works. With storage working, LogStore.head() returns a pending commit only once the version of it that it returns is in IndexedDB (R15). With storage unavailable from the start or after a failed write, head() returns the head without waiting for a write, so the server holds the only copy, and local stays 'failed': the store never reports such a commit as stored on this device.
  3. I3, pending sit on the tip. pending[i].draft.parent === tipSeq + i, and a pending restore's restores.position is the current position of its target commit.
  4. I4, confirmed only from the stream. A commit enters confirmed only through receive, in seq order with no gap (R26, R27).
  5. I5, the stored state was a real state. Writes are serialized and each is one IndexedDB transaction that counts as done only on its complete event, so what IndexedDB holds is always a state the tab held, possibly an older one. On open, pending commits whose ids are confirmed are deleted, not resent.
  6. I6, a look mints and records nothing. Until the first edit no sim id is minted and no record is written. Opening the store may open, and so create, an empty IndexedDB database.
  7. I7, only sendable commits are pending. A commit becomes pending, whether authored or re-applied, only after parseCommitDraft, fitsCommit and LogState.apply(…, { check: true }) on the local tip accepted it. A re-applied commit that fails is dropped and reported.
  8. I8, history from the log. Undo and redo targets come from the commits alone (R12); History's positions equal undoRedo's for every log.
  9. I9, nothing past a gap or a newer build. receive applies nothing after a commit whose seq is not the next one, or whose shapes is above SHAPES_REVISION; the latter, or a pending commit under such a revision, stops the store ('future') and leaves that record untouched.
  10. I10, one order. Two logs fed the same stream, each re-applying its own pending commits, end with the same confirmed commits and the same ruleset as the server (R18, R40).
  11. I11, never moved to another dataset by re-applying. A re-applied pending commit is stamped with the dataset the local fold is on after the commits before it; only a move commit carries another dataset, and a re-applied move to another dataset than the fold's is kept only while the server's dataset is unknown or equals the move's. Nothing is sent before the server's dataset is known (head() is null until setServerDataset, which plan 2 calls on hello), so a move kept while it was unknown is never sent unchecked.
  12. I12, authoring only on the page's dataset. A page authors on a sim only when the local fold's dataset is null or equals the page's, or the page knows it is current (its dataset equals the server's) and appends the move commit first (the dataset rule).

Decisions made in this plan

  1. Unit 4 is four plans: this core; the socket, registration and tabs; the page; reading on a sim's own dataset. Reason: each merges with /sim working, and the core's correctness can be reviewed without a page or a socket in the way. See the outline.
  2. Until unit 5, /sim holds one current sim per browser, its id in the IndexedDB meta row current; no route changes. LogStore.open(simId) takes any id, so unit 5's /sim/<simId> calls it with the route's id and nothing in the store changes.
  3. Two layers. LocalLog (plain class, pure) holds commits and does every fold and re-apply; LogStore (runes) adds drafts, the dataset gate, persistence and the editors' interface. Reason: logic a Node test drives.
  4. After a commit the page shows the fold, keeping the object it already shows when the fold is canonically equal to it (rulesetText), else the fold's object. Reason: I1, while a commit that changed nothing visible keeps identity, so callers that compare store.policy === before (Inspector.svelte:221-223, FundingTab.svelte:208-210) announce only real changes. apply also returns whether its own edit was applied.
  5. Pending commits are re-applied as soon as a foreign commit arrives, not only on behind. Reason: the page must show confirmed then pending (R16) at every moment; behind then only means "send again" (plan 2).
  6. A pending restore names its target by commit id (Pending.targetId, null for position 0) and its position is recomputed on every re-apply; a restore whose target was dropped is dropped. Reason: a target can itself be pending, and its position moves when foreign commits land before it. The spec's "keeps its target position" will be amended to read this way.
  7. Its own commit coming back skips the re-apply only when the confirmed commit is the head pending one by id with canonically equal changes; anything else re-applies everything.
  8. Drafts (R1). apply with a coalesce key opens or continues a draft (memory only, not a commit). The draft becomes a commit when: the next apply has another key or none; settle() is called (plan 3 calls it on focus leaving the inspector, visibilitychange to hidden, pagehide, beforeNavigate and the page's teardown); undo, redo, undoTo, reset, rename, importContent or claim runs; or a foreign commit arrives. A draft committed at pagehide is committed in memory; its write is best effort.
  9. Restore labels. An undo commit's label is the label of the change it undoes, a redo's the change it redoes, a jump's the caller's. History derives the labels from the log by the same walk as undoRedo.
  10. An undo whose target already equals the current ruleset goes on to the next target; the same for redo.
  11. Undo and redo are off whenever the store would have to move or is stopped: canUndo, canRedo false, undo(), redo() return null and author nothing. Reason: the move is a system commit that empties both stacks (R12).
  12. A jump to a position on another dataset restores and aligns in one commit: kind: 'restore', restores: { position, as: 'jump' }, changes diff(current, align(ruleset at position, stamp)); when align cannot reach that dataset the jump is refused. Reason: undoTo can land before a move made 250 ms earlier.
  13. The move and the alignment commit (R55): on move (the rule) the store authors, before the next commit, kind: 'system', source sim.dataset, label 'Moved to new data', changes diff(current, align(current, P)), stamped P; when the diff is empty no move commit is made and the next commit carries P. After every re-apply that kept pending commits, and when the server's dataset becomes known, if the fold is on P (or the decision is move) and align would still change it, one alignment commit of the same form is appended. A pending move is recomputed on every re-apply like a restore, and dropped, unreported, when its diff is empty, or when it moves to another dataset than the fold's and the server's known dataset is not its own.
  14. A refused edit is not applied. An edit whose diff/toLogForm throws, that parseCommitDraft or LogState refuses, that fails fitsCommit, or that would pass the pending cap leaves the policy as it was, sets refusal ('invalid', 'too-large', 'queue-full') and returns false; 'invalid' also logs [sim-store] edit refused.
  15. IndexedDB schema, version 1: database sfhousing-sim-log; stores sims (key simId), commits (key [simId, seq]), pending (key [simId, id], unique index order on [simId, n]), meta (key key). n comes from the meta row n:<simId> inside the write transaction. Writes use durability: 'strict' (MDN) and resolve only on the transaction's complete, rejecting on abort or error (a quota error surfaces as an abort). A later version adds an if (oldVersion < 2) step and never edits step 1.
  16. A write batch is the tab's whole dirty state in one transaction. A put of a pending record applies only while the stored record's owner is this tab, checked inside the transaction; a record another tab holds comes back as lost, and the store forgets it without sending. A remove deletes only this tab's records.
  17. Storage failure (R15 as amended): when IndexedDB is unavailable from the start or a write fails, the store keeps working, stops writing, and head() hands pending commits to be sent at once; local is 'failed', so the page never says "saved on this device". Whenever storage works, the strict order holds.
  18. Earlier positions are folded from checkpoints: confirmed positions from LogState clones at multiples of a spacing that starts at 256 and doubles whenever there would be more than 64; pending positions from a clone every 32 pending commits. Nothing keeps a ruleset per commit.
  19. Labels over LABEL_MAX are cut to 199 UTF-16 units, never inside a surrogate pair, plus …. Builder's call: editors' labels embed policy names.
  20. Sources (SOURCES): sim.edit (default for apply), sim.undo, sim.redo, sim.revert (a jump), sim.dataset (a move or an alignment), sim.name (a rename, as the server's rename), sim.import, sim.reset. apply takes an optional fourth argument source; plan 3 gives each control its own code.
  21. A stopped store authors nothing: with stopped set ('future', 'stale', 'unknown-dataset') apply, rename, reset, undoTo do nothing (apply returns false), undo and redo return null, and head() returns null. 'future' is permanent for the store's life; the other two clear when the decision becomes edit or move.
  22. Each tab shows the confirmed commits and its own pending ones. Another tab's pending work appears when it is confirmed. LogStore.open(simId, { claim }) and LogStore.claim(owners) take other tabs' pending commits atomically and re-apply them after this tab's own; plan 2 decides which owners are gone.
  23. The identical-stroke delete rule is computed against the tip passed to reapply, before the walk, for every delete whose key is k:<digest> or k:<digest>~n with n of 2 or more; a retargeted delete is applied to its target key directly. The count of repeats on the tip ignores adds of the same group earlier in the same commit: a commit from diff puts every delete before every add (sim-log.md, Diff, order 1 then 4), and reapply keeps a commit's order. It stays private to reapply.ts.
  24. The control plane's raw-error log lines are four, not three: resend/+server.ts:32,65, sims/[simId]/+page.server.ts:47, and members/[userId]/+server.ts:27.
  25. The IndexedDB code is tested in the client project (real Chromium), with the same contract suite run in Node against memorySimDb. Reason: no new dependency, and the real engine is the one that matters.
  26. The store does not check the hash chain. Reason: chainHash is async and receive must be synchronous.
  27. The pending cap: at most PENDING_MAX 1,000 commits and PENDING_BYTES_MAX 8 MiB (8,388,608 bytes of draft JSON) per tab per sim. An authored commit past either is refused 'queue-full'; re-applying never refuses for the cap. Reason: far inside the object's limits (100,000 commits and 64 MiB a sim, so a full queue alone never fills a sim), drained in about seven and a half minutes at the object's rate (a burst of 120, then 2 a second), and bounded in memory with checkpoints every 32.
  28. The current-sim pointer is set only if absent, inside the transaction that creates the sim. A fresh store whose first edit finds a current sim already set does not create a second one: it opens that sim and makes its first edit there as a pending commit.
  29. The structural editor interface DocStore names exactly what the page and the editors use of a schema 4 store today: policy, canUndo, canRedo, undoLabel, redoLabel, apply, undo, redo, undoTo, reset (SimPage.svelte:190-1048, Inspector.svelte:95-283, lens.ts:301-341). PolicyStore<SimPolicy4> and LogStore both satisfy it, checked at compile time; plan 3 switches Inspector.svelte:50 and its test host from the class (nominal, because of its #private fields) to it. LogStore.reset(p) is an undoable edit to p (source sim.reset, label 'Reset'), not a cleared history.
  30. The import hook: LogStore.importContent(content, marker) authors one system commit (source sim.import) and writes it with a marker compare-and-set in the same transaction; when the marker is not what the caller expected, nothing is written and the commit is withdrawn. Plan 3 uses it for the first import and for a re-import of a newer autosave record.
  31. undoTo(p) jumps to the commit that produced p; when that commit was dropped, or p was never a commit, it is an edit to p. A jump clears redo (R12: a jump counts as an edit), where PolicyStore kept it.
  32. Derived state is computed once per change: canUndo, undoLabel and the rest are runes set after each state change, never recomputed on each read.

Task 2: Re-apply retargets deletes of identical strokes

The log core's first carried "Log store" item: "with k deletes of one group of identical strokes in a commit, and t the highest repeat on the new tip, the i-th delete targets repeat t - k + i, and is dropped as gone when that is below 1" (decision 23). Today a pending delete of k:X on a tip holding k:X and k:X~2 is invalid (checked at plan time).

Interfaces

  • reapply(tip, input)'s signature and results do not change.
