Sim log store, plan 1: the store core

Unit 4 of the sim message log, first of four plans: the browser's log store (confirmed plus pending commits, drafts, undo and redo as restore commits, re-applying on a new tip, the dataset move) and its IndexedDB, with no change to any page.

For agentic workers REQUIRED SUB-SKILL: use superpowers:subagent-driven-development to implement this plan task by task. Steps are checklist items; progress is kept in the workspace ledger, not in the plan.

Overview

Goal
Build, test and document the browser's log store so that plan 2 (the socket) and plan 3 (the page) only wire it: a pure LocalLog that folds confirmed then pending commits and re-applies pending ones on a new tip, pure authoring of edit, restore and move commits, a durable SimDb on IndexedDB, and a LogStore with the interface PolicyStore has today. Also fix the carried items this unit owns that touch the log core and the server logs.
Architecture
New directory src/lib/sim-store/. Logic is in plain modules a Node test drives (history.ts, local-log.ts, author.ts); persistence is behind the SimDb interface with an in-memory implementation for Node and an IndexedDB one tested in real Chromium; log-store.svelte.ts is a thin rune facade. Nothing under src/lib/sim-page/, src/lib/timeline/ or src/routes/sim/ changes in this plan.
Tech stack
TypeScript, Svelte 5 runes (a .svelte.ts class, imported by Node specs as stroke-adapter.spec.ts imports PolicyStore), IndexedDB (no library), Vitest server (Node 24) and client (Chromium via Playwright) projects, fast-check.

Review Focus

  1. A co-writer's commit arriving in the middle of a drag. The draft was made on the old tip; showing it over the new tip without a commit would show a ruleset that is neither the fold nor the person's edit. Expected: the draft is committed first, then re-applied with the rest. Pinned by Task 8's "a foreign commit ends an open draft".
  2. Undo right after a reload. The commit to undo is pending, made by the tab before the reload, and the label must still be the change's. Pinned by Task 8's "reopens with its pending commits and its undo label".
  3. An undo whose target commit was dropped on a new tip. A restore cannot reproduce a position that no longer exists. Expected: the restore is dropped and reported, never sent with a wrong position. Pinned by Task 4's "drops a pending restore whose target was dropped".
  4. Deleting one of two identical strokes while another writer adds a third. Today the whole commit is refused. Pinned by Task 2.
  5. IndexedDB failing mid-session (quota, a browser that refuses). The page must keep the edit, never claim it is stored, and never send it (R15). Pinned by Task 8's "a failed write keeps the edit in the tab and sends nothing".

Invariants

Each holds after every public call returns. A task's tests name the ones they pin.

  1. I1, the page is the fold. With no draft open, LogStore.policy and name are LocalLog.ruleset(): the fold of the confirmed commits followed by the pending ones (R16). With a draft open they are the editor's output on top of that fold, and nothing else.
  2. I2, stored before sent. LogStore.head() returns a pending commit only once the version of it that it returns is in IndexedDB (R15). After a failed write it returns null for the rest of the store's life.
  3. I3, pending sit on the tip. pending[i].draft.parent === tipSeq + i, and a pending restore's restores.position is the current position of its target commit.
  4. I4, confirmed only from the stream. A commit enters confirmed only through receive, in seq order with no gap (R26, R27).
  5. I5, the stored state was a real state. Writes are serialized and each is one IndexedDB transaction, so what IndexedDB holds is always a state the tab held, possibly an older one. On reopen, pending commits whose ids are confirmed are removed before anything is re-applied.
  6. I6, a look writes nothing. Until the first edit, no sim id is minted and nothing is written; simId is null.
  7. I7, only foldable commits are pending. A commit becomes pending only after LogState.apply(…, { check: true }) accepted it on the local tip and fitsCommit passed.
  8. I8, history from the log. Undo and redo targets come from the commits alone (R12); History's positions equal undoRedo's for every log.
  9. I9, nothing past a gap or a newer build. receive applies nothing after a commit whose seq is not the next one, or whose shapes is above SHAPES_REVISION; the latter makes the store read-only.
  10. I10, one order. Two logs fed the same stream, each re-applying its own pending commits, end with the same confirmed commits and the same ruleset as the server (R18, R40).

Decisions made in this plan

  1. Unit 4 is four plans: this core; the socket, registration and tabs; the page; reading on a sim's own dataset. Reason: each merges with /sim working, and the core's correctness (re-applying, history) can be reviewed without a page or a socket in the way. See the outline.
  2. Until unit 5, /sim holds one current sim per browser, its id in the IndexedDB meta row current; no route changes. LogStore.open(simId) takes any id, so unit 5's /sim/<simId> calls it with the route's id and nothing in the store changes. Reason: the smallest change that gives a sim an id without inventing URLs unit 5 owns.
  3. Two layers. LocalLog (plain class, pure) holds commits and does every fold and re-apply; LogStore (runes) adds drafts, persistence and the editors' interface. Reason: lesson 4, logic a Node test drives.
  4. After a commit the page shows the fold's object, not the editor's. Reason: I1; the fold is the only source of rules. Callers that compare store.policy === before (Inspector.svelte:221-223, FundingTab.svelte:208-210) still see a change as a new object and no change as the same object.
  5. Pending commits are re-applied as soon as a foreign commit arrives, not only on behind. Reason: the page must show confirmed then pending (R16) at every moment; behind then only means "send again" (plan 2).
  6. A pending restore names its target by commit id (Pending.targetId, null for position 0) and its position is recomputed on every re-apply. A restore whose target commit was dropped is dropped. Reason: a target can itself be pending, and its position moves when foreign commits land before it (R18 "keeps its target").
  7. Its own commit coming back skips the re-apply only when the confirmed commit is the head pending one by id with canonically equal changes; anything else re-applies everything. Reason: cheap in the common case, safe otherwise.
  8. Drafts (R1). apply with a coalesce key opens or continues a draft (memory only, not a commit). The draft becomes a commit when: the next apply has another key or none; settle() is called (plan 3 calls it on focus leaving the inspector, on visibilitychange to hidden and on pagehide); undo, redo, undoTo or rename runs; or a foreign commit arrives (5). Reason: R1's three triggers, plus the moments a draft would otherwise sit on a stale base.
  9. Restore labels. An undo commit's label is the label of the change it undoes, a redo's the label of the change it redoes, a jump's the caller's ('Reverted a change' today). History derives the undo and redo labels from the log by the same walk as undoRedo. Reason: labels follow the log across reloads and devices (R13) with nothing stored beside it.
  10. An undo whose target already equals the current ruleset (a co-writer reverted it) goes on to the next target; the same for redo. Reason: an empty diff cannot be a commit, and a button that does nothing would stick.
  11. Undo and redo are off while the tip's dataset differs from the page's. Reason: the first commit would be the move, a system commit that empties both stacks (R12); offering an undo that then does nothing is worse.
  12. A jump to a position before a dataset move restores and moves in one commit: kind: 'restore', restores: { position, as: 'jump' }, changes diff(current, align(ruleset at position)). Reason: the one jump today (undoTo, back to the last document the engine accepted) can land before a move made 250 ms earlier; refusing it would leave a rejected document showing. The carried item allowed either.
  13. The move commit (R55) is authored before any commit (edit, restore, rename) when the local tip's dataset is not null and differs from the page's: kind: 'system', source sim.dataset, label 'Moved to new data', changes diff(current, align(current)). When the diff is empty no move commit is made (the next commit carries the new dataset). align is the page's (plan 3 passes reconcilePolicy4); here it is an option.
  14. A refused edit is not applied. apply whose result diff/toLogForm throws on, that LogState refuses, or that fails fitsCommit, leaves the policy as it was and sets refusal ('invalid' or 'too-large'); 'invalid' also logs [sim-store] edit refused. Reason: I7; the object would refuse it anyway and it could never be sent.
  15. IndexedDB schema, version 1: database sfhousing-sim-log; stores sims (key simId), commits (key [simId, seq]), pending (key [simId, id], unique index order on [simId, n]), meta (key key). n is allocated inside the write transaction from the meta row n:<simId>, so two tabs never collide. Writes use durability: 'strict' (MDN). A later version adds an if (oldVersion < 2) step and never edits step 1. Reason: the confirmed log, each tab's pending commits and the per-browser pointers, with ordering that survives several writers.
  16. A write batch is the tab's whole dirty state (new confirmed commits, changed and new pending, removed pending) in one transaction, not one transaction per event. Reason: I5 with no ordering bookkeeping; a burst of edits costs one write.
  17. When IndexedDB is unavailable or a write fails, the store keeps working in memory, local is 'failed', and head() returns null: nothing is sent. Reason: R15 as written. An alternative is an open question (Open questions).
  18. Earlier positions are folded from checkpoints: LogState clones at multiples of a spacing that starts at 256 and doubles whenever there would be more than 64. Reason: undo targets need any position synchronously (store.undo() returns its label at once, stroke-adapter.ts:89-90), and a 100,000-commit sim must neither refold from 0 nor hold a clone per commit.
  19. Labels over LABEL_MAX are cut to 199 UTF-16 units, never inside a surrogate pair, plus …. Builder's call: editors' labels embed policy names.
  20. Sources (SOURCES): sim.edit (default for apply), sim.undo, sim.redo, sim.revert (a jump), sim.dataset (a move), sim.name (a rename, as the server's rename), sim.import (plan 3). apply takes an optional fourth argument source; plan 3 gives each control its own code. Builder's call: the per-control list belongs with the page.
  21. A commit from a newer build makes the store read-only (stopped: 'future'): nothing more is folded, apply does nothing, and plan 3 offers a reload. Reason: editing on a tip the store cannot read would be refused behind for ever.
  22. Each tab shows the confirmed commits and its own pending ones. Another tab's pending work appears when it is confirmed. SimDb.claimPending moves pending commits to this tab; plan 2 decides when (a closed tab's, a reload's). Reason: R40 ("each socket sends its own commits") with no cross-tab re-apply.
  23. The identical-stroke delete rule is computed against the tip passed to reapply, before the walk, for every delete whose key is k:<digest> or k:<digest>~n; a retargeted delete is applied to its target key directly. It stays private to reapply.ts. Prototyped at plan time (What was run).
  24. The control plane's raw-error log lines are four, not three: resend/+server.ts:32,65, sims/[simId]/+page.server.ts:47, and also members/[userId]/+server.ts:27. All four are fixed.
  25. The IndexedDB code is tested in the client project (real Chromium), with the same contract suite run in Node against memorySimDb. Reason: no new dependency (fake-indexeddb is not installed) and the real engine is the one that matters.
  26. The store does not check the hash chain. The object already did; plan 2 may compare the tip hash after a resume. Reason: chainHash is async and receive must be synchronous for the page.

  position: number;
  /** For undo: the change undone. For redo: the change redone. */

export class History {
  /** Takes one commit, in seq order. */

Anything else pushes { position: cur, label: e.label } on undo and empties redo. Then cur = e.seq.
