Contracts implementation plan

The incremental game's interface rows as code: types and throwing stubs, the save sync and component stubs, the measure-dating stub, the e2e seam with its helpers, and the doc index.

For agentic workers REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps are checklist items; progress is kept in the workspace ledger, not in the plan.

Overview

Goal: Land every shape the later units of the incremental game build against (rows G1 to G5, S1 to S3, M1 and X1), so they can be written in parallel, while the application and every existing suite run unchanged.

Architecture: Pure type modules in src/lib/game/ whose functions throw Error('not implemented'), linked only by import type; a throwing GameStore, a working do-nothing createSaveSync and three components that render nothing; a dateMeasure stub that returns its policy. The e2e seam (src/lib/game/e2e.ts, no imports) and its Playwright helpers (e2e/helpers/game.ts) are implemented in full. No app module imports src/lib/game/ in this unit.

Tech Stack: TypeScript, Svelte 5 (runes), Vitest 4 (projects server and client, vite.config.ts:57, vite.config.client-test.ts:49), vitest-browser-svelte 3 for component rendering, Playwright 1.62 (projects chromium and mobile, playwright.config.ts:30-31; the web server builds with VITE_E2E=1, playwright.config.ts:51).

// src/lib/game/levels.ts
import type { Day } from '$lib/timelapse/time';

import type { GoalOutcome } from '$lib/timeline/outcome';

export type Level = 1 | 2 | 3 | 4 | 5;
export const LAST_LEVEL: Level = 5;

/** What the months reached so far show: `{ kind: 'reached'; on }` or `{ kind: 'missed'; short }`. */
export type Result = GoalOutcome;

/** The result to beat: the day a banked result reached the goal. */
export interface Bar {
  on: Day;
}

export function beats(seen: Result, bar: Bar): boolean;

/** Paint is won: capacity is at least the goal's amount. */
export function paintWon(net: number, amount: number): boolean;
reached.on
The first day of the calendar month in which the goal's amount is first met, as readGoal gives it.
  • beats(seen, bar) is true when seen reached the goal and seen.on is in an earlier calendar month than bar.on.
  • It is false in every other case: a tie never beats, and a missed result never beats.
  • paintWon(net, amount) is net >= amount.
  • Only a reached result is ever banked, so a bar is always a date.

SAVES_KEY
Holds { v: 1, current: string, saves: SaveEntry[] }.
saveKey(id)
Holds one GameSave. For the current game its plan and policy are stale: the records under sfhousing:plan:v1 and sfhousing:sim:v2 are the truth.
  • barOf is { on: banked[level - 1].on } at levels 3 to 5.
  • levelUp from level 1 takes null and banks nothing.
  • levelUp from levels 2 to 4 stores the day under the level being left and adds one to the level.
  • levelUp at level 5 stores banked[5] and keeps the level at 5.
  • The page calls won() when a win card first shows.
  • allowed is allowedAt(progress.level).
  • While open is true no page shows a game part: no level cell, no win card, no bar or "To beat" flag, no locked lane, no reworded outcome message, no Remix button, and no offer is set. The pages read open; they never compare allowed with ALL_ALLOWED.
  • The page calls setOffer with the win while its seen result wins the level, and with null on any edit and when it unmounts. The offer is kept in memory only.
  • The store's levelUp() banks the offer with the pure levelUp, clears the offer, and stores the game. The win card and the level panel both call it.
  • The page that set the offer reacts to the level changing: /sim returns the clock to today, and Paint opens /sim.
  • The page calls touched() after its autosave writes a record key. The store sets the current game's savedAt and calls sync.changed(currentId).
  • On first construction with no SAVES_KEY, the store makes one saved game at level 1 whose plan and policy are whatever the two record keys hold.
  • newGame, switchTo, remix and remove of the current game first copy the two record keys into the current game's stored save, then write the new current game's plan and policy into the two record keys.
  • After newGame, switchTo or remove answers ok, the caller loads the new current game's page with a full page load: / at level 1, /sim above it.
  • After remix answers ok, the caller loads / for a plan and /sim for a policy, with a full page load.
  • remix's record is the text the page's autosave holds under the record key for the published document. The caller builds it with the codec the page already uses, so the store never reads inside a plan or a policy.
  • remix of a policy copies the current game's progress and plan; remix of a plan copies the current game's progress and policy. The new game's name is defaultSaveName({ kind: 'remix', title }).
  • newGame, remix and adopt answer full and change nothing when they would pass MAX_SAVES.
  • rekey of the current game leaves it current, keeps the offer and needs no page load: the records and the progress are untouched. The save sync uses it when it keeps both sides of a conflict (S2).
  • A write that the browser refuses answers storage and leaves the stored games as they were.
  • remove of the current game makes the most recently changed other game current; with none left it makes a new game.
  • rename trims the name, cuts it at SAVE_NAME_MAX, ignores an empty one, and sets nameIsDefault false.
  • defaultSaveName gives "Game, 22 Nov", "Remix of {title}" or "{name} (this device)", and adds " (2)", " (3)" while the name is in taken.
  • The store calls sync.changed(id) after every change to a saved game and sync.removed(id) after a remove.
  • A stored value that will not parse is copied to sfhousing:save:corrupt:<ISO time> and left out of the list.
  • With storage: null the store keeps one game in memory.
  • useGame() outside a provider returns openGame(), so a component test that provides no game sees every control.
  • Only the root layout calls provideGame. It makes the save sync with createSaveSync (S2), constructs the store with it, calls sync.attach(store) and provides the store.
  • When e2eOpen (X1) is true, the root layout provides openGame() instead and makes no sync.
  • The root layout's script that makes and provides the store belongs to game-core.

  • allowedAt(1) and allowedAt(2) have no kinds.
  • allowedAt(3) has permitting; allowedAt(4) adds zoning; allowedAt(5) adds money with money: 'given'.
  • ALL_ALLOWED has all three kinds and money: 'all'. No level in this round returns it.
  • The published view at /s/<id> runs under ALL_ALLOWED, so playable returns its document unchanged (D5).
  • runs is false for a kind not in a.kinds.
  • runs is false for a money policy that is not given while a.money is 'given'.
  • playable returns the document with only the policies that run, in their order, and returns the same object when nothing is removed.
  • Every money policy that addPolicy makes from a funding preset carries the preset's id in preset and the preset's label as its label.
  • The schema 4 parser accepts null or a preset id of 1 to 60 characters in a money policy's preset. Zoning and permitting are unchanged.
  • A money policy stored or published before this build has preset null, so it is not a given measure. It runs in the published view and is locked in a game.
  • An edit that changes what a given measure pays sets its preset to null.
  • isGiven is false for every zoning and permitting policy.
  • isGiven does not check the id against the presets on offer. A hand-made document can carry any id on any pool; nothing ranks one player against another, so that is accepted.
  • simLocked is true exactly at level 1. Pages call it and needsHigher; no page compares a level itself.
  • levelNeeded of a document with no policies is 2.

S1 The saved-games API

// src/lib/game/save-api.ts
import type { GameSave, SaveEntry } from './saves';

export const MAX_SAVE_BYTES = 600_000;

/** What every answer about the account carries. */
export interface AccountLine {
  handle: string;
  /** This identity has changed its handle at least once. */
  handleClaimed: boolean;
}

// GET /api/game
type ListGames =
  | { status: 200; body: AccountLine & { saves: (SaveEntry & { rev: number })[]; removed: string[] } }
  | { status: 401 };

// GET /api/game/[id]
type GetGame = { status: 200; body: { rev: number; save: GameSave } } | { status: 401 | 404 | 410 };

// PUT /api/game/[id]
interface PutGameBody {
  /** The rev this browser last saw for this saved game; null when it has never sent it. */
  baseRev: number | null;
  save: GameSave;
}
type PutGame =
  | { status: 200; body: AccountLine & { rev: number } }
  | { status: 409; body: { rev: number; save: GameSave } }
  | { status: 410 }
  | { status: 401; body: { error: 'sign_in' } }
  | { status: 422; body: { error: 'invalid' | 'too_many' | 'no_win' } }
  | { status: 403 | 413 | 415 | 429 };

// DELETE /api/game/[id]
type DeleteGame = { status: 204 } | { status: 401 };
// src/lib/server/db/schema/gameSave.ts
export const gameSave = sqliteTable(
  'game_save',
  {
    identityId: text('identity_id').notNull().references(() => userIdentity.id),
    id: text('id').notNull(),
    rev: integer('rev').notNull(),
    name: text('name').notNull(),
    level: integer('level').notNull(),
    /** The GameSave as JSON; empty once removed. */
    body: text('body').notNull(),
    savedAt: integer('saved_at', { mode: 'timestamp_ms' }).notNull(),
    removedAt: integer('removed_at', { mode: 'timestamp_ms' })
  },
  (t) => [primaryKey({ columns: [t.identityId, t.id] })]
);
  • PUT with no session makes an anonymous account, behind PSEUDO_MINT_RL, and stores the saved game at rev 1.
  • PUT with no session on a device that has signed in before (the sfh_known cookie) answers 401 sign_in and makes nothing.
  • PUT with no session and a save whose progress.firstWinAt is null answers 422 no_win and makes nothing: an account is made at the first win, never before.
  • PUT stores the save and adds one to its rev when baseRev equals the stored rev, or when the account has no saved game with that id and baseRev is null.
  • PUT of an id the account has never held stores it at rev 1 whatever baseRev says.
  • PUT of an id the account holds with any other baseRev answers 409 with the stored save and changes nothing.
  • PUT to a removed id answers 410.
  • PUT of a new id when the account has 12 saved games answers 422 too_many.
  • The id in the path must equal save.id, else 422 invalid. A body parseGameSave refuses is 422 invalid. A body over MAX_SAVE_BYTES is 413.
  • DELETE clears the body and sets removedAt; the row stays so other devices learn of it. Deleting an unknown or removed id is 204.
  • GET /api/game lists the saved games that are not removed, and under removed the ids removed in the last 90 days.
  • Every write requires a same-origin JSON request, as the account routes do; a write from another origin is 403. /api/game is a session route prefix.
  • When two identities are joined, the absorbed identity's rows move to the survivor. Nothing is merged.
  • When both identities hold a saved game under one id, the absorbed one moves under a new id; an absorbed row that is removed is dropped. The cap of 12 is not applied to a join.
  • Deleting an account deletes its game_save rows.
  • The server never reads inside plan or policy.

S2 The browser's save sync

// src/lib/game/save-sync.svelte.ts
export type SyncState = 'local' | 'saving' | 'saved' | 'offline' | 'sign-in' | 'full';

export interface SaveSync {
  /** Reactive. */
  readonly state: SyncState;
  /** Reactive: the account as the server last answered (S1's `AccountLine`); null until it has. */
  readonly account: AccountLine | null;
  /** The saved game `id` changed. */
  changed(id: string): void;
  /** The saved game `id` was deleted in this browser. */
  removed(id: string): void;
  /** Bring the account's saved games here and send this browser's there. */
  pull(): Promise<void>;
  /** The store saved games are read from and adopted into. Called once by the root layout. */
  attach(store: GameStore): void;
}

export function createSaveSync(opts: {
  storage: Storage | null;
  fetchFn: typeof fetch;
  /** Whether the root layout's `user` is set now. */
  signedIn: () => boolean;
}): SaveSync;
  • state is local until this browser has a session.
  • changed(id) sends nothing while this browser has no session and the game's firstWinAt is null.
  • When the sync attaches with no session, every saved game that has firstWinAt set and has not been sent since it last changed is queued to send, so a first win whose send never went still makes the account.
  • changed(id) debounces to one PUT per saved game per 2 seconds, with the save read from the store at send time.
  • The browser keeps each saved game's last seen rev under sfhousing:saves:revs.
  • A 409 keeps both: the browser's version is stored as a new saved game with a new id and the name defaultSaveName({ kind: 'conflict', name }), the account's version is adopted under the old id, and the new saved game is sent.
  • When the old id was the current game, the browser's version stays current under its new id, so nothing changes under the player's hands.
  • A 410 keeps the saved game in this browser under a new id and sends it again: a change made here is never lost to a delete made on another device (D8).
  • pull() lists the account's saved games. It fetches and adopts those this browser lacks, and those it holds unchanged at an older rev. It removes those listed under removed that are unchanged here. It sends those the account lacks.
  • pull() runs once on load when signedIn(), and again when signedIn() turns true.
  • account is set from every answer that carries an AccountLine. After the PUT that made the account, the header shows the handle from it. The sync never invalidates page data: a page keeps its playhead, its card and its undo history.
  • Once a PUT has answered 200 the sync treats this browser as having a session, whatever signedIn() says.
  • The root layout calls createSaveSync once and gives the result to the store (G2). Components reach it as useGame().sync.
  • A network failure sets offline and the next changed tries again.
  • A 401 sign_in sets sign-in and stops sending until the page loads signed in.
  • A 422 too_many, or the store answering full, sets full.
  • The stub shipped by contracts has state local, a null account, and does nothing. game-save replaces the body of createSaveSync; no caller changes.

// src/lib/sim-page/funding-presets.ts
import type { Policy } from '$lib/timeline/policy4';

/** `policy` with its money dated from its first span's start; `policy` itself when nothing moves. */
export function dateMeasure(policy: Policy, cal: Calibration): Policy;

Build constraints

The design document's global constraints, verbatim. The spec's own list is identical.

  • Work happens in git worktrees under .claude/worktrees/. Commits follow Conventional Commits. No attribution to an AI anywhere.
  • Code style: 2-space indent, single quotes, no trailing commas, 100 columns.
  • Every Vitest test calls expect.
  • Signoff fails on server stderr, on timing crutches and on a retried flake. Each unit runs npm run lint, npm run check and the Vitest projects its files belong to before it hands back.
  • Port 4173 is shared by every session on this machine. A unit never kills a server it did not start; it waits.
  • Every agent runs every command in the foreground and never ends a turn while something it started is running.
  • Schema changes go through npm run db:generate. Nobody edits a migration.
  • No unit runs npm run signoff: its dataset step fails until the dataset is uploaded. closing runs it once, after the upload.
  • The dataset version changes in this build. The dataset is uploaded once, by closing, from the integration branch, after every unit has merged; no other unit uploads a dataset. reach-check builds one earlier to run the check and uploads nothing.
  • A unit that writes a hashed path regenerates the fixture dataset with npm run pipeline -- fixture and commits it.
  • WCAG 2.2 AA: every new control is at least 24 px and passes expectNoA11yViolations in light and dark.
  • Page text is short. No sentence says what something is not.
  • Nothing on the main screen says "RHNA". The goal is read from the Goal value, never from a constant.
  • The game's rules are read from src/lib/game/. No component compares a level to a number.
  • One future: no seed control, no band, no average over runs.
  • Published plans and policies, their ids and their pages keep working, including every policy published before this build.
  • A number that is a claim about the world carries its source and tier, in the existing Sourced, Unsourced and Evidence shapes.
  • A runtime dependency that ships in the bundle gets a credit in SOFTWARE. This build adds none.
  • CSP changes are interface changes. This build makes none.
  • Timing is measured only on a quiet machine. A unit that cannot get one defers the measurement and says so.
