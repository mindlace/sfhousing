Sim control plane plan

Unit 3 of the sim message log: browser-minted ids, the cap and the rate, the roster hook, kept sims, the operator takedown, the reaper removed and the rename as a name commit.

For agentic workers REQUIRED SUB-SKILL: use superpowers:subagent-driven-development to implement this plan task by task. Steps are checklist items; progress is kept in the workspace ledger, not in the plan.

Overview

Goal
Make the D1 control plane agree with the sim object: a sim is registered under an id the browser minted, membership changes reach open sockets, nothing a member does deletes a sim, an operator's takedown clears the object, and a rename is a commit.
Architecture
D1 stays the only source of who may write; the object stays the only holder of the log. The Worker tells the object of a roster change through onSimRosterChanged(env, simId) (rereadRoles()), writes on a person's behalf through one new RPC, appendAs, that runs inside LogHost's one serialized append path, and takes a sim down through deleteSim, which marks the id in a new D1 table, calls takeDown(), then deletes the D1 rows.
Tech stack
SvelteKit 2, Svelte 5, Cloudflare Workers and a SQLite Durable Object, D1 with Drizzle, Vitest (server project, the D1 shim src/lib/server/test/d1.ts, the object harness src/lib/server/sim-object/test/harness.ts), Playwright against wrangler dev.

Rules: R29, R30, R34, R42, R43, R44 to R53, R58 to R61, the Testing section's "Control plane" line, and both "Carried from" lists of "Left to the builder". Review Focus

  1. A role read that fails after a removal. The removed writer's open socket keeps writing until the next re-read or reconnect, and the person who removed them must still see the removal succeed. Pinned by Task 3's "a removal stands when every re-read fails" and Task 4's e2e of a removal ending write.
  2. A rename of a sim whose tip is on an older dataset. A server-side commit stamped with the Worker's current dataset would move the sim to it without a reconcile (R54, R55). Pinned by Task 1's "takes parent and dataset version from the tip".
  3. An RPC failure carrying a commit body or identity into Worker logs. A failed insert's error message holds its bound parameters. Pinned by Task 1 (appendAs throws a fixed text) and Task 8 (renameSim logs only loggable).
  4. An id registered while it is being taken down, or after. Registration must never recreate a taken-down sim. Pinned by Task 5's atomic insert test with a mark present and Task 7's e2e.
  5. A person with many sims. The fuse fans out one RPC per absorbed sim; it must be bounded and must never block sign-in. Pinned by Task 3's rosterChangedAll concurrency test and Task 6's "a failed sims read never blocks the fuse". Account deletion's budget is an open question (Open questions).

  2. The taken-down mark is a D1 table, sim_takedown (sim_id primary key, taken_down_at). Registration checks it and sim_index in D1 only, so an arbitrary id never creates an object. The insert that registers is one statement, insert into sim_index … select … where not exists (select 1 from sim_takedown …) on conflict do nothing returning sim_id, so a registration racing a takedown either lands before the mark (and is then taken down) or not at all. The object's own gone_at stays as unit 2 built it. Reason: the check must not wake an object, and D1 serializes the two statements.
  3. createSim has its own insert and grants manager only when that insert returned the row (R51). createSimRecord and ensureSimRecord are removed: neither has a non-test caller after this unit (grep at plan time), and ensureSimRecord makes any caller a manager. The insert passes the title through normTextToDriver (src/lib/server/db/columns.ts:23), because raw SQL skips the normText column's NFC write.
  4. Registration does not write the first commit. The first writer's socket does (R58, built in unit 2). Reason: registration stays a D1 operation, and the start commit already has one path.
  5. The /sims form mints the id on the server (newId() in the create action, in the /sims load's pending-sim resume and in /signin's start-fresh), and still requires a title. Reason: there is no browser store yet (unit 4); a form sim has no commits and gets its start commit at the first writer's open (R58). The pending-sim resume and start-fresh call createSim directly, outside the rate, as today: each makes one sim per sign-in or per mint.
  6. Order inside startSim: id check, title check, known device, (signed out) in-use check then mint, rate, (signed in) writer check, quota, insert, then the handle reseed. The writer check comes before the quota so a writer at the cap still gets the no-op. The reseed runs after the insert succeeded and only when a name was given (R51); its failure is logged and never reported as a failed registration.
  7. "Managed" counts sims where the person holds manager (foldManagedSimCount, unchanged). A sim with no members counts for nobody, so leaving frees a place.
  8. The roster hook (R53) is onSimRosterChanged(env, simId): a no-op without the binding or under npm run dev; otherwise rereadRoles() on a fresh stub, at most 2 attempts, the second only when the first did not throw an .overloaded error (Cloudflare: never retry an overloaded object, and recreate a stub after an exception: error handling). It never throws; after the last failure it logs [roster-hook] reread failed, the sim id and loggable(e). Callers write the roster first and then await it. Reason: the roster change has happened and must not be rolled back or reported as failed; a failed read revokes nobody (the object's rule), and the socket loses a stale right at its next open, where the route reads the role.
  9. Call sites: createSim (after the grant), removeSimMember (every removal, the last member's included), the API accept route, both accept paths of /invite/[token], and the fuse (Task 6). leaveSim, the members DELETE route and deleteAccount reach it through removeSimMember. Each passes platform?.env. env is a required argument everywhere it is threaded (a required unknown property must be named: checked at plan time), so no production caller can forget it.
  10. A sim with no members (R43): removeSimMember returns { empty }, never deletes; when empty it deletes the sim's pending invitations, then calls the hook (open writer sockets lose write). Its sim_index row stays, so its socket opens read-only for anyone; no one sees its member area (requireSimRole 404s for non-members) and it leaves every list (foldSimsForUser). Its id answers 409 to registration. The leave dialog and the account deletion text stop saying a sim is deleted.
  11. The fuse (R49): handleAccountLink takes an optional roster: { env, defer }. On a fuse it reads the absorbed identity's sims before the fuse writes (a failed read gives none and is logged), and hands rosterChangedAll(env, simIds) to defer, which better-auth.ts sets to platform.ctx.waitUntil. An upgrade calls nothing (R49: nothing changes for its sims). Reason: the fuse only ever grants write, so a call that misses costs nothing a reconnect does not restore, and sign-in must never wait on, or fail because of, one RPC per sim. rosterChangedAll runs ROSTER_FANOUT (6) calls at a time inside waitUntil's 30 seconds (context).
  12. Takedown (R43): an operator route, POST /api/operator/sims/[simId]/takedown, authorized by a bearer token in a new secret, SIM_TAKEDOWN_TOKEN (at least 32 characters). Unset, short or wrong token, or an invalid id: 404, the same answer, so the route is not discoverable. It calls deleteSim({ db, env, simId }): object stub first (503 if absent), mark, takeDown(), then one D1 batch deleting sim_index, sim_commit and pending sim_invite rows. Ledger grants stay (every fold joins sim_index, sim-roles.ts:88). Reason: the object's storage can be cleared only from inside the Worker, so a wrangler d1 command like the policy takedown cannot do it; the operator capability model needs a signed-in, verified operator, which needs a mail provider, which production may not have; a token works with curl and fails closed when unset. No admin UI.
  13. The server-side append: LogHost.appendAs(input), reached by a new RPC SimObject.appendAs. The Worker builds the draft without parent and datasetVersion; inside the one serialized section the host records the start commit first when the log is empty (R58), then sets parent to the tip and datasetVersion to the folded tip's, and runs the ordinary #appendNow: every check of unit 2 applies, a rate token is taken, the commit is broadcast and indexed. The author is { identity: actor, write: true }: the Worker checked the role (I8). The RPC catches its own failure, logs loggable, and throws Error('append failed'). Reason: behind cannot happen when the tip is read in the serialized path, and taking the Worker's dataset would move the sim without a reconcile.
  14. The rename (R42) is a rename form action on /sims/[simId], for managers and editors (requireSimRole(…, 'editor')), shown as a Rename disclosure under the title. Open questions

  • Takedown credential. The plan uses a bearer token (decision 12) because an operator sign-in needs mail, which production may not have. Recommendation: keep the token; if the owner prefers the operator capability once mail is configured, the route's check becomes requireCapability(locals, 'takedown.sim') and the path moves under a session prefix.
  • Deleting an account with many sims. With the cap at 1,000, deleteAccount removes up to 1,000 memberships in one request, each several D1 queries plus one RPC. Workers Paid allows 10,000 subrequests per invocation by default, D1 calls included (limits). A very active account could exceed it; the run is idempotent and marks the identity deleted last, so a retry finishes it. Recommendation: measure the D1 statements of one removal and, if a 1,000-sim deletion would pass the limit, raise limits.subrequests in wrangler.jsonc or move the removals to a queue. Not in this unit.
  • Signed-out probing. A signed-out POST /api/sims with an id in use costs two D1 reads and is not rate-limited (the rate is per identity, and minting is not reached). Recommendation: accept; ids are random and the answer says only "not yours".
  • Where the rename lives. On the member page, not on the list row (decision 14). Recommendation: keep; the header's name and list come in unit 5.
