Building choice implementation plan

Each lot lists the buildings it could hold at or below its cap, a developer's choice picks one, and San Francisco's own records check the picks.

For agentic workers REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps are checklist items; progress is kept in the workspace ledger, not in the plan.

Overview

Goal: Replace the five fill levels and the size buckets with a per-lot set of real building options (construction type, form, stories, homes), chosen at run time by residual land value with a fitted spread. Then pass the record checks on a new dataset.

Architecture: The pipeline bakes, per lot, a pruned option row (options.bin, replacing gross.bin) and the lot constants locationValue, breakEvenValue, meanOptionHomes and meanOptionCost. Cost, value, duration and choiceSpread go in calibration.json. At run time a view is only stories and a cap per lot. The allowed options are a prefix of the lot's row. A new pure module, src/lib/sim/choice/, turns them into the choice row, the expected homes and stories, the margin feature and the capacity. The world's start, revisions, durations, finance, parking and massing read the chosen option.

Tech stack: TypeScript, SvelteKit 2 worker code, DuckDB pipeline, Vitest (server, client, pipeline, perf projects), Playwright.

Spec: docs/superpowers/specs/2026-11-26-building-choice-design.html (approved 2026-11-26). Evidence: the taller-caps report and recon (scratchpad taller/REPORT.md, taller/RECON.md, taller/dl/permits.json) and the builder check, whose answers are the spec's "Call:" lines.

Global Constraints

  • World engine only. Old scenario-engine readers are not ported. Tests that fail only because they run the old engine (simulate.golden among them) are deleted (spec, Non-goals Call).
  • Realism over monotonicity. "A higher cap never builds fewer homes" is not a goal. Never tune a choice, parameter or tolerance toward homes rising with the cap. The homes-by-cap measurement is a report and never a gate. The record checks are the acceptance test.
  • A record check that still misses after model changes stops the work for the owner before upload (spec, Acceptance Call). Allowed model changes: forms, locationValue smoothing, multipliers, coverage, refits. Not allowed: fitting cost or duration to the model's own output.
  • Every parameter carries a Provenance with its tier: 0 per-record, 1 official aggregate, 2 inference, 3 literature, 4 invented. Tier-4 values say "invented" in label.
  • One future. The choice draw is drawOn(stream, P.SIZE, 0) on the lot's existing stream (src/lib/sim/world/world.ts:374). No new random streams and no bands.
  • Costs, values, durations, choiceSpread and locationValue are data inputs (calibration.json, options.bin), not code constants read at run time. The Controller's values stay sourced in src/lib/sim/finance/prototypes.ts:72-78, and the pipeline copies them into calibration.choice.
  • Cost per home (Controller 2026): A 729,700 (5 st, 45 homes); B 736,700 (8 st); C 857,700 (13 st); D 918,700 (24 st); E 929,700 (under 25 homes). Value per home = cost − shortfall: A 552,700; B 584,700; C 651,700; D 626,700; E 576,700.
  • Type story ranges: V 1 to 6; III 4 to 8; I 1 to the physical maximum; the I tower form 13 and above. Types II and IV are not modelled.
  • Carrying cost: constructionRate 0.085 on AVERAGE_DRAWN 0.55 of cost (src/lib/sim/finance/terms.ts:49,157).
  • Affordable cost per home 954,127 (AFFORDABLE.costPerHome, prototypes.ts:120-131).
  • Record-check tolerances: 2 standard errors of the record statistic at its own n. Binomial SE = √(p(1−p)/n). Median SE ≈ 1.25 × IQR ÷ (1.35 √n). Built height ÷ limit: mean within ±0.10. Check buckets need n ≥ 30.
  • Performance: precomputeOf on the live dataset stays within 1.5 times its pre-branch time. bench:map's purchase-to-ready wait stays within its pass bar (docs/dev/map-perf.md). Both are measured on a quiet machine only.
  • Dataset: the version changes. Finishing follows docs/dev/pipeline.md "Finishing a branch that changes the dataset" (lines 59-74).
  • Shell: never compound cd … && cmd. Never kill port 4173: it belongs to whichever session started preview, so wait for it. Run everything in the foreground.
  • Commits: Conventional Commits. No Claude or AI attribution anywhere. Multi-line messages are written to a temp file and committed with git commit -F <file>, then the file is deleted. No heredocs.
  • Vitest runs with expect.requireAssertions. Style: 2 spaces, single quotes, no trailing commas, 100 columns.
  • A new module the pipeline imports from src/ goes on the code-hash list PATHS (pipeline/lib/version.ts:41-53), with pipeline/test/version-paths.test.ts updated to match.
  • Signoff only through npm run signoff. chreode fails on server stderr (policeStderr), on timing crutches and on retried flakes. Do not git push before it.

Review Focus

  1. A lot where no allowed option gains a home (cap at or below existing homes, a density cap that clips every option, envelope 0). Expected: not hostable, capacity 0, hazard 0, no start, and no NaN or Infinity in any column. Pinned in Task 4 (choiceRow returns false) and Task 9 (the view marks the lot not hostable).
  2. Extreme residualLandValue ÷ (choiceSpread meanOptionHomes meanOptionCost): choiceSpread near 0, a lot with locationValue = 30, homes in the thousands. Expected: the softmax subtracts the row maximum, so choiceSpread → 0 gives the argmax and no exponent overflows. Pinned in Task 4.
  3. A cap above the lot's physical maximum, or a cap raised step by step. Expected: the allowed set only grows. choiceValue, meanOptionHomes and meanOptionCost do not move. The odds between options that were already allowed are unchanged. Capacity never falls. Pinned in Task 4 (property test) and Task 9 (netCapacity).
  4. A second start on a lot demolished earlier in the run (existing counted as 0). Expected: the choice row is rebuilt against 0 existing, as sizeCumAgainst does today (src/lib/sim/scenario/input.ts:346-351). Pinned in Task 9.
  5. Recorded and in-flight projects with no type and possibly no stories (revStories NaN). Expected: duration multiplier 1, finance priced by prototypeFor's binning (counted and reported), and the card and massing as today. Pinned in Tasks 9, 10 and 11.

Rulings made in this plan

The spec leaves these to the builder. The plan needs them now, so each is marked as a builder's call with its reason. A builder may change one only by stating the evidence in the task's commit.

  • Base (builder's call). Build on the scenario-engine removal. If it has merged, branch from origin/main. If not, branch from worktree-remove-scenario-engine (49e64c1c) and rebase onto main when it merges. Reason: the spec ports nothing of the old engine, and building on it avoids keeping it compiling.
  • K and encoding (builder's call). Rows have variable width (CSR offsets, as gross-table.ts:29-37), sorted by stories, then type, then form, and capped at 255 options a lot. Reason: one surviving option per (type, stories) gives about 1 to 91 per lot. A fixed width would cost several times the memory of today's 5-wide rows.
  • One candidate per (type, stories) (builder's call). Each candidate is the form with the most homes. Several towers use the most plates that fit. Reason: forms of the same type and stories share cost, value and time, so the others are always pruned.
  • Districts (builder's call). A district parcel has one option row. Each option sums its district lots, each massed at the same type and stories. Reason: the world runs one project per parcel row (world.ts:392-420).
  • Choice row computed lazily (builder's call). precomputeOf memoises per lot the expected homes, the expected stories, the margin and a gain flag. The cumulative row is built in O(K) into a scratch buffer when a start draws. Reason: memory, since sizeCum-sized arrays per view grow with K. The numbers are identical either way.
  • Value above 24 stories (builder's call). D's value per home, not scaled. Only cost takes the fitted permit-valuation ratio. Reason: no record supports value per home rising with height. Scaling it by a cost ratio would invent that.
  • Carrying cost carryPerHome (builder's call). carryPerHome = costPerHome × 0.085 × 0.55 × max(0, constructionMonths(option) − constructionMonths(anchor)) ÷ 12. constructionMonths is the construction-stage median months of the option's height band. The anchor is the prototype or prototypes its cost is read from (the stories-weighted mean where it interpolates). Reason: this is the spec's "months beyond the prototype's own band" with the band defined.
  • Height bands (builder's call). Edges ≤ 4, 5 to 7, 8 to 12, 13 to 20 and 21 and above, as in the raw pull. A band with fewer than cal.sizeMinN completed spells merges into its lower neighbour. Reason: these match the evidence table, and the merge rule is the size model's.
  • Stage intervals (builder's call; see Contradictions). The multipliers scale the model's own stages: permitIssued (issued to first construction document) and construction (first construction document to completion, pipeline/project-records/stages.ts:159-168). Each is fitted on that stage's spells and checked on the same interval. A multiplier is the band's median completed spell ÷ the pooled median. It applies to every row with known stories, recorded or simulated.
  • Location-value smoothing (builder's call). For each residential building first assessed after completion in 2015 or later: (land + improvement) ÷ units on its first roll after year_property_built, divided by that roll year's citywide median. locationValue for an Analysis Neighborhood is the median of those indices, shrunk to 1 by n ÷ (n + 10). The 10 is tier 4, flagged. Every lot takes its neighbourhood's locationValue. Reason: the neighbourhoods are already a pipeline source (datasf.ts:69-76), and shrinkage handles thin areas without a cliff.
  • Choice-spread fit (builder's call). Maximum likelihood of each 2015-on history's recorded stories, given its lot's options at its base limit and its locationValue. A history over its limit is excluded and counted in sizeOverEnvelope. The search is golden-section on log choiceSpread in [1e-3, 1e2]. Reason: it uses every record and does not aim at the acceptance moments, which stay an independent test.
  • Margin feature (builder's call). choiceMargin = max over allowed options of residualLandValue(option, choiceValue) ÷ (meanOptionHomes × meanOptionCost). It is unitless, so its bins hold across lot sizes.
  • Revisions (builder's call). Keep the ratio draw (stage.ts:134), so units = clamp(round(ratio × units), existing + 1, the most homes among the allowed options of the same type). The option becomes the same-type option with the fewest homes that holds them, and stories follow that option. Reason: the records' revision ratios are unit counts, and an entitled building keeps its construction type.
  • Tower plates (builder's call). As many plates of at most TOWER_PLATE_MAX_M2 900 at TOWER_SEPARATION_M 6 as fit inside the podium inset. Both stay tier 4 unless a Planning Code tower-spacing rule can be cited.
  • Full-coverage coverage (builder's call). The fit from LiDAR footprints is a one-off pipeline measurement whose value is committed into constants.ts with tier-0 provenance, as the PHYS_* constants were (constants.ts:104-133). If the fit fails, use 0.75 at tier 4, flagged.
  • Card copy (builder's call). The card does not name the construction type. Reason: the terse-copy rule. It shows stories and homes as today.

Spec and code contradictions found

  • The spec's stage Call reads "permit stage … first construction document to issued; construction stage … issued to completion". In the records, issued comes before the first construction document (permits.json: issued 2024-08-19, first construction document 2025-10-27). The model's stages are issued → first construction document (permitIssued) and first construction document → complete (construction) (stages.ts:159-168). The plan follows the Call's principle (fit each stage on its own interval, check on the same one) on the model's real intervals. The check table's raw issued-to-completion medians (28.4 … 40.1) then compare against permitIssued plus construction, summed per project. The owner should confirm this.
  • The spec's Baked section says "a fixed-width row of K", while K and the encoding are left to the builder. The plan uses variable width (see Rulings).
  • The spec cites src/lib/sim/scenario/{input,funded,massing,card,finance-score}.ts. After the removal these are moved or deleted (see File Structure).

Task 3: Option rows, pruning and the options codec

Interfaces

  • Consumes: generateForm (Task 2); costPerHome, valuePerHome and carryPerHome (Task 1).
  • Produces: candidatesOf(rec: ParcelRecord, seed: number): Option[]. It gives one option per (type, stories) that some form of the type fits, with the most homes, unpruned and uncapped, sorted by (stories, type code, form code).
