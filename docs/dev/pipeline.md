# Data pipeline

`pipeline/` turns open sources (DataSF parcels, land use and footprints; Overture buildings; a Protomaps basemap extract; Noto Sans glyphs; Muni, BART and Caltrain GTFS) into one immutable, versioned dataset: parcel chunks, the FZP scenario parcel file `scenarios/fzp/parcels.bin`, `buildings.pmtiles`, `basemap.pmtiles`, fonts, neighborhoods, `transit.json` and `manifest.json`. The Worker serves it from R2 (see [data-serving.md](data-serving.md)). Design: `docs/superpowers/specs/2026-10-10-data-pipeline-design.md`.

`datasf-streets` (`3psu-pn9h`, active street centrelines, PDDL-1.0) is read by the road-like rule (`55_road_lots.sql`) and the `boxes` command. It is normalised to `src_streets` (cnn, streetname, classcode, layer, `f_st` and `t_st` (the cross streets at each end, `COUNTY LINE` at the south edge; NULL when the raw file lacks them), geometry). Refresh it with `npm run pipeline -- fetch --only datasf-streets`.

`datasf-city-lands` (`gtnh-hgvs`, the City Lands inventory of city-owned land, PDDL-1.0) is a required DataSF source with no filter (about 1,035 rows), normalised to `src_city_lands` (land_id, land_name, dept_id, department_name, category, geometry in EPSG:7131, made valid). It feeds the road-like-lot rule and is not an as-of source (it is not in `AS_OF_SOURCE_IDS`). A lock without it fails `normaliseAll`. Refresh it with `npm run pipeline -- fetch --only datasf-city-lands`.

Project records (`scenarios/fzp/projects.json`: in-flight projects with their stage histories and multi-phase phasing) add eight DataSF sources to the lock, all fetched as paged JSON by `fetch`: `datasf-permits-newcon` (`i98e-djp9`, PDDL-1.0), `datasf-permits-named` (`i98e-djp9` unit-adding type 3/8 alterations, PDDL-1.0; kept only when a Planning record names them), `datasf-planning-projects` (`qvu5-m3a2`, public-domain), `datasf-planning-records` (`y673-d69b`, public-domain), `datasf-planning-review` (`d4jk-jw33`, PDDL-1.0), `datasf-unit-completions` (`j67f-aayr`, PDDL-1.0), `datasf-housing-production` (`xdht-4php`, public-domain) and `datasf-dev-pipeline` (`6jgi-cpb4`, CC0-1.0). Design: `docs/superpowers/specs/2026-10-16-project-records-design.md`. Both permit sources select `proposed_construction_type` (DBI codes `1` to `5`, parsed to the numerals I to V as `Permit.constructionType`; the building-choice record checks read it, see [building-choice.md](building-choice.md); the projects step counts the in-flight projects with no permit of a modelled type, I, III or V, as `projects.no_type`: the recorded projects that keep the finance binning, `prototypeFor`). Refresh just these with `npm run pipeline -- fetch --only datasf-permits-newcon,datasf-permits-named,datasf-planning-projects,datasf-planning-records,datasf-planning-review,datasf-unit-completions,datasf-housing-production,datasf-dev-pipeline`.

A ninth source, `datasf-mohcd-pipeline` (`aaxw-2cb8`, the MOHCD affordable housing pipeline, PDDL-1.0), feeds the baseline funding's income mix and `minHomes` (see [finance-data.md](finance-data.md)). It is **not an as-of source**: it is not in `PROJECT_SOURCE_IDS`, the project-records step never reads it, and it is a 2023 snapshot that adds no project events, so fetching it must not move `asOf`. The calibration step reads its locked pages as rows (`readRows`), and a lock without it is a `BuildError` (`lock has no datasf-mohcd-pipeline entry (run fetch --only datasf-mohcd-pipeline)`). `datasf-housing-production` is an as-of source, and its `select` now also asks for the four income-tier columns and `affordable_units`, which changes its URL; refreshing it alone would move `asOf` past the other sources' data. Refresh the eight project sources and the new one together: `npm run pipeline -- fetch --only datasf-permits-newcon,datasf-permits-named,datasf-planning-projects,datasf-planning-records,datasf-planning-review,datasf-unit-completions,datasf-housing-production,datasf-dev-pipeline,datasf-mohcd-pipeline`.

## The construction cost index (`dgs-ccci`)

The choice-spread fit prices each record at its own year's cost with the DGS California Construction Cost Index ([building-choice.md](building-choice.md), "Each record at its own year's market"). Its page states no terms of use and the index derives from ENR's Building Cost Index, so its values are never committed or shipped: `fetch --only dgs-ccci` (`pipeline/sources/dgs.ts`) reads the page's tables into a `year,month,ccci` CSV in the raw cache, pinned in the lock by sha256 like any other source, and the calibration step reads the yearly means from it (`readCostIndex`). A lock without it is a `BuildError` (`lock has no dgs-ccci entry (run fetch --only dgs-ccci)`). It is not an as-of source. The mini fixture's entry (`pipeline/test/fixtures/mini/ccci-raw.ts`) holds invented values. `fetch --restore` restores it from the R2 `sources/` archive only once an upload has archived it.

## Car-ownership sources (Census and DMV)

The car-ownership model's inputs are lock entries like any other (public domain; the DMV's "No restrictions on public use"), declared in `pipeline/census-config.ts` and fetched by `pipeline/sources/census.ts` (`fetchCensus`, `fetchDmv`). The Census data API needs a key, so none of them calls it: they read summary files, relationship files, TIGER/Line and PUMS CSV on `www2.census.gov` ([cars-data.md](cars-data.md) has the layouts and the checks). Each entry's one raw file is the San Francisco rows of the upstream files as a small CSV (a TIGER entry keeps the upstream zip). None is an as-of source (not in `AS_OF_SOURCE_IDS`), so fetching them never moves `asOf`.

## Requirements

Node >= 22, `tippecanoe 2.79.0` and `pmtiles 1.31.2` on `PATH` (macOS: `brew install tippecanoe pmtiles`; Homebrew's pmtiles prints `dev`, so `doctor` falls back to `brew list --versions pmtiles`). DuckDB (`@duckdb/node-api`, a devDependency that never ships in the worker) downloads its `spatial` and `httpfs` extensions on first use. `npm run pipeline -- doctor` checks all of this and prints an install hint for anything missing. `uv` (`brew install uv`) is needed only for `fetch --only usgs-lidar-sf`: it runs the pinned Python rasterizer in `pipeline/lidar-raster`. Build, fixture and the tests never need it.

## Finishing a branch that changes the dataset

Datasets ship with their code ([deploy.md](deploy.md)): the build computes `<v>` from the tree, and both signoff and the deploy workflows refuse a tree whose dataset is not published. So when a worktree branch changes `<v>`, building and uploading the dataset is part of finishing the branch.

To tell whether a branch changes it, compare `npm run pipeline -- version` (prints the `<v>` the tree computes) with `main`'s. `npx tsx scripts/dataset-version.ts --check` exits 1 unless staging serves that version's manifest; it is the same check the `dataset` signoff step and the deploy guards run. Builds need `pipeline/.cache` and the shared cache, `tippecanoe` and `pmtiles` locally; the downloads live in the shared cache, so a new worktree needs `npm run pipeline -- fetch --restore` only when this machine has never fetched the files (it fills `raw/` from the committed lock and the R2 archive).

0. Optional: refresh the sources with `npm run pipeline -- fetch` and commit `pipeline/sources.lock.json` (`all` only fetches when the lock is missing, so it never refreshes an existing lock). The lock is part of the hash, so this changes `<v>`; do it before step 1. An Overture refresh (`overture-buildings` or `overture-building-parts`) also needs `npm run pipeline -- boxes` (with the LiDAR tiles: `fetch --restore --lidar`; an earlier run with the same inputs is reused, see [Shared cache](#shared-cache)) before `build`, and the new `building-boxes` entry committed: `build` refuses boxes derived from other footprints ([building-boxes.md](building-boxes.md)).
1. `git merge origin/main`. The version hashes the merged code, so merge first.
2. `npm run pipeline -- build` (about 4.5 minutes on a 15-core machine, measured 2026-11-14 with the building boxes). Every invariant must pass, without `--skip-tiles`.
   2b. `npx tsx scripts/record-check.ts pipeline/out/<v>` must exit 0: on this data current law's first ten simulated years meet the permit records' targets (the build writes them to `pipeline/.cache/derived/<v>/record-targets.json`; [testing.md](testing.md), "The record check"). On exit 1 the builder may make the model changes the building-choice spec allows (forms, location-value smoothing, multipliers, coverage, refits; never cost or duration fitted to the model's own output) and rebuild; a check that still misses stops the work for the owner, and nothing is uploaded. Record `npx tsx scripts/cap-measure.ts pipeline/out/<v>` (the homes-by-cap report, never a gate) in the PR.
3. `npx tsx scripts/reach-check.ts pipeline/out/<v>` must exit 0: the full tree meets the last deadline; current law's reach is printed, not gated. On exit 1 nothing is uploaded and the owner decides ([game.md](game.md), "The reach check").
   3b. `npx tsx scripts/money-monotone.ts pipeline/out/<v>` runs beside reach-check, and its last line is recorded: whether any preset added to a set of funding presets costs it more than 5 homes on any reading ([testing.md](testing.md), "The money monotonicity check"). For now it is a report, not a gate: it exits 1 on today's model, and an exit 1 does not stop the upload ([finance-data.md](finance-data.md), "What current law builds against the check").
4. `npm run pipeline -- upload <v>`. It refuses, with nothing uploaded, unless `out/<v>/report.json` shows every invariant passing and tiles built, every file the manifest names exists, and the current lock is the one that built `<v>` (its canonical sha256 is recorded in `report.json` as `lockSha256`; fixture versions skip this check because they archive nothing). It aborts if `data/<v>/manifest.json` already exists (V13).
5. `npm run pipeline -- verify <v> --origin https://<staging-origin>`. Staging already serves any published `/data/<v>/`.
6. `npm run signoff`. The `dataset` step passes now. If `origin/main` moved in the meantime, signoff's merge changes `<v>`, the step fails, and the loop goes back to step 2. In a multi-unit build only the closing unit runs signoff, after the upload.
7. Open the PR and squash-merge it. Squashing does not change the tree, so `main` computes the same `<v>`, and staging deploys the code and its dataset together.
8. Remove the worktree.

### Changes on the funding paths

A change under `src/lib/sim/finance/**`, `src/lib/sim/world/rules/funding.ts`, `src/lib/sim/world/funding/**`, `src/lib/sim-page/funding-presets.ts` or `pipeline/**/funding.json` runs `npx tsx scripts/money-monotone.ts --version <v>` by hand before signoff (it needs no local dataset when `<v>` is published) and records its last line in the PR. It is a report, not a signoff step, until the money-limited funding spec makes it that spec's acceptance gate.

Old versions are never deleted, so saved plans keep loading.

## Shared cache

The large downloads live once per machine, in the cache root: `SFH_CACHE_DIR` when set, else `$XDG_CACHE_HOME/sfhousing` (an absolute `XDG_CACHE_HOME` only), else `~/.cache/sfhousing` (`pipeline/lib/cache-root.ts`). It holds `raw/<sha256>` (every downloaded file and the `boxes` artifact), `ept/` (the LiDAR node cache), `lidar-work/` (the rasterizer's work dirs) and `boxes-index/`. `derived/`, `review/` and `lidar-venv/` stay in each worktree's `pipeline/.cache`; so do `pipeline/out/` and the locks.

- Files are written to a temp sibling and renamed into place (`pipeline/lib/atomic.ts`), so a reader never sees a partial file and two worktrees can fetch at once. The one exception is the LiDAR rasterizer, whose work dir is shared: `fetch --only usgs-lidar-sf` holds `lidar-work/<hash8>.lock`, and a second fetch with the same settings waits for the first (`lidar: waiting for pid <pid> on <host> (<hash8>)`).
- Any command other than `cache` prints a notice when this worktree's `pipeline/.cache` still holds `raw`, `ept` or `lidar-work` files: `<dir> holds <names>: move them to <root> with npm run pipeline -- cache import <dir>`.
- `cache import <dir>` moves `<dir>/raw`, `ept` and `lidar-work` into the root (renames on one volume, copy-then-rename across volumes). A file already shared is dropped from `<dir>`; a `raw/` file whose content does not match its name is left in place, listed, and the command exits 1; partial `lidar-work` dirs (names starting with `.`) are removed. It then reads `<dir>/../sources.lock.json` (or `--lock <path>`) and indexes its `building-boxes` entry when the files verify in the shared `raw/` (`boxes-index: wrote <key>`; otherwise `boxes-index: skipped, <reason>`). It exits 2 when `<dir>` is not a directory or overlaps the root, or when its `raw`, `ept` or `lidar-work` is a symlink or resolves into the shared cache.
- `boxes` skips its derivation through `boxes-index/<key>.json`, where `<key>` is the sha256 of the `inputs.json` the run writes ([building-boxes.md](building-boxes.md) "The artifact and its recorded inputs"). Tests point `SFH_CACHE_DIR` at a temp dir ([testing.md](testing.md)).

## Where things land

- `<cache root>/raw/<sha256>`, `ept/`, `lidar-work/` and `boxes-index/`: the downloads, the LiDAR node cache, the rasterizer's work dirs and the boxes index, shared by every worktree on the machine ([Shared cache](#shared-cache)). Builds keep the normalised inputs in a temp dir (`pipeline/steps/build.ts`), not in a cache.
- `pipeline/out/<v>/`: the dataset, plus `report.json` with all counts, timings and tool versions (gitignored).
- `pipeline/.cache/derived/<v>/parcel-panel.parquet` and `parcel-lineage.parquet`: the T13 files, the parcel-by-roll-year panel and the retired-to-current parcel lineage, read by consumers in the same build and by project-records. They are build-internal and never uploaded (gitignored). `BuildOpts.derivedRoot` in `pipeline/steps/build.ts` sets the root: the default is `pipeline/.cache/derived` and the folder is `<derivedRoot>/<datasetVersion>/`. Fixture builds (`pipeline fixture`) pass a per-run temp folder, so they never touch the real cache and parallel fixture builds never share one.
- `pipeline/.cache/derived/<v>/road-lots.csv`: the road-like lots' review list, written by the scenario step (see Road-like lots below). Build-internal, never uploaded (gitignored); fixture builds write it to their temp folder.
- `pipeline/.cache/derived/<v>/project-histories.json` and `permits.parquet`: the project-records outputs (per-project stage histories and the parsed new-construction permits, with `proposed_stories`, `valuation` and `construction_type`), consumed by stage-calibration in the same build. Build-internal, never uploaded (gitignored).
- `pipeline/.cache/derived/<v>/record-targets.json`: the building-choice record targets (`recordTargets`, `pipeline/lib/building-records.ts`), written by the calibration step for the record check. Build-internal, never uploaded (gitignored); fixture builds write it to their temp folder.
- `pipeline/.cache/derived/<v>/quality-report.md`: the T14 data-quality report, one row per registered rule with its counts and shares, then the first 25 affected ids of each (see Data quality below). The build writes it once, after the last step that reports. After the Samples it has a `## Land clip` section: the land counts and the 20 largest removals (`landClipSection`, `pipeline/lib/land-report.ts`). Build-internal, never uploaded (gitignored); fixture builds write it to their temp folder, so it is not in `fixture-0`.
- `pipeline/.cache/derived/<v>/building-roofs.parquet` and `render-pieces.parquet`: the building boxes' review files, a copy of the artifact's per-building roof records and the clipped render boxes (GeoParquet, EPSG:7131), written by the render-boxes step only when the lock has a `building-boxes` entry. Build-internal, never uploaded (gitignored); query them with DuckDB `read_parquet` ([building-boxes.md](building-boxes.md) "Derived files").
- `pipeline/out/<v>/scenarios/fzp/projects.json`: the in-flight project file (validated by V20, at most 2 MB). It is uploaded with the dataset and listed in the manifest.
- `pipeline/out/<v>/scenarios/fzp/policy.bin`: the per-lot policy inputs of the sim data layers (codec `sfh-policy/2`, validated by V31, at most 1 MB). It is uploaded with the dataset and named in the manifest as the optional key `scenarios.fzp.policy`; see Policy parcels below.
- `gross.bin` (codec `sfh-gross/1`) is retired (building-choice Task 9b): datasets from before it may still carry one, named in the manifest as the optional key `scenarios.fzp.gross`, which the app accepts and never reads.
- `pipeline/out/<v>/scenarios/fzp/options.bin`: the per-lot building options (codec `sfh-options/1`, `src/lib/data/option-table.ts`, validated by V36, V40 and V41; see [building-choice.md](building-choice.md)): for each `parcels.bin` row, in the same order, the lot's options pruned without costs (`pruneOptions`) and its `locationValue`. The candidates (`candidatesOf` on the row's scenario record, from the decoded chunks) are generated inside the scenario step, before `parcels.bin` is written, on `availableParallelism() - 1` worker threads (`pipeline/steps/options.ts` `candidateRows`, `options-worker.ts`; the fixture uses one thread; a failing worker terminates the rest), together with one job per panel key: the distinct (lot, existing homes, floor area, stories) of `sc_base_yield`, whose `option_row` column points into the panel file. The options step runs after the projects step: it reads `locationValueByLot` and the shipped price and height-time step (`pipeline/lib/fzp-cal/shipped-step.ts`: the Controller anchors, the permit cost ratio above 24 stories and the height bands fitted on the stage spells from 2015 on), prunes, clamps homes above 65,535 (a warning names the lots) and writes `options.bin`, then `pipeline/.cache/derived/<v>/panel-options.bin` (same codec, one pruned row per panel key, build-internal) with `panel-options-keys.json` (the keys in row order). Counts: `options.rows`, `options.lots` (rows with an option), `options.values`, `options.per_lot.{p50,p90,p99,max}` over those lots, `options.clamped`, `options.district_rows`, `options.e_crossings` (drops the same-cost-series rule prevents across the Type V 25-home line), `options.per_lot_cost_pruned.{p50,p90,p99,max}` and `options.growth` (Σ options ÷ Σ options left by `pruneByCost` at the shipped step, a report only: nothing cost-based is written), `options.panel.rows`, `options.panel.values`, `options.bytes.payload` and, off fixture versions, `options.bytes.file`. ## Lock and `datasetVersion`

`pipeline/lidar.lock.json` holds only the LiDAR tiles (`usgs-lidar-sf`), in the same format. `fetch --restore` and `build` never read it; `upload` archives its files to `sources/<sha256>.sfhl`. The tiles are far larger than the other sources, so `upload` does not probe each one (the R2 existence probe downloads the object): it writes one marker key `sources/lidar-lock-<lock sha256>.json` after every tile is archived and skips all tile uploads when the marker exists. A tile that is neither in the raw cache nor in R2 refuses the upload with nothing sent. Fixture versions archive nothing.

The LiDAR source (`pipeline/sources/lidar.ts`) rasterizes the 2023 USGS 3DEP San Francisco point cloud (EPT `CA_SanFrancisco_1_B23`) into 500 m EPSG:7131 tiles in the `sfhl/1` format (`pipeline/lib/lidar/tile.ts`: height above ground at 0.25 m, ground elevation at 1 m, a vegetation mask), with the parameters from `pipeline/boxes-config.ts`. The rasterizer's work dir is `<cache root>/lidar-work/<hash8 of the upstream version>/` (a rerun resumes) and its EPT node cache `<cache root>/ept/`. It is not an as-of source.

`sources.lock.json` also holds one derived entry, `building-boxes` (written by `npm run pipeline -- boxes`, never by `fetch`): `boxes.parquet`, `roofs.parquet` and `inputs.json` with `derived:` URLs, archived and restored like any locked file. Its `upstreamVersion` (`boxes/2 code=<12> config=<12> overture-buildings=<12> overture-building-parts=<12> usgs-lidar-sf=<12> datasf-parcels=<12> datasf-streets=<12> datasf-neighborhoods=<12>`, `-` for an absent input) records 12-hex prefixes of every input the boxes were derived from: the boxes code hash, the `BOXES` config hash and each source's file hashes (`usgs-lidar-sf` from the LiDAR lock). `build` stops when the two Overture prefixes differ from the lock and only warns on the others (live builds). See [building-boxes.md](building-boxes.md).

The lock pins every input by sha256. `build` refuses to run if a cached file does not match it. `datasetVersion` is `<YYYY-MM-DD>-<h8>`: the date is the newest `retrievedAt` in the lock, `h8` hashes the canonical lock, the committed code under the `PATHS` in `pipeline/lib/version.ts`: `pipeline/`, `src/lib/config.ts`, `src/lib/data/`, `src/lib/generator/`, `src/lib/timelapse/`, `src/lib/plan/geometry.ts`, `src/lib/plan/types.ts`, `src/lib/sim/finance/`, `src/lib/sim/cars/`, `src/lib/sim/world/rules/rng.ts` and `src/lib/transit/` (a `git ls-tree` listing that excludes `sources.lock.json`, `.cache`, `out` and `pipeline/test/`, plus any uncommitted changes there), and the pinned tool versions. It is derived from inputs, so the same lock and code give the same version, and any change to pipeline code, the shared codec, the generator or the timelapse code gives a new version (the yields in `parcels.bin` come from the generator, so a generator change changes the data). A published version is immutable; fixtures use `fixture-<n>`.

`PATHS` is the files that a walk of the static imports from `pipeline/cli.ts` reaches outside `pipeline/`. `pipeline/test/version-paths.test.ts` holds the list to that walk: it fails naming a reached module under no entry, and an entry that nothing reaches. A new import from the pipeline into `src/lib` needs its path in `PATHS`.

The code-hash paths now decide what deploys serve: the app build computes the same `<v>` and the deploy guards refuse a commit whose `<v>` is not in R2. So any change under them needs a build and upload before merge, including changes that do not affect the data (a refactor, a comment in `src/lib/data/`); a change under `pipeline/test/` is the exception: it is outside the hash, does not move `<v>`, and chreode's `pipeline/test/**` rule runs lint, check, unit and pipeline but skips the `dataset` step (and e2e). See Finishing a branch that changes the dataset. chreode's `dataset` step enforces this at signoff. The Vite plugin that bakes `<v>` into the app build imports `pipeline/lib/version.ts`, `pipeline/config.ts`, `pipeline/sb79-config.ts` and `src/lib/generator/constants.ts` through Vite's native config loader, so new imports on that chain need explicit `.js` extensions (otherwise it prints to stderr and signoff's `policeStderr` fails).

The build's `asOf` (the day `projects.json` and `calibration.json` carry, the day project histories are censored at, and the scenario step's "today" for the FZP density cap) is a different date: the UTC day of the newest `retrievedAt` among the **as-of sources** only, `AS_OF_SOURCE_IDS` in `pipeline/project-records/parse.ts`. The members are the eight project-record event sources (`PROJECT_SOURCE_IDS`: permits, planning, completions, housing production, development pipeline). Membership is an allowlist: a source that feeds only policy, transit, tiles or parcel attributes (`datasf-historic-status`, `sfbos-sb79-exemptions`, GTFS, basemap) is not a member, so fetching or refreshing it leaves `asOf`, the histories and calibration unchanged. Without the rule, a refresh of a policy source alone would censor the histories days after their data ends, adding at-risk time with no events and lowering the stage hazards. A new source moves `asOf` only once it is added to the list; add it only if its rows become project events. The transit target date follows the same pattern over the GTFS feeds (`TRANSIT_DATE_SOURCE_IDS`; see Transit below). Only the `datasetVersion` date is whole-lock.

## Land mask

`pipeline/sql/45_land.sql` clips every lot to dry land, so water is not buildable (spec `docs/superpowers/specs/2026-10-19-underwater-lots-design.md`). It runs after `40_heights.sql` (it needs `buildings`) and before `50_clip.sql`, so every later file sees the clipped lot.

- **Source.** Land is the union of three layers: OpenStreetMap `earth` polygons and `landuse` polygons of kind `pier`, both read from the `protomaps-basemap` extract at z15 into `src_land` (`pipeline/sources/land.ts`; one row per feature, with its tile's lon/lat bounds) and, beside it, `src_land_tiles` (one row per z15 tile read, with or without land features, with the same bounds; its own parquet `protomaps-basemap-tiles.parquet`, loaded by `loadNormalised`), plus the existing `buildings`. Pier lines are not used: they would make marina water buildable.
- **Mask.** Each feature is clipped to its own tile, moved to EPSG:7131 and snapped to a 1 cm grid. The features are unioned, buffered out and back by `land_seam_m` (0.05 m, mitre joins) to close the seams between tiles, and simplified by `land_simplify_m` (0.5 m) so a clipped edge does not follow every coastline vertex. The result is `land_mask` (one row). It is then cut into `land_cell_m` (250 m) squares, so each lot is intersected with a few small pieces of the mask.
- **Clip.** A lot that loses less than `land_min_removed_m2` (5 m²) of land keeps its geometry exactly (`status` `unchanged` below 0.01 m², else `jitter`). Any other lot's dry part is its pieces of the mask and of the buildings it meets; pieces under `min_piece_m2` (2 m²) count as water. With no dry piece left the lot is `underwater`; otherwise, if it still loses 5 m² or more, it is `clipped` and its `geom`, `geom4326` and label point (`sfh_label`) come from the dry part, every piece kept. The thresholds are in `SQL_VARS` (`pipeline/config.ts`); all are tier 4, from the 2026-10-19 spike.
- **Outputs.** `parcels` gains `geom_orig` (the source polygon, for lineage matching) and `underwater`. An underwater lot keeps its original outline, so it stays on the map. `parcel_land(id, status, orig_m2, dry_m2, removed_m2, n_pieces)` lists every lot, ordered by id.
- **Downstream.** `60_attributes.sql` puts the flag on `parcel_out.underwater` and sets `parcel_out.eligible` to the land-use eligibility AND NOT underwater. `parcel_out.geojson7131_orig` holds the source outline of clipped lots only (null otherwise). `area_m2` is the dry area for a clipped lot and the original area for an underwater one, since it keeps its outline. The scenario step's spatial lineage (`80_scenario.sql`, `s_map_b`) matches a retired row's centroid against `parcels.geom_orig`, so a retired lot lying in the part a clip cut away still maps to its current lot. Parcel chunks carry the flag as the sparse column `uw` (strictly increasing row indices of underwater records), omitted when a chunk has none; the decoder rejects an underwater row that is also eligible.
- **Counts.** `land.tiles` (z15 tiles with land features), `land.mask_area_m2`, `land.clipped`, `land.underwater`, `land.jitter_kept`, `land.removed_m2` (over clipped lots), `land.underwater_m2`, `land.building_kept_m2` (dry area only buildings supply, over the lots the clip examined) and `land.outside_tiles` (lots not wholly inside the union of `src_land_tiles`, every tile read including all-water ones: the mask cannot speak for them). Areas are rounded to 3 decimals. The rules `sd.parcels.land-clip`, `sd.parcels.underwater` and `sd.parcels.outside-tiles` report the clipped, underwater and outside-the-tiles lots (Data quality below). The rule `sd.parcels.clip-yield-loss` is counted by the scenario step: of the clipped lots that keep more than 95% of their area, it fires on those whose top-fill yield was above 0 on the original outline and is 0 on the clipped one; any firing warns. The quality report has a `## Land clip` section (`pipeline/lib/land-report.ts`) with these counts and the 20 largest removals.

## Freeway land

Freeway land is unbuildable in every simulator run.

- **Catalog.** `pipeline/enrichment/freeway-land.json` (`FREEWAY_LAND_JSON.live`; the mini fixture's is `pipeline/test/fixtures/mini/enrichment/freeway-land.json`) lists curated vacant or public parcels under or fronting a freeway, by segment: `{ schema: 1, segments: [{ id, freeway, label, ref, cnn, removedBy, curated, parcels, excluded }] }`, parsed by `parseFreewayLand` in `pipeline/lib/freeway-land.ts`. `removedBy` names the highway truncation that frees the segment (null for a freeway that stays), `curated` is `hand` or `rule`, `parcels` is sorted and unique, and every `excluded` parcel carries a reason. A parcel listed in two segments, or both listed and excluded, fails. The curated list is the source of truth. The live catalog has 11 segments and 559 parcels.
- **Rule.** The scenario step passes each row's catalog membership to `scenarioEligible(rec, units, freewayLand)`, which returns false for a catalog parcel. The rule applies to the T11 rows of `parcels.bin` only (so `eligible`, `hostable` and `hostableBase` are 0 on freeway land and its options.bin row is empty, and the simulation sees it through `eligible`), not to the T13 panel: calibration describes the past market, so a catalog parcel's panel rows keep their `hostable_base`. V18 accordingly compares a catalog row's `hostableBase` with 0, not with the panel. `writeChunks` takes the catalog and writes its lots with `eligible` false, so the Paint editor refuses them too; `parcel_out.eligible` and `readParcelRecords` are unchanged, so the scenario step's calibration panel and freeway-land counts do not move.
- **Counts.** Always present, 0 without a catalog: `scenario.freeway_land.lots` (catalog rows in `parcels.bin`), `scenario.freeway_land.net_removed` and `scenario.freeway_land.net_removed.<freeway lower-cased>` per segment freeway: over catalog rows the rule turned unhostable (eligible, an FZP envelope of at least one story and an option there with more homes than now, without the rule), Σ max(0, the most homes of the row's options within the FZP envelope and cap − existing homes) on the row's candidates as if eligible (rule A), the static net capacity the simulation measures. With a catalog one warning names the totals (`scenario: freeway land makes <lots> lots unbuildable, <net> net homes of static capacity (<freeway> <n>, …)`), and catalog parcels not in `parcels.bin` are warned about.
- **Homes.** A catalog parcel with existing homes fails the build (`scenario: freeway-land parcel <id> has <n> existing homes`): freeway land holds none, and no home is ever demolished.
- **Check.** V17 compares `eligible` with `scenarioEligible` on the catalog and fails if any catalog parcel's chunk record is eligible. `build` passes the catalog it used; a standalone `check [<v>]` reads today's catalog of the version's kind (fixture or live), so an older out dir checked against a newer catalog can fail V17.
- **Paint, live.** On `2026-11-14-bb5c9d30` all 559 catalog lots are chunk-ineligible, and 151,799 of 155,020 chunk records are eligible. Every eligible lot painted at 80 stories (the brush's top, generated in `max` mode) gives 4,508,419 net homes, against the first goal of 82,069.

## Road-like lots

Lots that are road (street remnants, medians, slopes, undedicated streets, strips under ramps and beside kept freeways) stay on the map with their outline, homes and buildings, but are never candidates for building (spec `docs/superpowers/specs/2026-11-07-road-lots-design.md`). The imagery review, the lists behind the override file and the live build's measurements are in [road-lots.md](road-lots.md). They take the underwater path, not the freeway-land one: a road lot has no future as housing that a plan could free.

- **Source.** `pipeline/sql/55_road_lots.sql`, after `50_clip.sql` and before `60_attributes.sql`. It reads `parcels` (with `underwater`), `pieces`, `parcel_landuse`, `src_parcel_attrs`, `src_roll`, `src_streets` and `src_city_lands` (DataSF City Lands, see the top of this page), plus four input tables from `pipeline/lib/road-lots.ts`: `rl_word` (the word list, rewritten from code by every `runSql`), `rl_catalog` (the freeway-land catalog's parcels), `rl_keep` and `rl_road` (the override file). `runSql` creates the last three empty when a caller loaded none, so the SQL unit tests still run. The `road_*` thresholds are in `SQL_VARS` (`pipeline/config.ts`), all tier 4 from the 2026-11-07 investigation of the live parcels.
- **Evaluated lots.** A lot is evaluated when it is not underwater (the two sets stay disjoint) and its owner is public: zoning `P` (active rows, `blklot = mapblklot` first), or the latest roll year's class (the row `80_scenario.sql` picks: largest `property_area`, then `parcel_number`, `use_code`, `property_class_code`; roll rows mapped to lots through `src_parcel_attrs.blklot`) one of `VPUB`, `VG`, `IXG`, `IG`, `PLG`, `OG`, `GG`, `EG`, or a City Lands row names it.
- **City Lands join.** City Lands has no block-lot column, so it joins by geometry: a lot takes the City Lands row that covers the largest share of its area, when that share is at least `road_city_share_min` (0.5; ties by `land_id`, then geometry). One name per lot, so a sliver of a neighbouring median never names a house lot. Rows that name no lot are counted (`road_like.city_lands.unmatched`) and ignored.
- **Rule.** The raw rule flags an evaluated lot when its building cover (Overture pieces over lot area, not `floor_area_m2`, which neighbours' footprints leak into) is under `road_cover_max` (0.25), it has no homes (`parcel_landuse.units` 0, the chunk's `existingUnits`), it is not freeway-land catalog land (catalog membership wins), and any of:
  - **R7, the name:** its City Lands `land_name` holds a word of `ROAD_NAME_WORDS`;
  - **R1n, the strip:** cover under `road_bare_cover_max` (0.05: slivers of neighbours' footprints leak into lots, so 0 would miss real strips) and `(ST_MaximumInscribedCircle(geom, road_mic_tol_m)).radius` (tolerance 0.05 m) under `road_strip_radius_m` (3.5 m);
  - **R2s, beside the street:** cover under `road_bare_cover_max` and at least `road_street_share_min` (0.8, inclusive with a 1e-6 tolerance) of the lot within `road_street_band_m` (10 m, round-capped buffers unioned in `cnn` order) of a public street centreline: a `src_streets` line whose layer is not `FREEWAYS`, `PRIVATE`, `PRIVATE_PARKING`, `PAPER_WATER` or `PARKS%`;
  - **R3, on the freeway:** a `FREEWAYS` centreline crosses the lot, or the centreline nearest its `ST_PointOnSurface` (any layer, within `road_nearest_search_m`, 300 m; ties by the smaller `cnn`) is a `FREEWAYS` line under `road_freeway_m` (40 m) from that point (the investigation's measure, so its precision figure holds).

  `road_lots(id, reason, eligible_without)` holds the raw lots no `keep` row keeps, plus every `road` row's lot that is not catalog land and not underwater (a road row skips the other tests). Reason: `override` for a road row, else the first that fires of `r7`, `r1n`, `r2s`, `r3`. `road_lot_eval` keeps every evaluated lot with each rule's boolean, the measures, `raw`, `kept_by` and `listed`, so "R3 alone" is visible to the review. Every aggregate over geometry is ordered (V12).

- **Word list.** `ROAD_NAME_WORDS` in `pipeline/lib/road-lots.ts`, decided from the 1,035 live names (recon 2026-11-07), with a test per word. Every word matches whole (`\b…\b` on the upper-cased name, the same pattern in TS and DuckDB), because a substring `ROADWAY` hits `BROADWAY PARCEL (STAIRS)`, `I-480 BROADWAY PARCEL` and an air-rights health centre over the Broadway tunnel, and `ROW` hits `ROWING`. `PLAZA` is dropped: its 18 live matches include parks (Alta Plaza, Justin Herman Plaza, Fairmount Plaza), civic plazas (Mint, Hallidie, UN Plaza), a parking plaza and a MOHCD housing site (`Parcel E of Ridgetop Plaza`). `CIRCLE` is narrowed to `CHAVEZ ST CIRCLE`, its only road match. `RIGHT OF WAY` (unhyphenated) is listed beside `RIGHT-OF-WAY`. A new word needs a check of every live name it matches.
- **Override file.** `pipeline/enrichment/road-lots.json` (`ROAD_LOTS_JSON.live`; the mini fixture's is `pipeline/test/fixtures/mini/enrichment/road-lots.json`): `{ "keep": [{ "parcel" | "block", "reason" }], "road": [{ "parcel", "reason" }] }`, parsed by `parseRoadLots`. Every row has a non-blank reason; a keep row names exactly one of a parcel and a block (4 digits and an optional capital letter: `0026` and `0026T` are separate blocks, and a lot's block is its id's leading match of `^[0-9]{4}[A-Z]?`); duplicates, unknown keys and a parcel in both lists fail. A keep row by parcel wins over one by block. Prettier-checked like the other enrichment JSON. Treasure Island and the Octavia Blvd parcels belong in `keep`.
- **Build check.** After `runSql`, every build (live and fixture) runs `roadLotProblems` on the raw output and fails with a `BuildError` (`road lots: …`) on a keep row naming no parcel or block, a keep row the raw rule does not flag (stale, so the list stays honest), a road row naming no parcel, on an underwater lot, on catalog land, or on a lot the raw rule already flags.
- **Where it applies.** `60_attributes.sql` sets `parcel_out.eligible` false and `parcel_out.road_like` to the reason, so the lot leaves the Paint editor, T11 `parcels.bin` (`scenarioEligible` returns false on `roadLike`), the T13 panel (`hostable_base` false in every roll year, unlike freeway land: a road lot was never hostable in the past market either, so `calibration.json` changes) at once. Parcel chunks carry the reason as the sparse column `rl` (`[row, reason]` pairs, strictly increasing rows, omitted when a chunk has none) beside `uw`; the decoder rejects an `rl` row that is eligible or underwater, and decodes chunks without `rl`. No `src/` UI reads it yet.
- **Counts.** The SQL stage reports `road_like.candidates` (evaluated lots), `road_like.raw` and `road_like.raw.<rule>` (each rule that fires on a raw lot), `road_like.kept`, `road_like.listed`, `road_like.catalog_excluded` (lots the raw rule would flag but for the catalog), `road_like.lots` and `road_like.lots.<reason>`, and `road_like.city_lands.rows`, `.named_lots` and `.unmatched`; the quality rule `sd.parcels.road-like` counts `road_lots`. The scenario step adds, always present and 0 without road-like lots: `scenario.road_like.lots` and `.lots.<reason>` (T11 rows), `scenario.road_like.unhostable` and `.unhostable.<reason>` (rows the rule turned unhostable: eligible on `eligible_without`, an FZP envelope of at least one story and an uncapped full-fill yield above 0), `scenario.road_like.net_removed` and `.net_removed.<reason>` (over those rows, Σ max(0, capped FZP full-fill yield − existing homes), as freeway land's) and `scenario.road_like.with_roll_units` (road-like rows whose latest roll shows homes: the lot keeps them and stays ineligible). One warning names the totals (`scenario: road-like lots make <n> lots unbuildable, <net> net homes of static capacity (r7 <n>, r1n <n>, r2s <n>, r3 <n>, override <n>)`), and a second names the lots with roll homes, if any.
- **Review list.** The scenario step writes `pipeline/.cache/derived/<v>/road-lots.csv` (`writeRoadLotsCsv`): every lot the raw rule flags (kept ones with `keptBy` set and `reason` empty) and every road row's lot, with the rule booleans, reason, kept-by reason, `listed`, City Lands name and department, zoning, roll class, cover, inscribed radius, street share, nearest street and its distance, area, `netHomes` (what the rule takes away, or would take away from a kept lot) and the label point. Rows are sorted by `netHomes` descending, then id; numbers have 3 decimals, the label point 6. The build's DuckDB is gone after the build, so this file is what the imagery review reads.
- **Check.** V17 and V18 follow the chunk record's eligibility, as for underwater lots, with no special case: V17's `eligible` must equal `scenarioEligible` on the record (false for a road-like lot), and V18's panel and T11 rows agree because both read the record.

## Building boxes in build

`build` reads the locked `building-boxes` artifact (`boxes.parquet`, `roofs.parquet`; written by `npm run pipeline -- boxes`, which with `--probe <bids>` derives named buildings and writes nothing) and never the LiDAR tiles, so it needs no Python. The boxes are render-only: `pieces`, `parcel_out`, the chunks and every scenario file are computed as before.

- **Stale check.** Before normalising, `build` compares the artifact's recorded `overture-buildings` and `overture-building-parts` hashes (the 12-hex prefixes in the lock entry's `upstreamVersion`) with the lock and stops with a `BuildError` naming `npm run pipeline -- boxes` when either differs. The other recorded inputs (`usgs-lidar-sf`, `datasf-parcels`, `datasf-streets`, `datasf-neighborhoods`), the boxes code hash and the `BOXES` config hash only warn, on live builds only.
- **Composition.** `pipeline/steps/render-boxes.ts` loads the artifact into `bx_boxes` and `bx_roofs` and runs `pipeline/sql/76_render_boxes.sql`, which is not in `SQL_FILES`. `render_boxes(bid, k, src, base_m, height_m, hs, ground_m, ground_min_m, geom)` holds the artifact's rows of the bids in `buildings` (a base box without geometry covers the whole footprint) and, for every building with no artifact row, today's single box (`src` `box`, k 0, `buildings.height_m`, its `bx_roofs` ground when present). Row absence decides it, not `bx_roofs.fallback`: a parts building whose uncovered area fell back keeps its part rows and gets no full-height box. Artifact bids not in `buildings` are ignored.
- **Clip.** `render_pieces` copies 50_clip's logic per box (50_clip itself never changes) with `render_min_piece_m2` (0.25 m²) in place of `min_piece_m2` (2 m²), so 0.5 m-deep false-front strips survive. A whole-footprint box is cut exactly as `pieces` cuts its building. In the mini fixture, `besri` (1.2 m × 1.2 m in lot 6) is dropped from `pieces` but drawn at 0.25 m². `render_export` is the 4326 form, ordered by `parcel_id NULLS LAST, bid, k`.
- **Counts.** The artifact's `boxes.*` counts (`boxesCounts`), with `boxes.src.*` and `boxes.buildings.box` counted on `render_boxes`; `boxes.outside_footprint` (non-`part` boxes outside their footprint by more than 0.01 m², must be 0), `boxes.missing_buildings`, `boxes.artifact_unknown_bids`, `render.pieces` and `render.outside_parcels`. The parts check adds `boxes.parts.checked`, `boxes.parts.disputed` and `boxes.parts.rejected`, and the terraces `boxes.step.sliced` and `boxes.step.over_cap` (buildings with more steps than their own `step_cap`). A lock without the artifact creates none of these tables, adds no counts and draws today's boxes.
- **Tiles.** With the artifact, `buildings.pmtiles` keeps today's single box per building at z12–13 (a building with `part` render boxes draws them, from `low_export`) and carries `render_export` at z14–15 with `src`, `groundM` and `groundMinM` added, in one `buildings` layer (two tippecanoe runs, 400 KB tiles at z12–13 and 1 MB at z14–15, joined by `tile-join`); the tiles step counts `tiles.buildings.drops_z14plus`, `tiles.buildings.z12_parcels` and `tiles.buildings.z13_parcels` (and `tiles.buildings.bytes` on live builds), checked by V37. Without it the tiles input, arguments and archive are byte-identical to before ([building-boxes.md](building-boxes.md) "Tiles").
- **Review files.** `pipeline/.cache/derived/<v>/building-roofs.parquet` (a copy of the artifact's roofs) and `render-pieces.parquet` (GeoParquet, EPSG:7131). Build-internal, never uploaded.

## Project records: quality fields and record rules

Each in-flight project in `projects.json` (T3) and each history in `project-histories.json` (T4d) carries `quality`: the sorted, unique list of `pr.*` rule ids that changed or estimated one of its values. It is `[]` when no rule did. Rules that drop a record are never carried, and neither are observation rules, except `pr.multiphase.score-only` (see below). A history never carries `pr.parcels.shared-existing` or `pr.multiphase.da-netting`, because those act only on T3. `projects.json` also has `qualityRules`, one `{ id, label, tier, valueTier }` entry per id that some project carries, copied from `QUALITY_RULES` and sorted by id. That way the client can show the generic label without the registry. Scenario-data rules (`sd.*`) are never carried: they change values on M15's and M16's lots in the fixture, but the client does not see them. The rules themselves are listed under Data quality above.

- **DQ-2, pipeline rows with no status date** (spec section 4.2 step 10). A pipeline-only row whose `current_status_date` is missing or invalid has no date of its own, so it is linked by parcel to its real Planning record. The candidates are the anchor PRJs of open graph projects whose block-lot, or a child record's block-lot, resolves to a parcel of the row's `blklot`. The winner is chosen only among candidates whose project holds no pipeline row: the latest `open_date` wins, and ties go to the smallest `record_id`. The project keeps its id, dates, stages, pathway, label, parcels and units: the row adds only its `sources` entry (`6jgi-cpb4`, `key: 'case_no'`) and counts as the project's pipeline match, so the project is not stale. It is not multi-phase, and its `multiphase.json` entry is reported as unused. Such a project carries `pr.pipeline.status-date-linked`. When the project has no units or is outside the population, the row's units go to `projects.excludedNoUnits` and the warning `<case_no>: linked to <PRJ> with no units; excluded` names both records. A row with no candidate, or whose every candidate already holds a pipeline row, is dropped and counted under `pr.pipeline.no-status-date`; it has no project and is left out of V21. Live examples: Freedom West passes over `2024-003742PRJ` (which holds its own row) and joins `2020-006887PRJ`, and Flower Mart is excluded.
- **DA netting** (`pr.multiphase.da-netting`, spec section 4.10.2). Planning's remaining count for a PRX master already nets the DA's other pipeline rows, but not projects that entered the daily records after the quarterly snapshot. Before phasing, the masters are taken in id order. Each master's R is its `new_pipeline_units` minus the units of its netting projects: the in-flight projects that are not masters, hold no pipeline row (a DQ-2 linked row counts as one), have a parcel among the master's DA parcels, and have not netted an earlier master. The reduction is reported as `multiphase.netted.<caseNo>` for every master, and a reduced master carries the rule id. A master netted to 0 leaves flight and is counted in `multiphase.nettedOut`, with a warning. For a master whose entry has `schedule: null`, or that has no entry, the DA parcels also hold every current parcel descended from its tracking lot: the subdivision chain in `src_parcel_attrs` (a retired lot yields the lots on its block added on its drop day, followed through retired ones to the active lots, plus its `parcel_lineage` parcel; an active lot yields itself). The report gives `multiphase.descendants.<caseNo>` for every master, and the warning `<caseNo>: descendant parcel <id> is held by <projectId>, which is not a DA project` flags a descendant parcel held by an in-flight project outside the DA (not a same-`da` or base-case PRJ project) that did not net this master; it is checked after netting and does not change it. A master's base-case PRJ is the case without `PRX`, or that plus `PRJ` (`2018-007883PRX` → `2018-007883PRJ`).
- **Score-only masters** (`pr.multiphase.score-only`, DQ-3). A last-resort master has no phases. It is massed on its free DA parcels, which are the DA parcels that no other in-flight project, other master or completed history holds: one `generateForUnits` call with its remaining units and its `daHeights` as district options, usually a district of streets and lots (large-site massing spec section 4.7). The 1 m footprint ghost is drawn only when that call returns null or throws. When it has none, it is score-only: it is simulated and counted but not drawn. Its T3 row has `multiPhase: true`, `phases: null`, `parcelIds: []` and `existingUnits: 0`, and it carries `pr.multiphase.score-only`, so the client can say why it is not drawn. It is counted in `multiphase.scoreOnly` (and `multiphase.lastResort`) and named in the warning `<caseNo>: no free DA parcel; score-only`. No other project may have empty `parcelIds` (V20).

- **Stale open histories** (spec section 4.6, partner rulings E2, C2 and C3). After the in-flight decision (and DQ-2), before DA netting, three rules rewrite the `end` of an open history, in this order; the history alone carries the rule id. Rules 1 and 3 skip in-flight projects; rule 2 also ends an in-flight project's history, and the project leaves flight.
  1. `pr.stages.complete-from-evidence`: an open history at `construction` with no dead (non-superseded) permit is complete at the earliest `xdht-4php` `first_completion_date` on or after its construction day, on a new-construction row (form 1 or 2 with `net_units_completed` > 0; Ruling C4) naming one of its permits (`bpa`) or a lot that resolves to one of its parcels (`blocklot`); else at the `lien_day` of the first roll year after the construction year in which its parcels' assessor units rose by at least min(units, ceil(units / 2)) over the roll at or before the construction year (clamped to 2007), or a parcel's `year_built` reached the construction year; panel rows with `imputed` bit 3 or 5 (units replaced, row carried) are not read. A multi-building project is dated by its first building. It sets `entered.complete` but not `unitsAt.complete` (nothing was certified), and lists the dating xdht row in `sources` (`xdht-4php`, `key: 'bpa'`).
  2. `pr.stages.statutory-expiry`: an open history at `permitIssued` or `construction` exits `expired` at that stage when every unit-bearing permit is past its SF Building Code §106A.4.4 deadline: issued day + Table B completion days + the single extension, by era (E0 before 2009-07-23, E1 to 2013-03-07, E2 after, E3 for applications filed on or after 2026-06-21, which never expire under this rule) and by valuation (`revised_cost`, else `estimated_cost`; a `revised_cost` under $1,000 is a placeholder, filled after linking with the first real valuation of the permit's own estimate, another row of the same permit, else the nearest permit of its project by filed day (none: its own estimate as recorded), rule `pr.permits.placeholder-valuation`, carried by the projects holding such a permit, counted in `permits.placeholderFilled.*` and `permits.placeholderUnfilled`; a site permit of $2.5M or more gets +50%; no valuation takes the middle bracket and is counted by `pr.stages.expiry-no-valuation`). A permit with `last_permit_activity_date` after its own deadline, or with status `reinstated`, keeps the history open; `suspend` does not. A history with a unit-bearing permit that has a completion day or status `complete` (one finished building) is not tested and stays open (`histories.statutoryExpiry.excludedCompletePermit`). The exit day is the latest deadline (at least the stage's entry day, L1). The table, with a citation for every value, is `pipeline/project-records/expiry.ts`; DataSF has no expiry, extension or reinstatement field, and an `expired` status's `status_date` is DBI's batch posting day, not the legal expiry. An in-flight project that meets the test exits too and leaves flight: `projects.excludedStatutory` and `projects.excludedStatutoryUnits`, with the warning `<id>: past statutory completion deadline; expired, left flight`. An in-flight project whose unit-bearing permits are all `suspend` gets the status `suspended` and leaves flight with its history open: `projects.excludedSuspended` (and `…Units`), warning `<id>: every permit suspended; left flight`. Its history then goes through the history rules like any other out-of-flight history, and `suspend` does not block the exit, so a suspended project past its deadline still expires. Both happen before DA netting.
  3. `pr.stages.verified-construction`: the curated verdicts below.

  `pipeline/enrichment/construction-verified.json` (zod schema `pipeline/enrichment/construction-schema.ts`; a parse failure is a `BuildError`; fixture builds read `pipeline/test/fixtures/mini/enrichment/construction-verified.json`) is `{ "schema": 1, "projects": [...] }`, one entry per checked history, ids unique and sorted: `{ "id", "verdict": "complete" | "dead" | "unknown", "checked": "YYYY-MM-DD", "source" (e.g. "partner imagery check"), "completeDay"?: "YYYY-MM-DD" (required for `complete`, only then, not after `checked`), "note"? }`. Curate it for stalled histories the records cannot settle (street-level or aerial imagery): `complete` completes the history at `completeDay`; `dead` (no building found) exits it `withdrawn` at its last stage, dated at the later of the history's last observed day and, at `permitIssued` or `construction`, its permits' statutory completion deadline (Table B with one extension), capped at `checked` and never before the last stage's entry day (time in construction stops when the evidence stops, but not before the permit could lawfully lapse); `unknown` records the check and changes nothing. A verdict applies only to a history still open after rules 1 and 2 (records win). A `dead` verdict applies to an in-flight project too: its history exits the same way and it leaves flight (status `verifiedDead`, `projects.excludedVerifiedDead`, a warning naming it). One naming no open history, or a `complete` or `unknown` verdict on an in-flight project, is a build warning (`... names no open history; not applied` or `... is in flight; not applied`), not a failure. The committed file holds the partner's curated verdicts.

- **Lapsed approvals** (spec section 4.6 rules 4 and 5, partner ruling 2b-d). Two rules end an open history whose last stage is `entitled`. `pr.stages.inferred-lapse`: a discretionary (or Housing Choice-SF) approval whose project has no permit and whose Planning record names none in `building_permits`, no later child record, no development-agreement tie and no other project active on its lots since a year before approval exits `expired` a year after the later of its rule expiry (3 years, with AB 1561 or the Zoning Administrator's COVID extension, then AB 2729; `pipeline/project-records/entitlement.ts`) and its last observed day. It is an inference (the condition is not self-executing and extensions leave no status), so an in-flight project that meets it stays in flight and is only flagged (`projects.lapseFlagged`, a warning naming it). `pr.stages.streamlined-expiry`: an SB 35 / SB 423 / AB 2011 approval exits at 3 years plus the one-time 1-year extension (with AB 1561 / AB 2729), in flight too (`projects.excludedStreamlinedExpiry`), unless half or more of its proposed units are affordable (`number_affordable_units_prop`; `histories.streamlinedExpiry.affordableExempt`). Litigation tolling is not recorded and is not modelled. HSD and AB 2162 approvals take no lapse rule (`projects.lapseNoRule`).
- **Refiled Planning cases** (spec section 4.7, partner ruling 3, rule `pr.projects.superseded`). Before DA netting, in-flight projects anchored on a Planning record whose Planning records give the same street address (`project_address`, else the project label; upper-cased, whitespace collapsed, a trailing ZIP or ZIP+4 and a trailing ", San Francisco[, CA]" stripped; never a missing or `0 UNKNOWN` address), whose parcels share a block, and whose units are within 25% describe one project: the latest-opened Planning record stays in flight and every one opened strictly earlier leaves (records opened the same day, or whose first permits were filed the same day, are sibling buildings and all stay) (status `superseded`, `projects.excludedSuperseded`, a warning naming the keeper). Histories are unchanged and no record carries the rule.
- **Linkage of named alterations and lot BPs** (spec section 4.2, Rulings L1, L2, L2a, L2b, C1a). `datasf-permits-named` holds the unit-adding type 3/8 permits; a build keeps only those a Planning record's `building_permits` names (`parse.named.kept`, `.unnamed`, `.inNewcon`: a permit in both sources takes the new-construction row). For units, beside a live type 1/2 permit, one that records no existing units carries none (it restates the new building), while an alteration of an existing building keeps its gross units; alone, the named alterations count as the largest of their `proposed_units` (each records the building's total). Their completions count gross too: existing units plus the units the completion certifies. A `BP:` project (no Planning record) with at least one proposed unit joins a new-construction Planning-record project (`new_construction` checked, at least 1 unit, no type 1/2 permit of its own, history not exited before the BP's filing) when their parcels overlap (no descendants) and its first permit was filed no more than a year before that project's entitled day (its filing day when never entitled). ## Multi-phase enrichment

`pipeline/enrichment/multiphase.json` is the hand-curated list of Development Agreement (DA) phasings behind the "PRX" master rows of `datasf-dev-pipeline` (`6jgi-cpb4`, `case_no` ending `PRX`). A master is entitled once; its phases are separate permitting sub-projects, so `projects.json` carries them as `phases`. Only a PRX row whose `bpa_no` names no fetched permit is a master (`CASE:<case_no>`, `multiPhase` true); one whose `bpa_no` names a fetched permit joins that permit's project like any pipeline row (`multiPhase` false, spec section 4.2 steps 4 and 9), and its entry stays valid but unused, with the warning `<caseNo>: PRX row joins permit <bpa>; multiphase entry unused`. The file is committed, read directly by `build` (not fetched, not in the lock) and part of the dataset-version hash. Its zod schema is `pipeline/enrichment/schema.ts` and a parse failure is a `BuildError`. Fixture builds read `pipeline/test/fixtures/mini/enrichment/multiphase.json`.

Curation rules (spec section 4.10.1):

- Every PRX row with `new_pipeline_units >= 1` needs an entry (V24). Live on 2026-10-16 that is 21 of 24 rows; `pipeline/test/project-records/multiphase-file.test.ts` pins the list.
- With a published phasing (DA or DDA phasing exhibit, schedule of performance, approved major-phase or sub-phase applications), fill `schedule` and `phases`: the DA's own phase name, gross `units`, `blklots`, `plannedPermitFiled` (the schedule's site-permit or vertical-application deadline, else null; never turn a horizontal or infrastructure date into one) and a `status`.
- `status` is `remaining`, `built` or `separate`. A phase the records show as completed is `built`. A phase that is its own pipeline or permit row is `separate` and needs `separateRef` (`{ dataset, id, key? }`, e.g. `6jgi-cpb4` / `bpa_no`). Only `remaining` phases are drawn; the build fails V24 on a `remaining` phase whose parcels all belong to another in-flight or completed project.
- Every fact (`units`, `blklots`, and `plannedPermitFiled` when set) carries a URL, a `retrieved` date and a `locator` (page, table or exhibit). A count derived by subtraction or a block-lot mapped by the curator (area match, geometry overlay) must say so in the locator.
- Without a published phasing, set `schedule: null`, `phases: []` and list every URL searched in `searched` (non-empty). The build then uses its fallback; that is a recorded decision, not an omission. Do not invent a phase split from arithmetic alone.
- Prefer active `blklot`s from `acdm-wktn`. A retired lot is replaced by the active lots that replaced it, and condominium lots stacked on the same footprint are not listed.
- `units` is at least 1 for every phase, built and separate phases included. Units are gross schedule units. Where a separately tracked building sits inside a phase, either mark it `separate` or net it out of the `remaining` phase (and say so in the locator), so it is not drawn twice.
- Retrieval dates cannot be after the build's `asOf`.
- Heights (large-site massing spec section 4.6): an entry may carry `heights` (`stories`, the prevailing residential height; `maxStories`, the tallest permitted; `openSpaceShare`, the share of land in parks and open space, 0 to 0.9), with or without a schedule, and a phase may carry `stories` and `maxStories`. Stories are integers 1 to 80; a height given in feet is converted with `storiesFromFt` and the locator says so. Every value needs its fact in `heights.facts` or the phase's `facts`. The build carries them to `projects.json` as the master's `daHeights` (each value or null; null without `heights`) and each phase's `stories` with `storiesTier` 1 and its `maxStories` (each null on a fallback phase, and on a merged phase unless every merged phase gives the same value). It also writes `districtMaxStories`: the nearest-rank 90th percentile of recorded (tier 0) stories over in-flight and completed records with at least `DISTRICT_DEFAULT_MIN_UNITS` (100) units, tier 2, omitted when none qualifies; the report counts it as `projects.districtMaxStories` (-1 when omitted) and `projects.districtMaxStories.n`.
- Curating heights: cite only the project's own published design document (Design for Development, Design Standards and Guidelines or Design Controls on sfplanning.org, sfport.com, sfocii.org or sf.gov), with the page and figure or table in the locator. `stories` is the height that covers the largest share of residential blocks (or developable footprint, where the document tabulates it) in the document's height map; when the map does not make that clear (mixed or flexible land use, or a near tie by area whose locator does not state the tie-break), omit `stories` and give only `maxStories`. A near tie may give `stories` when its locator states how the tie was broken. `openSpaceShare` is park and open-space acres over site acres, both from the same document. A phase carries `stories` only when the document covers that phase's area. A value that cannot be cited is left out, never estimated: an entry with no citable value has no `heights`. The 2026-10-19 curation and the entries left without heights are listed in that commit's message.

How the build uses it (spec section 4.10.2): first each master's R is netted (DA netting, above); R below is the netted count. An entry with a schedule and at least one `remaining` phase is **enriched**. The `remaining` phases in file order become `phases`, with parcels resolved from `blklots` minus parcels owned by other in-flight or completed projects. A phase with no parcels left merges into its neighbour. If Planning's remaining count R (the PRX row's `new_pipeline_units`) differs from the phase total, units are scaled to R by largest remainder and the factor, taken with R before netting, is reported as `multiphase.scale.<caseNo>`; V24 fails outside [0.8, 1.25]. An entry without a schedule is **fallback**: k phases of about the median size of the project's completed buildings (else the citywide median of completed buildings of 50 or more units since 2015), at most one per free DA parcel. If neither works (no phase size, no free DA parcel, or ruling L2) the master is a **last resort** (`phases` null): it is massed on its free DA parcels (a footprint ghost only when massing fails), or is score-only when it has none (see above). Unresolvable `blklots` and a schedule with no `remaining` phase do not fail the build; they come back as warnings in `report.json`. The report counts `multiphase.enriched`, `multiphase.fallback`, `multiphase.lastResort`, `multiphase.scoreOnly`, `multiphase.nettedOut` and `multiphase.netted.<caseNo>`.

Rule notes (amendments to spec sections 4.6 and 4.10.2 found on the live data):

- L1, exit after later entered stages: the spec's "latest entered stage on or before the exit day" contradicts V23 (`end.day` not before the last entered day) when stages were entered after the exit day. Then `exit.stage` is the last entered stage and `exit.day` is its entry day.
- L2, fully excluded enriched master: when every phase of an enriched master is left with no parcels and the tracking parcels are all excluded as well, the master is a last resort (`phases` null) instead of a single phase on the tracking parcel, which would draw a parcel twice (spec 4.10.3, V24 disjointness).

## Funding enrichment

`pipeline/enrichment/funding.json` is the hand-transcribed public funding of affordable housing in San Francisco: per-home funding by source (Exhibit F of the Budget and Legislative Analyst's 2026 report), the City's multifamily spending by source (Exhibit E), the state and federal pools, and the CDLAC and CTCAC award rows behind the check. It is committed, read directly by `build` (not fetched, not in the lock) and part of the dataset-version hash. Its zod schema is `pipeline/enrichment/funding-schema.ts` (`strictObject`, `YYYY-MM-DD` dates, non-empty text), and a parse failure is a `BuildError` naming the zod path, before any step runs. `FUNDING` in `pipeline/steps/build.ts` holds the paths: live `pipeline/enrichment/funding.json`, and on a `fixture-<n>` version the twin `pipeline/test/fixtures/mini/enrichment/funding.json`. The calibration step reads it through `readFundingFile` and `baselineFunding` (`pipeline/lib/fzp-cal/funding.ts`) turns it into `calibration.baselineFunding`. What it contains, how to update it and how to read the report sections are in [finance-data.md](finance-data.md).

Refinements (each a `BuildError`):

- `perHome` parts sum to `total`: "perHome parts must sum to total".
- `city.sources` dollars sum to `city.total`: "city sources must sum to total".
- Ids (`city.sources[].id`, `state.id`, `federal.id`) are unique, match `^[a-z0-9][a-z0-9-]{0,30}$` and do not start `u-`. Ids are stable: stored policies name them, so one is never renamed or reused, and a source that ends moves its id to `retiredIds`.
- No current id is in `retiredIds`: "funding id <x> is retired and cannot be reused".
- `debt` is set exactly when `kind` is `goBond` or `cop`.
- `awards.years` is non-empty, ascending and unique, and every award row's `year` is in it.
- A source whose `bound` has money remaining (`kind: 'remaining'`, `dollars` above 0) has a yearly amount above 0: "a source with money remaining needs a yearly amount".
- `federal.dollarsPerYear` is the most new-construction homes awarded in one year (`awards.rows` with `newConstruction`) times `perHome.federal`: "federal.dollarsPerYear must be the most new-construction homes awarded in one year times perHome.federal".

Cross-check with the model's constants: `perHome.total` must equal `AFFORDABLE.costPerHome` and `perHome.permanentLoans + perHome.other` must equal `AFFORDABLE.ownPerHome` (`src/lib/sim/finance`), or the step throws `funding.json perHome disagrees with AFFORDABLE (src/lib/sim/finance)`. Both transcribe the same exhibit.

The fixture twin has the live `perHome`, ids and kinds, invented City and state dollars and two invented award rows, every citation labelled "Fixture:"; every `baselineFunding` provenance entry of a fixture build is tier 4. The mini fixture's MOHCD rows (two 100% affordable new-construction rows of 2 and 6 homes, and an inclusionary row that must be left out) give `minHomes` 2.

## Scenario parcels

`build` runs `pipeline/steps/scenario.ts` after the parcel chunks are written. It produces one T11 file the client reads and two T13 files for pipeline consumers; design in `docs/superpowers/specs/2026-10-16-scenario-data-design.md`.

- **Sources** (DataSF, pinned in the lock): the height and bulk districts `h9wh-cg3m`, the parcel attributes `acdm-wktn` (zoning code; active and retired parcels) and the assessor historical secured rolls `wv5m-vpq2`. Planning Director Bulletin No. 11 and the Planning Code give the Local Program rules and density caps. SQL is `pipeline/sql/80_scenario.sql` and `81_scenario_features.sql`; the TS step does yields and encoding.
- **T11** `scenarios/fzp/parcels.bin` (codec `sfh-scenario/2`, `src/lib/data/scenario-codec.ts`): a deflate-raw column file with one row per emitted parcel: height district, base and FZP envelope in stories, Local Program flag, base and FZP density caps (`baseCap`, `fzpCap`), latest-roll features, an imputed-field bitmask and the hostable flags. A lot's homes at an envelope are its options.bin row's (rule A): the most homes among its options at or below the envelope, each clipped by the cap. Major 2 dropped the fill-level yields (`yield`, `baseYield`), `fillLevels` and the derived `potentialRatio` and `storiesGap`, and added `fzpCap`; the decoder refuses major 1 (`unsupported major 1`). Fixture reports omit its deflate size.
- **T13** `parcel-panel.parquet` (one row per parcel and roll year, with that year's `base_yield`, the most homes of its options at or below the base stories after the cap in force on its lien date, and its `hostable_base`) and `parcel-lineage.parquet` (retired parcel to current parcel). They live in the derived cache (see Where things land) and are never uploaded. The DuckDB tables `scenario_panel` and `parcel_lineage` stay in the build's database for later steps of the same build.
- **Eligible.** The scenario's eligibility is the chunk record's (a land-use row that is not `OPENSPACE`, and the lot is neither underwater nor road-like: neither is ever eligible, see Land mask and Road-like lots above), plus `sd.landuse.none-with-units`: a parcel with no land-use row is eligible when the assessor roll shows homes on it (latest roll for `parcels.bin`, each roll year's own homes for the panel); with none it stays ineligible. `parcels.bin` ships it as `flags` bit 5 (`eligible`), and `scenarioRecordOf` puts it on the record, so the generator, the yields, the hostable flags and the worker all read it. The chunk records and the editor use `parcel_out.eligible` without the `sd.landuse.none-with-units` addition. `report.json` has `scenario.eligible` (T11 parcels) and `scenario.panel.landuse_none_with_units` (panel parcel-years the rule makes eligible); the rule's `fired`/`of` are on T11 parcels.
- **Hostable.** A parcel is hostable (may receive a simulated project) when it is eligible (above), its envelope has at least one story, and one of its building options at or below that envelope has more homes than the parcel has now (`envelope-row.ts`; the scenario step reads its candidates, `rowTopHomes`). `hostable` uses the FZP envelope and `hostableBase` (the panel's `hostable_base`) the base envelope. The density cap is not part of the test: it shapes the homes a start builds (rule A, at run time) and `base_yield`, but a cap at or below the existing homes does not remove a parcel from the at-risk set, so the 2022-11-27 fourplex change does not flip `hostable_base` (partner ruling, option c). V17 recomputes both flags from options.bin (its pruning keeps each row's best option), and the step counts `scenario.hostable_mismatch` and `scenario.hostable_base_mismatch` against its own candidates. `report.json` has `hostable_base` for each roll year (`scenario.panel.hostable_base.<year>`), and, pairing each panel year with the previous panel year (a missing roll year is spanned, not skipped), the parcels with a row in both (`.<year>.both_rows`) and their counts in each year (`.<year>.both`, `.<year>.both_prev`). V18 requires those two counts to differ by at most 5%, and it fails a pair that shares no parcel. `scenario.capacity.fzp_net_total` is Σ max(0, the most homes after the FZP cap − existing homes) over hostable Local Program parcels (V17's cross-check against Planning's figure).
- **Evidence tiers.** Roll features are tier 0 with tier 2 imputation; the envelope is tier 3 (the RH-1 35 ft limit, tier 1); the caps and hostable rule are tier 3 or 4. `parcels.bin` carries a `provenance` block for each, and every numeric parameter in the scenario code has a comment naming its tier and source.

Every option's homes (options.bin, the panel's `base_yield`, the hostable flags, and the SB 79 and current-law layers of `policy.bin`) come from the candidate generator (`candidatesOf` in `src/lib/sim/choice/options.ts`, see [building-choice.md](building-choice.md)). It is code under the `datasetVersion` hash: changing it changes the published options and needs a new version. Recorded projects (`generateForUnits`, `generateDistrictForUnits`) are not capped, because their stated stories are tier 0 evidence.

**RH-1 height (Planning Code Sec. 261(b)(1), tier 1).** No dwelling in an RH-1, RH-1(D) or RH-1(S) District may exceed 35 ft, whatever the mapped height district (Planning ZAB No. 5: "In RH-1 districts, regardless of the mapped height limit, the maximum allowable height is 35 feet"; http://sf-ca.elaws.us/code/plco_art2.5_sec261). The base stories of a lot whose zoning code is RH-1-family in every component are `storiesFromFt(min(baseFt, 35))` = 3 under a 40-X (or taller) district (`baseHeightFt` in `pipeline/lib/heights.ts`), in `parcels.bin` (`baseStories`, and `envelopeStories` off the Local Program) and the panel's `base_stories` (`sc_parcel`) alike. The Local Program height is not capped. The slope exceptions (40 ft, 30 ft) and the 30 ft front envelope of Sec. 261(c) are not modelled, nor any RH-2 or RH-3 limit (RH-2's 40 ft equals the 40-X district). §207.11 reads this limit as the applicable height (`s207HeightFt`), so an RH-1 lot in 40-X is under 40 ft and, where §207.11 applies, rises to 40 ft (4 stories).

### Data rules

### Density caps

`pipeline/lib/density-caps.ts` gives base-zoning units per lot in three periods, chosen by the day asked for:

1. Before 2022-11-27: the as-of-right per-lot counts for RH districts (the per-area alternatives then needed a conditional use authorisation). Source: Planning code summary 2021-010762PCA (the four-unit density exception).
2. 2022-11-27 to 2026-01-11, the fourplex period: the current RH tables with a floor of four units per lot.
3. From 2026-01-12, the Family Zoning Plan date: as in 2, except that NC lots inside the R-4 height and bulk district have form-based density and no cap (Ordinance 245-25).

The panel uses the period of each roll year's lien date (1 January). In `parcels.bin`, `baseCap` is the cap on the day before 2026-01-12; `fzpCap` is none on Local Program parcels and the cap on the build's snapshot day elsewhere. The 2026-01-12 date is a coordinator ruling (the ordinance was signed 2025-12-12), not an official effective-date notice.

Sources are the official ones: Planning code summary 2021-010762PCA on sfplanning.org, and Ordinance No. 245-25 (`o0245-25.pdf`) on sfbos.org. The consolidated Code on amlegal blocks automated access (HTTP 403), so amendments after Ord. 245-25 were not checked there; a gocodebook mirror dated 2026-09-23 agrees with every current value. Each row of `DENSITY_CAP_TABLE` carries its section and a page-anchored URL.

Verification status: every table row is `official`. `UNVERIFIED_DISTRICTS` is the generic `NCD` and `NCT` codes (plus any `mirror` row, currently none): they default to no cap, and every build prints a warning with the parcel counts.

### SB 79 as written

The `sb79*` columns are SB 79 (Gov. Code §§65912.155–65912.162) applied to every lot as the statute is written: a stock layer, separate from current law (Task 9), with the parameters, cites and evidence tiers in `pipeline/sb79-config.ts`. The functions are pure, in `pipeline/lib/sb79.ts`; the step is `writePolicy`.

- **Tier source** (`TIER_SOURCE = 'gtfs'`, branch B). MTC's SB 79 stop map carries a disclaimer licence with no redistribution grant, so it is not shipped and there is no cross-check against it in the build. `stopTiers` reads the transit step's `transit.json`: a stop on a heavy-rail pattern is tier 1; a commuter-rail stop is tier 1 when its station (the stops sharing its `stationId`) has at least 72 trains a day (Σ `tpd`, `VHF_TPD`) and tier 2 at 48 (`HF_TPD`); a light-rail or streetcar stop (`LIGHT_RAIL_MODES`, not cable car) is tier 2; so is a stop in `MUNI_TIER2_STOP_IDS`, the 438 Muni stops MTC designates current tier 2 (our own id list cited to MTC). The lowest tier wins. MTC's 9 planned BRT stops (Hunters Point, Candlestick) are left out, though §65912.156(p) counts planned stops: a known undercount near those stops, listed in `UNSOURCED`. `runPolicySql` writes the tiered stops to `pol_stops`.
- **Bands.** `pol_tod` (82_policy.sql) holds, per parcel and tier, the distance from the DataSF outline (`geom_orig`, EPSG:7131) to the nearest stop of that tier within ½ mile (`SQL_VARS.tod_half_m`, 804.672 m). The statute measures to a "pedestrian access point"; stop points stand in for them (tier 4, in `UNSOURCED`). `bandOf`: adjacent ≤ 200 ft (60.96 m), quarter ≤ ¼ mile (402.336 m), half ≤ ½ mile, each inclusive at its upper edge. `bestStandard` takes, over the tiers in reach, the standard (`STANDARDS[tier][band]`) with the greatest height; a tie goes to tier 1. `todTier` and `todBand` are that standard's.
- **Statuses** (`sb79Row`, in precedence order): `outside` (no stop within ½ mile); `not-eligible` (not scenario-eligible, `parcels.bin` flags bit 5); `zone` (`zoneClassOf(zoning_code)` is `excluded`, or `unlisted`: no `ZONE_CLASS_RULES` entry; a split code takes its most permissive component); `rent-control` (§65912.157(h), more than two rent-controlled units: `rentControlExcluded`, `parcels.bin` `rentControlLikely` (homes built before 1979 on the latest roll) and more than `RENT_CONTROL_MAX_UNITS` (2) existing homes; a proxy, tier 2 in `UNSOURCED`: the statute counts units occupied by tenants in the past seven years or demolished within seven years, and the model has no occupancy or demolition history, so every pre-1979 home counts); then the envelope: `storiesFromFt(heightFt)` stories and the statute density cap `unitsFor(duPerAcre, lotAreaM2)` = ⌈du/ac × acres⌉ (ruling 2; SB 79 has no fractional-unit rule, so `UNITS_ROUNDING` takes §65915(q)'s round-up, tier 2). Its homes are the most among the lot's options at or below those stories after the cap (`topHomesAt`, rule A); under 5 homes (`MIN_UNITS`, §65912.157(a)(1)) it is `min-units`, else `applies`. Every status but `applies` has 0 stories and no cap (`0xffff`); `hostableSb79` is `applies`. The Density Bonus Law is not modelled. The City's exemption tables are ignored here (ruling 3): they are current law's.
- **Counts:** `policy.sb79.<status>` (one per status); `policy.sb79.stops.tier1`, `.tier2`; `policy.sb79.cap_binds` (`applies` rows whose most homes before the cap exceed those after it); `policy.sb79.net_capacity` (Σ over `applies` rows of the most homes − existing homes, at least 0); `policy.sb79.tod_share` (parcels within ½ mile over all parcels, × 10⁴). T14 rule `sd.sb79.zone-unlisted` counts parcels within ½ mile whose zoning code has no zone class; `sd.sb79.tier2-unmatched` counts the `MUNI_TIER2_STOP_IDS` ids with no stop in `transit.json` (they tier nothing; V32 requires at least `muniTier2MatchMin` matched). Mini fixture: 7 `applies`, 5 `rent-control`, 3 `not-eligible`, 1 `zone`, 2 `min-units`, 0 `outside`; 3 tier-1 and 2 tier-2 stops; cap binds on 6; net capacity 89 (the mini README lists the lots).
- **V32** checks the columns against the statute; see Invariants above. Unsourced readings (rounding, stop points, rent-control proxy, planned stops) are in `UNSOURCED` in `pipeline/sb79-config.ts`.

### Current law (FZP + §207.11)

Ruling 1: current law is the FZP envelope plus Planning Code §207.11 (Ordinance 082-26 §5, Board File 260132), with the City's permanent and temporary exemption tables applied (`CURRENT_LAW_RULE = 'fzp+s207.11'` in the header). SB 79 as written (above) is a separate stock layer. The `current*` columns are the comparison twin plan 2 reads, and its protection reset. The functions are pure, in `pipeline/lib/current-law.ts`; the parameters and cites are `S207` in `pipeline/sb79-config.ts`; the step is `writePolicy`.

- **Statuses** (`s207Status`, in precedence order), each §207.11(b) condition with its data proxy and evidence tier:
  - `outside`: (b)(1), not within ½ mile of an SB 79 TOD stop; the SB 79 tiers and bands above (`todBand` 0; tier 1 statute, stop points tier 4).
  - `not-eligible`: not scenario-eligible (`parcels.bin` flags bit 5); a model rule, not a §207.11 condition.
  - `exempt`: (b)(6), listed in either exemption table (`exemptPermanent` or `exemptTemporary`; tier 0 transcription of the Board File tables).
  - `not-residential`: (b)(2), the district does not principally permit residential use (`zoneClassOf(zoning_code).principallyResidential`; tier 2–3, in `UNSOURCED`).
  - `no-limit`: (b)(3) fails. (b)(3) reads "Either limits residential density by Numeric Density, or has a height limit of less than 40 feet". The lot has no numeric density limit (`fzpCap` none: form-based districts and Local Program parcels) and its applicable height is not under 40 ft. The applicable height is the height limit of the envelope the model's project uses: `sc_district.lp_ft` (else `base_ft`) on a Local Program lot, `base_ft` elsewhere, at most 35 ft on an RH-1 lot (Sec. 261(b)(1), `s207HeightFt`; `policy.s207.base_ft_mismatch` still compares the mapped heights) (tier 2: the ordinance names "the" height limit of the project; listed in `UNSOURCED`). A lot with no height district counts as not under 40 (tier 4, invented: there is no height to judge; listed in `UNSOURCED`).
  - `r4`: (b)(4), in an R-4 height district (`sc_district.r4`; tier 0). An R-4 lot is usually `no-limit` first: on the Local Program its FZP cap is none, and its applicable height is 40 ft or more.
  - `historic`: (b)(7), an Article 10 landmark or district contributor or an Article 11 Category I–IV building, approximated by historic status A\* (`S207.historicCodes`; tier 2, in `UNSOURCED`).
  - `meets-minimum`: (b)(8) fails. (b)(8) reads "The permitted density prior to applying the density and height exception in subsection (c) does not meet the minimum density required by California Government Code Section 65912.157", and Planning's reading of the minimum (controller ruling; Alternative Plan memo footnote 4, tier 1) is: the FZP cap is at least `unitsFor(S207.minDensityDuPerAcre(tier, band), lotAreaM2, 1, 'round')`, half the SB 79 density of the lot's tier and band (band 1 with the adjacency intensifier). An uncapped lot permits unlimited density, so it meets any minimum: it is `meets-minimum` when it reaches (b)(8), which only an uncapped lot under 40 ft does (otherwise it is `no-limit`). It never qualifies, and an `applies` row with no cap is a bug (`s207Row` throws; V33 flags it). The literal 30 du/ac reading is kept in `UNSOURCED`.
  - `applies`: every condition holds. (b)(5), no §206.6 density bonus, is not modelled: HCD's approval requires SF not to enforce it. The SB 79 rent-control exclusion does not apply to §207.11.
- **Height and cap** (`s207Envelope`, §207.11(c)): (c)(2) reads "For any housing development project located on a site meeting the criteria in subsection (b) and with a height limit of less than 40 feet, the applicable height limit shall be 40 feet." An applicable height (above) under 40 ft becomes 40 ft, so stories are `max(envelopeStories, storiesFromFt(40))` = at least 4 (c)(2); otherwise the FZP stories. The cap is `max(fzpCap, unitsFor(STANDARDS[tier][band].duPerAcre, lotAreaM2, 0.5, 'round'))`: half the SB 79 density × lot acres, rounded half up (`S207.rounding`, Planning's "normal rounding", tier 1), never below a larger existing cap (tier 2, in `UNSOURCED`). The Coastal Zone clause of (c)(1) is not modelled. Its homes are the most among the lot's options within those stories after the cap (`envelopeRow`, the same rule as `parcels.bin`'s FZP layer); `hostable` is scenario-eligible, at least one story and an option there with more homes than now, before the cap. Every status but `applies` returns the FZP row.
- **Exemption tables.** The §3 Table of Permanent Exclusions (industrial employment hubs) and the §4 Table of Temporary Exemptions (low-resource parcels, Ver2), joined as in Policy parcels above. They exempt a lot from §207.11 only; SB 79 as written ignores them (ruling 3).
- **Tie rule** (`currentLawRow`): a lot takes §207.11 (`currentFromS207` 1) when it is `applies` and `mostPermissive(fzp, s207)` is `b`: §207.11 is hostable and FZP is not, or §207.11's options hold more homes within its stories and cap. A tie keeps FZP. Stories, cap and homes always come from one layer.
- **Counts:** `policy.s207.<status>` (one per status); `policy.s207.base_ft_mismatch` (the step's `sc_district` applicable height or R-4 flag ≠ the one parsed from `parcels.bin`'s district string, which V33 reads; must be 0); `policy.current.from_s207`; `policy.current.net_capacity` (Σ over `hostableCurrent` rows of the most homes − existing homes, at least 0); `policy.current.fzp_mismatch` (rows where the step's FZP cap or `envelopeRow`'s hostable flag ≠ `parcels.bin`'s; must be 0). Mini fixture: 3 `applies` (lots 6, 17, 18), 2 `exempt` (12, 15), 7 `no-limit` (1–4, 11, 13, 14), 3 `meets-minimum` (5, 8, 10), 3 `not-eligible` (7, 9, 16); 2 from §207.11 (17, 18); net capacity 124.
- **V33** recomputes every row's status, and the §207.11 stories and cap where `currentFromS207` is 1, from `parcels.bin` (eligibility, lot area, FZP stories, and the applicable height and R-4 flag parsed from the height district string; the applicable height is the Local Program height on a Local Program lot and the base height elsewhere), the policy columns and `zoneClassOf(useDistrict)`; see Invariants above. `check` reads each layer's homes from options.bin; the step's `policy.current.fzp_mismatch` must be 0.

## Transit

`transit.json` (codec `sfh-transit/1`) is the reduced transit network the capacity features read; design in the transit spec (`docs/superpowers/specs/2026-10-14-transit-capacity-design.md`).

- Feeds come only from the agencies' own GTFS URLs (`pipeline/transit-config.ts`), never 511. They are pinned in the lock as `gtfs-muni`, `gtfs-bart` and `gtfs-caltrain`.
- Vehicles and route-to-vehicle assignments live in `pipeline/transit-config.ts`, each citing its source and an as-of date (or `null`). Every `url` is currently `null`: the spec supplies none, so add one when a row is re-sourced. Update them when SFMTA reassigns fleets, then run `npm run pipeline -- build`: a non-fixture build is strict (`strict: !fixtureMode` in `pipeline/steps/build.ts`; there is no CLI flag) and fails when an assigned line is missing from a feed, which catches renamed lines. Fixture builds and `npm run data:transit` skip that check.
- The service day is chosen per feed: the first Tuesday with service on or after the **transit target date**, the UTC date of the newest `retrievedAt` among the GTFS feeds only (`TRANSIT_DATE_SOURCE_IDS` in `pipeline/steps/transit.ts`, an allowlist equal to `GTFS_IDS`). Fetching a DataSF or policy source does not move it, so `transit.json` and the SB 79 tiers it feeds change only with a GTFS refresh. A feed whose calendar has expired is a warning, not a failure.
- **Archived feeds** (the car back-cast's transit by year): `GTFS_ARCHIVES` in `pipeline/transit-config.ts`, one feed per operator and year (the version in force on 1 April), locked as `gtfs-archive-<operator>-<year>`. They are not in `GTFS_IDS`, `TRANSIT_DATE_SOURCE_IDS` or `AS_OF_SOURCE_IDS`, so they never change today's network, the transit target date or `asOf`. A plain `fetch` skips them; `fetch --only gtfs-archive` fetches them all (or name one id). `fetchGtfsArchive` refuses a feed that is not GTFS, has no route of the operator's route types, no stop in San Francisco, or no service on 1 April of its year. `lockTransitYears` / `transitByYear` give the network for a year (per operator: that year's archive, else the earliest later one, else today's feed; `sourceYear` reports it) and `accessByYear` (`pipeline/lib/cars/access.ts`) the zone access. Sources and gaps: [cars-data.md](cars-data.md#archived-muni-bart-caltrain-gtfs).
- `npm run data:transit` exists for local use: it builds `transit.json` from live feeds into the local dataset (see [developing.md](developing.md)). It clips to the loaded dataset's neighborhoods, so it needs a real dataset from `npm run data:local`; `fixture-0` yields only a handful of stops.

## Car zones and households

The car step (`pipeline/steps/cars.ts`, `carsStep`) builds the car-ownership model's zones and start population (spec `docs/superpowers/specs/2026-11-24-car-ownership-design.html`, "Households"). It runs after transit and before calibration, and needs the Census entries `census-acs5-bg-*`, `census-pums5-*`, `census-tiger-bg-*` and `census-puma-*`: with none it writes nothing and returns nulls, with only some it warns and writes nothing.

- **Zones.** The block groups of the latest ACS release's vintage (2020 for 2020-2024), sorted by GEOID (`pipeline/lib/cars/zones.ts`). A lot's zone is the block group its label point falls in (`lotZone`, -1 for none, `cars.lotsNoZone`; on a shared edge the lowest zone). Area is TIGER's land area. Each zone's PUMA is its tract's (`src_tract_puma`).
- **Households.** Each zone holds `round(occupied × homes)` households (`floor(x + 0.5)`): homes are the `existingUnits` of its lots, `occupied` the zone's B25002 occupied share (the citywide share where B25002 has no total), held constant by the sim. The latest PUMS release on the same PUMAs is the seed: the zone's PUMA's records are raked (`balance`, `pipeline/lib/cars/ipf.ts`, at most 200 passes to 1e-6) to the zone's B25044 tenure by vehicles (0, 1, 2, 3+), B25009 tenure by size (1, 2, 3, 4+) and B19001 income (16 brackets), each scaled to the zone's total; once the choice is fitted, the population is raked again with the vehicle margin replaced by the zone's shrunk shares (share\*, below; `startPopulation`'s `levels`), so the start holds the model's shares at month 0 and zones do not drift as households turn over; the type-by-cars weights are split with `splitSystematic` at u = 0.5 (`pipeline/lib/cars/population.ts`). No block-group table counts workers per household (B08202 is tract only, B08301 counts persons), so workers follow the PUMS records; B08301 is a cross-check (`cars.workers` against `cars.acs.workers`).
- **Types.** `TYPE_BANDS` (`pipeline/lib/cars/config.ts`): size 1, 2, 3, 4+; workers 0, 1, 2+; income at the weighted PUMS quartiles of the release (`typeBandsOf`); own or rent. 96 types. The bands go into the model (`CarModel.bands`) with the choice.
- **Access.** Each zone's transit access is the homes-weighted mean of today's access grid (`buildAccessGrid` on the build's network) at its lots (`pipeline/lib/cars/access.ts`); a zone with no homes takes the plain mean over its lots.
- **Choice.** A multinomial logit over 0, 1, 2, 3+ cars (`fitChoice`, `pipeline/lib/cars/fit.ts`; Newton fits in `pipeline/lib/cars/mnl.ts`, fdlibm `exp`/`log`). Stage 1: household terms (size, workers and income band dummies, renter) on the PUMS records (WGTP) with the PUMA's mean density and access. Stage 2: household terms fixed; constants, density (households per hectare of ALAND) and access on the start population by block group. Each block group's B25044 shares are shrunk toward the model's (`shrinkShares`: empirical Bayes, share\* = (n·obs + n0·pred)/(n + n0), n the block group's effective sample size from its B25044 margins of error (`effectiveSizes`: n_eff = Σ p(1−p) / Σ SE(p)², SE = MOE/1.645, a level's MOE by the Census rule for a sum (nonzero cells in quadrature plus only the largest MOE among zero-estimate cells; "Understanding and Using American Community Survey Data", 2020, ch. 8), Census proportion formula, clamped to [1, households]; estimated households, with a warning, when the lock has no margins), n0 by the method of moments on the dispersion beyond sampling variance; n0 = 0 when that dispersion reaches the multinomial limit), so an observed zero level keeps a nonzero share; zone constants (`CarData.constant`, in `cars.bin`) then make its predicted 0/1/2/3+ shares equal the shrunk ones, refitted (`refitConstants`) over the re-raked start's type mix (a zone with no B25044 households keeps 0). A term the data cannot identify (no variation, fewer than 3 PUMAs or peopled zones) is dropped at 0. The step returns the fitted part as `choice` (`CarChoiceModel`: bands, choice, `threePlusMean`, supply over use); `model` stays null until moves, new-home mixes and parking join it. Report section 14 (`carsReportLines`, `pipeline/lib/cars/report.ts`) sets the coefficients beside the MTC TM2 and ActivitySim priors (`pipeline/lib/cars/priors.ts`, tier 3), gives the fit by block group and citywide, the DMV cross-check and today's spaces per new home.
- **Files.** `scenarios/fzp/cars.bin` (`sfh-cars/1`, `src/lib/data/cars-codec.ts`, raw-deflated like `policy.bin`; `decodeCarData` takes the inflated payload and `parcels.bin`'s row count) and `scenarios/fzp/car-zones.json` (the block groups simplified to 5 m, lng/lat to 6 decimals, properties `z` and `geoid`; TIGER polygons, so coastal zones reach into the water).
- **Counts.** `cars.zones`, `cars.lotsNoZone`, `cars.homes`, `cars.homesNoZone`, `cars.households`, `cars.households.noCar`, `cars.acs.households`, `cars.acs.noCar`, `cars.pums.households`, `cars.zones.occupiedFallback`, `cars.zones.seedOnly`, `cars.zones.ipfUnmet` (zones missing a margin class by more than 1%, warned), `cars.workers`, `cars.acs.workers`, `cars.types`, `cars.pumas`, `cars.acsRelease`, `cars.pumsRelease`, `cars.fit.records`, `cars.fit.constants`, `cars.fit.noObservation`, `cars.fit.observedZero`, `cars.bytes`, `cars.zonesJson.bytes`.
- **First live numbers** (2026-11-24, census lock entries over the `2026-11-14-1a31d026` parcels): 681 zones in 8 PUMAs, 31 lots (27 homes) in no zone, 383,825 homes, 334,652 households (ACS 2020-2024 363,970: the assessor counts fewer homes than ACS's 414,602), 32.1% with no car (ACS 30.2%), 1 zone missing a margin by more than 1%, 6 zones on the citywide occupied share; `cars.bin` 105 KB, `car-zones.json` 260 KB; under a second. With the choice fitted (same date): zero-car share error by block group before the constants median 7.6 points, 90th percentile 19.3; effective sample size median 20.5 against a median 500 estimated households; n0 = 50.9; after the constants, against the raw B25044 shares, median 5.4 points, 90th percentile 14.2, mean 6.9; constants range -1.83 to 2.22 (-22.2 to 21.6 fitted to the raw shares, 304 observed-zero shares); start households against the model at month 0: zero-car gap median 0.36 points, households-weighted mean 0.40 (rounding); citywide the start households and the model on them give 32.1% with no car, the model on B25044's households 30.1% (ACS 30.2%), the difference being where assessor homes sit against ACS households; `cars.bin` 120 KB; 1.5 s.

## ODbL obligations

`buildings.pmtiles`, `basemap.pmtiles` and the parcel chunks are Derivative Databases of ODbL data (OpenStreetMap, Overture), published under **ODbL-1.0**. The manifest `sources` carry each licence, with Overture expanded per contributing dataset, and About's Data and licences (`/about#about-data`) renders the notice from them (`overtureNotice`, `src/lib/about/credits.ts`: Overture's contributors grouped by licence). Do not add a source without recording its licence in the lock. DataSF sources are PDDL or public domain (credit is courtesy). Spec section 4.12 has the visible-attribution wording.
