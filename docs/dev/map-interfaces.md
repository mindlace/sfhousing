# Map-view interfaces for page and subsystem consumers

Contracts that `SimMap` (`src/lib/map/SimMap.svelte`) publishes for code that lives outside it, such as the dock, the palette strip and sheets.

## Bottom-right controls footprint

MapLibre's bottom-right container (`.maplibregl-ctrl-bottom-right`, holding the map's credit, "The credit" below) occupies a corner of the map. Anything anchored to the map's bottom-right must clear it. `SimMap` publishes the footprint as two CSS custom properties.

| Property                        | Meaning                                                                                                                                                         |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--map-controls-br-inline-size` | px from the map root's right edge to the left edge of the controls: horizontal clearance for right-anchored elements.                                           |
| `--map-controls-br-block-size`  | px from the map root's bottom edge to the top edge of the controls. Includes the bottom-inset lift (`setBottomInset`), so it is measured from the map's bottom. |

- **Where:** on `document.documentElement` (`:root`), and mirrored on the `[data-testid=map-root]` element. Publish on `:root` because consumers (the dock, the palette strip, the notice pills) are siblings of SimMap's root inside `BrushEditor` and `TimelineMode`, not descendants, so a variable on the map root is invisible to them. Only one `SimMap` mounts per page.
- **Direction:** the values are physical right and bottom distances (the app is LTR only), not logical inline-end/block-end.
- **Never below the inset:** the published block is never less than the bottom inset (`setBottomInset`). While the map is loading, remounting, unsupported or in error (no controls to measure), the inline size is `0px` and the block is the inset (`0px` only when the inset is 0). `setBottomInset` publishes at once, before a map exists too. A page whose sheet sits over the map from the first frame calls it on the SimMap component (`bind:this`), not on the `onready` handle: `onready` waits for deck.gl, while the credit and Reset view show as soon as the map loads, and with no inset they sit under the sheet's handle until then (BrushEditor on `/` and `/p/:id`; issue #111).
- **Units:** integer px (`Math.ceil`), always with the `px` suffix.
- **Unmount:** both properties are removed from `:root` when `SimMap` unmounts, so consumers should use a fallback: `var(--map-controls-br-inline-size, 60px)`. A consumer that knows its own floor (Paint's sheet handle) takes the larger, as `MapKeyControl`'s `floor` does.
- **Updates:** measured synchronously: in the task that adds the credit (right after `addControl`), in `setBottomInset`, and in a `ResizeObserver` callback on the controls container and the map root (after layout, before paint). No frame shows the controls with an old value. Opening or collapsing the credit resizes the container and so updates the inline size; the block stays the same (one 24 px line either way). Nothing runs on map `move` (zero map-view JS during pan).
- **Geometry:** the pure function `controlsFootprint` in `src/lib/map/footprint.ts`.

Example:

```css
.my-floating-button {
  position: absolute;
  right: max(1rem, var(--map-controls-br-inline-size, 60px));
  bottom: max(1rem, var(--map-controls-br-block-size, 60px));
}
```

### The credit

MapLibre's `AttributionControl` with `compact: true` at every width and `customAttribution: creditHtml()` (`src/lib/map/attribution.ts`): open, one line, "© OpenStreetMap" (linked to `https://www.openstreetmap.org/copyright`, `target="_blank"` with `rel="noopener noreferrer"`, as About's source links) · "About this model" (`/about#about-data`); collapsed, the (i) alone. The full credits live in About ([about.md](about.md)).

- **The control.** A `<details>`; its `<summary>` is the (i), named "Map credits" (the map's `locale`, `'AttributionControl.ToggleAttribution'`, as `aria-label` and `title`), 24 by 24 px, reached by Tab, with `aria-expanded` kept in step with the open class (`maplibregl-compact-show`). SimMap also keeps the details' `open` in step when it or a drag collapses it, so assistive tech hears the same state. Its focus ring shows for the keyboard only (`:focus-visible`; see "The (i) and forced colours").
- **Size.** One 24 px line open or collapsed (open: `padding: 2px 28px 2px 8px`, line height 20 px, no wrap; 236 by 24 px with fixture-0's fonts; collapsed, the 24 by 24 px (i)), flush in the corner (no margin, as the old text strip was) with only the corner facing the map rounded (12 px). So the footprint's block is 24 px plus the inset, the same open or collapsed, and nothing anchored above it (the map key) moves when it collapses. The map key needs that room: at 1280x800 its open panel fits in the simulation at rest only with a block of at most 24 px and the box 4 px below the map's top ("The map key control": `top-1`, 0.5rem until slice 9, when the credit's 24 px line took 4 px more than the old 20 px strip). At 320 px the open line's left edge is 45 px right of Reset view's right edge.
- **The (i) and forced colours.** MapLibre's glyph is redrawn as a `mask` over `currentColor` (a `::before`; black, as MapLibre's image was), so a forced-colours theme recolours it: there the (i) is `ButtonText` on `ButtonFace` (`forced-color-adjust: none`), the control is outlined in `CanvasText` (an outline, so the box keeps its 24 px), and the ring is `Highlight`. The keyboard ring is a 2 px accent outline (`accent-dark` in a dark theme) inset 2 px, inside the 24 px button, since the (i) is flush in the map's corner and the map clips its overflow; on `:focus-visible` only; MapLibre's box-shadow ring, which forced colours drop, is off. Outside forced colours the credit is MapLibre's light chip in both themes, as are its other controls.
- **Collapse rules.** It is added open and collapses at most once by itself: `creditShowMs` after the map's `load` (prop, default `CREDIT_SHOW_MS`, 5,000 ms, so the credit shows with the map however long the load takes; 0 in a `VITE_E2E` build, which collapses it as it is added, so e2e specs start collapsed and open it with its toggle), on the first user zoom, rotate or pitch (an event with `originalEvent`; a programmatic `jumpTo` or `easeTo` does not count), or on `SimMapHandle.collapseCredit()` (below). A press on the (i) or focus moving inside the credit (a Tab onto a link), before any of these, ends them: from then on only the person opens and closes it. A pointer on the credit only pauses the timer: when it leaves, the timer starts again in full (once the map has loaded), and the first-move rule holds throughout. MapLibre's own rule stays: every user drag collapses it. The timer lives on the credit, not in the loading timers, and is cleared on teardown.
- **Escape.** With focus in the credit (the (i) or a link) and the credit open, Escape closes it, focuses the (i) and marks the key handled (`preventDefault`); a key already handled (an open explanation took it) is left alone. It counts as a press.
- **`collapseCredit()`.** Collapses it now, opened by hand or not (a credit opened before Paint's strip appears would cover the strip's end), unless focus is inside it; the person can open it again. A no-op before the map exists. `BrushEditor` calls it when Paint's phone palette strip appears (and when the map hands over its handle with the strip showing): the strip spans the map's bottom at 375 px. Opened by hand with the strip showing, the credit draws above it (`PaletteStrip`'s rule: `z-index: 31` on the bottom-right container while it holds the open credit, above the strip's `z-30`), covering the strip's right end until it is closed or the map is dragged.
- **Links.** In the simulation and on `/s/<id>` a plain click on "About this model" opens the About dialog at Data and licences (`interceptAboutLinks`, [about.md](about.md), "The link rule"); elsewhere (Paint, `/p/<id>`) it navigates to `/about#about-data`. The OpenStreetMap link is a navigation in the same tab (`rel="noopener noreferrer"`, no `target`).

## The dock's width and the bottom-left control

`Dock` (`src/lib/dock/Dock.svelte`) publishes `--dock-w` on its host, the nearest ancestor with the class `sfh-dock-host` (BrushEditor's root, on `/` and `/p/:id`): from 768 px, `320px` while the panel is open and `48px` while it is folded to the rail; unset below 768 px (the phone sheet sits over the map's bottom instead) and when no dock renders. Anything placed over the map from the left reads it with a fallback, `calc(var(--dock-w, 0px) + 1rem)` (the notice stack's centre, SimMap's failure chips' centre, `calc(50% + var(--dock-w, 0px) / 2)`, and the left of the area the project card may take: the card opens beside the clicked building, never under the dock or a showing notice pill; see [fzp-mode.md](fzp-mode.md), "Card placement").

The same host rule moves MapLibre's bottom-left container (`.maplibregl-ctrl-bottom-left`: zoom and compass, fine pointers only) to `left: var(--dock-w)`, so the dock never covers it (WCAG 2.2 2.4.11). Below 768 px the phone sheet's height is added to the map's bottom inset (`setBottomInset`, through TimelineMode's `bottomExtra`; on `/` and `/p/:id`, BrushEditor's inset is the sheet's height alone: nothing sits under the sheet there, since the score is in the header, so `--fzp-scrubber-h` is unset and reads as 0), so both bottom containers, and `--map-controls-br-block-size`, sit above the sheet's handle. While the phone palette strip shows, `PaletteStrip` lifts the bottom-left controls (the navigation control on fine pointers, SimMap's Reset view button on coarse ones) 4rem above the inset, clear of the strip.

## The run view

`SimMapHandle.setRunView(on)` shows the whole city, flat and north up, and locks the camera there. A page calls it to play a run over the map; `setRunView(false)` hands the map back.

- **The fit.** `true` remembers the camera and jumps, with no animation, to `runFrame(width, height, bottomInset)` (`src/lib/map/camera.ts`): pitch 0, bearing 0, `RUN_BOUNDS` (mainland San Francisco, `SF_GRID_BBOX`) kept `RUN_PAD_PX` (24 px) inside each side of the box less the bottom inset. The zoom is never below `RUN_MIN_ZOOM` (8). About 11.6 at 1280 by 744, about 10.5 at 375 px wide.
- **Lifted limits.** While locked, `maxBounds` is null and the minimum zoom is `RUN_MIN_ZOOM`, so the city fits a small box. Unlock restores `CONSTRAINTS` after its jump.
- **No camera moves.** The eight handlers are off (`dragPan`, `dragRotate`, `scrollZoom`, `boxZoom`, `doubleClickZoom`, `keyboard`, `touchZoomRotate`, `touchPitch`), whatever `setPanEnabled` says. The bottom-left controls are hidden and Reset view is not rendered. The canvas container has the class `sim-map-run-locked`: `touch-action: none` and `cursor: default`. `setPanEnabled` while locked stores its value; it takes effect at unlock. The credit stays and works.
- **Nothing picked.** No hover pick, tap or click is made or delivered, and no tooltip or card shows. The lock closes an open one and, after a hover hit, sends `timelinePick` one hover miss; then nothing until unlock. deck.gl does not pick (`_pickable: false`). A press that began while locked is never delivered. After unlock, hover picks start at the next pointer move.
- **Unlock.** `false` jumps back to the remembered camera, then restores the limits, which clamp it as any camera. A resize or new inset while locked keeps the remembered centre and zoom.
- **Refit.** Locked, a map `resize` or `setBottomInset` jumps to the fit for the new box. Neither changes the remembered camera.
- **Remount.** The value survives a remount, as the pan state does. A map made while locked starts locked and fitted; unlock goes to the camera from before the lock, or to the map's initial camera when no map was there at the lock. `true` then `false` before any map leaves nothing. A new `SimMap` starts unlocked.
- **Calls.** A call with the value in force does nothing. A call before the map exists stores the value and never throws, in any state.
- **Events.** Each jump fires `movestart`, `move` and `moveend` once, with no `originalEvent` (so the credit does not collapse). A `moveend` reader sees the city at the lock and the remembered view at the unlock. `map.project` gives positions in the fitted camera.
- **The root.** `[data-testid=map-root]` carries `data-run-view="on"` while locked, from mount, with or without a map; no attribute otherwise.
- **Merged timeline.** While locked the timeline draws as one solid and one ghost layer over every cell (`timeline-solid-run`, `timeline-ghost-run`), never culled or picked; unlock returns the per-cell layers.

What shows at the fitted zoom (the run view changes what no layer draws):

| Thing                                                 | Desktop, zoom about 11.6                                   | Phone, zoom about 10.5   |
| ----------------------------------------------------- | ---------------------------------------------------------- | ------------------------ |
| Basemap: land, water, parks, main roads, place labels | Yes                                                        | Yes, fewer labels        |
| Existing buildings                                    | No: the layer starts at zoom 12                            | No                       |
| Timeline ghosts and solids                            | Yes, seen from above; a lot is about 1 px                  | Yes; a lot is under 1 px |
| Bars, far mode                                        | At most 20% alpha at zoom 11.6, only bars whose gate is 12 | No                       |
| Bars, street mode                                     | No                                                         | No                       |
| Policy marks                                          | Yes, one per 800 m square, about 40 px apart               | Yes, about 19 px apart   |
| Transit access shading, when on                       | Yes                                                        | Yes                      |
| Regional stops, when on                               | Yes                                                        | Yes                      |
| Rail and bus stops                                    | No                                                         | No                       |
| Height-limit contours and labels, when on             | Yes, no lids                                               | Yes, no lids             |
| Tooltips and cards                                    | No: locked                                                 | No: locked               |
| The credit                                            | Yes                                                        | Yes                      |

Which timeline cells the map holds at a citywide view is the page's stream's choice. A label point outside `RUN_BOUNDS` still lands on the map within the 24 px margin: about 480 m at zoom 11.6, 1 km at 10.5.

## The notice pills and the failure chips

From 768 px the page's notice stack (`NoticePills`, `src/lib/shell/NoticePills.svelte`, on `/`, `/s/<id>` and `/p/:id`) overlays the map's top centre, where `SimMap`'s failure messages ("Some parcels didn't load", "Existing buildings couldn't load") sit too. So `NoticePills` publishes the stack's bottom edge, in px from its host's top (the host is its parent element: TimelineMode's root or BrushEditor's, whose top is the map's), as `--notice-pills-bottom` on that host. It is `0px` while the stack is empty and below 768 px, where the stack is in flow above the map; it is removed when the stack unmounts, so readers use a `0px` fallback. Its optional `onbottom(px)` reports the same value on change.

`SimMap`'s two failure messages are one column (`data-testid="sim-map-chips"`, `flex-col gap-2`), centred right of the dock, its top padding `calc(var(--notice-pills-bottom, 0px) + 0.5rem)`, so a notice never covers a Retry and the two never cover each other (parcels first, a chip; buildings under it, a card; both in the map palette, `.sim-map-panel`). `SimMap` publishes the column's bottom as `--map-chips-bottom`:

- **Where:** on `:root` and mirrored on the map root, as the footprint vars (the stroke chip is a sibling of SimMap's root).
- **Value:** integer px (`Math.ceil`) from the map root's top to the column's bottom; `0px` while neither failure shows; removed on unmount (read it with a `0px` fallback).
- **Updates:** a `ResizeObserver` on the column's border box. The column's offset from the map's top is its padding, so a change of `--notice-pills-bottom` resizes the box and re-measures too. Nothing runs on map move.

`BrushEditor`'s stroke chip (on `/` and `/p/:id`) sits at `top: calc(max(var(--notice-pills-bottom, 0px), var(--map-chips-bottom, 0px)) + 0.5rem)`: below whichever is lower, so it covers neither a notice nor a failure's Retry. The header's "Autosave off" pop-over is `z-40`, above all of these, so at 375 px the stroke chip never covers it.

Consumers of `--map-controls-br-block-size` from md include the project card's placement area (`cardArea` in `src/lib/fzp/card-place.ts`): its bottom is the map's height less the larger of the time bar and this footprint, so a card opened beside a building never covers the credit; its left is right of the bottom-left controls' right edge (read from their box); its right is the map key control's left edge (read from its box, `controls.right`; "The map key control" below), so a card never covers the key. A change to the footprint re-places an open card (`watchCardArea`, `src/lib/fzp/card-area-watch.ts`, watches the inline value on `:root`). Below md the card is a bottom sheet over the same footprint (see [fzp-mode.md](fzp-mode.md), "Card placement").

## The map key control

`MapKeyControl` (`src/lib/map/key/MapKeyControl.svelte`, shared by the simulation and Paint: the opening and `/p/:id` mount it with `PaintKey`, closed at rest) is a toolbar at the map's bottom right with a "Key" toggle (named "Map key") and, when the page passes `layers`, a "Layers" toggle (named "Map layers") before it, 4 px apart, each the shared `BUTTON` with `ON_MAP` (`src/lib/shell/ui.ts`; at least 24x24 px on every pointer, the open panel's toggle one step raised), with `aria-expanded` and `aria-controls`. Each opens its panel (a group named "Map key" or "Map layers"; test ids `map-key-panel`, `map-layers-panel`) right-aligned 12 px above the toolbar (so on a phone it clears the Reset view); at most one is open. On Paint below md, while the palette strip shows, the toolbar rests 10 px above the strip (`BrushEditor` passes the strip's height in `floor`). Test ids: `map-key-control`, `map-key-toggle`, `map-layers-toggle`. The toggles' words are fixed; anything that changes lives in the panels. Opening one panel closes the other, and focus stays on the pressed toggle. The Layers panel holds the page's `LayerSwitches` (`src/lib/view/LayerSwitches.svelte`, the layer rows; see Transit layers, UI gating); there is no header View menu.

- **Placement.** Mount it in the map's positioned box, after the map, so Tab reaches it after the map's own controls (zoom, compass, the credit's (i) and, open, its links) and before the page's next region. Its box is `absolute right-2 top-1 z-20` with `bottom: calc(max(var(--map-controls-br-block-size, 60px), <floor>px) + 0.5rem)` (`floor`: Paint passes its sheet's height, so the toolbar is above the handle in every map state, failed or not yet measured): it reads the bottom-right footprint (which includes the bottom inset and the phone sheet's lift), so the toolbar sits 8 px in and 0.5rem above the credit at every width and moves with it. **Tab order:** the toolbar comes first in the DOM and the box is `flex-col-reverse`, so the panels still sit above the toolbar while Tab reaches Layers, then Key, then the open panel and its controls. The box spans the room from 4 px below the map's top (`top-1`) down to the toolbar but ignores the pointer (`pointer-events: none`); its toolbar and panel do not. A panel is `w-60` from md and `min(18rem, 100vw - 1rem)` below, and scrolls inside that room (it is focusable, so the keyboard can scroll it). The free corner was measured at every width in the opening and the simulation (the plan's Measured table); the top centre (notices, failure chips, the stroke chip) and the bottom left (zoom, Reset view, the palette strip) are taken.
- **Open and close.** `openFromMd` opens the key at rest from 768 px (the simulation); below md it always starts closed. After that the viewer's toggle holds for the visit (it is not stored): going below md closes the open panel, moving focus from inside it to its toggle as Escape does; going back up keeps whatever state the viewer has, so a key closed below md, or by the viewer, stays closed, and a panel opened below md stays open. A crossing is handled once: a press made after the width changed but before its `change` event arrives (a rendering update later) counts as made at the new width, so the event never closes what it opened (#131). Escape closes the open panel and focuses its toggle, unless an explanation (`Explain`) is open inside it: that takes the first Escape (with focus inside the explanation, a native listener on its wrapper that stops the key there; opened by hover with focus elsewhere, a capture-phase window listener that marks it handled with `preventDefault`, which the control, the card, the header Menu, the dock, the brush size and height pop-overs (`RadiusPopover`, `PaletteStrip`) and the "Autosave off" popover (`SaveIndicator`) skip), so the next one closes the panel; below md a `pointerdown` on the map (anywhere in the parent box outside the control) closes it; from md it stays until its toggle closes it. `hidden` (below md while a card's sheet covers the corner, or Paint's sheet is open) sets `hidden` and `inert`. Panels are hidden, not unmounted, so `onopenchange` reports the panel the viewer can see (`'key'`, `'layers'`, or null while none is open or the control is hidden); Paint uses it to clear a height's outline when its row is out of sight.
- **More below.** A panel that scrolls (a key panel taller than its room) says so: each panel carries `.more-below` and `{@attach moreBelow}` (`src/lib/shell/more-below.ts`), so while it overflows and is not scrolled to its end a 24 px fade to the surface sits at its foot, gone at the end; a 2 px `CanvasText` line under forced colours; it never takes a press and nothing animates ([timeline-ui.md](timeline-ui.md), Activity, for the mechanism).
- **Colours.** It puts `timelineTokenCss('.sfh-map-key')` in `<svelte:head>` and carries the class, so `KeySwatch` (ghost, solid, bar and mark swatches, `aria-hidden`, beside their words; a mark is a diamond) reads the `--map-*` properties. `stale` sets `data-stale` on the key panel: its text turns to the muted ink, the swatches dim, controls keep their colours. The Layers panel never dims (its rows are not numbers).
- **The card.** The simulation's card area ends at the control's left edge (`cardArea`'s `controls.right` = the map's right less the control's left, 0 while it is hidden), and `watchCardArea` observes the control's box (`CardAreaTargets.key`), so an open card is re-placed when a panel opens or closes and never covers the key.

## Transit layers

Transit spec section 6. `SimMap` draws a transit access surface and the stops as ordinary MapLibre layers, present only when the manifest names `transit` (`src/lib/map/style.ts`).

- **Sources:** GeoJSON `transit-access` (binned 10-minute-walk capacity polygons) and `transit-stops`. The stops source is filled from `transit.json`, the access source once the map is idle (the grid is built on the main thread).
- **Layers:** `transit-access` (fill) and `transit-stops-bus`, `transit-stops-rail`, `transit-stops-regional` (circles; bus from zoom 15, rail from 13, regional always). Stack order: base, `transit-access`, `existing-buildings`, chunk layers, labels, the stop layers, `overlay-anchor`. So the surface sits under existing buildings and the stops sit above the labels.
- **Props:** `SimMapProps.view` (`ViewPrefs`: `transitStops`, `transitAccess`, `heightLimits`, `carsPerHousehold`; default stops off, capacity off, limits on, cars off, and a stored choice wins; SimMap reads the two transit fields and `carsPerHousehold`) toggles layer `visibility`; `SimMapProps.fetchTransit` replaces the `transit.json` loader (tests inject a fixture network).
- **Why MapLibre layers:** `setOverlayLayers` is single-owner (the overlay mux, `src/lib/map/overlay-mux.ts`, on `/`: in the opening and on `/p/:id` its `ring` slot holds the brush ring and its `outline` slot the outline of the height the map key shows; in the simulation the `outline` slot is the selected painted area's or the eraser's), so transit does not use it.
- **UI gating:** the map toolbar's Layers panel (`MapKeyControl`'s `layers`, holding `LayerSwitches`, `src/lib/view/LayerSwitches.svelte`: a checkbox per row, each label a 24 px target on every pointer, with its legend or caption; prefs persist in localStorage `sfhousing:view`, one record for every route, via `readViewPrefs` and `writeViewPrefs`). Gating is per route. In the opening and on `/p/:id` the page passes `layers` (through `BrushEditor`) only when the manifest the map renders has `transit`, with the two transit rows (the default `rows`); without it there is no Layers toggle. Those pages never show `heightLimits` and write back the value they read. In the simulation (and on `/s/:id`) the page always passes `layers` (through `TimelineMode`, whose control mounts once the map and session are there), so only the transit rows are gated on `manifest.transit` (the limits row needs no transit), with `rows` `['transitStops', 'transitAccess', 'carsPerHousehold', 'heightLimits']`, less the transit rows without `manifest.transit` and less the cars row without `manifest.scenarios.fzp.carZones` (see Cars per household). Without `manifest.transit` there are no transit sources, layers or transit rows, and `transit.json` is never fetched.
- **Known gap:** the stop tooltip is pointer-only. It has no keyboard parity yet.

## Basemap road clones (`__lc`)

Some older datasets moved removed freeway stretches into a second roads
source layer (`LC_ROADS_SOURCE_LAYER`), and its manifest says so (`manifest.splitRoads`, from an
older manifest's scenario entry). For such a dataset `buildStyle` (`src/lib/map/style.ts`) gives
every protomaps layer on source layer `roads` a clone, id `${id}__lc` (`LC_CLONE_SUFFIX`), on that
source layer, placed right after it, with the same filter, layout and paint (and the same theme
paint diff), so those stretches draw as roads. Every page draws the clones unfiltered. A consumer
that queries or restyles basemap roads by layer id should include the `__lc` clones; a consumer
that inserts layers relative to a road layer should not assume the next layer is another road
layer.

## Height limits

Height-lids spec (`docs/superpowers/specs/2026-11-01-height-lids-design.md`); it replaces the height fog (sim-runs spec §4), whose layer, grid and token are gone. The simulation draws the zoning height limit as glass lids over the lots (zoomed in) and as contour lines on the ground (zoomed out), through SimMap's `setOverlayLayers` in the overlay mux's `limits` slot (`src/lib/map/overlay-mux.ts`), so it is a deck layer, not a MapLibre one.

- **Layer:** `HeightLimitsLayer` (`src/lib/map/height/limits-layer.ts`, id `LIMITS_LAYER_ID` = `sim-height-limits`), built by `heightLimitsLayer({ city, lids, mode, theme })`. A composite layer: glaze faces and walls (depth-tested against MapLibre's buildings, see [testing.md](testing.md)), ink rims, contour chains and two label layers. Lids fade in and contours fade out over `LIDS_FADE` (zoom 14.5 to 15.5); a sublayer at opacity 0 is hidden, not dropped. The look per mode is pure (`limits-style.ts`).
- **Data, two messages** ([sim-levers.md](sim-levers.md)): the scenario worker posts `heights` (`HeightCity`: city-wide contour chains and region labels) with each lever revision; TimelineMode's `onheights` hands it to SimPage ([fzp-mode.md](fzp-mode.md)). The lids are a request: `SimClientApi.heightLids(bbox)` answers a `HeightLids` for the view (pieces, faces, rims, walls, labels), tagged with the `limitsRev` and `sourceIds` of the limits it was built on. SimPage asks on each `moveend` from z14.5 (`LidRequest`, latest wins) with the view bbox clamped to 3 km (`LID_MAX_SPAN_M`) around the view centre, so a pitched view far out asks for a bounded area.
- **Modes:** `LimitsView` is `{ kind: 'plain' } | { kind: 'paint' } | { kind: 'rule'; ruleId } | { kind: 'fzp' }`. Plain: a solid translucent edge at limit steps, source boundaries hidden. Paint (brush or eraser chosen, or a painted area selected in the simulation): lots set by paint, and the lines bounding them, are dashed in the paint tone, source boundaries included. Rule: the selected rule's rims and its lot-set outline are full edge colour (the outline 1.5 px), everything else dims, glaze shows on its lots only; zoomed out, its outline is a bold contour. The page passes a rule by id; the layer maps it through the `sourceIds` of the lids or of the city (they may be from different revisions), so a rule that decides nothing in one of them dims everything there. `fzp` (the FZP baseline row selected in the simulation) is rule mode on `SRC_FZP`: the lots FZP sets in full edge colour, everything else dimmed.
- **Gating:** drawn while `viewPrefs.heightLimits` is on (the Layers panel's "Zoning height limits" row, default on) and a city is in hand, in both modes. It is not gated on `manifest.transit`. Selecting a transit policy or the fixed "Current law" zoning row turns the row on ([sim-page.md](sim-page.md), "Selection and the limits view").
- **Theme:** the `limit-ink`, `limit-edge`, `limit-glaze`, `limit-wall` and `limit-halo` tokens (and `painted-outline` for the paint tone) of the system theme (`useSystemTheme()`, the same instance that themes the Layers panel's swatches). Only the layer rebuilds on a theme change, not the data.
- **Labels:** one per region (a component of lots with the same limit, joined across streets up to 30 m), showing the limit and the room to grow. Placement is per zoom in the worker (`placeLabels`), then a screen-space collision pass (`declutter`) on the main thread, one per label key (integer zoom, pitch and bearing steps), so the labels shown never overlap. When part of a component is set by paint, the plain-mode label still shows the whole region's room to grow (and the rule selection dims it only when none of the region's lots are the rule's); only its placement sits on the roomier part, which can leave it less space, so it may drop out at lower zooms. Paint mode labels the paint part and the rest separately, each with its own room.
- **Module:** `limits-layer.ts` is lazy-imported once on mount, beside `@deck.gl/layers`.

## Timeline lookups and cohorts

`SimMapHandle.setTimelineLookups(l)` takes a lookup set (`{ chance, typicalMonths }`, from `chanceTable` and `typicalMonths`) and, optionally, a second set under `inFlight` (plan 4, Call 15). Absent `inFlight`, in-flight slots read the top-level (fresh) set. The packed cell carries `slotCohort: Uint8Array` (0 fresh, 1 in flight; in the transferables and validated: wrong length or a value above 1 fails). The chance texture has 36 rows, `chanceRow(pathway, stage, cohort) = cohort · 18 + pathway · 6 + stage`; a bar's `segRow` and typical days read its slot's cohort. Lookups compare by identity, so send one object per posted `lookups`. The shader is unchanged (the row index is per-instance data). The map does not apply the in-flight `chanceShift` (a card does): see [sim-page.md](sim-page.md), Known gaps. Details: [fzp-mode.md](fzp-mode.md), "Cohort-aware bars".

## Slot flags

`TimedPackedCell.slotFlags?: Uint8Array`, one byte per slot, holds `SLOT_FLAG` bits (`src/lib/map/types.ts`): `zoning` (1) and `money` (2). `packTimedCell` always writes it (an item's `TimedPackInput.flags`, default 0) and `packTimedTransferables` lists its buffer; a cell without it (older fixtures) has no flags. `validateTimedCell` checks it only when present: length equal to the slots, each value at most 3.

In the simulation the map stream sets them from `slotFlags` (`src/lib/sim/world/runner/flags.ts`), read in the frame of the model month of the row's first entered stage, of the plan's timeline in use:

- `zoning`: a simulated row whose lot's limit owner (`limitsAt`) is not current law: a painted policy or a transit rule above it. It over-counts (some would have started under current law) and never means "because of". Pipeline and phase rows never carry it.
- `money`: a funded row with a programme whose pool is not a baseline pool (`ds.loaded.fzp.finance.pools`): a pool you added. Scaling the baseline funds through baseline pools and sets no bit.

The bits do not sum to "+N from your policy". `scenario/geometry.ts` packs zeros.

## Policy marks

`SimMapHandle.setHalos({ from })` turns on the policy marks for projects whose first stage day is after `from` (a page passes the dataset date, so nothing shows at today); `setHalos(null)`, the default, draws none. Like `setTime`, a call before the timeline controller exists is kept and applied when it does. The Paint pages never call it. The name is the layer's: it once drew rings too.

The `TimelineController` draws them as one deck layer, `timeline-halos` (`HaloLayer`, `src/lib/map/timelapse/halo-layer.ts`), from records `buildHalos(cells, from)` makes (`src/lib/map/timelapse/halos.ts`): per slot with a `SLOT_FLAG` bit and a first stage day after `from`, one mark at the bbox centre of its final revision's parts, in cell then slot order. A mark is a filled diamond (`MARK_PX` across) in `tl-halo-policy` (the site accent) with a 1 px `land` edge. Shape, not colour alone, says "under your policy".

A mark lives in simulated time: it shows from its first stage day until the end (`DYING_DAYS` after an exit). `evalHalo(h, t, zoom = Infinity)` is the CPU reference the vertex shader ports. Nothing moves or fades, so there is no reduced-motion case. A paused playhead holds every mark where it is; scrubbing back hides the ones whose day is now ahead; an edit's replaced cells take their marks with them.

**The gate, one per square.** Below `MARK_AREA_ZOOM` (14) a square of the `MARK_AREA_M` (800 m) grid (`cityGroup`, `city-grid.ts`) shows one diamond; from 14 every mark shows. Each record carries `areaFrom`: from that day until its `until` it is its square's one diamond below the gate. `buildHalos` sets it once per rebuild, on the CPU (`areaMarks`): it groups the marks by the square of their anchor, orders each square's marks by first stage day, then homes descending, then project id, and gives the square to the first standing mark, which keeps it until its own end; the square then hands over to the first still standing, or, with none, to the next revealed. `evalHalo` and the shader are the same test: hidden when `zoom < MARK_AREA_ZOOM` and `t < areaFrom`. The shader compares deck's `project.scale` with `2^14`, exact at an integer zoom. The reveal rule holds: a mark never shows before its first stage day, scrubbing back hides it, and an edit's rebuild chooses again. The gate is fixed, not set per feed: a page with marks and no feed (the bench's "playback + halos") is gated alike.

Draw order: solids, ghosts, `timeline-bars`, `timeline-halos`, then the overlay slot, all before the first label layer. The layer is not pickable and has no depth test. Cadence: the records are rebuilt when an update's last slice has installed and it added or removed cells (a re-encode for new lookups does not count), and when `setHalos` changes its value. `setTime` sets no prop: the layer reads the clock the bars read in `draw`. The debug snapshot (`__sfhMap.timelineSnapshot()`) reports `marks` (records), `marksShown` (marks visible on the clock's day at the map's zoom, behind the gate), `flagged` (installed slots with parts and a `SLOT_FLAG` bit, marks on or off; `e2e/sim-halos.spec.ts` checks `marks === flagged`), `projects` (installed slots with parts) and the feed counts below.

## The citywide feed

`TimelineUpdate.city?: CityDelta` (`src/lib/map/types.ts`) carries one marker per project row of the plan world that has a T11 lot, whether its cell is loaded or not. Struct of arrays:

- `rows`: the world's row count after this update. The page drops every marker at or past it.
- `from?`: the drop floor, only after a rewind (at most `rows`). Before applying this delta's rows the page forgets every marker at or past `from`; the rows below `from` in the delta are changed survivors, those at or past it the re-created rows (every row there that has a marker). Absent: nothing to forget beyond `rows`.
- Per changed row, ascending, each below `rows`: `row` (`Int32Array`), `lngLat` (`Float32Array`, 2: the anchor lot's label point, about 0.7 m at San Francisco), `days` (`Float32Array`, 3, indexed by `CITY_DAY`: `approved` = the first of entitled and permitIssued, `started` = construction, `completed` = a complete end; `NaN` = not (yet)), `homes` (`Uint16Array`: the final revision's units, capped at 65,535, below 0 sent as 0), `existing` (`Uint16Array`: the homes the project replaces, as the score series takes them off: the row's existing homes once it enters construction after the dataset date, else 0; capped at 65,535, below 0 sent as 0), `flags` (`Uint8Array`: `SLOT_FLAG` bits, at most 3).
- For a completed marker, `homes - existing` is the project's net effect on the goal's measure (`completedNet`). Summed over the markers, the completed ones' `homes` less every marker's `existing` is the marked rows' `completedNet` at the same day, short of the caps.
- 29 bytes a row (`CITY_DELTA_BYTES_PER_ROW`), transferred, not copied (`cityTransferables` lists the six buffers once each). 30,000 projects in a revision 0 or a resync: 870,000 bytes.
- Revision 0 holds every marker and replaces the page's set whole (it carries no `from`); a revision 0 without `city` means no feed, so the page clears it. A later update holds only the rows whose marker changed since the last update (rows an event touched, or a rewind changed), and none at rest: a playhead move, a pan or a zoom sends nothing. A later update without `city` changes no marker.
- Days run ahead of the playhead: the worker reads the world as of its last stepped month, and the page hides what the clock has not reached.
- `validateCityDelta` (`src/lib/map/city-delta.ts`) throws `RangeError` on a missing `existing`, a wrong length, a row not ascending or at or past `rows`, a bad `rows`, a `from` that is not an integer in [0, `rows`], or a flag above 3.

Producers: only the simulation's map stream ([map-stream.md](map-stream.md), "The city feed"). `scenario/geometry.ts` sends no `city`.

Consumers: Activity in the simulation, and the map's controller for its debug counts. `TimelineMode.applyRender` feeds every update with `city` (and every revision 0) to its own `CityStore`, inside `ActivityIndex` (`src/lib/timeline/activity.ts`), before it forwards the update to the map (or queues it until the map is ready), so Activity's list needs no map and the buffers are read before the map may take them. The controller keeps its own `CityStore` (`src/lib/map/timelapse/city.ts`) only for the snapshot's `cityMarkers` and `cityFlagged`; nothing draws from it. That is a second copy of the markers, 29 bytes a row. Besides `recent`, `ActivityIndex.markers()` lists every marker held, ascending by row, with its label point, completed day, `homes`, `existing` and `flags`: the game's run reads it to place drops and to colour a drop from a project the policy marks. See [timeline-ui.md](timeline-ui.md), "Activity".

The controller's `CityStore` (`src/lib/map/timelapse/city.ts`): `apply` validates `u.city` with the cells, before anything installs (a `RangeError` leaves everything as it was). A revision 0 (a swap's too) replaces the store from its `city`, or clears it without one; a later update forgets the markers at or past `from`, drops those at or past `rows`, then writes its rows. A delta with `from` and no rows is still a city update. The debug snapshot reports `cityMarkers` (markers held) and `cityFlagged` (of them, with a flag); `timelineSnapshot()` has no other city count.

## Bar modes

`SimMapHandle.setBarMode(mode)` picks how the progress bars (`timeline-bars`) draw. `'street'`, the default, is the bars as they were: from zoom 15 (`BAR_MIN_ZOOM`), 32 by 6 px growing to 48 by 8 at zoom 17. `'far'` shows them from zoom 12 (`BAR_FAR_MIN_ZOOM`) at one size, 32 by 6 px (`BAR_FAR_PX`), at every zoom. The simulation calls it with `'far'` once its map is ready; the Paint pages never call it and keep street bars. Like `setTime`, a call before the timeline controller exists is kept and applied when it does. The mode changes the zoom gate, the size and the declutter only: a bar still shows only from its project's first stage to its end, as in street mode (the reveal rule).

**Declutter.** `declutter(bars, mode)` returns the records the bar layer draws. Both modes visit in one total order: policy first (`BarAttrs.policy`: the slot has a `SLOT_FLAG` bit), then homes descending, then `parcelId`, then `projectId`, so the same bars always get the same gates. Neither mode depends on the camera or the clock: the controller declutters when it rebuilds the bars (an update's last slice installed or removed cells, new lookups, or a `setBarMode` change), never in `setTime`, on a pan or on a zoom.

- **Street** (unchanged): gates the bars in place and returns them. Each project takes one gate (`minZoom`) for its whole life, the lowest rung of the ladder (15 to `DECLUTTER_MAX_ZOOM` by `DECLUTTER_STEP`) at which it is a bar's width from every earlier project it shares time with.
- **Far** (time-split, `FarDeclutter`): each bar (a revision, at its own anchor, over its own `[from, to)`) is first cut at its end day (`completeDay` when complete, `endDay` when exited) into a live unit and a tail unit (the hold and fade, or the dying ghost). Every live unit is visited before every tail unit, then in the order above (and `from`, `to`, unit index), so a finished bar's afterglow never holds back a bar still in progress. Each unit is cut into pieces, each a record with its own window and gate. An earlier piece holds a unit back only while both are in time: during their common days it raises the unit's gate to the first rung of the ladder (12 to 18) at which their anchors are `declutterPx(z, 'far')` apart (the diagonal of the 32 by 6 box grown by `BAR_FAR_GAP_PX`, 12 px), unless the piece itself is gated at or above that rung. A unit's gate on a day is the highest such rung, else 12; its window is cut where that changes. At most `BAR_FAR_MAX_PIECES` (4) pieces a unit: past that, the shortest piece merges into its neighbour with the higher gate and the merged piece keeps the higher one, so a merge only ever hides. So on any day, two far bars shown together at a ladder zoom never overlap and keep a 12 px gap across or up, and a bar held back by a neighbour shows from the day that neighbour's piece ends. The pieces tile the bar's window with today's `[from, to)` ends, so the shader needs nothing new: each piece is an ordinary bar record. The grid's slots keep their entries sorted by `from`, so a scan stops at the first entry that starts at or after the unit's end (the same records as a full scan; a test holds them equal).

**Far runs in slices.** The controller builds the bars at once (as in street mode) but runs the far declutter through its slice queue: one slice for the setup (units, grid, order), then `FAR_UNITS_PER_SLICE` (1,500) units a slice, a structural budget. The bar layer on the map stays until the last slice swaps the new one in, with one emit. An update that installs or removes cells does not stop a run in flight: the run is newer than the bars on the map, so it finishes and swaps in, and the bars are marked dirty, so one more run starts once it has swapped in and the update's slices have drained. So the bars on the map are at most about two run lengths behind the cells, even while a fill or refill keeps updates coming. New lookups, a `setBarMode` change, a revision 0 or `destroy` drop a run in flight (its step leaves the queue and it never swaps in); the bars rebuild once the cell slices drain. The city and halo rebuilds at a drain do not wait for a far run's steps. `pending` in the debug snapshot counts these slices. Street mode keeps its one synchronous pass.

Which bars show changes only at a record's start or end and on a rebuild, never back and forth between neighbours as the playhead moves. On the synthetic 30,000 projects (38,977 bars, 64,438 units) far mode makes 117,959 records; the whole run takes about 260 to 310 ms against street's 14 ms (warm, a busy machine; not benched), in 44 slices: the setup about 27 ms, each step under about 8 ms (the bar build before them, about 34 ms, is street's too). `BAR_FAR_GAP_PX` is set for density: at the desktop default camera (zoom 13, pitch 55) the page shows 395, 439 and 416 bars at days 22,000, 25,000 and 28,000, and 259 and 262 at zoom 12 (days 22,000 and 25,000).

**At the anchor's zoom.** In far mode the shader reads the gate at each bar's anchor, not at the map's zoom: `barZoomAt(zoom, focalW, w, 'far') = zoom + log2(focalW / w)`, where `w` is the anchor's clip w and `focalW` the view centre's (deck's `project.focalDistance`). Toward a pitched view's horizon a ground metre spans fewer px, so bars there need the gate they would need zoomed out and the declutter's spacing holds on screen; near the bottom edge more show. `StageBarLayer` takes `far: boolean` (default false) as a prop and a uniform; nothing else changes in the shader.

**Debug counts** (`timelineSnapshot()`): `bars` counts the layer's records (in far mode, pieces), `barMode`, and `barsShown`: bars `evalBar` shows on the clock's day at the zoom at each anchor, anchors in the map's view, each projected at its raised anchor (`DebugView.clip(lng, lat, alt)` with `anchor[2]`, as the shader) (every bar in time without a view).

## Timeline demolitions after revision 0

`TimelineUpdate.demolish` after revision 0 adds entries, applied as revision 0's are. `restore?: ParcelId[]` takes back every entry of each listed lot and is applied before `demolish`; revision 0 ignores it. An update with no `restore` and an empty `demolish` changes nothing. In `TimelineController.apply` this is `DemolishPump.amend(add, restore)`: the applied set stays the new list's prefix at the target, and feature-state follows by the same diff as `swap`. Producer: [map-stream.md](map-stream.md).

## Cars per household

The plan world's cars per household by zone (Census block group) at the playhead's month, on
the simulation only (car-ownership Task 12).

- **Data:** `car-zones.json` (`manifest.scenarios.fzp.carZones`: block-group polygons, property
  `z`, the zone index) and `TimelineView.cars.zones[month]` (a `Float32Array`, NaN for a zone with
  no households). `TimelineMode` passes the playhead month's array as `SimMapProps.carZones` (undefined unless the run carries car data, which keeps the layer off and fetches nothing; null
  past the fill or without car data); it is the same array for the same month, so the source is
  rebuilt only when the month changes.
- **Style:** `buildStyle` adds source `CARS_SOURCE` (`car-zones`) and the fill `CARS_LAYER`
  (`cars-per-household`, `carsLayer(theme)`) only when the manifest names `carZones`, above
  transit capacity and below the transit stops and roads, hidden at rest. The fill steps over
  `CARS_BINS` (0.5, 0.75, 1, 1.5) through the `cars-1` to `cars-5` tokens at `CARS_OPACITY`; a
  feature whose `v` is not a number (no households) draws nothing: no data, never 0.
- **Loading:** SimMap fetches `car-zones.json` the first time the layer is turned on
  (`SimMapProps.fetchCarZones` replaces the loader in tests), then sets the source to
  `zonesCollection(geo, carZones)` (`src/lib/map/cars-layer.ts`: `v` per zone, null where NaN)
  on every `carZones` change while the layer shows (off, nothing is rebuilt; turning it on pushes the latest month). A failed fetch is a warning and the layer stays empty; the next turn-on fetches again.
- **Layers panel:** the row "Cars per household" (`CARS_LABEL`) with the legend `CARS_LEGEND`
  (swatches `carsSwatch(theme, k)`, the token composited over land) and the caption
  `CARS_CAPTION`, after the transit rows.
